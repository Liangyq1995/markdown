概述

本文是对 Claude Agent Skills 机制的首要原则级深度剖析。作者 Han Lee 通过逆向分析 Claude Code 的源码，揭示了 Skills 系统的真实工作原理——它并非可执行代码，而是一套声明式的 Prompt 模板系统，通过向对话上下文注入专域指令来引导 Claude 完成复杂工作流。文章涵盖从 Skill 的目录结构、SKILL.md 写法、内部调度架构，到完整的五阶段执行生命周期的端到端解析，是目前对 Claude Skills 机制最深入的公开分析。

一、Skills 是什么：三个关键澄清

在深入技术细节之前，必须先纠正对 Skills 的三种常见误解。理解"Skills 不是什么"与理解"Skills 是什么"同样重要。

❌ Skills 不是

  • 可执行代码（无 Python/JS 运行时）
  • 硬编码进系统提示词的指令
  • 通过嵌入向量或分类器匹配的模块
  • 并发安全的工具（不能并发调用）

✅ Skills 是

  • 专域 Prompt 模板（SKILL.md 文件）
  • 通过 LLM 语言推理 按需加载
  • 向对话上下文注入专域指令
  • 动态修改工具权限和模型配置
核心定义：Skill = Prompt 模板 + 对话上下文注入 + 执行上下文修改 + 可选数据文件和 Python 脚本

术语区分

文章刻意区分了两个大小写不同的概念，初学者极易混淆：

术语含义位置
Skill 工具（大写 S）Claude API tools 数组中的 meta-tool，负责管理和调度所有 skillstools 数组
skills（小写 s）单个 Prompt 模板，如 pdf、skill-creator、internal-comms文件系统

传统工具 vs Skills 全面对比

维度传统工具（Bash/Read/Write）Skills
执行模型同步，直接执行Prompt 展开（上下文注入）
目的执行特定操作引导复杂工作流
返回值立即返回操作结果修改对话上下文 + 执行上下文
类型字段各类类型始终为 "prompt"
并发安全一般安全不安全（不可并发调用）
Token 开销极小（~100 tokens）显著（~1,500+ tokens/turn）
示例Read、Write、Bashinternal-comms、skill-creator、pdf

二、构建 Agent Skills：目录结构与 SKILL.md

一个 Skill 本质上是一个文件夹，包含核心指令文件和可选的辅助资源。理解目录结构是写出好 Skill 的前提。

目录结构

my-skill/
├── SKILL.md              # 核心：Prompt 指令（必需）
├── scripts/              # 可执行的 Python/Bash 脚本
├── references/           # 文档，会被 Read 工具加载进上下文
└── assets/               # 模板和二进制文件（仅按路径引用，不进上下文）

Skill 发现来源（优先级顺序）

  1. 用户全局设置：~/.config/claude/skills/
  2. 项目本地设置：.claude/skills/
  3. 插件提供的 Skills
  4. 内置 Skills

渐进式信息披露原则

Skills 系统采用"按需加载"的渐进式策略，避免一次性将大量指令塞进上下文：

三、SKILL.md 详解：Frontmatter 字段与内容结构

SKILL.md 是一个 Skill 的灵魂，分为两部分：YAML Frontmatter（配置元数据）和 Markdown 正文（给 Claude 的指令）。每个字段的设计都有深刻的工程考量。

Frontmatter 字段完整解析

① name（必需）

是什么：Skill 的唯一标识符，用作 Skill 工具的 command 参数。

为什么：Claude 调用 Skill tool 时传入的就是这个名字：{"command": "pdf"}。

② description（必需）

是什么：Claude 进行 Skill 选择的主要信号，系统会自动追加来源信息如 (plugin:skills)。

为什么：整个选择过程完全依赖 LLM 的语言理解，description 写得好不好直接决定 Skill 能否被正确触发。

怎么做：写清楚"在什么场景下使用"，而不只是"这个 Skill 做什么"。参考 skill-creator 的示例：

---
name: skill-creator
description: Guide for creating effective skills. This skill should be used when
  users want to create a new skill, need help structuring a skill, or want to
  understand best practices for skill development.
license: Complete terms in LICENSE.txt
---

③ when_to_use（未文档化，可能已弃用）

⚠️ 注意：该字段出现在源码中但官方文档缺失，可能是废弃特性或内测功能。建议用详细的 description 替代，不要依赖此字段。

源码中的实际处理逻辑：

function formatSkill(skill) {
  let description = skill.whenToUse
    ? `${skill.description} - ${skill.whenToUse}`
    : skill.description;
  return `"${skill.name}": ${description}`;
}

④ allowed-tools（可选）

是什么：该 Skill 执行时预授权的工具列表，支持通配符和命令级粒度控制。

为什么：最小权限原则——Skill 执行期间只开放必要工具，执行结束后权限自动收回。

怎么做：

# ✅ 只允许特定 git 子命令
allowed-tools: "Bash(git status:*),Bash(git diff:*),Bash(git log:*),Read,Grep"

# ✅ 只允许文件操作
allowed-tools: "Read,Write,Edit,Glob,Grep"

# ❌ 权限过大（攻击面过宽）
allowed-tools: "Bash,Read,Write,Edit,Glob,Grep,WebSearch,Task,Agent"

# ❌ 允许所有 npm 命令（过宽）
allowed-tools: "Bash(npm:*),Read,Write"

⑤ model（可选）

允许为特定 Skill 指定不同的模型，实现性能与成本的精细化控制：

model: "claude-opus-4-20250514"  # 指定高能力模型用于复杂任务
model: "inherit"                  # 继承当前会话模型（默认行为）

⑥ disable-model-invocation（可选）

设为 true 时，该 Skill 从 Skill 工具列表中隐藏，必须通过 /skill-name 手动调用。适合不希望被自动触发的 Skill。

SKILL.md 正文最佳实践

正文是直接给 Claude 看的 Prompt，其质量决定 Skill 的执行效果：

原则错误示范正确示范
长度控制嵌入大量文档内容保持 5000 词以内，详细内容放 references/ 目录
语气"You should analyze the code...""Analyze the code for..."（祈使句）
路径引用Read /home/user/project/config.jsonRead {baseDir}/config.json
💡 关键：{baseDir} 是自动注入的变量，指向 Skill 文件所在目录。永远不要硬编码绝对路径。

四、打包资源：三个目录的不同用途

Skill 可以附带辅助资源，但三个目录的使用方式有本质区别，直接影响 Token 消耗。

目录使用方式是否消耗 Token适合存放
scripts/通过 Bash 工具执行否（脚本结果进上下文）Python/Bash 自动化脚本
references/通过 Read 工具加载进上下文是需要 Claude 理解的文档
assets/仅按路径引用，不加载内容否模板、二进制文件

scripts/ 目录

是什么：Claude 通过 Bash 工具执行的 Python/Bash 脚本，实现需要确定性逻辑的复杂操作。

为什么：某些操作（如文件格式转换、统计计算）用确定性代码比让 Claude 自行实现更可靠。

怎么做：在 SKILL.md 中明确指令：

When creating a new skill from scratch, always run the `init_skill.py` script:
Usage: scripts/init_skill.py <skill-name> --path <output-directory>

references/ 目录

是什么：会被 Read 工具完整加载进 Claude 对话上下文的文档。

为什么：将大型参考文档与核心指令分离，保持 SKILL.md 简洁，同时允许 Claude 按需查阅详细规范。

效果：消耗 Token，但在复杂 Skill 中是必要的。

assets/ 目录

是什么：模板或二进制文件，仅通过路径引用，内容不进入上下文。

怎么做： 

Use the template at {baseDir}/assets/report-template.html as the report structure.

五、五种常用 Skill 设计模式

作者总结了五种在实践中被反复验证的 Skill 设计模式，每种模式针对不同类型的工作流。

模式 1：脚本自动化（Script Automation）

适用场景：需要确定性逻辑的复杂操作（文件分析、批量处理）。

allowed-tools: "Bash(python {baseDir}/scripts/*:*), Read, Write"

模式 2：读取-处理-写入（Read-Process-Write）

适用场景：文件转换、内容格式化。

allowed-tools: "Read, Write"

模式 3：搜索-分析-报告（Search-Analyze-Report）

适用场景：代码库分析、文档审查。

allowed-tools: "Grep, Read"

模式 4：命令链执行（Command Chain Execution）

适用场景：多步骤 CI/CD 类工作流。

Execute analysis pipeline:
npm install && npm run lint && npm test
Report results from each stage.

模式 5：高级模式（向导式 / 模板生成 / 迭代精化 / 上下文聚合）

模式描述关键设计
向导式多步复杂任务拆解为离散步骤，每阶段请求用户确认每个 Step 末尾加"等待用户确认后继续"
模板生成从 assets/ 加载模板，填充占位符，写出文件模板放 assets/，不进 Token
迭代精化多轮扫描，深度递增（宽泛→深入→建议）明确定义每轮的输出格式
上下文聚合从多来源收集数据并综合明确定义聚合逻辑和冲突处理

六、内部架构：Skill 工具的实现原理

这是全文最有价值的部分。作者通过逆向源码，揭示了 Skill 工具（大写 S）在 Claude Code 中的真实实现方式。

Skill 工具对象结构

Skill 工具是一个特殊的 Pd 对象，与普通工具共享接口但行为截然不同：

Pd = {
  name: "Skill",

  inputSchema: {
    command: string  // 例如 "pdf"、"skill-creator"
  },

  // 🔑 关键：动态生成可用 Skills 列表
  prompt: async () => fN2(),

  // 校验 + 执行 + 权限检查
  validateInput: async (input, context) => { /* 5 种错误码 */ },
  checkPermissions: async (input, context) => { /* allow/deny/ask */ },
  call: async *(input, context) => { /* 生成消息 + 修改上下文 */ }
}

动态 Prompt 生成器 fN2()

是什么：每次 API 调用时动态构建 <available_skills> 列表，注入到 Skill 工具的 description 字段中。

为什么：Skills 列表会随用户安装的插件变化，必须动态生成，不能静态硬编码。

Token 预算：默认限制 <available_skills> 内容最大 15,000 字符，超出时自动截断。

生成的 Skill 工具 description 最终结构：

Execute a skill within the main conversation

<skills_instructions>
When users ask you to perform tasks, check if any of the available skills
below can help complete the task more effectively...
</skills_instructions>

<available_skills>
"pdf": Extract text from PDF documents - When user wants to extract or process text from PDF files
"skill-creator": Guide for creating effective skills...
"internal-comms": Draft internal communications...
</available_skills>

API 请求结构：Skills 在 tools 数组，不在 system prompt

这是一个关键的架构决策。Skills 不是系统提示词的一部分，而是作为工具被加载：

{
  "model": "claude-sonnet-4-5-20250929",
  "system": "You are Claude Code, Anthropic's official CLI...",
  "messages": [
    {"role": "user", "content": "Help me create a new skill"}
  ],
  "tools": [
    {
      "name": "Skill",
      "description": "Execute a skill...\n\n<skills_instructions>...\n\n<available_skills>\n...",
      "input_schema": {
        "type": "object",
        "properties": {
          "command": {"type": "string", "description": "The skill name"}
        }
      }
    },
    {"name": "Bash", "description": "Execute bash commands..."},
    {"name": "Read"}
  ]
}
💡 为什么放在 tools 而非 system？系统提示词是全局持久化的，而 Skills 需要临时的、作用域受限的上下文注入。将 Skill 工具放在 tools 数组中，使其 description 可以动态更新，且权限修改只在 Skill 执行期间生效。

七、对话上下文注入：两条消息设计的深意

Skill 被选中后，系统会向对话中注入两条 user 角色消息，而非一条。这个设计解决了"透明度"与"信息安全"之间的根本矛盾。

为什么是两条消息？

如果只用一条消息且 isMeta: false，几千词的 AI 指令会直接显示在用户聊天界面：

┌─────────────────────────────────────────────┐
│ The "pdf" skill is loading                  │
│                                             │
│ You are a PDF processing specialist.        │
│ Your task is to extract text from PDF       │
│ documents using the pdftotext tool.         │
│ ...                                         │
│ [500 more lines]                            │
└─────────────────────────────────────────────┘

两条消息设计通过 isMeta 标志优雅地解决了这个问题：

维度消息 1（元数据）消息 2（完整 Skill Prompt）
受众人类用户Claude（AI）
目的状态透明度执行指令
长度~50-200 字符~500-5,000 词
格式结构化 XML 标签自然语言 Markdown
可见性用户可见（isMeta: false）用户不可见（isMeta: true）
内容"发生了什么？""怎么做？"

消息 1：元数据（用户可见）

let metadata = [
  `<command-message>${statusMessage}</command-message>`,
  `<command-name>${skillName}</command-name>`,
  args ? `<command-args>${args}</command-args>` : null
].filter(Boolean).join('\n');

// 无 isMeta 标志 → 默认 false → 用户可见
messages.push({ content: metadata });

用户界面实际显示：

<command-message>The "pdf" skill is loading</command-message>
<command-name>pdf</command-name>
<command-args>report.pdf</command-args>

消息 2：完整 Skill Prompt（用户不可见）

let skillPrompt = await skill.getPromptForCommand(args, context);

// 显式 isMeta: true → 发送给 Claude 但对用户隐藏
messages.push({ content: skillPrompt, isMeta: true });

执行上下文修改（contextModifier）

除了注入消息，Skill 调用还通过 contextModifier 动态修改执行环境。这是权限系统的核心：

contextModifier(context) {
  let modified = context;

  // 修改 1：预授权工具权限（仅在 Skill 执行期间有效）
  if (allowedTools.length > 0) {
    modified = {
      ...modified,
      async getAppState() {
        const state = await context.getAppState();
        return {
          ...state,
          toolPermissionContext: {
            ...state.toolPermissionContext,
            alwaysAllowRules: {
              ...state.toolPermissionContext.alwaysAllowRules.command,
              command: [...existingRules, ...allowedTools]  // 追加预授权工具
            }
          }
        };
      }
    };
  }

  // 修改 2：如果指定了 model，覆盖当前会话模型
  if (modelOverride) {
    modified = {
      ...modified,
      options: { ...modified.options, mainLoopModel: modelOverride }
    };
  }

  return modified;
}
关键洞察：权限修改是作用域限定的。allowed-tools 中声明的工具只在 Skill 执行期间被预授权，不会永久改变用户的全局权限设置。

八、完整执行生命周期：五个阶段端到端解析

以"从 report.pdf 提取文本"为例，完整走一遍 Skill 从被发现到执行完成的全过程。

阶段 1：发现与加载（启动时）

Claude Code 启动时并行扫描所有 Skill 来源：

async function getAllCommands() {
  let [userCommands, skillsAndPlugins, pluginCommands, builtins] =
    await Promise.all([
      loadUserCommands(),      // ~/.claude/commands/
      loadSkills(),            // .claude/skills/ + 插件
      loadPluginCommands(),    // 插件定义的命令
      getBuiltinCommands()     // 内置命令
    ]);
  return [...userCommands, ...skillsAndPlugins, ...pluginCommands, ...builtins]
    .filter(cmd => cmd.isEnabled());
}

加载后的 pdf Skill 对象：

{
  type: "prompt",
  name: "pdf",
  description: "Extract text from PDF documents (plugin:document-tools)",
  whenToUse: "When user wants to extract or process text from PDF files",
  allowedTools: ["Bash(pdftotext:*)", "Read", "Write"],
  model: undefined,
  isSkill: true,
  disableModelInvocation: false,
  promptContent: "You are a PDF processing specialist...",
}

阶段 2：Turn 1 — 用户请求与 Skill 选择

Skill 选择过程分三步：过滤 → 格式化 → LLM 决策。

过滤条件（满足所有条件才进入 Skills 列表）：

allCommands.filter(cmd =>
  cmd.type === "prompt" &&
  cmd.isSkill === true &&
  !cmd.disableModelInvocation &&
  (cmd.source !== "builtin" || cmd.isModeCommand === true) &&
  (cmd.hasUserSpecifiedDescription || cmd.whenToUse)
)

格式化后呈现给 Claude：

"pdf": Extract text from PDF documents - When user wants to extract or process text from PDF files

Claude 的决策（纯 LLM 语言推理，无算法匹配）：

{
  "type": "tool_use",
  "id": "toolu_123abc",
  "name": "Skill",
  "input": { "command": "pdf" }
}

阶段 3：Skill 工具执行（校验 → 权限 → 调用）

Step 1：validateInput（5 种错误码）

错误码含义
1command 为空
2Skill 不存在
3Skill 无法加载
4disableModelInvocation 为 true
5不是 prompt 类型

Step 2：checkPermissions（三种结果）

  • allow：匹配 allow 规则，直接执行
  • deny：匹配 deny 规则，拒绝并给出原因
  • ask：无匹配规则，弹窗询问用户

阶段 4：Turn 1 完成 — 完整 API Payload

{
  "model": "claude-sonnet-4-5-20250929",
  "messages": [
    {"role": "user", "content": "Extract text from report.pdf"},
    {"role": "assistant", "content": [{"type": "tool_use", "name": "Skill", "input": {"command": "pdf"}}]},
    {"role": "user", "content": "<command-message>The \"pdf\" skill is loading</command-message>\n<command-name>pdf</command-name>"},
    {"role": "user", "content": "You are a PDF processing specialist...\n\n## Process\n1. Validate PDF exists\n2. Run pdftotext...", "isMeta": true},
    {"role": "user", "content": {"type": "command_permissions", "allowedTools": ["Bash(pdftotext:*)", "Read", "Write"], "model": null}}
  ]
}

阶段 5：Bash 工具执行（携带 Skill 上下文）

此时 Claude 已接收 Skill Prompt，且 Bash(pdftotext:*) 已被预授权，无需再弹窗请求用户确认：

{
  "type": "tool_use",
  "id": "toolu_456def",
  "name": "Bash",
  "input": {
    "command": "pdftotext report.pdf output.txt",
    "description": "Extract text from PDF using pdftotext"
  }
}

九、关键技术对比

普通工具 vs Skill 工具：消息轮次对比

sequenceDiagram
    participant U as 用户
    participant C as Claude
    participant T as 工具

    Note over U,T: 普通工具调用（3-4 条消息）
    U->>C: 执行某操作
    C->>T: tool_use: Bash
    T->>C: tool_result
    C->>U: 返回结果

    Note over U,T: Skill 调用（5-10+ 条消息）
    U->>C: 执行复杂任务
    C->>T: tool_use: Skill{command}
    T->>C: tool_result + 元数据消息(可见) + Skill Prompt(隐藏) + 权限修改
    C->>T: tool_use: Bash(预授权，无弹窗)
    T->>C: tool_result
    C->>U: 返回结果

十、总结与关键洞察

作者在文末归纳了七条核心结论，这些结论颠覆了大多数人对 Skills 的直觉认知：

  1. Skills 是 SKILL.md 中的 Prompt 模板，不是可执行代码
  2. Skill 工具（大写 S）是 tools 数组中的 meta-tool，不在系统提示词里
  3. Skills 通过 isMeta: true 消息修改对话上下文来注入指令
  4. Skills 通过 contextModifier 修改执行上下文来变更工具权限和模型
  5. Skill 选择是通过 LLM 语言推理完成的，无算法匹配、无嵌入向量、无分类器
  6. 工具权限通过执行上下文修改作用域限定于 Skill 执行期间
  7. 每次 Skill 调用注入两条 user 消息：一条用户可见的元数据，一条 AI 可见的隐藏指令
设计哲学总结：Skills 将专域知识建模为"修改对话上下文的 Prompt"和"修改执行上下文的权限"，而非运行代码。这种声明式、Prompt-native 的设计与 LLM 的工作方式高度吻合，但也带来了 Token 开销大、并发不安全等固有局限。
