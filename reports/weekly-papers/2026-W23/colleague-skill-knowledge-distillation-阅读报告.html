概述

COLLEAGUE.SKILL 是上海 AI Lab 团队提出的一套端到端专家知识蒸馏框架，其核心洞察极为简洁而深刻："People leave. Skills don't."——人会离开，但他们的工作智慧、决策逻辑与沟通风格，理论上可以被永久保存并随时召唤。

这篇论文解决的不是"如何让 LLM 更聪明"，而是一个更具工程实践意义的问题：当一位同事、导师或领域专家留下了海量的异质 trace（飞书消息、GitHub PR 评论、设计文档、邮件往来），如何把这些碎片化的隐性知识，自动转化为一个可安装、可更新、可回滚的 AI 技能包，让后来者能够随时"咨询"这位虚拟专家？

论文提出了包含制品契约（Artifact Contract）、生成工作流（Generation Workflow）、纠错生命周期（Correction Lifecycle）和部署面（Deployment Surface）在内的完整系统，并以 ~18,500 GitHub Stars 的社区采用数据验证了其实际价值。截至 2026 年 5 月，社区已贡献 215 个真实技能，涵盖同事、导师、公众人物、虚构角色等多种类型。

研究背景

理解 COLLEAGUE.SKILL 的必要性，需要先厘清两个层面的问题：专家知识为什么难以被 LLM 直接利用，以及现有 Agent 记忆/Persona 方案为何不够用。

专家知识蒸馏的核心难点

人类专家的知识存在于两个维度：显性知识（文档、规范、教程）和隐性知识（决策直觉、风格偏好、情境判断、错误经验）。前者已被 RAG 等技术较好地利用，但后者——也是最有价值的部分——往往散落在：

  • 即时通讯工具（飞书、钉钉、Slack、微信）中的碎片化对话
  • 代码审查（GitHub PR review）中的评论与讨论
  • 会议纪要、设计文档、邮件往来
  • 截图、录音转写、PDF 报告

这些 trace 的特点是：异质性强（格式不统一）、上下文依赖（单条消息意义不完整）、噪声大（包含大量无关内容）、隐性结构（知识不以"规则"形式存在，而以行为模式呈现）。将它们转化为可操作的 AI 行为规范，需要专门设计的蒸馏流程。

现有 Agent 记忆方案的局限

学术界和工业界已有多种方案尝试让 LLM 携带个性化知识，但各有明显局限：

方案类型 代表工作 核心局限
RAG（检索增强） Lewis et al., 2020; LaMP 只能检索文档片段，无法提炼决策逻辑；每次查询都是独立的，缺乏对人格的整体建模
Memory Systems Reflexion, MemGPT 记忆是会话级的，不持久化为可分发的制品；无法跨 Agent 宿主安装；不可检查/审计
Persona/角色扮演 CharacterLLM, RoleLLM, Sotopia 主要针对虚构角色；依赖人工编写的角色描述；缺乏从真实 trace 自动生成的工作流；无版本控制
System Prompt 注入 各类 Agent 框架 是"不透明的提示词"，用户无法检查内部逻辑；无法增量更新；不支持自然语言纠错
Fine-tuning PersonaAgent 成本高；更新需重新训练；不支持分发；对普通用户门槛极高

上述方案的共同缺陷在于：它们要么只捕获知识片段（RAG），要么不可持久化分发（Memory），要么依赖人工编写（Persona），要么不透明不可纠错（System Prompt）。没有任何一套方案提供了从异质 trace 到可用技能的端到端自动化工作流。

研究空白（Research Gap）：不存在一套端到端的工作流，能将异质人类 trace 转化为"可检查、可纠错、可跨宿主安装"的 AI 技能包。COLLEAGUE.SKILL 正是填补这一空白而生。

核心架构

COLLEAGUE.SKILL 的系统架构由四个核心组件构成，形成一条从原始材料到可用技能的完整流水线。整体设计遵循"制品优先"原则：每个阶段的输出都是结构化、版本化的制品，而非隐藏在模型权重或会话上下文中的隐性状态。

制品契约（Artifact Contract）

制品契约是整个系统的核心数据结构，规定了技能包的标准格式、必含字段和版本语义。与"提示词模板"不同，制品契约是一个可机器读取、可人工检查、可差分更新的结构化文档。

一个典型的技能包文件结构如下：

colleague-skill/
├── SKILL.md              # 技能元数据（名称、版本、作者、权限）
├── capability/
│   ├── practices.md      # 工作实践：该专家如何处理具体任务
│   ├── mental-models.md  # 心智模型：决策框架与思维方式
│   └── heuristics.md     # 启发式规则：经验法则与判断标准
├── behavior/
│   ├── style.md          # 沟通风格：措辞、语气、格式偏好
│   ├── interaction.md    # 交互规则：何时追问、如何拒绝、边界条件
│   └── corrections.md    # 纠错历史：版本化的行为修正记录
└── metadata/
    ├── version.json      # 版本号、变更日志
    └── permissions.json  # 分发权限配置

这种结构的关键优势在于：人类可读（可以直接打开检查技能内容是否符合预期）、机器可操作（Agent 可以结构化地加载特定层级的内容）、版本可追溯（每次修改都有明确的变更记录）。

生成工作流（Generation Workflow）

生成工作流是蒸馏过程的执行引擎，分为四个顺序阶段：

  1. Intake（摄入）：调用各平台 Collector（飞书 API、钉钉浏览器自动化、Slack API、微信 SQLite 解析）抓取原始 trace，进行去重、清洗、时间排序。
  2. Analysis（分析）：Knowledge Extractor 对 trace 进行多轮 LLM 分析，识别重复出现的决策模式、偏好表达、拒绝理由等信号；Style Analyzer 提取语言风格特征（句式长度、专业术语密度、表情符号使用习惯等）。
  3. Build（构建）：Skill Builder 将分析结果按制品契约组装为双轨结构，进行内部一致性校验（例如：能力轨中的"快速原型优先"原则与行为轨中的"不催促交付时间线"规则是否冲突）。
  4. Merge（合并）：当有增量新材料时，Merger 组件负责将新提取的内容与现有技能包合并，保持版本连续性，避免覆盖已有的人工纠错记录。

双轨技能包设计

COLLEAGUE.SKILL 最核心的设计决策是将技能包分为能力轨（Capability Track）和行为轨（Bounded Behavior Track）两个协调运作的维度。这一设计源于对人类专家知识结构的深刻观察：一个人的"能做什么"和"怎么做人"是两种性质不同的知识，需要不同的表示方式和更新策略。

⚡ 能力轨（Capability Track）

回答的问题：这位专家如何解决问题？

  • 实践方法（Practices）：具体任务的处理流程，例如"代码审查时优先检查边界条件"
  • 心智模型（Mental Models）：思考框架，例如"用第一性原理拆解复杂问题"
  • 决策启发（Decision Heuristics）：快速判断规则，例如"超过 500 行的 PR 要求拆分"

更新频率：较低，随专家积累新经验时更新

可见性：完全可检查，鼓励用户阅读和验证

🎯 行为轨（Bounded Behavior Track）

回答的问题：这位专家如何与人互动？

  • 沟通风格（Style）：语气、措辞偏好、格式习惯
  • 交互规则（Interaction Rules）：何时追问澄清、如何表达不同意、拒绝请求的方式
  • 纠错历史（Correction History）：版本化的行为修正记录，记录"曾经做错了什么、如何修正"

更新频率：较高，每次用户反馈后即时更新

可见性：完全透明，包含完整的修正历史

为什么要分两轨？

两轨分离的设计解决了一个重要的工程问题：不同类型的知识有不同的稳定性和更新语义。

能力轨的内容（如"如何设计 API"）相对稳定，即使专家离职数年后仍然有效；而行为轨的内容（如"倾向于用反问句引导思考"）则高度个性化，且可能随用户的使用反馈而需要频繁调整。如果两者混在一起，对能力轨的更新可能意外覆盖行为轨的纠错记录，反之亦然。

此外，两轨在 Agent 执行时的加载优先级也不同：行为轨通常作为持久化的系统级约束，而能力轨则根据当前任务按需检索。

版本控制与回滚机制

技能包的版本控制遵循语义化版本（Semantic Versioning）规范，并针对 AI 技能的特殊性做了扩展：

版本变更类型触发条件版本号变化是否可自动合并
增量知识补充 导入新的 trace 材料 patch 版本 +1 是（Merger 自动处理）
行为纠错 用户自然语言反馈 minor 版本 +1 是（纠错流水线处理）
结构性重构 心智模型发生根本变化 major 版本 +1 否（需人工确认）
回滚 用户指定回到历史版本 版本号不变，打 rollback 标签 是（git-style 操作）

回滚机制的设计参考了 Git 的分支模型：每个版本都完整保存，回滚操作不会删除历史记录，而是在历史版本基础上创建新的"修复分支"。这对于 AI 技能尤为重要——当用户发现某次更新导致技能行为变差时，可以精确回到上一个好版本，而不是从头重新生成。

安装机制详解

技能包的安装遵循 AgentSkills 规范，支持多种 Agent 宿主。以 Claude Code 为例，安装只需一条命令： 

# 方式一：直接 clone 到 skills 目录
git clone https://github.com/titanwings/colleague-skill ~/.claude/skills/create-colleague

# 方式二：通过 Agent 自然语言指令安装
# "Install the dot-skill skill for me: https://github.com/titanwings/colleague-skill"

# 安装后，通过 slug 命令调用
# /colleague-zhang        → 调用完整技能（能力轨 + 行为轨）
# /colleague-zhang-work   → 仅调用能力轨
# /colleague-zhang-persona → 仅调用行为轨

这种分层调用设计允许用户根据场景选择加载粒度：在技术咨询场景只需加载能力轨，在模拟对话场景则同时加载两轨。

纠错流水线（Correction Pipeline）

纠错是技能生命周期中最关键的质量保障机制。系统支持自然语言反馈，无需用户了解技能包的内部结构：

用户："他不会用这么正式的语气，他喜欢用反问句引导思考"

系统：解析反馈 → 定位到 behavior/style.md → 更新"语气"和"引导方式"字段 → 记录到 corrections.md → 版本号 minor +1

纠错记录不仅是修正历史，也是未来蒸馏的负样本库：当导入新 trace 时，Merger 会自动避免重新引入已被纠错的行为模式。

COLLEAGUE.SKILL 不仅是一篇论文，更是一个已经获得大规模社区采用的开源项目。本节从工程实现和生态数据两个维度分析其现状。

兼容的 Agent 宿主

技能包遵循 AgentSkills 开放规范（agentskills.io/specification），可跨平台安装：

  • Claude Code（Anthropic）：官方支持，通过 ~/.claude/skills/ 目录加载
  • OpenClaw：开源 Agent 框架，支持 AgentSkills 规范
  • Hermes Agent：企业级 Agent 平台
  • Codex（OpenAI）：通过 MCP 协议桥接
  • MCP 兼容宿主：任何支持 Model Context Protocol 的 Agent 框架

Gallery 机制

社区技能的发现和分发通过 Gallery 机制实现，流程设计极为轻量：

  1. 贡献者填写 GitHub Issue 模板（技能名称、数据来源类型、简介、预览片段）
  2. CI 自动运行格式校验（制品契约完整性、版本号格式、权限字段合规性）
  3. 校验通过后自动合并，技能卡片即时上线展示
  4. 其他用户可一键 fork 并安装到自己的 Agent 宿主

Gallery 中的技能按角色家族（colleague/relationship/celebrity）和领域标签分类，支持按 Stars 数、更新时间、数据来源类型等维度筛选。

核心差异化定位

RAG 解决的是"知道什么"（知识检索），Memory 解决的是"记住了什么"（会话持久化），Persona 解决的是"像谁"（风格模仿）。COLLEAGUE.SKILL 解决的是更完整的问题：如何系统性地将一个真实人类的工作智慧转化为可维护、可分发、可进化的 AI 技能单元。

总结与启发

COLLEAGUE.SKILL 不仅是一个技术系统，更代表了 AI Agent 个性化知识管理领域的一次范式转移——从"记忆"到"技能"，从"隐性状态"到"可检查制品"，从"一次性提示词"到"版本化知识资产"。

范式转移：从"记忆"到"技能"

传统的 Agent 个性化方案将知识视为"记忆"——一种需要被检索或注入的被动存储物。COLLEAGUE.SKILL 则将其重新定义为"技能"——一种主动的、结构化的、可进化的知识单元。

这一转变的深层含义在于：技能是一等公民（first-class citizen）。它有自己的生命周期（生成→安装→更新→分发），有自己的版本历史，有自己的权限模型，可以像软件包一样被管理和分发。这与软件工程中从"脚本"到"模块"、从"模块"到"包"的演进路径高度相似。

可检查性的工程价值

"可检查、可纠错、可分发"这三个特性看似简单，实则是工程实践中极为关键的需求：

  • 可检查性解决了 AI 系统的信任问题。当一个 Agent 代表"已离职的张工"给出建议时，团队成员需要能够审查这个技能包的内容，确认它确实反映了张工的真实工作方式，而不是 LLM 的幻觉。
  • 可纠错性解决了知识衰减问题。随着时间推移，技术栈更新，某些历史知识可能变得过时甚至有害。能够通过自然语言反馈精确修正特定行为，而不影响其他内容，是维护知识质量的关键。
  • 可分发性解决了知识孤岛问题。一个工程师花时间蒸馏的专家技能，可以通过 Gallery 分享给整个社区，而不是被锁定在特定的 Agent 实例中。

对 AI 系统设计的启发

这篇论文对 AI 系统设计有几点重要启发：

  1. 制品优先（Artifact-First）原则：AI 系统的知识状态应该以可检查的制品形式存在，而不是隐藏在模型权重或会话上下文中。这是构建可维护、可审计 AI 系统的基础。
  2. 知识的双轨表示：将"能做什么"（能力）和"怎么做人"（行为）分离建模，不仅符合认知科学对人类专业知识的理解，也带来了实际的工程优势（不同更新频率、不同加载策略）。
  3. 开放标准的重要性：AgentSkills 规范的存在使技能包能够跨宿主安装，这对于 AI 生态的健康发展至关重要。正如 npm/pip 之于软件包生态，开放的技能分发标准可能成为 Agent 生态的基础设施。
  4. 社区驱动的知识积累：215 个技能、165 个贡献者的数据表明，当工具足够易用时，社区会自发地积累和分享知识。这种"众包专家知识"的模式可能比单一机构的知识工程更具规模效应。

局限性与开放问题

论文也诚实地讨论了若干局限性：

  • 数据隐私问题：从真实人物的通讯记录蒸馏技能，涉及复杂的隐私和同意问题。论文提出了"Responsible Deployment"框架，但具体的法律合规路径仍需各地区分别处理。
  • 蒸馏质量的上限：蒸馏质量依赖于 trace 的数量和质量。对于留下 trace 较少的人（如不常用文字沟通的专家），蒸馏结果可能不够准确。
  • 幻觉风险：当 trace 材料不足以覆盖某个问题域时，LLM 可能会"脑补"该专家的回答，产生与真实情况不符的输出。可检查性机制只能部分缓解这一问题。
  • 知识时效性：人的知识和观点会随时间演变。一个基于 2023 年 trace 蒸馏的技能包，到 2026 年可能已经过时。系统提供了增量更新机制，但用户需要主动维护。

一句话总结：COLLEAGUE.SKILL 将"让 AI 像某个专家一样思考"这一长期愿景，从科幻叙事变成了一套有工程规范、有版本控制、有社区生态的可操作系统。它的意义不仅在于技术本身，更在于它为"AI 技能"这一概念建立了一套可持续演进的工程范式。
