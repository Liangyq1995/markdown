LLM Gateway 在 Agent RL 训练中的应用

Rollout 管理 · 轨迹缓存 · Token 预算 · 工具代理 · 训练可观测性 | 专注 Gateway 与 Agent RL 训练系统的深度集成

核心议题LLM Gateway 如何成为 Agent RL 训练基础设施的关键组件
涉及能力并发 Rollout 管理、子轨迹语义缓存、训练 Token 预算控制、工具调用代理、轨迹级可观测性、多 Provider 路由

1. 为什么 Agent RL 训练特别需要 Gateway

Agent RL 训练的 Rollout 阶段会产生远比推理场景更极端的压力：同时采样数十条长轨迹（每条 10K~100K token）、频繁并发工具调用、需要跨多个 Provider 路由以控制成本——这些在直连 LLM API 的架构下根本无法管理。

直连 LLM API 的 Agent RL 训练会遭遇什么？
  • 并行 G=16 条轨迹 × 平均 20 步 = 每个 Batch 320 次 LLM 调用，直接命中 Provider RPM 限制
  • 单条 70K token 轨迹 × 16 并行 = 112M tokens/batch，成本失控，无预算保护
  • Provider 临时限速或故障直接中断训练，无熔断/故障转移，需要从头重跑
  • 轨迹中出现的相似子序列被重复送给 LLM 推理，无任何缓存复用
  • 训练崩溃后无法定位是哪步工具调用或哪个 Provider 导致的，缺乏可观测性

Gateway 在 Agent RL 训练中承担的不只是"代理转发"，而是成为训练基础设施的关键控制平面：

🔀 Rollout 并发管理
控制 G 条并行轨迹的 LLM 调用队列，匀速发送，防止 Provider 限速中断
💾 子轨迹语义缓存
相同前缀轨迹的 LLM 续写可复用缓存，节省重复计算
💰 训练 Token 预算
按 Batch/Epoch 设置 Token 上限，防止 RL 训练 Loop 中的成本爆炸
🔧 工具调用统一代理
Gateway 作为工具执行层，统一处理超时/重试/结果截断
📊 轨迹级可观测性
追踪每条轨迹的 token 消耗、步骤延迟、工具成功率，定位训练问题
⚡ 多 Provider 故障转移
训练中某 Provider 不可用时自动切换，保证 Rollout 不中断

3. Rollout 并发管理：Gateway 的调度核心

3.1 并发 Rollout 的核心矛盾

Agent RL 的 Rollout 阶段需要对同一任务并行采样 $G$ 条轨迹（GRPO 中 $G=8\sim16$），每条轨迹本身又是串行多步的——在每步 LLM 推理结束前无法进行下一步。这产生了"轨迹间并发、轨迹内串行"的特殊访问模式：

$$\text{并发 LLM 调用数} = G \times B \times \frac{1}{\bar{T}_{step}}$$

其中 $G$ 为并行轨迹数，$B$ 为 batch 中的任务数，$\bar{T}_{step}$ 为每步平均耗时。对于 $G=16, B=32, \bar{T}_{step}=3s$，峰值并发约 171 QPS——远超大多数 Provider 的 RPM 限制。

队列调度策略——步数少的轨迹优先（Shortest-Job-First 变体）：

$$\text{priority}(\tau) = \frac{1}{T_{current} + 1} + \alpha \cdot \frac{R_{partial}(\tau)}{T_{max}}$$

步数少的轨迹优先完成，释放资源；第二项鼓励奖励信号更高的轨迹优先推进（减少等待高质量经验）。

Algorithm 1: Rollout 并发调度器

class RolloutScheduler:

max_concurrent = 64 // 全局并发槽位上限

provider_rpm = {gpt4o: 500, claude: 200, gemini: 1000}

active_slots = Semaphore(max_concurrent)

pq = PriorityQueue()


async def submit(traj_id, step, request):

priority = -step // 步数少 → 负数更大 → 更高优先级

await pq.put((priority, traj_id, request))


async def dispatch_loop():

while True:

_, traj_id, req = await pq.get()

await active_slots.acquire()

// 检查 Provider 限速：按 RPM 令牌桶

provider = select_provider(req) // 路由决策

await rpm_bucket(provider).acquire()

asyncio.create_task(call_llm(req, traj_id))

// call_llm 结束时 release active_slots

3.3 训练感知的 Provider 路由

Agent RL 训练中 Provider 路由的目标与推理场景不同：训练更在意成本控制和轨迹多样性，而非最低延迟。

训练阶段路由策略原因
探索期（初期 Rollout）低成本 Provider 优先（Gemini/本地模型）早期策略质量差，省钱探索即可
精炼期（成功轨迹附近）高质量 Provider（GPT-4o/Claude）临近成功时需高质量推理找到正确路径
验证期（固定 Benchmark 评测）固定单一 Provider控制变量，保证评测可比性
大规模采样期多 Provider 混合 + 负载均衡并行度高，需要分散压力

路由决策可以注入轨迹元信息进行决策：

def select_provider_for_rollout(request: RolloutRequest) -> Provider:
    step = request.headers.get("X-Trajectory-Step", 0)
    partial_reward = request.headers.get("X-Partial-Reward", 0.0)
    is_eval = request.headers.get("X-Is-Eval", False)

    if is_eval:
        return FIXED_EVAL_PROVIDER  # 评测固定 Provider

    # 高奖励轨迹（接近成功）用更好的模型
    if partial_reward > 0.6:
        return Provider.GPT4O

    # 探索期（低步数 + 低奖励）用便宜模型
    if step < 5 and partial_reward < 0.2:
        return Provider.GEMINI_FLASH

    # 默认：UCB 选择（见 Gateway 路由报告）
    return ucb_router.select()

4. 子轨迹语义缓存：Agent RL 的独特缓存策略

4.1 Agent RL 中的缓存机会

标准 LLM 缓存（精确匹配或语义相似）在 Agent RL 中需要针对轨迹结构做特化设计，因为存在多种可复用的模式：

① 相同前缀轨迹
同一任务的 G 条并行轨迹，在初始步骤（系统提示 + 初始 obs）完全相同，第一步 LLM 调用可 100% 缓存复用，节省 G-1 次调用
② 跨轨迹相似子状态
不同任务的中间状态可能语义相近（如"搜索后发现信息不足，需要换关键词"），语义缓存可复用对应步骤的行动策略
③ 跨 Iteration 缓存
相邻训练迭代中，策略更新幅度小（KL < 0.05），相同子状态的最优动作基本不变，可复用上一 Iteration 的缓存
④ KV Cache 前缀共享
Gateway 感知公共前缀（系统提示 + 工具文档），在 vLLM 等推理引擎中启用 prefix caching，减少 TTFT

4.3 跨 Iteration 策略缓存

当相邻 RL 迭代的策略更新幅度较小时，缓存上一迭代的 $(s, a)$ 对具有复用价值。判断是否启用跨迭代缓存的条件：

$$\text{use\_cache} = D_{KL}(\pi_{\theta_{new}} \| \pi_{\theta_{old}}) \leq \delta_{cache}, \quad \delta_{cache} \approx 0.02$$

对于 KL 满足条件的状态，缓存命中的响应以概率 $p_{accept}$ 直接使用：

$$p_{accept}(s, a) = \min\!\left(1,\; \frac{\pi_{\theta_{new}}(a|s)}{\pi_{\theta_{old}}(a|s)}\right)$$

这实际上是 Metropolis-Hastings 接受准则——缓存命中但新策略更倾向该动作时接受，否则以相应概率重新采样。这样既节省了 LLM 调用成本，又保证了采样分布的正确性。

Algorithm 2: 跨 Iteration 策略缓存查找

Input: 状态 s_t, 新策略 π_new, 旧策略 π_old, KL阈值 δ=0.02


// Step 1: 检查全局 KL 是否允许缓存复用

if global_kl(π_new, π_old) > δ:

return fresh_llm_call(s_t) // 策略变化太大，不复用


// Step 2: 查找语义缓存（向量 DB）

cached = vector_db.search(embed(s_t), threshold=0.97)

if not cached:

return fresh_llm_call(s_t)


// Step 3: Metropolis-Hastings 接受准则

a_cached = cached.action

log_ratio = π_new.log_prob(a_cached | s_t) - π_old.log_prob(a_cached | s_t)

p_accept = min(1.0, exp(log_ratio))

if random() < p_accept:

return a_cached // 缓存命中，节省 LLM 调用

else:

return fresh_llm_call(s_t) // 拒绝缓存，重新采样

5. Training Token 预算控制

5.1 RL 训练的 Token 消耗模型

一个完整 RL 训练 Epoch 的 Token 消耗估算：

$$N_{tokens}^{epoch} = B \times G \times \bar{T} \times (\bar{L}_{ctx} + \bar{L}_{out})$$

其中 $B$ 为每 Epoch 的 Batch 数，$G$ 为并行轨迹数，$\bar{T}$ 为平均轨迹步数，$\bar{L}_{ctx}$ 为平均 Context 长度，$\bar{L}_{out}$ 为平均输出长度。

以典型参数（$B=100, G=16, \bar{T}=15, \bar{L}_{ctx}=8000, \bar{L}_{out}=500$）估算：

$$N_{tokens}^{epoch} = 100 \times 16 \times 15 \times 8500 \approx 204 \text{ 亿 tokens/epoch}$$

使用 GPT-4o 价格（输入 $2.50/M，输出 $10.00/M$），单 Epoch 成本约 $\$5.1$万——没有 Token 预算控制就是灾难。

5.3 Gateway 的预算强制执行

class TrainingTokenBudget:
    """Gateway 中的训练 Token 预算控制器"""

    def __init__(self, epoch_limit: int, batch_limit: int, traj_limit: int):
        self.epoch_budget = TokenBucket(epoch_limit, refill_on="epoch_start")
        self.batch_budget = TokenBucket(batch_limit, refill_on="batch_start")
        self.traj_budgets: dict[str, int] = {}  # traj_id → consumed

    async def check_and_consume(self, request: RolloutRequest) -> BudgetDecision:
        traj_id = request.headers["X-Trajectory-ID"]
        estimated_tokens = estimate_tokens(request)

        # 层次检查（从粗到细）
        if not self.epoch_budget.try_consume(estimated_tokens):
            return BudgetDecision.PAUSE_ROLLOUT  # 暂停当前 Epoch 的 Rollout
            # Gateway 返回 503 + Retry-After: {seconds_to_next_epoch}

        if not self.batch_budget.try_consume(estimated_tokens):
            return BudgetDecision.DROP_BATCH_REMAINDER  # 丢弃当前 Batch 残余

        traj_consumed = self.traj_budgets.get(traj_id, 0)
        if traj_consumed + estimated_tokens > TRAJ_LIMIT:
            # 注入强制终止指令：在 system 消息末尾追加终止提示
            request.inject_finish_instruction()
            return BudgetDecision.FORCE_FINISH

        self.traj_budgets[traj_id] = traj_consumed + estimated_tokens
        return BudgetDecision.ALLOW

5.4 Cost-Aware 训练策略

Gateway 的预算信息可以反馈给 RL 训练器，动态调整采样策略：

预算状态Gateway 响应训练器调整
充裕（>60% 剩余）全速放行保持 G=16，高质量 Provider
适中（30-60% 剩余）降低并发上限降至 G=8，混合 Provider
紧张（<30% 剩余）优先保成功轨迹G=4，低成本 Provider，跳过低奖励任务
耗尽（<5% 剩余）503 暂停采样用已有轨迹做 PPO 更新，等待预算重置

6. 工具调用统一代理层

6.1 为什么 Gateway 应该代理工具调用

在标准 Agent 架构中，工具调用由 Agent 代码直接执行。引入 Gateway 作为工具代理层后，带来以下收益：

统一超时控制
代码沙箱 30s 超时、网页加载 15s 超时，统一在 Gateway 层配置，Agent 代码无需关心
工具结果截断
大型工具输出（如搜索返回 100K 字符）在 Gateway 层智能截断，防止 Context 爆炸
工具幻觉拦截
Agent 调用不存在的工具时，Gateway 拦截并返回结构化错误，不产生真实副作用
工具调用审计
所有工具调用记录在 Gateway，追踪工具使用频率、成功率、耗时分布

6.3 工具结果智能截断算法

大型工具输出（测试报告、搜索结果、文件内容）需要智能截断，保留对 Agent 决策最有价值的部分：

def smart_truncate_tool_output(
    output: str,
    max_tokens: int = 3000,
    func_name: str = "bash"
) -> str:
    """按工具类型选择最优截断策略"""

    if count_tokens(output) <= max_tokens:
        return output  # 不需要截断

    if func_name in ("bash", "python"):
        # 代码执行：保留最后 N 行（错误通常在末尾）+ 前几行（输出开头）
        lines = output.split("\n")
        head = "\n".join(lines[:20])        # 前 20 行
        tail = "\n".join(lines[-50:])       # 最后 50 行（包含 traceback）
        middle_note = f"\n...[已截断 {len(lines)-70} 行]...\n"
        return head + middle_note + tail

    elif func_name == "search":
        # 搜索结果：保留每个结果的标题 + 摘要，去掉正文
        results = parse_search_results(output)
        truncated = [f"[{i+1}] {r.title}\n{r.snippet[:200]}"
                     for i, r in enumerate(results[:10])]
        return "\n\n".join(truncated)

    elif func_name == "read_file":
        # 文件读取：保留头部 + 尾部，注明中间被截断
        chars_per_token = 4
        max_chars = max_tokens * chars_per_token
        half = max_chars // 2
        return output[:half] + f"\n...[截断 {len(output)-max_chars} 字符]...\n" + output[-half:]

    else:
        # 默认：直接截断
        return output[:max_tokens * 4] + "\n...[已截断]"

8. 熔断器在训练稳定性中的作用

8.1 训练特有的熔断场景

Agent RL 训练中的熔断需求与推理服务不同，除了 Provider 故障，还需要应对训练内生的不稳定性：

触发场景熔断层级恢复策略
Provider API 返回 5xx 连续 10 次Provider 级熔断切换备用 Provider，指数退避重试
单批次 Token 消耗超预算 2 倍Batch 级熔断丢弃当前 Batch，降低并行度后重启
工具沙箱连续 OOM / Timeout工具级熔断降低工具输出 Token 上限，重启沙箱
KL 散度连续 3 个 Batch 超阈值训练级告警通知训练器降低学习率
策略 loss 突然变 NaN训练级熔断暂停 Rollout，加载上一个 Checkpoint

8.2 Checkpoint 感知的熔断器

训练级熔断最重要的恢复动作是加载上一个稳定 Checkpoint，而 Gateway 是触发这一动作的最早感知点：

class TrainingCircuitBreaker:
    def __init__(self, trainer_callback):
        self.trainer_callback = trainer_callback  # 通知训练器的回调
        self.consecutive_bad_batches = 0
        self.loss_history = deque(maxlen=10)

    async def on_batch_complete(self, metrics: BatchMetrics):
        self.loss_history.append(metrics.policy_loss)

        # 检测 NaN/Inf
        if math.isnan(metrics.policy_loss) or math.isinf(metrics.policy_loss):
            await self.trainer_callback.pause_training()
            await self.trainer_callback.load_checkpoint("last_stable")
            self.consecutive_bad_batches = 0
            return

        # 检测 Loss Spike（超过历史 3σ）
        if len(self.loss_history) >= 5:
            mean_loss = statistics.mean(self.loss_history)
            std_loss = statistics.stdev(self.loss_history)
            if abs(metrics.policy_loss - mean_loss) > 3 * std_loss:
                self.consecutive_bad_batches += 1
                if self.consecutive_bad_batches >= 3:
                    # 连续 3 个 Batch 异常，触发熔断
                    await self.trainer_callback.reduce_lr(factor=0.5)
                    await self.trainer_callback.pause_rollout(seconds=60)
            else:
                self.consecutive_bad_batches = 0

9. 多 Provider 协同的 Rollout 策略

9.1 混合精度 Rollout：不同 Provider 承担不同角色

Agent RL 训练中并非所有步骤都需要最强的模型，Gateway 可以根据轨迹状态动态分配 Provider：

flowchart LR
    T["轨迹状态\n每步判断"] --> INIT["初始步骤\nt=0~2\n探索阶段"]
    T --> MID["中间步骤\nt=3~N-3\n执行阶段"]
    T --> CRIT["关键步骤\n接近成功时\npartial_reward>0.6"]
    T --> FINAL["最终步骤\n生成答案"]

    INIT -->|"便宜模型"| GF["Gemini Flash\n低成本探索"]
    MID -->|"中等模型"| GM["GPT-4o-mini\n均衡性价比"]
    CRIT -->|"最强模型"| G4["GPT-4o / Claude\n关键决策"]
    FINAL -->|"高质量模型"| G4

    style MID fill:#2a2a3e,stroke:#89b4fa

混合精度路由的成本节省估算（假设 30% 初始步 + 50% 中间步 + 20% 关键步）：

$$\text{cost}_{mixed} = 0.3 \cdot c_{cheap} + 0.5 \cdot c_{medium} + 0.2 \cdot c_{strong}$$

$$= 0.3 \times \$0.3 + 0.5 \times \$1.5 + 0.2 \times \$10 = \$2.84/\text{M tokens}$$

与全程使用 GPT-4o（$\$10/\text{M tokens}$）相比，节省约 72% 成本，而训练效果损失有限（关键步骤仍用最强模型）。

9.2 同构/异构 Provider 的 Rollout 差异处理

当不同步骤使用不同 Provider 时，需要处理模型间的输出风格差异：

  • 格式一致性：Gateway 对不同 Provider 的工具调用格式做统一归一化（Anthropic 的 tool_use → OpenAI 的 function_call）
  • Token 计数不一致：不同模型的 tokenizer 不同，Gateway 用各自 tokenizer 精确计数，统一转为字符数后再做截断
  • 重要性比率修正：若轨迹内不同步骤由不同模型生成，PPO 的 importance ratio $\pi_{new}(a|s)/\pi_{old}(a|s)$ 中的 $\pi_{old}$ 需要记录生成时的实际模型概率，而非统一用当前模型估算

11.2 Rollout Worker 与 Gateway 的交互接口

class GatewayRolloutClient:
    """Rollout Worker 使用的 Gateway 客户端"""

    def __init__(self, gateway_url: str, session_id: str):
        self.base = gateway_url
        self.session_id = session_id

    async def llm_step(
        self,
        traj_id: str,
        step: int,
        messages: list[dict],
        partial_reward: float = 0.0,
        tools: list[dict] = None,
    ) -> LLMStepResult:
        """发送单步 LLM 请求，Gateway 自动处理路由/缓存/预算"""
        response = await self.client.post(
            f"{self.base}/v1/chat/completions",
            json={"model": "auto", "messages": messages, "tools": tools},
            headers={
                "X-Training-Session": self.session_id,
                "X-Trajectory-ID": traj_id,
                "X-Trajectory-Step": str(step),
                "X-Partial-Reward": str(partial_reward),  # 用于路由决策
            }
        )
        if response.status_code == 503:
            # Gateway 预算耗尽，等待后重试
            retry_after = int(response.headers.get("Retry-After", 60))
            await asyncio.sleep(retry_after)
            return await self.llm_step(traj_id, step, messages, partial_reward)
        return LLMStepResult.from_response(response)

    async def execute_tool(self, traj_id: str, step: int, tool_call: ToolCall) -> ToolResult:
        """通过 Gateway 工具代理执行工具调用"""
        response = await self.client.post(
            f"{self.base}/v1/tool/execute",
            json={"tool_call": tool_call.dict()},
            headers={
                "X-Trajectory-ID": traj_id,
                "X-Trajectory-Step": str(step),
            }
        )
        return ToolResult.from_response(response)

12. 性能收益量化

13. 核心洞见

🔑 洞见 1：Gateway 的并发调度是 Agent RL 规模化的关键瓶颈
G=16、Batch=32 意味着同时维护 512 条活跃轨迹的 LLM 调用队列。没有 Gateway 的并发控制，直连 Provider 的 RPM 限制会将实际并发压缩到个位数，训练速度损失 10 倍以上。
🔑 洞见 2：跨 Iteration 策略缓存可以节省 15~30% Token 成本
Agent RL 相邻迭代的策略 KL 通常在 0.01~0.05，大量中间状态的最优动作基本不变。用 Metropolis-Hastings 接受准则复用缓存，在保证采样分布正确性的同时实现可观的成本节省。
🔑 洞见 3：混合精度 Rollout（不同步骤用不同 Provider）可节省 60~75% 成本
探索期和中间步骤不需要最强模型，只有关键决策步（接近成功）才需要 GPT-4o 级别。Gateway 根据 partial_reward 自动切换 Provider，成本与全用强模型相比大幅下降。
⚠️ 陷阱 1：工具代理的超时设置必须比 LLM 超时更长
代码执行（pytest）可能需要 60s+，如果 Gateway 工具代理超时过短（如 30s），会导致频繁的"工具超时"误报，Agent 被迫处理虚假错误，严重干扰训练信号质量。建议代码执行超时 ≥ 120s，并支持流式进度上报。
⚠️ 陷阱 2：不要对工具结果做语义缓存（应做精确哈希缓存）
工具执行结果（测试输出、文件内容）必须精确匹配才能复用，不能用语义相似度——99% 相似的两个测试报告可能结论完全相反（1个 FAIL vs 0个 FAIL）。工具结果缓存只能用 hash(input) 精确匹配。
💡 实践建议：先用本地 vLLM 验证训练逻辑，再接入 Gateway 做规模化
调试阶段（G=2，B=4）用本地 vLLM 推理，验证奖励函数、轨迹格式、工具调用链路正确性，成本近乎零。逻辑验证通过后，接入 Gateway 做并发控制和成本管理，再逐步放大到生产规模（G=16，B=32）。
