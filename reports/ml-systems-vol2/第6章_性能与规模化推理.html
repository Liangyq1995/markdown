一、开篇：Profile 本地，Proof 舰队

Vol.1 第 7 章用 Roofline 诊断硬件、用 MLPerf Server 场景问责 claim——Profile 给出方向，Benchmark 给出 Proof。本章把同一纪律推到 LLM 部署：先在单节点用 profiler 把 kernel 推近硅片物理上限，再在多副本舰队问该数字在 Poisson 到达与 tail SLO 下是否可持续。

全书锚点不变：70B LLM，8×H100 NVLink 单节点，产品 SLO 为 TTFT <500 ms、ITL <50 ms、稳态吞吐 ≥1000 tok/s。性能工程（Profile）回答「这一刀该砍带宽还是算力」；规模化推理（Proof）回答「1050 tok/s 的 Offline 数字能否在 $\lambda=8$ req/s 的聊天流量下兑现，且 $/token 仍盈利」。两问共用同一模型、同一栈——不是两章拼接，而是一条证据链。

本章验收问题（Proof 标准）

Round 2 后在固定 batch=32、prompt=512、output=128 的Offline 压测中达到 1050 tok/s——这只是 Profile 终点。上线后须同时满足：

  • MLPerf Server 类比：Poisson 到达、p99 TTFT <500 ms、p99 ITL <50 ms 下的有效 tok/s
  • $/token = (GPU·hr × 副本数) / (有效 tok/s × 3600)，含 SLO headroom 与冷启动浪费
  • Continuous batching + PagedAttention 不把 KV 或 Prefill 算力变成新瓶颈

二、Roofline 诊断与 Prefill/Decode 双体制

内存墙与脊点 $I_{\text{ridge}} = R_{\text{peak}}/\text{BW}$ 的完整推导见 Vol.1 第 7 章；此处只保留服务所需的一次诊断。H100 FP16：$R_{\text{peak}}\approx 989$ TFLOP/s，HBM 3.35 TB/s → $I_{\text{ridge,FP16}}\approx 295$ FLOP/byte。Attainable 吞吐 $R_{\text{attain}}=\min(R_{\text{peak}},\,\text{BW}\times I)$——LLM serving 的关键不是背公式，而是同一 forward 里 prefill 与 decode 落在 Roofline 的不同区域。

$$R_{\text{attain}} = \min\big(R_{\text{peak}},\; \text{BW} \times I\big)$$

2.1 Prefill：算力型提示处理

一次 forward 并行处理 prompt 长度 $S$；GEMM 有效 batch 含 $S$，算术强度随 $S$ 上升。$S=1024$、FP16 权重时 $I \approx 1024$ FLOP/byte → compute-bound，TTFT 由 Tensor Core 与 FlashAttention 决定。FlashAttention-2 对 prefill 收益最大：$S=8192$、64 head、$d=128$ 时朴素 attention 每层 HBM 驻留 ~34.9 GB，FA-2 持久状态 ~537 MB——online softmax 在 SRAM 分块，削减 $S^2$ 材料化。

2.2 Decode：带宽型逐 token 生成

$$I_{\text{decode}}(B) = \frac{2PB}{P s_{\text{param}} + B d_{\text{model}} s_{\text{elem}}}$$

$B=1$ 时 $I \approx 1$ FLOP/byte，远低于脊点——GPU 等 HBM 搬 70B 权重，MFU 个位数仍「正常」。增大 batch $B$ 线性提高 $I$，但 KV cache 占满 HBM：70B FP16 权重 140 GB 跨 8 卡后，每卡约 62.5 GB 留给 KV。batch-1 decode 看带宽 + 容量；大 batch decode 可能转向 compute-bound——Round 1 量化后瓶颈会迁移（waterbed）。

Profile 循环（每轮优化后必做）

  1. Nsight / PyTorch profiler 测 TTFT、ITL、tok/s 与 kernel 占比
  2. 按上表分类瓶颈：mem / compute / overhead
  3. 选最高杠杆一类动刀（memory-bound 时 compile 先于量化 = 零收益）
  4. 复测——waterbed 后下一刀对准新脊点

三、单节点优化栈：字节、融合与 launch

在 70B 锚点上，优化栈按瓶颈类型排序，而非按技术时髦度堆叠。

3.1 字节杠杆：量化与 KV 压缩

Decode memory-bound 时，INT4 AWQ 将 70B 权重从 17.5 GB/GPU 压至 4.4 GB/GPU，权重读流量约 4× 降；INT8 KV cache 使每 token 驻留减半，可用 KV 池从 ~62.5 GB/GPU 扩至 ~75.6 GB/GPU。Horowitz 能量层级：HBM 读 ~640 pJ vs SRAM ~0.5 pJ——量化攻击的是字节移动成本，不是抽象「少几位」。

3.2 融合杠杆：少一次 HBM 往返

Transformer 层 bias-GELU-dropout 未融合：每层多 2 次 HBM round-trip，80 层 × 67 MB ≈ 5.4 GB/forward 纯流量。FlashAttention 族把 attention 的 softmax 留在 SRAM；与 PagedAttention 配合时 decode 瓶颈从 $S^2$ 矩阵转向KV 块读——prefill 与 decode 收益不对称，须分阶段 profile。

3.3 Launch 杠杆：compile 与 CUDA Graph

基线 eager 模式 element-wise 占 14%、kernel launch 占 12%——对 batch=1 decode，launch gap 可与 GEMM 同量级。推荐顺序（memory-bound serving）：

  1. INT4/FP8 权重 + INT8 KV（先于 compile）
  2. FlashAttention-2 + PagedAttention
  3. torch.compile max-autotune / CUDA Graph
  4. Speculative decoding（需 draft 模型，最后上）

四、70B Playbook：三轮优化与 1050 tok/s claim

基线（FP16 eager，8×H100 TP=8）：TTFT 1200 ms，ITL 85 ms，max batch=4，Offline 吞吐 280 tok/s——距 SLO 与 1000 tok/s 目标均远。以下三轮在同一节点、同一 trace 上迭代；每轮后 reprofile。

Round 1 — 精度工程（带宽刀）

  • AWQ INT4 权重 + INT8 KV cache
  • max batch 4→32（KV 池释放）
  • 结果：batch=1 ITL 48 ms ✓；batch=32 吞吐 720 tok/s（仍 <1000）
  • 新瓶颈：大 batch 下 element-wise + launch；Prefill 仍偏 compute

Round 2 — 融合与编译（launch + prefill 刀）

  • torch.compile max-autotune：element-wise 14%→4%
  • FlashAttention-2 + CUDA Graph：launch 12%→~0
  • 结果：TTFT 380 ms ✓，ITL 32 ms ✓，batch=32 Offline 吞吐 1050 tok/s ✓

Round 3 — 条件 Speculative Decoding（延迟刀，非吞吐刀）

1.5B INT4 draft（0.75 GB）一次提案 $k=5$ token（4 ms）；70B 验证 ~32 ms。接受率 $p_{\text{acc}}=0.78$：

$$\text{ITL}_{\text{eff}} = \frac{T_{\text{draft}} + T_{\text{verify}}}{(1-p_{\text{acc}}^{k+1})/(1-p_{\text{acc}})} \approx \frac{4+32}{(1-0.78^{6})/(1-0.78)} \approx \frac{36}{3.5} \approx 10.3\ \text{ms/token}$$

相对 Round 2 的 32 ms 约 3.1×——但 batch≥16 时 verification 不再「免费」。生产策略：队列深度 <8 开 spec；高负载回退自回归，保 1050 tok/s 吞吐上限。

4.1 速增不可相乘（waterbed）

INT4 单独测带宽路径 ~3.7×；FlashAttention 单独测 1.9×——若 naive 相乘期待 ~7×，实际叠加仅 ~3.8×。二者均攻击 HBM 项；Round 1 后 decode 大 batch 已部分 compute-bound，再堆纯带宽优化收益递减。工程含义：每轮只信 reprofile 数字，不信乘法表。

Round 2 的 1050 tok/s 是在 prompt=512、output=128、batch=32 静态填满的 Offline 条件下测得——GPU 利用率 ~95%，无排队、无 tail。产品流量是 Poisson 到达、长短 prompt 混部、会话粘滞与 autoscale 冷启动：Profile 终点恰是 Proof 起点。下一节起用同一栈问舰队经济学与 Server 有效吞吐。

五、$/token 经济学：把节点吞吐换成舰队账单

训练是一次性 CapEx；推理是持续性 OpEx——Facebook 2018 量级每日数十万亿次推理。LLM API 竞价使 $/token 成为产品 KPI。Vol.1 单 H100 Llama3 8B AWQ：Prefill 瓶颈 10 req/s → ~$0.066/M tokens（$3/hr 云租）。70B 8×H100 节点云租约 $24/hr；若错误地用 Offline 1050 tok/s 规划：

$$\$/M\,\text{tok} \approx \frac{24}{1050 \times 3.6} \approx \$0.0063$$

看起来极便宜——但 Offline 忽略 SLO headroom、排队与副本空转。真实成本模型：

$$\$/M\,\text{tok} \approx \frac{C_{\text{GPU·hr}} \times N_{\text{replicas}}}{\text{tok/s}_{\text{valid}} \times 3600 \times 10^{6}}$$

成本乘子（与 1050 tok/s claim 挂钩）

  • SLO headroom：p99 约束强制平均利用率 $\rho \lt 60\%$ → 等效 tok/s ×0.6，$/token ×1.67
  • 冷启动 / 缩容滞后：30% 副本空转 warm → 再 ×1.43
  • 跨 AZ 与 PD 分离：Prefill→Decode 跨网络 adds TTFT；须单独计费 Prefill 池

仅 headroom + 空转：$0.0063 \times 1.67 \times 1.43 \approx \$0.015/M tok——仍乐观，因尚未用 Server 有效 tok/s 替换 1050。

维度选项对 70B 舰队的影响
部署集中 / 边缘 / 混合8×H100 节点仅适合集中；边缘用蒸馏小模型
状态无状态 / KV 有状态70B 长会话必须 sticky 或共享 KV 层
精度INT4 权重 + INT8 KV与 playbook 一致；FP16 回退 = 带宽地板 ×4
并行TP=8 单节点 / 多副本 DPTP 限 NVLink 域；扩吞吐靠副本非加卡 TP

六、Continuous Batching 与 KV：利用率第二战场

Static batch 等最长序列完成才释放 slot → GPU 空泡。Continuous batching（vLLM、TGI）在iteration 级插入/移除序列；Prefill 与 Decode 可异构混批——这正是把 Offline batch=32 推广到变长、动态到达的关键机制。

$$L_{\text{total}} \approx T_{\text{prefill}}(\text{prompt}) + N_{\text{out}} \times \text{TPOT}$$

舰队吞吐上限常由Prefill 算力或KV 驻留容量二选一绑定。70B GQA（FP16 KV 口径）：每 token 每序列 KV ≈ 0.31 MB。32 序列 × 8K context ≈ 80 GB 仅 KV——超单卡 HBM，须 PagedAttention 分页 + 8 卡 TP 分布。

PagedAttention 与 70B 并发槽

KV 块大小 16 token/block：碎片率从 40–50% 降至 90%+ 利用率。同 75.6 GB/GPU KV 池（Round 1 后）：

  • 朴素连续分配：~700 并发槽（avg context 4K）
  • PagedAttention：~1700 槽——等效 tok/s 上限随槽位线性上升

PCIe KV offload（~32 GB/s）会把 TPOT 下限抬升——playbook 栈默认 KV 在 HBM；offload 是 Proof 失败时的退路，非 Profile 首选。

6.1 KV cache 字节数（70B GQA 手算）

每层 KV 驻留（GQA，$n_{\text{kv\_head}}=8$，$d_{\text{head}}=128$，FP16 $s_{\text{elem}}=2$）：

$$M_{\text{KV/token/layer}} = 2 \times n_{\text{kv\_head}} \times d_{\text{head}} \times s_{\text{elem}} = 2 \times 8 \times 128 \times 2 = 4096\ \text{bytes}$$

80 层 × 4096 B ≈ 0.31 MB/token/序列。context=8192、batch=32：$0.31 \times 8192 \times 32 \approx 81$ GB——超过单卡 80 GB HBM，印证必须 TP 分片 + PagedAttention，而非单纯增大 static batch。

6.2 Prefill 与 Decode 容量分裂

Vol.1 Llama3 8B 单卡：Prefill ~10 req/s vs Decode ~1749 并发槽——算力与内存不同维度瓶颈。70B 8×H100 经 playbook 后：Prefill（512 tok）~380 ms → 单节点 ~2.6 prompt/s/GPU 组；Decode 1050 tok/s Offline。Poisson 聊天（avg prompt 512、output 128、$\lambda=8$ req/s/节点）下，Prefill 池与 Decode 池若混在同一 continuous batcher，长 prompt 尖峰会挤占 decode slot → TTFT p99 恶化。Proof 阶段须分池度量 Prefill tok/s 与 Decode tok/s，而非只报 blended 1050。

七、路由、PD 分离与多副本拓扑

单节点 Profile 完成；舰队 Proof 还须回答请求落在哪一副本、KV 是否复用、Prefill 是否重复计算。

  • 最短队列 / WRR：忽略 KV 亲和 → 会话迁移后 Prefill 重算，TTFT 翻倍
  • Session affinity：同 session_id 粘滞副本，利于 prefix cache 与 KV 局部性
  • Prefill-Decode 分离（PD disaggregation）：算力型 Prefill 池（吃 FA-2、大 $S$）+ 带宽型 Decode 池（吃 INT4、PagedAttention），各自 HPA

路由错误是 silent killer：Offline 1050 tok/s 不变，但有效 tok/s因重复 Prefill 可跌 20–40%。Prefix caching（相同 system prompt）在 affinity 下 hit 率 >60% 常见；无 affinity 时 hit≈0。

7.1 Autoscaling：GPU 指标，非 CPU

K8s HPA 默认 CPU 对 LLM 失效。Prometheus 规则示例（与 70B Proof 设计点 $\lambda=8$ 对齐）：

# HPA 自定义指标（KEDA / Prometheus adapter）
- name: decode_queue_depth
  query: avg(vllm:num_requests_waiting{model="llama70b"})
  scaleUp:   value > 12 for 2m    # ~1.5× 设计点
  scaleDown: value < 4  for 10m   # 防抖动

- name: ttft_p99_ms
  query: histogram_quantile(0.99, vllm:time_to_first_token_seconds)
  scaleUp:   value > 450 for 3m   # SLO 500 ms 留 10% 余量

- name: kv_cache_usage_pct
  query: avg(vllm:gpu_cache_usage_perc)
  scaleUp:   value > 85 for 5m    # 接近 OOM 前扩容

缩容过激进会触发冷启动：8×H100 加载 INT4 权重 + compile cache 常需 3–8 min，期间该副本 tok/s=0 仍计费——计入 §5 的 30% 空转乘子。多租户混部须 MIG 或时间片；INT4 租户与 FP16 租户 OOM 连坐——内存配额与 eviction 策略属于 Proof 范畴，不在单节点 Profile 内。

八、Server Proof：1050 tok/s 在 Poisson SLO 下还成立吗？

MLPerf Inference Server 场景：请求 Poisson 到达、延迟 SLO 约束下最大化吞吐。Vol.1 ResNet-50：Offline ~45K img/s vs Server p99<15 ms ~8.5K img/s——Offline 比 Server 高 ~5×。LLM continuous batching 缩小鸿沟，但不会消失：动态 batch、排队与 tail 仍吃掉 headroom。

Proof 结论（单节点）

1050 tok/s 在 Poisson Server 下不能原样成立。在 p99 SLO 内可持续的设计点约 870–900 tok/s（$\lambda \approx 7$–8 req/s，ρ≈55–60%）。Round 3 spec decode 可将 ITL p99 从 32 ms 压至 ~15 ms，使同负载下 SLO 违反率 11%→4%，有效 tok/s 872→940——spec 是 Proof 工具，不是 Profile 吞吐工具。

8.3 舰队副本数与 $/token 闭环

目标峰值 $\Lambda=400$ req/s，每节点设计点 $\lambda=8$/s、有效 900 tok/s ≈ 7200 tok/min/节点：

$$N_{\text{replicas}} \approx \frac{\Lambda}{\lambda \times (1 - h_{\text{headroom}})} = \frac{400}{8 \times 0.55} \approx 91\ \text{节点}$$

$C_{\text{GPU·hr}}=24$、$N=91$：

$$\$/M\,\text{tok} \approx \frac{24 \times 91}{900 \times 3600} \approx \$0.067$$

若错误用 Offline 1050 与 $N=76$ 规划：$/M tok 看似 $0.053——低 21% 的幻觉，上线后要么 SLO 违约要么隐性加班扩容。Profile → Proof 闭环：节点 playbook 给出上限；Server 压测 + 路由 + 经济学给出可售卖数字。

8.5 Goodhart 与 benchmark–production gap

三类常见 gaming，均与 1050 tok/s claim 相关：

  • 固定 trace 过拟合：只在 prompt=512 上调 AWQ 校准 → 长文档 TTFT 劣化 40%，Server 有效 tok/s 再降 15%
  • 关闭 SLO 报 peak：marketing 写「单节点 1050 tok/s」而合同写 p99 ITL <50 ms——二者不可同时取 max
  • 忽略路由损耗：压测直连 vLLM，生产经 Gateway 无 affinity → 重复 Prefill，有效 tok/s 再 ×0.7

舰队 Proof 检查清单（上线前）

  1. Poisson Server 压测 ≥4 h，报告 tok/svalid 非 raw
  2. Prompt 长度分布覆盖 p95（如 2K token），非仅 512
  3. Session affinity 与 prefix cache hit 率可观测
  4. Autoscale 冷启动窗口内 SLO 降级策略（排队 vs 拒载）
  5. $/M tok 用 tok/svalid 与 $N_{\text{replicas}}$ 重算，与 Offline 1050 对比偏差 >15% 则驳回容量计划

九、章节总结

Profile → Proof 推理链（70B @ 8×H100）

  1. Profile：Roofline 一次诊断 → Prefill 攻 FLOPs/FA-2，Decode 攻 bytes（INT4+INT8 KV）→ compile 攻 launch；三轮 playbook Offline 1050 tok/s
  2. Waterbed：速增不可相乘；每轮 reprofile；高负载关闭 spec 保吞吐
  3. Proof：Continuous batching + PagedAttention 将动态负载接入 playbook 栈；Prefill/Decode 分池度量
  4. 路由：Session affinity 与 PD 分离决定 KV 局部性与重复 Prefill；路由失误 silent 降有效 tok/s
  5. Server 验收：Poisson + p99 SLO 下有效 ~900 tok/s，非 1050；$/M tok ~$0.067 @ 400 req/s 舰队
  6. 与 Vol.1 第 7 章同构：Roofline/Profile 在节点；MLPerf Server/有效 QPS 在舰队——LLM 只是把 QPS 换成 tok/s、把 batch 换成 continuous batching

单节点优化把 tensor 路径匹配硅片物理；舰队 Proof 问同一栈在 Poisson 到达、SLO headroom 与多副本下是否仍盈利——Offline 数字是上限，Server 数字才是合同。
