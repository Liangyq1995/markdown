关键结论：PD 分离已成为 2025 年大规模 LLM 服务的工业标准，DistServe 实现 7.4× goodput 提升，Mooncake 使 Kimi 请求处理量提升 59%–525%

1. LLM 推理的两阶段本质

现代 LLM 的自回归推理由两个性质截然不同的计算阶段组成： Prefill（预填充）和 Decode（解码）。 理解这两个阶段的根本差异是 PD 分离技术的理论基础。

⚡ Prefill 阶段（计算密集型）

  • 一次性并行处理所有输入 tokens
  • 执行大矩阵乘法（Tensor Core 满载）
  • 生成并存储 KV Cache
  • 瓶颈：GPU 算力（Compute-bound）
  • 决定指标：TTFT（Time To First Token）
  • 典型算力利用率：>80%（MFU）

🔁 Decode 阶段（内存带宽密集型）

  • 每次只生成一个 token（自回归）
  • 反复读取 KV Cache + 模型权重
  • 计算量极小但内存访问量大
  • 瓶颈：GPU 内存带宽（Memory-bound）
  • 决定指标：ITL/TPOT（Inter-Token Latency）
  • 典型 MFU：<10%（大量时间等内存）

1.1 Roofline 模型分析

以 A100 80GB GPU 为例（算力 312 TFLOPS FP16，内存带宽 2 TB/s），计算算术强度阈值（Ridge Point）：

$$I_{ridge} = \frac{\text{Peak FLOPS}}{\text{Bandwidth}} = \frac{312 \times 10^{12}}{2 \times 10^{12}} = 156 \; \text{FLOP/byte}$$

Prefill 阶段算术强度约为 $I_{prefill} \approx \frac{2 \cdot B \cdot d^2}{2 \cdot d \cdot B} = d$（$d$ 为隐层维度）， 对于 LLaMA-2-13B（$d = 5120$）远超 Ridge Point → 计算密集。
Decode 阶段（batch=1）算术强度约为 $I_{decode} \approx \frac{2 \cdot d^2}{2 \cdot d} = d$ 理论上相同， 但实际上 batch size 小，矩阵退化为矩阵-向量乘，硬件利用率极低（<5%）。

1.2 KV Cache 的核心地位

KV Cache 是连接两阶段的核心数据结构。Prefill 阶段产生 KV Cache 并存储于 GPU HBM，Decode 阶段每步都需读取完整 KV Cache。其大小公式：

$$S_{KV} = 2 \times L \times H \times d_h \times s \times \text{dtype\_bytes}$$

其中 $L$ 为层数，$H$ 为注意力头数，$d_h$ 为头维度，$s$ 为序列长度。 以 OPT-66B、512 tokens 为例：$S_{KV} \approx 1.13 \text{ GB}$，是跨节点传输的主要开销来源。

2. 混跑（Colocation）的干扰问题

传统推理系统（如 Orca、早期 vLLM）将 Prefill 和 Decode 混跑在同一 GPU 上， 通过连续批处理（Continuous Batching）提升吞吐。这在低负载下工作良好，但在高并发时产生严重干扰。

    Colocation --> Effect
  • Prefill 打断 Decode（Stall）：当有新请求到达需要 Prefill 时，正在进行的 Decode 批次必须等待或被中断， 导致 ITL（Token 间延迟）出现"毛刺"（spike），P99 延迟极高。
  • Decode 拖累 Prefill（Bubble）：为了避免 Decode 饥饿，调度器限制 Prefill batch size， 导致 Prefill 阶段 GPU 算力大量浪费，TTFT 无谓延长。

2.2 SARATHI-Serve 的局部解：Chunked Prefill

SARATHI-Serve（2023） 提出将长 Prefill 切成小块（Chunks）插入 Decode 批次， 减少干扰但未根本解决资源配置不匹配问题：

$$\text{Chunked Prefill:} \quad P_{long} \rightarrow \{P_{chunk_1}, P_{chunk_2}, \ldots\} \quad \text{interleaved with Decode}$$

优点：大幅降低 ITL spike，P95 TTFT 改善 40%–60%（32K token 长输入）。 缺点：两阶段仍共享 GPU，无法独立扩缩容，资源利用率仍受限。

3. PD 分离：核心架构与原理

3.1 核心思想

将 Prefill 和 Decode 部署在物理隔离的 GPU 实例上，消除两阶段间的干扰， 允许各自独立扩缩容和调优，从而同时满足 TTFT 和 TPOT 的 SLO 约束。

4.1 DistServe（OSDI 2024）

DistServe: Disaggregating Prefill and Decoding for Goodput-optimized LLM Serving

OSDI 2024 UC San Diego / Hao Zhang Goodput 优化

核心贡献：DistServe 首次从 Goodput（有效吞吐）视角系统性地定义和解决 PD 分离问题。

Goodput 的定义：在满足 TTFT 和 TPOT SLO 约束下，单位时间单 GPU 处理的请求数：

$$\text{Goodput} = \frac{\text{请求数（满足SLO）}}{\text{时间} \times \text{GPU 数量}}$$

关键设计：

  • 独立并行策略搜索：对 Prefill 实例使用 Tensor Parallelism（TP）处理大矩阵乘； 对 Decode 实例使用 Pipeline Parallelism（PP）+ 更多副本，提升内存带宽利用率
  • 节点亲和性放置：同节点内 Prefill→Decode KV Cache 传输走 NVLINK（600 GB/s 峰值）， 跨节点走 InfiniBand（800 Gbps），保证传输开销可忽略
  • Pull-based 调度：Decode worker 主动从 Prefill worker 拉取 KV Cache， 防止 spiky Prefill 工作负载淹没 Decode 队列
实验结果（4节点 32× A100 80GB）：相比 Orca（混跑基线）， DistServe 在相同 SLO 约束下实现 7.4× 更多请求处理量（goodput），SLO 达标率提升 12.6×。

KV Cache 传输开销分析：

OPT-66B + 512 tokens 请求，KV Cache 约 1.13 GB。若平均到达率 10 req/s，需要 90 Gbps 带宽。 现代 GPU 集群的 InfiniBand（800 Gbps）和 NVLINK（600 GB/s）均远超此需求，传输开销可忽略不计。

4.2 Splitwise（ISCA 2024）

Splitwise: Efficient Generative LLM Inference Using Phase Splitting

ISCA 2024 Microsoft Research 成本/功耗优化

与 DistServe 的差异：Splitwise 从成本和功耗视角出发，发现 Prefill 和 Decode 对硬件规格的需求截然不同：

维度Prefill 偏好Decode 偏好
GPU 算力越高越好（H100 > A100）中等算力即可
内存带宽中等即可越高越好（HBM3 优先）
GPU 内存容量较少（短暂存 KV Cache）较多（需存储全部 KV Cache）
最优 GPU 类型H100 SXM（高算力）A100/H800 或 Groq LPU
实验结果：Splitwise 在相同硬件下实现 2.35× 吞吐提升， 或以 20% 更低成本达到相同吞吐，同时降低了数据中心能耗。

FAST 2025 Best Paper Moonshot AI / Tsinghua KVCache 中心化

Mooncake 是 Kimi（月之暗面）生产推理系统的技术支撑，提出了超越简单 PD 分离的KVCache-centric（以 KV Cache 为中心）架构：

Mooncake 三大核心创新：

  1. 分层 KVCache 存储（Mooncake Store）： 将 GPU HBM、CPU DRAM、NVMe SSD 整合为统一的分布式 KV Cache 池， 充分利用 GPU 集群中闲置的 CPU 内存和 SSD 资源， 大幅扩展有效 KV Cache 容量（"用存储换计算"）
  2. Transfer Engine： 高效 KV Cache 传输引擎，支持 RDMA、NVLink、PCIe 等多种传输通道， 支持分层传输（layer-wise）和异步流水线，已被 vLLM、SGLang 官方集成
  3. 预测性早拒策略（Prediction-based Early Rejection）： 在高负载场景下，基于历史 trace 预测请求完成可能性，主动拒绝无法在 SLO 内完成的请求， 避免资源浪费在注定违反 SLO 的请求上
生产实验结果：
  • 在 NVIDIA A800 集群：Kimi 请求处理量提升 115%
  • 在 NVIDIA H800 集群：Kimi 请求处理量提升 107%
  • 模拟场景（长文本场景）：有效请求容量提升 59%–525%（含 SLO 约束）
  • 日处理 token 量：生产环境 千亿 tokens/天，横跨数千节点
  • Kimi K2（2025 年7月）：128 H200 GPU，Prefill 224k tokens/s，Decode 288k tokens/s

缓存命中率优化：Mooncake 通过 Prefix Caching + 全局 KVCache 调度， 生产 trace 显示系统可实现约 50% 的 KV Cache 命中率，大量减少重复 Prefill 计算。

5. KV Cache 传输：PD 分离的核心挑战

KV Cache 传输是 PD 分离的核心工程挑战。Prefill 完成后，必须将 KV Cache 从 Prefill GPU 高效传输到 Decode GPU。

5.1 传输通道与带宽

传输通道带宽适用场景延迟
NVLink（节点内） 600 GB/s 峰值（A100），900 GB/s（H100） 同节点 GPU 间传输（最优） 微秒级
InfiniBand（跨节点） 800 Gbps（HDR/NDR IB） 跨节点 GPU 间，RDMA 直传 1–10 μs
PCIe + 以太网 64–128 Gbps 低成本集群 10–100 μs
RDMA (GPUDirect) 取决于网络 GPU 直接读写远端内存，绕过 CPU 最低
跨数据中心 100 Gbps 级 WAN "Prefill-as-a-Service"（2025 新研究方向） 毫秒级

5.2 传输带宽需求计算

对于规模为 $N_P$ GPU 的 Prefill 集群，对外 KV Cache 传输带宽需求：

$$B_{out} = N_P \cdot \Phi_{kv}(L_{avg}) = N_P \cdot \frac{\mathbb{E}[S_{kv}]}{\mathbb{E}[T_{prefill}]}$$

其中 $\Phi_{kv}(L_{avg})$ 为单 Prefill GPU 的 KV Cache 吞吐率（GB/s）， 以 OPT-66B 为例，10 req/s 场景需要 90 Gbps 带宽，远小于现代集群 IB 带宽。

5.3 Layer-wise 流水线传输

Mooncake Transfer Engine 和 NVIDIA NIXL 均支持逐层（Layer-wise）流水线传输： Prefill 在计算第 $l$ 层时，同时将第 $l-1$ 层的 KV Cache 传输给 Decode GPU， 实现计算与传输的重叠（overlap），进一步降低 Prefill→Decode 的切换延迟。 

sequenceDiagram
    participant P as Prefill GPU
    participant Net as 传输通道
    participant D as Decode GPU

    P->>P: 计算 Layer 1 KV Cache
    P->>Net: 传输 Layer 1 KV Cache
    P->>P: 计算 Layer 2 KV Cache（并行）
    Net->>D: Layer 1 KV Cache 到达
    P->>Net: 传输 Layer 2 KV Cache
    P->>P: 计算 Layer 3 KV Cache（并行）
    Net->>D: Layer 2 KV Cache 到达
    Note over P,D: 计算 & 传输完全流水，延迟隐藏
    D->>D: 开始 Decode（无需等待所有层传输完毕）

  • 兼容性：支持 vLLM、SGLang、TensorRT-LLM 三大主流推理引擎
性能数据（NVIDIA 官方）： 在 NVIDIA Blackwell 上运行 DeepSeek-R1，Dynamo PD 分离模式 vs 传统混跑， requests served 提升最高 30×；Baseten 生产实测 KV-aware 路由带来 34%–62% 吞吐增益。

DeepSeek 的关键技术决策：

设计维度Prefill 节点Decode 节点
并行策略 小 EP + 小 DP（高效处理大 Prompt） 超大 EP（≈256）+ 高 DP（8-16）
为什么 EP256？ - 最大化 MoE 模型的 GroupGEMM 利用率，摊薄 Expert 路由开销
P:D 比例 3 节点 9 节点（约 1:3，根据负载动态调整）
KV 传输 3FS 库（聚合数千块 SSD + RDMA），提供极高传输带宽

值得注意的是，Decode 阶段使用超大 Expert Parallelism（EP≈256）是 MoE 模型特有的优化： 更多 GPU 分担 Expert 权重，使每个 Token 的路由延迟降低，但需要高速 All-to-All 通信。 DeepSeek 专门开发了 DeepEP 库来高效实现 MoE 的 EP 通信。

8.1 什么时候不适合 PD 分离？

  • 短 Prompt 场景：若大多数请求 Prompt 较短（<512 tokens），Prefill 耗时极短，PD 分离的 KV 传输开销占比上升，收益下降
  • 高缓存命中场景：若系统缓存命中率极高（>80%），Prefill 计算量减少，混跑即可高效运行
  • 小模型/单节点：7B 以下模型在单节点内 NVLink 速度极快，PD 分离的工程复杂度可能不值得
  • 资源受限：PD 分离至少需要两套 GPU 池，成本门槛较高

10. 前沿趋势与开放问题

10.1 Prefill-as-a-Service（跨数据中心 PD 分离）

2025 年末出现了"Prefill-as-a-Service"的研究方向： 将 Prefill 计算独立为可跨数据中心调用的服务，KV Cache 通过广域网传输给位于不同地理位置的 Decode 集群。 主要挑战是广域网带宽有限（100 Gbps 级别），需要高效的 KV Cache 压缩和增量传输技术。

10.2 异构硬件的深度利用

  • NVIDIA Rubin CPX：专为 Prefill 计算优化（超高算力密度）
  • Groq LPU：专为 Decode 设计（极高内存带宽，低延迟自回归生成）
  • 多厂商异构：Gimlet Labs 测试 NVIDIA（Prefill）+ Intel Gaudi 3（Decode）组合，实现 1.7× TCO 改善

10.3 推理模型（Reasoning Model）的新挑战

DeepSeek-R1、Claude Opus 4 等推理模型的输出长度极长（数千 token CoT）， 使得 Decode 计算量大幅增加，P:D 比例需要相应调整（更多 Decode GPU）， 同时 Decode 阶段的 KV Cache 也会随输出长度增长而膨胀，对内存管理提出更高要求。

10.4 PD 聚合 vs 分离的辩论

学界和工业界对"PD 聚合还是分离更优"仍有争论：

  • 支持聚合（Sarathi-Serve、Agrawal 等）：Chunked Prefill 可以大幅缓解干扰，无需引入 KV 传输的额外复杂度；在中等负载下资源利用率更高
  • 支持分离（DistServe、Splitwise、Mooncake）：在严格 SLO约束和高负载下，分离是唯一能同时优化 TTFT 和 TPOT 的方法；2025 年已成为大规模生产的事实标准
  • 新方向：统一框架（如 arxiv:2508.01989）尝试自适应决定 per-request 的聚合/分离策略，根据请求 SLO 紧急程度动态选择

11. 核心洞见与工程启示

11.1 为什么 PD 分离在 2025 年突然成为主流？

DistServe 在 2024 年初发表时受到了开源社区的大量质疑，认为引入架构复杂性得不偿失。 但到 2025 年，局势骤然反转——几乎所有主流推理框架都将 PD 分离作为首选架构。 转折点有三个：① DeepSeek-V3/R1 超长输出序列使 Decode 成为明显瓶颈； ② NVIDIA Dynamo 提供了成熟的开源 PD 分离基础设施，工程复杂度大幅降低； ③ Mooncake/LMCache 提供了生产验证的 KV Cache 传输层。 （来源：DistServe Retro，Hao AI Lab）

11.2 P:D 资源比例的工程决策

PD 分离的核心工程问题之一是 Prefill 和 Decode 的资源比例（P:D 比）。 以 DeepSeek-V3 为例采用 3:9（1:3）。一般经验公式：

$$\frac{N_P}{N_D} \approx \frac{T_{prefill} \times r_{in}}{T_{decode} \times r_{out}}$$

其中 $r_{in}$、$r_{out}$ 为输入/输出 token 速率，$T_{prefill}$、$T_{decode}$ 为单 token 处理时间。 对于长输出（推理模型），需要更多 Decode GPU；对于长输入（RAG 场景），需要更多 Prefill GPU。

11.3 KV Cache 传输优先级

  • 优先同节点内传输（NVLink）：速度最快，延迟最低，首选方案
  • 次选跨节点 IB：800 Gbps IB 足以覆盖大多数场景
  • Layer-wise 流水传输：可将 KV 传输与 Prefill 计算重叠，几乎消除传输延迟
  • KV Cache 量化：FP8/INT8 量化 KV Cache 可将传输量减半，是降低带宽需求的重要手段

11.4 PD 分离的本质：资源专用化

PD 分离的本质不仅是"把两个阶段分开"，更是把计算机体系结构设计原则应用于 LLM 推理： 不同的计算特征应该匹配不同的硬件。正如 CPU 和 GPU 的分工， LLM 推理中的"计算密集型"和"内存带宽密集型"工作负载也应该由专用硬件承担。 这一思想将在未来的 AI 芯片设计（NVIDIA Rubin、Groq 等）中进一步深化。
