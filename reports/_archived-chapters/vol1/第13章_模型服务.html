一、开篇：Serving 反转训练优先级

训练最大化吞吐（samples/s），大 batch、长 epoch，延迟尖峰被 invisible 吸收。Serving 最小化每请求延迟（ms）——单次慢响应即 broken product。铁律中 $L_{\text{lat}}$（调度、网络、编排开销）从 rounding error 变为主导约束。

定义：模型服务（Model Serving）

在严格延迟约束下向用户或下游系统提供模型预测的操作阶段——将训练时的 $\eta_{\text{hw}}$ 优先级反转为 p99 尾延迟约束。

  • 常见陷阱：Serving ≠ forward pass；路由、预处理、队列、后处理占同等重要地位
  • D·A·M 反转：Data→实时新鲜度；Algorithm→冻结权重；Machine→headroom 而非饱和

2.1 静态 vs 动态推理

  • 静态（Offline/Batch）：预计算预测、查表返回——移出请求路径，适合可预测输入（相册 overnight 分类）
  • 动态（Online/Real-time）：请求到达时计算——处理任意输入，受 SLO 约束（内容审核 API）

延迟成本（$4/h GPU）

Batch=1：5 ms 延迟，200 req/s → 每百万 query $5.56
Batch=8：10 ms 延迟，800 req/s → 每百万 query $1.39
延迟减半 → 硬件账单增 300%——须量化业务价值是否 justify 4× 成本。

Black Friday 流量尖峰

推荐系统 50 ms @ 1K QPS 舒适运行；10× 至 10K QPS 时非线性崩溃——延迟 10 s、超时、有用吞吐趋零。Fix：load shedding、autoscaling、降级（缓存/更 dumb 模型）。

三、请求生命周期与延迟预算

优化系统上，预处理+后处理+网络可主导总延迟——"推理时间" ≠ "服务时间"。REST vs gRPC：JSON 序列化是瓶颈之一；gRPC + protobuf 更高效但生态复杂。

阶段典型占比优化手段
序列化/网络10–30%gRPC、压缩、colocation
预处理20–60%GPU 预处理、分辨率路由
模型推理10–40%TensorRT、量化、batching
后处理5–20%融合 softmax+topk
队列等待0–50%+headroom、admission control

Hardware duty cycle：重叠 I/O 与计算（pipeline）提升 accelerator 有效利用率——空闲等待数据即浪费 SLO 预算。

四、排队论

4.1 Little 定律

$$Q_{\text{req}} = \lambda_{\text{arr}} \cdot T_{\text{lat}}$$

1,000 QPS × 50 ms SLO → 需容纳 50 并发请求 的内存/队列状态。GPU batch 32 内存不足则物理上无法达标——须降 $T_{\text{lat}}$ 或加内存/副本。

Little 定律等价形式：$W = L/\lambda$，其中 $W$ 为平均等待+服务时间，$L$ 为系统中平均请求数。DR 边缘相机无排队（单线程 embedded），但云端 DR 批量审核 100 QPS × 1.8 s p99 → 需 $L = 100 \times 1.8 = 180$ 并发槽位。

4.2 M/M/1 利用率–延迟

$$T_{\text{lat}} = \frac{1}{\mu - \lambda_{\text{arr}}} = \frac{\text{service time}}{1 - \rho_{\text{serv}}}$$

$\rho_{\text{serv}} = \lambda_{\text{arr}}/\mu$。利用率接近 100% 时延迟超线性爆炸——生产目标 40–60% 平均利用率保留 headroom。

4.3 Batching Tax

$$L_{\text{lat,total}} \approx \underbrace{\frac{B-1}{2\lambda_{\text{arr}}}}_{\text{Formation delay}} + \underbrace{T_{\text{inf}}(B)}_{\text{Inference time}}$$

500 QPS 下 batch 1→32：formation delay 0→31 ms，总延迟 2 ms→46 ms（23×）。Batch 是吞吐–延迟 Pareto 前沿上的显式税。

4.4 Tail Latency 与容错

$$T_{\text{lat,p99}} \approx \frac{4.6 \cdot \text{service time}}{1 - \rho_{\text{serv}}}$$

Tail at Scale：fan-out 到 N 个后端，至少一个慢响应概率随 N 快速增长。技术：hedging（冗余请求赛跑）、canary requests、admission control（503 拒载保护已接纳请求）、graceful degradation（缓存/短输出/子 ensemble）。

ResNet-50 容量规划示例

目标 p99 50 ms，峰值 5K QPS，service 5 ms → 安全 $\rho \leq 54\%$ → 需 ~9 V100 + 30% headroom → 12 GPU N+1。

五、模型生命周期管理

  • Training-serving skew：预处理/特征/模型版本不一致 → 静默精度下降
  • Cold start：容器启动+模型加载+预热，秒–分钟级——Serverless 尤其 painful
  • Model caching：内存/SSD 分层缓存多模型；multi-model serving 需 swap 策略

Cold start 分解

TensorRT ResNet-50 on V100：容器 pull 5 s + 引擎加载 12 s + 预热 50×batch 13 s ≈ 30 s 首可用。Serverless 按请求计费时，冷启动占用户感知延迟主体——须 keep-warm 或 provisioned concurrency。

七、LLM Serving

LLM 三特性：自回归（每 token 依赖历史）、变长输出、KV cache 动态增长——分类 serving 指标不足以描述。

7.1 TTFT 与 TPOT

指标含义瓶颈 regime典型 SLO
TTFT首 token 时间Compute-bound Prefill$\lt 500$ ms（1K prompt）
TPOT每输出 token 时间Memory-bound Decode$\lt 50$ ms (~20 tok/s)

Decode 内存墙

每新 token 须重读全部权重 + 增长 KV state，算术强度极低——加算力核心对 TPOT 零帮助，须更快 HBM 或更小模型/量化。70B GQA：FP16 KV ~0.31 MB/token；32 序列 × 8K context ≈ 80 GB 仅 KV cache。

7.2 解码策略与优化

  • Greedy/Sampling：低延迟；beam width 5 ≈ 5× 每 token 算力
  • Prefix caching：共享 system prompt/RAG 上下文 KV，省 $(N-1)S_{\text{prefix}}$ prefill
  • KV offloading：溢出到 CPU/NVMe，受 PCIe 带宽下限
  • Speculative decoding：小 draft 模型提议 + 大模型并行验证，打破串行瓶颈

7.3 B Speculative Decoding 速算

Draft 模型（1B）提议 $k=4$ token，Target（8B）一次 forward 验证：

  • 无投机：4 × 1.53 ms = 6.12 ms（串行 decode）
  • 有投机（接受率 75%）：1 × 1.53 + 1 × 0.4（draft）≈ 1.93 ms → 3.2× 加速

接受率取决于 draft/target 分布对齐；代码生成等高确定性任务受益更大。

7.4 案例研究：Llama 3 8B Serving

教材端到端算例：将 Prefill/Decode 分解、Roofline、KV 容量与单位成本连成可验证框架。

部署假设

  • 模型：Llama 3 8B，AWQ 4-bit → 权重 4.1 GB
  • 硬件：H100 80 GB SXM（3.35 TB/s HBM，$3/hr 云租）
  • 请求：1000 token prompt（Prefill）+ 256 token 输出（Decode）
  • SLO：TTFT < 200 ms，TPOT < 20 ms

Prefill → TTFT

H100 prefill 吞吐 ~10,000 tok/s（并行处理 prompt）：

$$T_{\text{prefill}} = \frac{1000}{10000} = 100\ \text{ms}$$

+ 20 ms 系统开销（网络、分词）→ TTFT = 120 ms（< 200 ms SLO ✓）。Prefill 为 compute-bound，受益于 Tensor Core。

Decode → TPOT

每 token 须重读 4.1 GB 权重 + 更新 KV cache。Roofline 分析：decode 算术强度极低，memory-bound。

$$T_{\text{token,floor}} = \frac{4.1\ \text{GB}}{3350\ \text{GB/s}} \approx 1.2\ \text{ms}$$

+ kernel launch、attention、生产安全裕度 → TPOT ≈ 1.53 ms（< 20 ms SLO ✓）。A100（2.04 TB/s）同模型 ≈ 2.0 ms/token——带宽差 1.64× 直接映射 TPOT。

256 token 总 decode：$256 \times 1.53 = 391$ ms。端到端 ~511 ms，用户感知由 streaming 分解为「120 ms 出字 + 流畅续写」。

KV Cache 与并发

权重占 4.1 GB，剩余 ~75 GB 给 KV。Llama3 GQA：每 token KV ≈ 0.033 MB（INT4）。

$$\text{Capacity} \approx \frac{72\ \text{GB}}{0.033\ \text{MB/token}} \approx 2.2\ \text{M tokens}$$

单请求 1256 token → 理论并发 ~1749 请求。PagedAttention 将碎片利用率从 40–50% 提至 90%+，使上述数字可达。

吞吐与单位经济学

Prefill 限制：$10000/1000 = 10$ req/s。KV 限制：$1749/0.44 \approx 3931$ req/s。瓶颈在 Prefill → 有效吞吐 10 req/s。

$$\text{Tokens/hr} = 10 \times 3600 \times 1256 \approx 45.2\ \text{M}$$
$$\text{Cost} = \frac{\$3/\text{hr}}{45.2\ \text{M tokens/hr}} \approx \$0.066/\text{M tokens}$$

升级决策框架

  • Upgrade P（加算力）：decode-bound 时 TPOT 几乎不变——Roofline 脊点以下加 FLOP 无效
  • Upgrade Q（加带宽/VRAM）：降 TPOT 或提 KV 并发 → 降 $/token
  • 本案例 traffic mix 下，Prefill 算力决定吞吐上限；长输出 chat 场景 decode 占比升，Upgrade Q 更优

八、章节总结

核心要点

  1. Serving 反转训练 physics：延迟 SLO、headroom、tail 优先于平均吞吐
  2. 完整 pipeline（非仅模型）竞争同一延迟预算；端到端 profiling 必需
  3. Little 定律 + M/M/1 是容量规划基础；~70% 利用率是 queueing knee
  4. Batching 是显式 latency tax；dynamic/continuous batching 按流量模式选择
  5. Training-serving skew 与 cold start 是静默失败源
  6. LLM：TTFT/TPOT 分解 prefill/decode；PagedAttention + prefix cache 攻击 KV 瓶颈
  7. Facebook 教训：训练造模型，serving 付 recurring bill——fleet-scale 一阶问题
Facebook 2018：推理每日数十万亿次运算，尾延迟 SLO 下 batch 受限——ML 的昂贵部分已移至 serving。模型架构训练便宜，服务可能太贵、太 memory-bound 或 tail 太 variable。
