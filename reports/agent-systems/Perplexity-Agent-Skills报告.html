Perplexity Agent Skills 工程实践深度解析

Designing, Refining, and Maintaining Agent Skills · Perplexity Agents Team · 生成日期：2026-05-13

核心命题：写 Skill 不是写代码，而是为模型构建上下文。这两件事有本质不同的设计原则，传统软件工程的直觉往往在 Skill 开发中变成反模式。
来源Perplexity Research Blog — Designing, Refining, and Maintaining Agent Skills at Perplexity
核心洞察Skill = 上下文构建；每 token 都有成本；描述是路由触发器；Gotchas 是最高价值内容

一、系统架构与三层上下文成本模型

1.1 三层上下文成本

Skill 系统的核心设计约束是上下文窗口是有限且昂贵的。Perplexity 将 Skill 内容按使用频率和成本分为三层：

层级内容Token 成本触发时机成本标签
索引层（Index）每个 Skill 的 name + description~100 tokens/Skill每次会话，每个用户都付始终付
加载层（Load）SKILL.md 完整正文~5,000 tokens路由命中时加载按需付
运行时层（Runtime）scripts/ references/ assets/ config.json0 → 无上限按条件按需读取条件付

设计含义：索引层的每一个词都在每次会话中向每个用户收费。一个 100 Skill 的系统中，光是所有 Skill 的 description 就要消耗约 10,000 tokens——这是注意力资源的持续税，必须精心设计。

1.2 目录结构

my-skill/
├── SKILL.md          # frontmatter + 核心指令（hub）— 加载层
├── scripts/          # 确定性逻辑代码 — 运行时层
├── references/       # 重型参考文档，按条件加载 — 运行时层
├── assets/           # 输出模板、Schema、数据 — 运行时层
└── config.json       # 首次运行用户配置 — 运行时层

1.3 路由机制

flowchart TD
  Q["用户输入"] --> IDX["扫描 Skills 索引
name + description
（每次会话都执行）"]
  IDX --> MATCH{"隐式模式匹配
是否命中？"}
  MATCH -->|"是"| LOAD["加载 SKILL.md 正文
~5000 tokens 进入上下文"]
  MATCH -->|"否"| SKIP["跳过，不增加成本"]
  LOAD --> EXEC["执行 Skill 指令"]
  EXEC --> NEED{"需要附属文件？"}
  NEED -->|"是"| READ["按需读取
scripts/ references/ assets/"]
  NEED -->|"否"| RESP["生成响应"]
  READ --> RESP

激活是隐式模式匹配，而非显式调用 load_skill("name")。模型根据 description 与用户意图的语义匹配程度自动决策——这意味着 description 的措辞直接决定 Skill 的激活精准率。

二、Skill 四维定义

2.1 目录（A Directory）

为什么是目录而非单一文件？单一文件无法支持渐进式信息加载——"始终要加载的核心指令"和"只在特定条件下需要的重型内容"必须物理分离，才能实现按需付出成本。

税法三级嵌套案例

Perplexity Computer 的所得税能力中，将美国国税局（IRS）全部 1,945 个章节组织成三级嵌套：

  • 一级：20 个主题领域（个人所得税/企业税/遗产税…）
  • 二级：每个领域下的 15 个具体主题
  • 三级：具体条款

将 1,945 个章节放进单一文件夹时，模型性能不如不加载 Skill（上下文过载导致注意力稀释）。层级化后，模型先在 20 个主题域中选择，再在 15 个具体主题中定位，精准度大幅提升。

当领域知识规模超过模型一次性选择能力（>20 个选项），人工设计的信息架构是不可替代的工程工作。

2.2 格式（A Format）

frontmatter 必填字段

---
name: my-skill-name        # 全小写、无空格、可用连字符，必须与目录名一致
description: Load when...  # 路由触发器，而非内部文档
depends: other-skill       # 层级依赖（可选）
metadata:
  version: 1.0             # 评测和 review 用（可选）
---

[Skill 正文内容...]

Computer 的 frontmatter 处理：Computer 加载 Skill 时会剥离 frontmatter，模型只看到正文。这允许配置信息保留在 SKILL.md 中，同时不污染模型上下文。

name 的唯一性约束：name 是路由键，必须全局唯一。两个 name 相似的 Skill 会在路由层产生干扰（action at a distance）。

2.3 可调用（Invocable）与渐进式（Progressive）

传统工具调用（显式）
load_skill("my-skill")
run_task(...)

用户必须知道 Skill 名称才能调用，限制了自动化能力

Skill 路由（隐式模式匹配）

用户说："帮我监控这个 PR 直到合并"

→ 模型自动匹配 description "Load when: user says babysit, watch CI..."

→ Skill 被激活，无需用户知道 Skill 名

渐进式加载的经济学：一次会话可能同时加载 3-5 个 Skill，每个 Skill 的 token 成本在整个对话中持续累计直到压缩边界。充斥"废话"的 Skill 几乎必然导致性能变差——因为它们挤占了真正有用内容的注意力空间。

三、何时需要 Skill

3.1 判断标准

唯一可靠的判断方法：先不加 Skill 跑几个关键查询，再评估结果。需要 Skill 当且仅当：

  1. Agent 会出错：没有特殊上下文，模型会做错或做得不一致
  2. 超出一句 Prompt 能解决的范围：太复杂，不是系统 prompt 里一句话能搞定的

核心测试：对 Skill 中每一句话问——"没有这句话，Agent 会出错吗？"如果答案是"不会"，这句话不能留。每次会话、每个用户都在为它付出 token 成本。

3.2 不需要 Skill 的常见误区

误区原因正确做法
写一堆 git 命令顺序模型本身就知道 git 用法，无需教它删除，让模型自己决策
重复系统 Prompt 的内容大多数请求都用到的知识属于全局上下文放系统 Prompt，不建 Skill
描述变化比维护速度快的内容如频繁更新的远程 MCP endpoint不建 Skill，避免 drift
把所有领域知识塞入一个 Skill上下文过载，模型性能反而下降分层嵌套，渐进加载

Step 0：先写评测（最重要）

为什么先写评测？如果不先定义"成功标准"，迭代无从衡量。没有评测就上 PR，是团队最常见的错误之一。

评测用例来源说明重要性
真实用户查询从生产环境采样，或从专家大脑中提取正例基础
已知失败案例正是因为没有这个 Skill 导致的失败验证必要性
邻域混淆案例接近 Skill 边界但不应路由到此 Skill 的查询最关键——负例往往比正例更有力量

两类评测维度

  • Skill 加载评测：精准率（不误触发）、召回率（不漏触发）、forbidden 检查
  • 端到端任务完成评测：全 Agent 循环 + LLM judge 按评分标准打分
"如果你在 Skill 合并后修改 description，你已经偏轨了——任何影响路由的改动都必须有对应的 eval 支撑。"

Step 1：Description 设计（最难的部分）

Description 是 Skill 中最重要、最难写的部分，是路由决策的唯一依据。Description 中的每个词都在：

  • 消耗注意力资源（每次会话都付）
  • 影响该 Skill 的命中率
  • 通过溢出效应影响相邻 Skill 的命中率（action at a distance）
坏的 Description（描述 Skill 做什么）

"A Skill for monitoring pull requests and tracking CI status"

问题：这是 Skill 的功能介绍，不是路由触发器。用户不会用这些词来描述需求。

好的 Description（描述用户意图和语言）

"Load when: user says babysit, watch CI, make sure this lands"

直接用真实查询中出现的词汇，与用户沮丧或需要帮助时说的话完全匹配。

写法原则

  • 用 "Load when..." 格式，而非 "This skill does..."
  • 用真实查询中出现的词汇（包括用户沮丧时说的话）
  • 2-3 个真实查询示例覆盖 80% 场景，不要贪多

Step 2：编写 Skill 正文

Python 之禅 vs Skill 开发原则（完整反转表）

Python 之禅（传统代码）Skill 开发原则（反转）
简单优于复杂复杂是特性（模型无法处理你认为"显而易见"的情况才需要 Skill）
如果实现容易解释，可能是好想法如果容易解释，模型已经知道了，删掉
特殊情况没有特殊到要打破规则Gotchas 就是那些特殊情况，是最高价值内容
显式优于隐式激活是隐式模式匹配（Description 路由，非显式调用）
稀疏优于密集每 token 最大化信息量（稀疏 = 废话 = 性能损失）
错误不应该被悄悄忽略Gotchas 记录的就是悄悄发生的错误模式

好坏写法对比

坏的写法（像写 README，列步骤）
1. git checkout main
2. git pull origin main
3. git checkout -b feature/my-fix
4. git cherry-pick <commit-hash>
5. git push origin feature/my-fix

过度规定步骤序列：出现异常情况时模型会僵化失败（步骤 3 失败怎么办？有冲突怎么办？）

好的写法（意图导向，给有经验的同事的备忘）
Cherry-pick the commit onto a clean branch.
Resolve conflicts preserving intent.
If it can't land cleanly, explain why.

描述意图和原则，而非步骤。模型可以在异常情况下灵活应对，而不是僵化失败。

Gotchas（陷阱条目）——最高价值内容

Gotchas 是"模型在这个 Skill 上会犯的特定错误"的负例描述，是 Skill 中信息密度最高的部分：

  • 每当 Agent 犯一个新错误，就在 Skill 末尾追加一条 Gotcha
  • 随时间有机增长，无需一次性写完
  • 格式：描述错误模式 + 正确行为

LLM 自动生成 Skill 无效的研究结论

"Self-generated Skills provide no benefit on average, showing that models cannot reliably author the procedural knowledge they benefit from consuming."
——Perplexity 早期内部研究

含义：人类的领域专业知识和意见（opinion）不可替代。Skill 的价值在于注入人类的观点和经验，这无法被 LLM 自动化取代。

Step 3：Hub-and-Spoke 层级结构

内容类型放在哪里原因
核心流程指令SKILL.md（hub）每次加载都需要，值得付成本
确定性逻辑代码scripts/（spoke）代理执行而非重新发明，按需加载
重型参考文档references/（spoke）只在特定分支条件下需要，避免总是付出成本
输出格式模板assets/（spoke）代理直接复制填写，减少幻觉
用户配置config.json询问一次，保存复用，避免重复打扰用户

hub 保持精简的原则：SKILL.md 正文应只包含"每次执行都会用到的内容"。条件分支逻辑（"如果是 Python 项目，加载 Python 规范；如果是 Go 项目，加载 Go 规范"）应推迟到运行时按需加载。

Step 4/5：迭代与发布

  • 在独立分支上完成所有迭代，提交时包含完整变更集（评测用例 + Skill 内容）
  • 不提交小增量 PR（除新 Gotcha 外），因为 Description 改动的溢出效应让逐步审查极难
  • Description 字段的所有微调必须在发布前完成，之后修改需重新运行整体评测套件

五、维护：陷阱飞轮（Gotchas Flywheel）

flowchart LR
  A["Agent 在特定场景出错"] --> B["分析根本原因"]
  B --> C["在 Gotchas 追加一条负例
（唯一允许不附带 eval 的 PR）"]
  C --> D["Skill 质量提升"]
  D --> E["Agent 在该场景不再出错"]
  E --> F["新的边缘场景出现"] --> A

维护规则

场景操作注意
路由误触发（精准率低）收紧 description + 增加负例 eval必须同时更新 eval，不能只改 description
路由漏触发（召回率低）添加关键词 + 增加正例 eval同上
系统 Prompt 变更检查 Skill 是否与新 Prompt 冲突或重复全局变更会影响所有 Skill 的路由行为
Agent 出现新错误在 Gotchas 追加负例唯一允许不附带 eval 的 PR

多模型兼容性测试

Perplexity Computer 支持至少三种编排模型家族（GPT、Claude Opus、Claude Sonnet），同一 Skill 在不同模型下路由行为差异显著。

测试维度内容必须覆盖的模型
Skill 加载测试精准率、召回率、forbidden 检查GPT、Claude Opus、Claude Sonnet
端到端任务完成测试全 Agent 循环 + LLM judge 评分GPT、Claude Opus、Claude Sonnet
"发布新 Skill 前必须运行整体评测套件，不只是新 Skill 自身的测试。"新增一个 Skill 可能在不触碰旧 Skill 的情况下改变其路由行为（Action at a Distance）。

六、工程启示与价值总结

6.1 核心范式转换

写代码是给运行时系统看的；写 Skill 是给语言模型看的。两者理解和处理信息的方式完全不同：

  • 运行时系统：精确执行，步骤越详细越好，不理解意图
  • 语言模型：理解意图，意图越清晰越好，过度规定的步骤反而限制灵活性

6.2 三条可迁移的通用原则

  1. 三层渐进式上下文成本框架：适用于任何 RAG/Tool 系统的知识组织——始终付/按需付/条件付三层结构，可迁移到任何 Agent 知识系统设计。
  2. Description 即路由器：理解为什么一个词的改变会产生意想不到的全局影响——因为所有 Skill 共享同一个路由空间，改动是非局部的。
  3. 负例大于正例的评测直觉：在 LLM 路由系统中，告诉模型"不要做什么"往往比"要做什么"更有力。同样适用于 prompt engineering、few-shot 示例设计等场景。
