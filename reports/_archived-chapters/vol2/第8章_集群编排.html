一、调度问题：硬件充足仍空转

10,000 GPU × \$2/GPU·h = \$480k/天。利用率 50%→80% 等价于白买 3,000 GPU·当量，年省 \$52M 量级。ML 调度区别于普通云：同步 AllReduce 要求 gang scheduling——1024 GPU 任务拿到 900 块仍 100% 浪费（~\$1,800/h 空烧），因缺 rank 无法迭代。

War Story：OpenAI K8s gang 死锁（2021）

7,500 节点 K8s 上两个实验各要整集群；调度器各放一半 pod → 两个 job 都无法 AllReduce → 集群「很忙」但零 useful step。教训：分布式 ML 必须把 gang 语义编进调度器（PodGroup / Volcano / Kueue），「部分 pod 已调度」≠ 部分进度。

2.1 Slurm ML 扩展

  • --array=0-99：超参 sweep 一次提交，scheduler 可 backfill 小 trial
  • 异构 job：8 GPU 节点训练 + CPU 节点 tokenization（hetjob）
  • PreemptMode + GraceTime：SIGTERM → 60–300 s 写 checkpoint → SIGKILL（依赖第 7 章 checkpoint）
  • TRES 加权：H100 GPU·h 与 V100 不同价，fair-share 按经济成本而非核数

2.2 Kubernetes 与混合架构

K8s 控制环：Deployment 保副本数、node 失效自动换 pod——适合推理。分布式训练需 PyTorchJob/MPIJob + PodGroup 保证 gang。常见混合：K8s 管 CI/CD/RBAC/推理，Slurm partition 跑大 pretrain；或 K8s Operator 把 TrainingJob CRD 翻译成 sbatch。

# TorchElastic：声明弹性范围，供调度器 resize
torchrun --nnodes=4:16 --nproc_per_node=8 \
  --rdzv_backend=c10d --max_restarts=3 train.py

4:16 节点 = 32–128 GPU，调度器可在负载低时扩、高优先级到达时缩，避免「等 8 h 凑齐 gang 再开跑」。

三、拓扑感知放置

64 GPU 随机散列 vs 同 leaf 打包：1 GB AllReduce 延迟 120 ms → 25 ms（4.8×）。端到端训练因 overlap 通常损失 15–30% 吞吐，仍值得优化。

$$\text{Cost}_{\text{locality}} = \sum_{i

$d=0$ 同节点（NVLink，$w=0$）；$d=1$ 同 rack（$w=1$）；$d=2$ 跨 rack（$w=10$）。

3D 并行放置规则（256 GPU：TP=8, PP=4, DP=8）

  1. TP：每组 8 GPU 锁在同一 NVLink 节点（900 GB/s）
  2. PP：相邻 stage 放同 rack leaf（~50 GB/s，1 hop）
  3. DP：副本跨 rack；rail-aligned——各节点 GPU $r$ 连同一 rail，AllReduce 不跨 rail 争用

反例：TP 跨两节点 → 1 GB 激活 2.2 ms（NVLink）变 20 ms（IB），约 9× 慢，80 层 transformer 每层都付税。

静态 topology.conf 不够——「limping switch」CRC 高仍显示 up。需 NCCL 实测带宽 + switch counter；劣化 rack taints/drain，必要时 checkpoint 迁移（10–15 min）若 >20% 降速且 run 还剩数周。

四、Goodput 与 ML 定制调度器

Google ML Productivity Goodput（C³ 生产度量）

$$\text{Goodput} = \eta_{\text{program}} \times \eta_{\text{runtime}} \times \eta_{\text{scheduling}}$$
  • $\eta_{\text{program}}$（Compute）：代码是否喂满硬件（MFU、有效 FLOPs）
  • $\eta_{\text{runtime}}$（Communication）：通信 stall、故障恢复、straggler
  • $\eta_{\text{scheduling}}$（Coordination）：排队、抢占、重配置、fragmentation

三者相乘：92% hardware utilization + 30% MFU 说明 GPU「忙」在 bubble/重算/同步——应看 MFU 与 Goodput，而非 SM 占用 alone。

五、Spot、弹性与成本

$$C_{\text{effective}} = C_{\text{spot}} \times \frac{T_{\text{total}}}{T_{\text{productive}}}$$

512 GPU × 14 天 70B：按需 \$344k；spot 65% 折扣 + checkpoint/重启开销 → ~\$162k（53% 省）但 wall-clock +34%。容错基础设施双回报：抗硬件故障 + 使 spot 经济可行（AWS 2 min / GCP 30 s 抢占通知 + panic checkpoint）。

六、章节总结

决策要点

  1. 同步训练：gang + topology 优先于 bin-packing 利用率
  2. 大 pretrain 选 Slurm/混合；推理与平台统一选 K8s；探索 Ray 但自担可靠性
  3. 用 Goodput 三因子定位损失：代码、通信、调度
  4. 定制调度器从 Tiresias 类低侵入开始，Pollux 级需证明 ROI > checkpoint 税
编排是故意支付的 coordination tax：用一致性、放置约束和公平策略，换 fleet 不因死锁与碎片化把百万美元算力变成队列里的 heat。
