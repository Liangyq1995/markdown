标题Harness Handbook: Making Evolving Agent Harnesses Readable, Navigable, and Editable
核心问题现代 AI agent 的能力高度依赖 harness（构造 prompt、管理状态、调用工具、协调执行）。当模型/API/环境/需求演化时，开发者要先定位实现目标行为的所有代码位置，而“行为→代码”映射难以手工恢复——行为定位（behavior localization）是 harness 演化的核心瓶颈。
核心方法提出 Harness Handbook（行为为中心的表示，静态分析 + LLM 辅助结构化自动生成）与 Behavior-Guided Progressive Disclosure (BGPD) 工作流，并支持非空 diff 后的自动再同步（resynchronization）。
关键结果在 Codex 与 Terminus-2 两个开源 harness 上，Handbook-Assisted 规划的总体胜率分别 +10.0 / +18.9 个百分点，planner token 用量下降 12.7% / 8.6%；弱 planner 在 24 项 Recall/Precision/F1 指标上全部超过无 handbook 的基线，F1 提升 5.0–18.8 个百分点。
作者 / 机构Ruhan Wang, Yucheng Shi, Zongxia Li, Zhongzhi Li, Yue Yu, Junyao Yang, Kishan Panaganti, Haitao Mi, Dongruo Zhou, Leoweiliang。Tencent HY LLM Frontier、Indiana University、University of Maryland、University of Georgia、National University of Singapore。
开源地址项目主页：https://ruhan-wang.github.io/Harness-Handbook/
一句话总结： 不要问“编辑怎么写”，先问“编辑落在哪”。Harness Handbook 把仓库知识围绕运行时行为而非文件/函数重组，把每个行为链接到其分散的源代码实现，让弱 planner 借助 handbook 就能在行为定位上逼近更强模型，且更省 token。

1. 概述

现代 AI agent 的能力并不只取决于 foundation model，还取决于它的 harness——一个负责构造 prompt、管理状态、调用工具、协调跨组件执行的软件层。当模型、API、执行环境与应用需求持续演化时，harness 必须不断被修改以新增能力或适配既有行为。无论是人类开发者还是 coding agent，在做改动之前都面临同一个前置问题：定位实现目标行为的所有代码位置。这在生产级 harness 中非常困难，因为它们往往庞大、紧耦合，且行为分散在文件、函数、执行阶段与状态迁移之中，而修改请求只描述“系统应该做什么”，仓库却是按文件/函数/模块组织的。

已有的代码搜索、仓库索引、长上下文处理方法能让代码更易查看，但仍把“行为↔实现”的映射留给开发者自己恢复。论文将这一前置挑战命名为 behavior localization（行为定位），并提出 Harness Handbook：一种行为为中心的表示，通过静态程序分析与 LLM 辅助行为结构化自动从代码库合成，把实现知识围绕系统行为组织，并把每个行为链接到对应源码。配套的 BGPD（Behavior-Guided Progressive Disclosure） 引导 coding agent 从高层行为描述逐级下钻到相关实现细节，并对照当前源码验证候选位置。每次非空 diff 还会触发 handbook 的自动再同步。

在两个开源 agent harness（Terminus-2，Python 终端 agent，function-as-leaf；Codex，Rust 单体仓库，file-as-leaf）的 60 个行为驱动修改请求上评测，Handbook-Assisted 规划同时提升计划质量、降低 planner token 用量。最大收益出现在涉及分散实现点、稀有执行路径与跨模块交互的改动上。论文由此给出关键论断：演化复杂 agentic 系统，不仅取决于能否生成编辑，更取决于能否确定编辑应落在何处。

2. 研究背景与动机

2.1 Agent Harness 与演化瓶颈

LLM 的进展催生了大量 agentic 系统，这些系统通过与工具、API、复杂执行环境的交互扩展模型能力，而这些交互由 harness 协调。harness 决定了“模型能力如何被翻译为系统行为”。Code as Agent Harness[15] 把 harness 形式化为一个可执行、有状态的软件层，支持 reasoning、acting、feedback 与 coordination；综述与工程实践[21,22]进一步把 harness 刻画为负责 prompt 构造、状态管理、工具调用、控制流与外部交互的运行时基础设施。AutoGen[23]、OpenHands[13] 等框架与 Claude Code、Codex[25] 等工业系统都把 harness 设计视为构建可靠长时 coding agent 的关键因素。但这些工作主要关注 harness 的构造与系统设计，而非理解和演化既有的生产级 harness。

随着 coding agent 能力增强，软件工程正从“手工实现功能”转向“自动演化底层 harness”[7,13]。近期工作开始研究 harness engineering、自适应 harness 优化与自动 harness 修复[8,10,14,26-28]。本文处理的是一个互补的前置问题：在直接修改 harness 实现之前，先解决行为定位。在大型、结构复杂的 harness 仓库中，人类开发者要花大量时间建立系统心智模型、跨文件跨阶段追踪行为；coding agent 还受限于输入上下文，只能迭代探索仓库，仍可能漏掉分散或稀有路径[16,17]。

2.2 与既有仓库表示工作的区别

仓库地图、代码搜索、代码摘要、仓库记忆、长上下文编辑[16-20,29,30] 都让代码库更易探索，但它们仍以实现为中心，按源码、仓库结构或执行基础设施组织信息，而非按行为组织。它们可能定位到个别相关代码片段，却不展示这些片段如何协同产生行为、也不保证所有受影响位置都被找到。下表对比 Harness Handbook 与这些方向的关键区别：

3. 核心方法

Harness Handbook 由三部分组成：（1）围绕运行时行为组织的表示（3.1）；（2）从仓库自动构建该表示的构造流水线（3.2）；（3）用 handbook 引导代码改动并在每次非空 diff 后自动再同步的修改工作流（3.3）。方法总览如下：

3.1 Harness Handbook 表示

源码仓库展示“代码存在哪”，却不直接展示“运行时行为如何展开”。一个行为可能跨越多个文件、执行阶段与共享状态。Handbook 把这些信息围绕行为重组，同时保留到源码的链接。它由一个 L1–L3 文档树 D 与一个互补的状态寄存器视图 Z 组成：

graph TD
  L1["L1 系统概览：架构 / 执行模型 / 主要阶段 / 全局数据流"] --> L2a["L2 组件概览（阶段 2.1 初始化）"]
  L1 --> L2b["L2 组件概览（阶段 2.4 主循环）"]
  L1 --> L2c["L2 组件概览（阶段 4.x 组件）"]
  L2a --> L3a["L3 单元深挖：源码 locator（函数/区域 或 文件）"]
  L2b --> L3b["L3：_run_agent_loop, _step, _should_exit"]
  L2c --> L3c["L3：4.1 Prompting / 4.2 Memory / 4.3 Tools / 4.4 Main Loop"]
  Z["状态寄存器视图 Z：跨阶段状态读写位点"] -.->|"跨阶段耦合"| L2a
  Z -.-> L2b
  Z -.-> L2c

读者通常从 L1（系统概览）开始，了解架构、执行模型、主要阶段与全局数据流；再到 L2（组件概览）查看某个阶段的责任、输入/输出、依赖与局部状态；最后到 L3（单元深挖），把该阶段链接到源码锚定的实现条目。互补视图 Z 记录跨阶段边界的状态关系（如某状态在一个阶段写入、若干阶段后才被消费）。

两条规则保持表示有用：

  • 渐进式披露（Progressive disclosure）：读者仅在任务需要更多细节时才从 L1 下钻到 L3。
  • 行为–实现对齐（Behavior–implementation alignment）：每个 active 的 L3 locator 必须仍能解析到当前仓库。若无法重新校验，该条目被冻结并从定位中排除，直到刷新。仓库始终是实现细节的权威来源。

3.2 Harness Handbook 构造

构造从仓库 R 构建 handbook。叶子模式 g ∈ {function, file} 在 handbook 生命周期内固定不变，决定 L3 条目粒度：function-as-leaf 下每个 L3 条目覆盖一个完整函数或若干连续区域；file-as-leaf 下每个 L3 条目代表一个文件。

两种模式在阶段骨架如何获得上不同：function-as-leaf 从含阶段与状态寄存器定义的 seed skeleton S0 出发（当有可信 seed 且函数级 L3 在预算内时使用）；file-as-leaf 则不依赖 seed，先描述每个文件再推断骨架（当无 seed 或函数级组织会超预算时使用）。选定 g 后，构造分三阶段进行：

Phase I — 静态事实抽取（共享，确定性，无 LLM）

语言特定适配器解析 R，抽取函数、命名外部边界、源码位置、签名与调用边。程序图 G 只保留能解析到内部函数或命名边界的调用；未解析调用写入审计日志而非猜测目标。内部函数节点记录限定名、源文件、签名、行范围、所属类与观测到的状态访问；边界节点代表命名外部目标（如库函数）。这一阶段完全确定性，后续所有组织步骤都建立在这些源码锚定事实上。

Phase II — 行为组织

把 G 中的源单元围绕执行行为组织，产出当前阶段骨架 S 与模式特定组织状态 U_g。

  • Function-as-leaf：用源码与调用图上下文提出函数→阶段分配，通过迭代审阅精炼。一个函数可整体或按连续区域分配到一个或多个阶段。每轮先检查阶段是否应增删/合并/分裂（结构变更仅在层级合法且所有状态寄存器声明仍指向存在阶段时才接受），再对受影响函数重新分类，最后做全局审计与区域边界修复。变更须经模型审阅才能应用；轮次在骨架与分配稳定且无函数待重审时停止，否则停在组织预算处。
  • File-as-leaf（S0 = ∅）：Step 1 为每个扫描文件建一张卡（含目的、仓库角色、执行生命周期位置；deep 模式还含函数清单、签名、源范围、已解析调用——模型可解释但不可改）；Step 2 按目录分组并结合图派生入口点与调用，起草有序阶段骨架，把每个文件分配到一个主阶段（横切文件如日志/协议/类型/配置工具可另命名 1–2 个次阶段）；Step 3 用文件调用图给出 caller-before-callee 序，再用文件卡精炼为主题分组与可读序列。组织变体（oneshot / doctor / agent）决定是否精炼。

Phase III — 层级合成与打包

把 (S, U_g) 转为文档树 D 与状态寄存器视图 Z，可复用生成输出存入缓存 B，并对照仓库校验后打包。两模式合成方向相反：function-as-leaf 自顶向下（已知骨架提供大纲，L1→L2→L3，每个 L1/L2/L3 节点用有界 generate–review–revise 循环）；file-as-leaf 自底向上（已验证文件卡即 L3 内容，逐层 rollup 生成 L2 与 L1）。渲染前对 D 中每个 L3 locator 解析校验，无法校验者标记 frozen 并从定位排除。最终打包视图 V 与 D, Z, g 及机器可读再同步状态 K_g 为 handbook H。

3.3 Handbook 引导的修改与再同步

构造完成后，handbook 作为行为导向的修改向导。给定请求 q，工作流使用 handbook H 与对应仓库 R，叶模式 g 全程不变。工作流分四步（Algorithm 1）：BGPD 定位 → Plan 生成编辑计划 P 与动作声明 Γ → Execute 应用到仓库 → 若 diff Δ 非空则触发 Resync 再同步。完整伪代码如下：

Algorithm 1: Handbook-Guided Modification with Automatic Resynchronization

Require: 请求 q、handbook 包 H、对应仓库快照 R

Ensure: 计划 P 与声明 Γ；更新后仓库 R'、diff Δ、handbook 包 H'

1: g ← LeafMode(H)

2: Eq ← BGPD(q, H, R)

3: (P, Γ) ← Plan(q, Eq)

4: R' ← Execute(R, P)

5: Δ ← Diff(R, R')

6: if Δ ≠ ∅ then

7: H' ← Resyncg(H, R, R', Δ, Γ)

8: else

9: H' ← H

10: end if

11: return (P, Γ, R', Δ, H')

3.3.1 BGPD 行为定位

BGPD 不把所有源位置同等对待，而是用 handbook 从粗到细识别候选位点，再对照当前仓库验证。其流程为：

flowchart TD
  S1["阶段选择：读 L1/L2 选相关执行阶段"] --> S2["沿 Z 加入经共享状态耦合的阶段（结构远但互相依赖）"]
  S2 --> S3["条目选择：在选定阶段内选最相关 L3，取其源码 locator"]
  S3 --> S4["调用关系扩展：沿 G 扩展候选集（function-call 图 或 file-call 图）"]
  S4 --> S5["源码验证：打开 R，解析每个 locator，仅保留与 q 相关的位点"]
  S5 --> S6["产出验证后证据 Eq：文件路径 + 可选函数/区域锚 + 当前源码片段"]
  • 阶段选择：从 D 的 L1/L2 选与 q 匹配的执行阶段，再沿 Z 加入经共享状态耦合的阶段——这恢复了结构上遥远但互相依赖的行为（如某值在一阶段写入、若干阶段后才被消费）。
  • 条目选择：在选定阶段内打开 stage 页面，选最相关 L3 条目；每条目暴露摘要与源码 locator，正文仅在需要时披露以限制不必要上下文。
  • 调用关系扩展：在程序图 G 上沿调用关系扩展候选集（function 模式用函数调用图，file 模式用诱导的文件调用图）。命名外部边界节点提供上下文但绝不作为编辑位点返回。
  • 源码验证：以上步骤都在 handbook 上操作；随后打开当前仓库 R，解析每个候选 locator，仅保留仍与 q 相关的位点，得到验证后证据 Eq。每条记录含文件路径、可选函数/区域锚与当前源码片段。handbook 引导搜索，仓库仍是编辑计划的权威。

3.3.2 编辑计划与执行

planner 把 Eq 转为编辑计划 P，每个 edit block 指定改动位置、支撑源码证据与意图变更，记录目标文件、可选函数/区域锚、当前源码片段与意图改动（实现中以 verbatim old/new 对表达）。每个 edit 还产出动作声明，含目标文件、可选锚与三种动作类型之一：modify / add / remove，收集为 Γ = (Γmodify, Γadd, Γremove)；重命名表示为一次 removal + 一次 addition。executor 应用 P 到 R 产出 R'，diff Δ = Diff(R, R') 驱动 handbook 失效；Γ 仅用于检查执行是否遵循计划。

3.3.3 自动再同步

每个非空 Δ 触发 Resyncg，只更新受影响部分而非重建整个 handbook：

  1. 版本对齐：重新解析 R'、刷新程序图为 G'，对照 Δ 识别增/删/改单元。function 模式用不依赖行号的 body fingerprint 匹配函数（仅移动的函数视为未变，locator 按行偏移 roll-forward；重命名按签名行以下的 body 匹配）；file 模式用文件集差异与内容哈希（路径重命名表现为一删一增）。
  2. 范围更新：若阶段骨架 S 仍能容纳变更，则 S' = S，仅更新受影响的 Ug 部分（function 模式：删成员、继承匹配函数、重分类新增/变更函数、刷新区域锚与哈希与阶段内排序；file 模式：删过时卡与分配、刷新变更文件卡、分配新文件、重组受影响阶段、更新覆盖记录 Y）。随后重生成受影响 L3 条目及其 L2/L1 祖先与依赖状态寄存器，未受影响生成输出从 B 复用。若 S 已无法容纳，则以同 g 与 Θ 在 R' 上重跑 Algorithm 2。
  3. 保守处理：无法解析或分类的源码不猜测——locator 或源哈希无法重校验的 L3 条目标记 frozen 并从定位排除；无法映射的新/变更函数显式记为 unmapped；无有效卡/分配的文件留在覆盖记录 Y' 中。

再同步中模型调用仅限四种语义步骤：classification、file assignment、within-stage organization、description revision，其余操作均确定性。完成后 (R', H') 成为下一请求的起始状态。

设计要点： 整个流程把 静态可确定的事实（路径、签名、源范围、已解析调用、文件指纹、内容哈希） 与 需要语义判断的描述（行为组织、阶段分配、文字说明） 严格分离——前者由静态分析锁定、模型不可覆盖；后者由 LLM 生成但须经审阅与对照源码校验。这使得 handbook 既可读又可追溯到源码，且能在 diff 后低成本地保持同步。

4. 实验结果与分析

4.1 实验设置

评测对象：在两个开源 agent harness 上评测行为定位与编辑计划质量——Terminus-2（Harbor 框架的 Python 终端 agent，通过 tmux 会话在 observe–decide–act 循环中驱动真实终端，紧凑 6 文件但行为丰富）与 Codex（Rust 单体仓库，跨 CLI/TUI/app-server/配置/沙箱等多 crate，数千文件、深调用图）。按 3.2 的选择规则，Terminus-2 用 function-as-leaf（有可信 seed 且函数级条目在预算内），Codex 用 file-as-leaf（在仓库规模上推断层级）。两仓库在文件/函数/调用边上相差约两个数量级，恰好各自实例化一种叶模式。

评测指标：（1）计划质量：三 judge 在 Localization / Scope Control / Reasoning 三维上打分（0–5，步长 0.5），加权得分

$$ S = 0.5\,S_\mathrm{Loc} + 0.25\,S_\mathrm{Scope} + 0.25\,S_\mathrm{Reason} $$

换算到 0–100 尺度；当两臂得分差至少 δ = 3 分时宣布胜者，否则平局。胜率 = 该切片胜数 / 有效 judge–请求比较数。（2）定位准确率：对照 Opus 4.8 与 GPT-5.5 独立参考计划，报告 file 与 symbol 粒度的 Recall / Precision / F1 / Wrong（Wrong 为零重叠占比，越低越好）。（3）计划成本：每请求平均 planner token 数（含 handbook 与源码上下文）。

4.5 一个真实的 Handbook-Assisted 走查（Appendix E）

以 Terminus-2 上一个真实 run（case Q1，DeepSeek-V4-Pro planner）为例。请求为 Query 类：“要求模型连续标记 task_complete 三次才真正评分，前两次只重显终端状态并询问是否确认。” 请求未点名任何文件/函数，故首要任务就是定位。BGPD 两步：

Phase 1 路由 handbook：SKILL.md → overview.md → index.md，定位拥有逐迭代继续与终止的阶段；读 stages/stage-4.8.md（Completion Gate）与 stage-4.7.md（Command Execute），确认握手在 gate；读 registers.md，发现 gate 由状态寄存器 reg-pending-completion 支撑，其读写位点跨主循环、初始化与逐 run 重置。由此推出：改动局限于单阶段单寄存器，且寄存器写位点揭示初始化与逐 run 重置必须与循环一起改，而不仅是显而易见的 return 分支。

Phase 2 对照活源码验证：在 terminus_2.py 中 search_file_content _pending_completion 得 7 处，均在同一文件。阅读后确认是一个 Boolean flag：首次完成标记置位、第二次返回前测试、任何非完成回合与每次 run 开始时清零。最终定位三处：Terminus2.__init__（~L292，初始化）、Terminus2._reset_per_run_state（~L1574，逐 run 清零）、Terminus2._run_agent_loop（~L1427–1440, L1552–1559，读写的观察分支与完成 gate）。计划把 Boolean _pending_completion 换成整数计数器 _completion_confirmations：循环在每次完成标记时自增、非完成回合重置、仅在第三次连续标记时返回评分。改动集为 4 个 modify 动作，均在 terminus_2.py。核心编辑前后对照：

# Before — 两次标记的 Boolean 握手
if is_task_complete:
    if was_pending_completion:
        # second task_complete: confirmed, grade now
        return
    else:
        # first attempt: ask to confirm, continue
        prompt = observation
        continue

# After — 三次标记的计数器
if is_task_complete:
    if was_completion_confirmations >= 2:
        # third consecutive task_complete: confirmed, grade now
        return
    else:
        # first or second attempt: ask to confirm, continue
        prompt = observation
        continue

该走查典型地体现了 BGPD 的两个核心动作：先经 handbook 路由确定哪些代码位点在 scope 内，再对照活源码逐一验证后写出计划。尤其值得注意的是，registers.md 揭示的“初始化 + 逐 run 重置必须随循环一起改”这一结论，是自顶向下读代码很容易漏掉的——这正对应论文强调的“分散、稀有路径与跨模块交互”场景的最大收益来源。

5. 总结与启发

5.1 局限性

论文未单设 Limitations 节，但通读全文可归纳出若干边界条件与潜在局限（以下为基于原文的合理归纳，论文未逐一明示）：

  • 依赖可信 seed skeleton（function-as-leaf）：Terminus-2 选用 function 模式的前提是“有可靠 seed skeleton 且函数级条目在预算内”。对缺乏可信 seed 的 harness，只能退回 file-as-leaf 推断骨架，组织质量受文件卡描述质量制约。
  • 静态分析的语言覆盖面：Phase I 由语言特定适配器完成，只解析能静态识别的函数/边界/调用。未解析调用只能进审计日志而非猜测——对大量动态分派、反射、跨语言 FFI 的 harness，程序图可能不完整，BGPD 的调用关系扩展会受影响。
  • 评测规模与范围：仅两个 harness、各 30 个请求；planner 仅 DeepSeek-V4-Pro 一种；judge 三模型但均来自同一代前沿模型族。结论（尤其“弱 planner 逼近强模型”）是否外推到更多 harness、更多 planner 仍待验证。
  • 只评计划、不评执行结果：评测直接打分 edit plan P，明确不评最终 diff 或执行正确性（executor 跨臂共享、out of scope）。handbook 对“执行后是否真的跑通”的增益未在本文度量。
  • handbook 构建与再同步的 LLM 成本未单独报告：论文强调 planner 侧 token 下降，但 handbook 构造与 resync 中四类语义步骤的模型调用成本（classification/file assignment/within-stage organization/description revision）未在主表中量化，仅以“预算”Θ约束。
  • 保守处理可能冻结有效条目：无法重校验的 locator 会被冻结并从定位排除，直至刷新。在频繁重构（大规模重命名/格式化）的仓库中，可能出现大量 frozen 条目，需要额外的刷新流程。

5.2 核心洞见与读后评注

  1. “在哪改”先于“怎么改”。 论文最核心的论点是：在 harness 演化中，确定编辑应落在何处是与生成编辑本身并列、甚至更前置的瓶颈。Handbook-Assisted 同时提升质量与降低 token，直接驳斥了“给 agent 更大上下文/更多 token 就能解决定位”的朴素假设——问题不在上下文大小，而在缺少行为到实现的结构化映射。
  2. 表示层的范式转换：从“实现为中心”到“行为为中心”。 现有 repo map / 代码搜索 / 仓库记忆都按文件/函数/模块组织，与“修改请求描述行为”的语义层级不匹配。Handbook 用 L1–L3 行为树 + 跨阶段状态寄存器视图，把“一个行为分散在多处”显式化，使“找全位点”从隐式推理变成可导航索引。这是把可读性工程引入 agent 自演化的一次尝试。
  3. 静态分析 + LLM 的分工是可信度的关键。 模型只能写行为描述、不能改路径/签名/源范围/已解析调用；所有 locator 必须对照当前仓库重校验，失败即冻结。这种“事实由静态锁定、语义由 LLM 生成、二者分离并交叉校验”的设计，是 handbook 既可读又可追溯、且能低成本 resync 的工程基石。它也给“用 LLM 理解代码库”一类工作提供了一个降低幻觉的范本。
  4. 状态寄存器视图 Z 是“分散位点”的最大杀手。 走查案例中，registers.md 揭示“初始化 + 逐 run 重置 + 循环”必须一起改——这正是自顶向下读代码易漏、关键词搜索难命中的场景。论文报告 Search-Hostile 与 Cross-file 请求上增益最大（Terminus SH +33.3，CF +20.0/+16.3），与该机制直接对应：状态读写的跨阶段耦合天然把分散位点显式化。
  5. 渐进式披露 = 用更少 token 做更准定位。 BGPD 先在 handbook 上粗到细导航（L1→L2→L3 + Z + 调用图扩展），再打开仓库只验证候选位点。这把“全仓库扫描”压缩为“定向验证”，token 用量不增反降（-12.7% / -8.6%）。这对上下文受限的 coding agent 有直接工程价值：不是塞更多上下文，而是先用行为索引裁剪 scope。
  6. “弱 planner + 好 map” 逼近 “强 planner”。 借 handbook，DeepSeek-V4-Pro 在 Terminus-2 上 file-level F1 达 89.3%、Precision 达 93.3%（对 GPT-5.5 参考），逼近甚至匹配更强模型的定位。这暗示定位能力可在相当程度上从模型能力中“外化”到表示层——对成本敏感的工业部署是重要信号。
  7. diff 驱动的局部再同步是“活文档”的关键。 非空 diff 只更新受影响部分（函数指纹/内容哈希做版本对齐、S 失效才全量重建），模型调用仅限四类语义步骤。这让 handbook 不会在仓库演化后迅速过期，是区别于一次性文档生成的核心。论文展望的harness 自演化（以 handbook 为共享行为记忆，agent 自主闭环定位→规划→执行→再同步）顺理成章，是该路线的自然下一步。
  8. 评注与展望。 本文把一个被广泛忽视的前置问题（行为定位）形式化并给出可工程化方案，立场鲜明、实验设计干净（两臂仅 handbook 访问不同、三 judge 独立、参考计划来自两独立模型）。可质疑处在于：增益在 Codex（大仓库、file-as-leaf）上明显小于 Terminus-2（小仓库、function-as-leaf）——file 模式下 L3 条目即整文件，粒度更粗，handbook 行为组织优势可能被稀释；这提示handbook 的收益与叶模式/仓库结构强相关。若能补上 handbook 构建成本、resync 频次与冻结率、以及对执行后正确性的端到端影响，论证会更完整。
