核心问题与动机

随着大型语言模型（LLM）驱动的智能体（Agent）在代码编写、系统操控、软件工程等任务中大规模部署，如何让智能体有效积累、复用并持续改进其能力（Skills）成为关键瓶颈。现有方法存在以下核心问题：

🧩 技能定义不统一
现有智能体技能库缺乏统一的结构规范。部分只有可执行脚本，无法传递"如何使用"的程序性知识；另一些仅为自然语言描述，无法直接执行。可执行脚本与程序性指导割裂是核心矛盾。
📦 语料质量参差不齐
百万级开源语料库中，技能的环境依赖多样、质量不一、可验证性差，直接使用会引入不可靠技能，影响智能体表现。
🔍 执行前无有效推荐
智能体在面对新任务时缺乏结构化的技能检索机制。朴素的向量搜索忽视了技能库的层次结构，无法做到渐进式披露（Progressive Disclosure），导致上下文污染或遗漏。
🔄 执行后缺少闭环演化
智能体执行轨迹中蕴含大量新发现，但如何将成功经验归因到具体技能并安全更新技能库至今缺乏系统机制，存在冗余更新、环境敏感性引入、不安全更新等风险。
核心研究动机
技能（Skill）是智能体经验积累的最小可复用单元。SkillsVote 将技能治理提升为一个完整生命周期工程问题——从语料采集到执行推荐，再到执行后演化，形成持续改进的闭环，而非一次性的工具积累。

背景与相关工作

智能体技能库的发展脉络

早期工具调用（Tool Use）
以 API/函数调用为中心，技能即固定函数接口。代表工作：Toolformer（2023）、API-Bank。技能为静态，无学习能力。
代码生成式技能库（Voyager / DEPS）
Voyager（Wang et al., 2023）在 Minecraft 中让智能体自动生成并积累 JavaScript 技能函数；DEPS 引入自然语言规划与代码执行。首次出现运行时技能增长，但缺乏质量治理。
结构化经验存储（Reflexion / ExpeL）
Reflexion 将执行反思作为未来提示；ExpeL 将成功轨迹提炼为自然语言洞察。引入经验管理概念，但经验与可执行技能仍未统一。
软件工程专项技能（SWE-Agent / CodeAct）
面向代码仓库操控、补丁生成，设计专用动作空间与 shell 技能。技能场景垂直化，但跨任务复用与治理仍为空白。
SkillsVote（本文）：生命周期治理
统一技能模式（SKILL.md + scripts/ + references/ + assets/），覆盖从百万级语料分析、执行前推荐到执行后演化的完整治理闭环，首次引入证据门控更新机制。

相关技术背景

RAG for Agents
将外部知识库接入智能体上下文，本文将技能库视为一种结构化 RAG，需要超越朴素语义检索的层次化搜索策略。
轨迹归因（Attribution）
借鉴强化学习中的信用分配（Credit Assignment），将轨迹结果分解归因至技能使用、智能体探索、环境因素三类，实现精细化更新控制。
在线/离线演化
类似 RLHF 的离线偏好学习与在线 RL 的对立；本文同时支持离线批量演化（Terminal-Bench 2.0）和在线持续演化（SWE-Bench Pro），探索两种范式的互补价值。

框架整体逻辑
SkillsVote 以 技能模式（Skill Schema） 为核心数据结构，串联起六个阶段：语料采集分析 → 技能库构建 → 执行前推荐 → 智能体执行 → 执行后归因 → 证据门控演化。整个框架形成 闭环自增强——每次执行都可能产生新的经验更新技能库，反哺下一轮推荐。

关键技术 · 技能模式（Skill Schema）

SkillsVote 提出了一套标准化的技能模式，将智能体技能视为可执行脚本 + 程序性指导的耦合体。这一设计源于一个核心观察：仅有代码无法告知智能体"何时用、如何用"；仅有文字描述无法直接执行。

技能目录结构

skill_name/
├── SKILL.md # 技能元数据 + 程序性指导（核心文件）
├── scripts/ # 可执行脚本
│ ├── main.py # 主要实现
│ └── utils.sh # 辅助工具脚本
├── references/ # 外部文档引用 (API docs / papers)
│ └── api_reference.md
└── assets/ # 静态资产 (配置、示例输入等)
    └── config.yaml

SKILL.md 关键字段

元数据区（Metadata）
· name：技能唯一标识名称
· category：功能类别（文件操作 / 网络 / 编译等）
· dependencies：运行时环境依赖列表
· version：版本号（支持演化追踪）
· source：来源语料 URL / 归属
· quality_score：语料分析阶段评估得分
程序性指导区（Procedural Guidance）
· description：技能功能的自然语言描述
· when_to_use：适用场景（触发条件）
· step_by_step：分步使用指南
· preconditions：前置条件
· postconditions：后置状态/副作用
· caveats：注意事项与已知限制
设计哲学
将技能视为"经验模式（Experience Schema）"而非单纯工具。scripts/ 提供"做什么"的能力，SKILL.md 的程序性指导传递"如何做、何时做、注意什么"的隐性知识。这种耦合使技能在被推荐给智能体时能够直接嵌入上下文并指导行动，而非仅提供代码片段。

关键技术 · 大规模语料分析与合成

构建高质量技能库的第一步是对百万级开源语料库进行系统性分析，识别可用技能并过滤低质量候选。

语料分析三维度

🌐 环境依赖分析
对每个语料单元分析其运行时环境需求：
· 操作系统类型（Linux / macOS / Windows）
· 运行时版本（Python 3.x / Node.js / etc.）
· 第三方包依赖及版本约束
· 外部服务依赖（数据库、API 等）
输出：结构化环境清单，支持技能部署决策
⭐ 质量评估
多维度质量打分：
· 代码完整性（可独立执行）
· 文档完备性（有无注释/说明）
· 社区活跃度（star / fork / issue 数）
· 测试覆盖率
输出：质量分数 $q \in [0,1]$，低于阈值 $\tau_q$ 的语料被过滤
✅ 可验证性检验
判断技能执行结果是否可客观验证：
· 有明确输入/输出规约
· 可通过测试用例验证
· 结果具有确定性
不可验证技能被标记为参考型（reference-only），不参与自动演化

可验证任务合成

针对可验证技能，SkillsVote 采用 LLM 驱动的任务合成流程，自动生成配对的（任务描述，验证测试）对，用于：

  • 技能库的基准评测（衡量技能本身的质量）
  • 为演化阶段提供成功/失败判断依据
  • 丰富技能的触发场景描述（增强推荐精度）
规模挑战
百万级语料库的处理需要高效的并行分析流水线。环境依赖图的精确解析（尤其是隐式依赖）和可验证性的自动判断是技术难点。论文在此维度的细节将是重要的工程贡献。

关键技术 · 技能推荐（Pre-Execution）

在智能体执行任务之前，SkillsVote 通过 Agentic Library Search 将结构化技能上下文注入智能体提示，实现执行前的知识增强。

核心挑战：为什么朴素检索不够

朴素向量相似度搜索（如 BM25 + FAISS）忽略了技能库的层次结构（类别 → 子类 → 具体技能），容易在 top-k 候选中引入相关但不精确的技能，造成上下文污染（Context Pollution）。同时，一次性返回所有细节会超过 LLM 上下文窗口限制。

Agentic Library Search

本文将技能推荐设计为一个智能体驱动的层次化搜索过程：

  1. 任务解析：将用户任务分解为结构化子目标，识别所需能力类型
  2. 类别导航：先在技能库顶层类别中检索，确定相关类别集合
  3. 精细化搜索：在候选类别内做二次语义搜索，获取 top-k 技能
  4. 渐进式披露：先返回技能摘要（SKILL.md 简介），按需展开完整程序性指导与脚本

渐进式上下文披露（Progressive Disclosure）

层级 L1：摘要
技能名称 + 一句话描述 + 适用场景标签。用于快速筛选，极低 token 消耗。
层级 L2：指导
完整程序性指导（SKILL.md 全文），包含步骤、前置条件、注意事项。智能体据此规划行动。
层级 L3：实现
可执行脚本（scripts/）完整代码。仅在智能体确认需要直接调用时展开，避免 token 浪费。

设推荐的 top-k 技能集合为 $\mathcal{S}_k = \{s_1, s_2, \ldots, s_k\}$，每个技能 $s_i$ 按需披露层级 $l_i \in \{L1, L2, L3\}$，总上下文消耗为：

$C_{rec} = \sum_{i=1}^{k} \text{tokens}(s_i, l_i) \quad \text{s.t.} \quad C_{rec} \leq C_{budget}$

关键技术 · 归因分析（Trajectory Attribution）

执行完成后，SkillsVote 对智能体轨迹进行精细化归因，将任务结果分解到不同来源，为技能演化提供可靠的决策依据。

轨迹分解

给定执行轨迹 $\tau = (a_1, o_1, a_2, o_2, \ldots, a_T, o_T)$（动作-观察序列），SkillsVote 首先将其分解为技能关联的子任务：

$\tau \rightarrow \{(st_j, s_j^*)\}_{j=1}^{M}$

其中 $st_j$ 是第 $j$ 个子任务片段，$s_j^*$ 是与之关联的技能（若存在）。

四维归因空间

🔧 技能使用（Skill Use）
结果可归因于直接调用了已有技能。若成功，该技能的使用频率和成功率指标上升；若失败，分析是技能本身问题还是使用方式问题。
🧭 智能体探索（Agent Exploration）
结果来自智能体自主探索发现的新方法，未依赖现有技能。这类轨迹片段是最有价值的演化候选——可能成为新技能或扩展现有技能。
🌍 环境因素（Environment）
结果受特定环境状态影响（如特定版本、特定配置）。这类技能更新需要标记环境敏感性，防止将偶然成功泛化为通用技能更新。
📡 结果信号（Result Signals）
显式的外部验证信号（测试通过 / CI 绿灯 / 用户确认）。高可靠的归因锚点，用于校准其他三个维度的归因置信度。

关键技术 · 技能演化（Post-Execution Evolution）

归因完成后，SkillsVote 通过证据门控更新机制（Evidence-Gated Updates）决策是否以及如何更新技能库，确保演化的安全性与可靠性。

证据门控更新流程

成功可复用性判断
只有被归因为成功的、可复用的发现（非偶发）才被允许进入演化流程。失败轨迹、环境敏感发现直接被过滤或标记。
冗余检测（Redundancy Control）
检查候选更新是否与现有技能库中已有技能高度重叠（语义相似度 $\gt \theta_{dup}$）。冗余更新被丢弃或合并，防止技能库膨胀与碎片化。
环境敏感性过滤
对归因含有"环境因素"成分的发现，标注环境约束条件而非直接泛化更新，确保技能库的跨环境可迁移性。
安全性审查
自动检测候选技能更新中是否包含高风险操作（rm -rf 类、权限提升、数据删除等），不安全更新被拒绝并记录审计日志。
技能库写入
通过全部审核的发现以版本化方式写入技能库，支持回滚。同时更新技能的使用统计和质量分数，形成技能的完整历史记录。

离线演化 vs. 在线演化

离线演化（Offline Evolution）
在固定数据集上批量分析历史轨迹，一次性更新技能库。

· 优势：可做全局冗余检测、大规模质量审核
· 场景：Terminal-Bench 2.0（+7.9 pp）
· 适用：技能库初始构建、定期迭代
在线演化（Online Evolution）
在任务执行过程中实时更新技能库，后续任务立即受益。

· 优势：技能增长与任务并行，当轮即可受益
· 场景：SWE-Bench Pro（+2.6 pp）
· 适用：持续运行的智能体系统
外部治理技能库
SkillsVote 还验证了一个重要发现：经治理的外部技能库可在不更新模型权重的情况下提升冻结智能体的性能。这意味着技能治理为模型版本固定的生产系统提供了一条无需重训的能力提升路径。

冻结智能体增强（外部技能库治理）

关键发现：无需模型更新的能力提升
实验表明，将经治理的外部技能库注入权重冻结的智能体，即可在 Terminal-Bench 2.0 和 SWE-Bench Pro 上获得显著提升。这验证了 SkillsVote 技能治理框架作为独立模块的价值——可插拔式集成到任何已部署的智能体系统中，无需触碰模型训练流程。

消融实验

消融实验系统地验证了 SkillsVote 各核心组件的独立贡献，揭示了技能生命周期治理各阶段的增益来源。

消融 A：移除 Skill Schema（退化为纯文本技能）
当技能降级为纯自然语言描述（无 scripts/ 目录）时，推荐命中率不变，但智能体实际执行精度显著下降。验证了可执行脚本与程序性指导耦合对技能有效性的关键作用。
消融 B：移除 Agentic Library Search（退化为朴素检索）
使用扁平化向量检索替代层次化 Agentic Library Search 后，上下文相关性降低，智能体频繁召回无关技能。渐进式披露机制对 top-k 精度提升贡献尤为突出。
消融 C：移除归因分析（直接全量更新）
跳过四维归因直接将成功轨迹写入技能库后，技能库中出现大量环境敏感和冗余技能，导致演化后性能反而下降（负迁移）。证明归因分析是安全演化的必要前提。
消融 D：移除证据门控（关闭冗余/安全过滤）
仅保留成功判断，关闭冗余检测与安全审查后，技能库快速膨胀至 3x 体积，检索效率下降，同时引入若干高风险操作技能。证据门控是控制技能库质量的关键。

局限性

重要局限性说明
以下局限性基于框架设计特征和实验范围的合理推断，具体数值和细节以论文正式发布内容为准。
⚠️ 技能爆炸风险
随着演化迭代次数增加，技能库规模持续增长，可能导致检索效率下降和技能间关系复杂化。冗余检测的阈值 $\theta_{dup}$ 选择对库规模有显著影响，需要持续校准。
⚠️ 归因的不确定性
四维归因空间的边界并非总是清晰——"智能体探索"与"环境因素"可能同时作用于同一轨迹片段。LLM 归因判断的一致性和准确性是潜在误差来源，错误归因可能导致错误演化决策。
⚠️ 任务领域覆盖范围
当前实验集中于终端操控（Terminal-Bench 2.0）和软件工程（SWE-Bench Pro），技能治理在多模态任务、具身智能、长期规划等场景下的效果尚未充分验证。
⚠️ 在线演化延迟
在线演化模式中，归因分析和证据门控的计算开销会增加每个任务的平均延迟。高频任务场景下，演化管道的 latency 需要优化，否则可能成为系统瓶颈。
⚠️ 安全审查完备性
基于规则和 LLM 的安全审查机制无法穷举所有高风险操作模式，尤其是组合式攻击（单独安全但组合危险的技能序列）难以被静态审查捕获，存在安全盲区。
⚠️ 依赖语料来源质量
初始技能库的质量上限受开源语料质量约束。若开源社区中某领域缺乏高质量代码（如特定垂直行业工具），技能库的初始覆盖将存在领域盲区，演化也无法填补该缺口。

核心洞见

01
技能 = 经验模式，而非工具
SkillsVote 最根本的贡献在于重新定义了"技能"的本质：技能不是可调用的 API，而是一种经验模式（Experience Schema），将"做了什么"（脚本）和"如何做、何时做、注意什么"（程序性指导）耦合在一起。这使得技能既可被智能体直接执行，也可被智能体阅读理解并仿效，大幅提升了技能的复用价值。
02
技能治理必须是生命周期工程
实验中消融任何单一阶段（语料分析、推荐、归因、演化）都会导致整体性能下降，证明技能价值不仅来源于单点技术，而来源于全生命周期的协同治理。这一发现呼应了软件工程中"DevOps 不是工具，而是文化"的理念——智能体技能需要"AgentOps"。
03
证据门控是安全演化的关键闸门
消融实验 C/D 表明，无管控的技能演化比不演化更糟糕。冗余技能、环境敏感技能、不安全技能一旦进入技能库，会通过推荐机制系统性污染后续任务的执行。证据门控不是可选的保险层，而是演化机制能够成立的必要前提。
04
外部技能库为生产系统提供无侵入升级路径
"冻结智能体 + 治理技能库"的组合在两个基准上均取得有意义的提升，这为工业部署场景提供了极具价值的信号：不需要重新训练或微调模型，通过持续治理的技能库即可在生产环境中实现能力迭代。这大幅降低了智能体系统的维护成本和风险。
05
渐进式披露解决了 RAG 的上下文困境
传统 RAG 将检索结果全量注入上下文，面临"注入过多则干扰、注入过少则遗漏"的两难。SkillsVote 的渐进式披露通过按需展开策略，在 token 预算约束下最大化了有效信息密度，是一种值得借鉴的结构化 RAG 设计范式，可推广到其他知识密集型智能体场景。
06
离线演化与在线演化各有侧重，可互补
离线演化（+7.9 pp）在有大规模历史数据时效果显著，适合技能库初始构建和周期性优化；在线演化（+2.6 pp）适合持续运行系统，实现技能随任务积累实时增长。两种范式并非竞争，而是互补的演化策略，实际部署中可结合使用。
