一、开篇：约束驱动架构

智能手表上的唤醒词检测与数据中心推荐引擎，几乎不共享任何基础设施——功耗与内存各差约 $10^9$ 倍。这不是设计偏好，而是物理定律划定的运行区间。

ML 系统工程的定义性洞察是：约束驱动架构（Constraints Drive Architecture）。光速为远端响应设绝对下限；热力学限制单位体积算力；内存物理使搬数据往往比计算更贵。数据中心可训练十亿参数模型，却无法保证数千公里外用户的低延迟；手机可即时响应，但内存只有云端的零头；微控制器可 coin-cell 电池运行数年，算力却仅够简单关键词检测。

单节点栈（Single-Node Stack）

本章锚定 D·A·M 中 Machine 轴的四层模型，后续各章逐层深入：

  1. Hardware（硅片）：$R_{\text{peak}}$、BW、HBM 容量——memory wall 是首要约束
  2. Systems（平台）：功耗包络、散热、NVLink 等节点互连
  3. Workloads（模型）：训练吞吐或推理延迟目标
  4. Missions（场景）：应用级 SLA（如智能门铃 1 年电池寿命）

五座灯塔模型（ResNet-50、GPT-2、DLRM、MobileNetV2、Keyword Spotting）贯穿全书，隔离不同系统瓶颈。

二、物理三墙：范式为何存在

2.1 光速屏障（Light Barrier）

$$L_{lat,\min} = \frac{2 \times \text{Distance}}{c_{fiber}} \approx \frac{2 \times \text{Distance}}{200{,}000\ \text{km/s}}$$

光纤中光速约为真空的 2/3。加州到弗吉尼亚直线约 3600 km → 往返 ~36 ms，尚未开始任何推理。实际云服务常再加 60–150 ms 软件开销。10 ms 安全回路（如机械臂急停）在物理上不可能使用远端 Cloud——这是 Edge/TinyML 存在的根因，而非优化问题。

餐巾纸计算：距离惩罚

场景：机械臂安全监控，端到端预算 10 ms，云数据中心距离 1500 km。

往返传播：(1500 km × 2) / 200,000 km/s = 15 ms → 预算已为负（-5 ms headroom）。

结论：物理上 Cloud 不可行，模型必须移至 Edge。

2.2 功耗墙（Power Wall）

Dennard 缩放（~2006 年前）下 $V \propto f$，故 $P \propto CV^2f \propto f^3$——频率翻倍需约 8× 功率。缩放关系失效后，行业转向多核并行与专用加速器（GPU/TPU）。

手机被动散热预算 3–5 W，超限则热节流（throttling）：图像增强模型前 90 秒 60 FPS，之后降至 15 FPS——Mobile 范式必须按稳态热地板设计，而非峰值 burst。

2.3 内存墙（Memory Wall）

$$\frac{\text{Compute Growth Rate}}{\text{Memory BW Growth Rate}} \approx \frac{1.6}{1.2} \approx 1.33 \ \text{/year}$$

算力约每 18 个月翻倍，带宽年增 ~20%——差距持续扩大，数据移动成为多数 ML 工作负载的主导成本与能耗来源。Profiler 显示 HBM 利用率 94%、TFLOPS 升级仅带来 8% 端到端改善 → 典型 memory-bound 签名。

三、工作负载分析与瓶颈原则

$$T = \frac{D_{vol}}{BW} + \frac{O}{R_{peak}\cdot\eta_{hw}} + L_{lat}$$

流水线重叠时，求和变为取 max（瓶颈原则）：

$$T_{bottleneck} = \max\!\left(\frac{D_{vol}}{BW},\ \frac{O}{R_{peak}\cdot\eta_{hw}},\ T_{network}\right) + L_{lat}$$

优化非瓶颈项收益为零——这是 ML 系统与"平均情况优化"的传统软件的根本区别。

餐巾纸计算：ResNet-50 Cloud vs Mobile（batch=1）

ResNet-50：4.1 GFLOP/推理，25.6M 参数（FP16 51.2 MB）。

A100：$T_{comp}$=0.013 ms，$T_{mem}$=0.025 ms → Memory 瓶颈（1.9×）。算术强度 80 FLOP/byte。

Mobile NPU（INT8）：$T_{comp}$=0.12 ms，$T_{mem}$=0.26 ms → 仍 memory-bound（2.2×）。

启示：两平台 batch=1 推理均 memory-bound；A100 带宽 20.4× 于 mobile → 推理约快 10×，而非峰值 TFLOPS 比例。字节削减与低精度比"买更多 FLOPS"更有效。

3.2 训练 vs 推理：D·A·M × Phase

组件训练（可变）推理（固定权重）

同一 ResNet-50 在 A100 上 batch=256 训练可能 compute-bound，batch=1 推理则 memory-bound——阶段切换即瓶颈切换。

五、Cloud ML：算力规模

定义：Cloud ML

在中心化数据中心部署，用延迟换弹性算力——解耦计算能力与数据/用户物理位置。

  • 优势：按需数千加速器、PFLOP/s 级训练（GPT-3 ~3634 PFLOP-days，~1024 V100 × 15 天，~$460 万）
  • 硬约束：$L_{lat}$ 10–100 ms+，数据 ingest 的 $D_{vol}/BW$ 瓶颈
  • 常见误区："Cloud = 无限算力"——距离惩罚与 ingest 瓶颈是物理地板，软件无法消除

Cloud 天然承载 Compute Beast、Bandwidth Hog、Sparse Scatter 三类原型：ResNet 训练需持续 TFLOP/s；LLM 推理需 TB/s HBM；DLRM 需 TB 级 embedding 表与 all-to-all 通信。

PUE（Power Usage Effectiveness）1.06 的顶级数据中心，6% 非计算开销仍等于兆瓦级散热成本——TinyML 范式根本不存在此类开销，这是六数量级经济差距的一部分。

六、Edge ML：延迟与隐私

定义：Edge ML

优化延迟确定性与数据本地化——计算物理邻近数据源，消除 $D_{vol}/BW_{IO}$（网络 I/O）项。

6.1 数据局部性不变量（Data Locality Invariant）

$$\frac{D_{vol}}{BW_{network}} \gt L_{lat,network} + \frac{O}{R_{peak,remote}\cdot\eta_{hw,remote}} \Rightarrow \text{必须本地处理}$$

餐巾纸计算：带宽瓶颈（工厂质检）

100 路 1080p@30FPS 摄像头：单路 ~186.6 MB/s → 合计 18.7 GB/s。10 Gbps 专线仅 1.25 GB/s → 负载需 14.9× 于可用带宽。

Edge 仅上传缺陷元数据（~1 KB/事件，~20 事件/s）→ 带宽降约 933,120×。Cloud 流式传输在此场景下物理不可行。

6.2 Edge 部署案例：零售人体检测

500 店 × 20 摄像头 × 15 FPS = 300 推理/s/店；YOLOv8-nano 8.7 GFLOP/推理 → 需 ~5.22 TOPS（含 2× headroom）。

设备INT8 TOPS功耗单价500 店 fleet 成本
Jetson Orin NX10010–25 W$600$300,000
Coral（3 板/店）~6（derated）6 W$450$225,000 + 3 年电费 ~$9.5k

对比 Cloud 推理 3 年 TCO ~$985 万——Edge 在带宽与延迟约束下同时赢得技术与经济账。

无线电传输能耗可达本地推理的 1000×——电池供电 Edge 设备（无人机、可穿戴）即使带宽够，Offload 仍物理不可行。

七、Mobile ML：离线智能

Modern SoC 集成 CPU+GPU+NPU，共享 2–5 W 系统功耗预算。NPU 峰值 TOPS 对 1–2 秒交互 burst 有预测力，对持续常开负载则是 poor predictor——热饱和后同样降频。

  • 优势：利用现有设备、离线能力、数据留机内（隐私）
  • 约束：INT8/FP16 量化必需；模型通常限 100 MB–1 GB；热节流按 steady-state 设计
  • 工具链：TFLite、CoreML、NNAPI——比 Cloud/TinyML 更易上手

八、TinyML：无处不在的感知

定义：TinyML

Always-On Sensing，受 KB 级内存与 mW 级功耗约束——主指标是 Energy/Inference（µJ），非参数量本身。

  • 模型须完全驻留片上 SRAM（DRAM 访问能耗高约 100×）
  • ~1 mW 以下可由能量收集（太阳能 thumbnail、热电）"永久"供电
  • CR2032 电池（675 mWh）+ 10–50 µW → 1–10 年"部署即忘"
范式工作负载能耗/推理3000mAh 电池可支撑推理次数
CloudGPT-4 查询~1 kJ~40 次
CloudResNet-50（服务器）68.8 mJ~58 万
EdgeResNet-50（Jetson）12.3 mJ~326 万
MobileMobileNet（NPU）2.46 mJ~1627 万
TinyMLKeyword Spotting10 µJ~39.96 亿

Cloud LLM 与 TinyML 唤醒词相差约 $10^8$ 能效——常开感知只有 TinyML 范式在能量上可行。唤醒词模型是"电源门"：超 ~1 mW 则无法阻止主 AP 的无谓唤醒（100–1000× 功耗差）。

FarmBeats / 野生动物监测：本地音频分析将 4.3 GB/天原始音频压缩为 400 KB/天摘要（10,750×）——TinyML 将 Edge 的局部性逻辑推至节点本身必须在 mW 预算内运行。

案例：自动驾驶紧急制动

100 km/h 时 100 ms 车辆行进 2.8 m。Cloud RTT 50–150 ms → 物理淘汰 Cloud（先于算力/成本考虑）。行人检测 ~300 GFLOP/s@30FPS → TinyML 不可行，需车载 Edge GPU（$500–1000/车，10 年摊销 $50–100/年，安全关键 justify）。Cloud 仅用于训练与 fleet 分析。

复杂度税（Complexity Tax）

启发式：50 行代码、~1 h/月维护、无漂移。ML 流水线：模型 50 行 + 基础设施 ~2000 行 + ~40 h/月调试漂移。

90%→95% 准确率若带来 40× 复杂度，启发式可能是更优系统选择——ML 系统工程是最小化此税的艺术。

十、混合架构

生产系统很少单一范式：语音 = TinyML(唤醒) + Mobile(STT) + Cloud(NLU)；自动驾驶 = Edge 感知 + Cloud 训练。

模式权衡适用避免
Train-Serve Split训练成本 vs 推理延迟训练需规模、推理要本地需持续 on-device 学习
Hierarchical Processing本地自治 vs 全局优化数据量超传输能力单 tier 可完成且网络可靠
Progressive Deployment质量 vs 部署广度同模型多级压缩部署无法 meaningful 压缩

训练一次数百万美元，推理单次 sub-cent——Train-Serve 成本不对称可超 $10^6$×，是 Split 的经济 rationale。Hybrid 两 tier 须同步特征定义、模型版本与预处理，否则 tier 边界出现 training-serving skew。

十一、系统熵与常见误区

  • 谬误：Cloud 算力"无限" → 距离与 ingest 是物理地板
  • 谬误：四范式是营销分类 → 由光速/热/内存墙划分
  • 谬误：仅按准确率选范式 → 99% 准确但 RTT 超制动预算 = 零效用
  • 陷阱：部署=终点 → OTA 带宽、版本差距、漂移监控是持续负担

十二、从范式到 Workflow：约束写入接口契约

以上十一节建立了部署物理约束与四范式谱系：光速/功耗/内存三墙划分 Cloud → Edge → Mobile → TinyML；铁律 $T = \max(D_{vol}/BW,\ O/(R_{peak}\cdot\eta),\ T_{network}) + L_{lat}$ 诊断瓶颈；决策门顺序为隐私 → 延迟 → 算力 → 成本。

知道 Cloud/Edge/TinyML 区间之后，Workflow 的任务是把 D·A·M 约束写入各 stage 的接口契约——让 512 MB、亚 10 ms 延迟、离线运行等 Machine 约束从 Day 1 反向驱动数据选型、架构选择与监控策略，而不是 Day 153 才发现模型放不进平板。

Zillow $304M 减记不是模型不准，而是缺乏追踪市场漂移的系统流程。以下用 DR 筛查贯穿案例，展示六阶段如何把部署约束落实为可验证交付物。

十三、Workflow 是整张地图

经典失败：第 153 天

Day 1：「为农村诊所建 DR 筛查模型。」Day 90：测试集 95% 准确率。Day 120：96%。Day 150：交给部署团队。Day 151：模型需 4 GB 内存。Day 152：目标设备是 512 MB 平板。五个月工作作废——不是模型差，是 workflow 失败：部署约束本应从 Day 1 反向约束架构选型。

Beede et al. (2020) 泰国诊所实地研究进一步说明：上线前 6 个月约 21% 图像因光照/相机/散瞳流程不符而被质量门拒绝——问题常在 workflow 与基础设施，而非单纯准确率。

ML Workflow = 在每个阶段显式化约束，并追踪其如何在 Data、Algorithm、Machine 三轴传播。从「模型研究员」到「系统工程师」的分水岭正在于此。

1.2 迭代税（Iteration Tax）

餐巾纸计算：轻量模型 vs 大模型（6 个月）

  • 大模型：1 周/实验 × 26 周 ≈ 26 次迭代，每次 +0.15% 准确率（递减）
  • 小模型：1 小时/实验 × 26×168 小时 ≈ 4368 次可能实验；100 次有效迭代 × 0.1%/次 可超越 95% 起点的大模型

系统启示：迭代速度是特性，不是副产品。Startup 常凭快速实验击败资源更足但周期更长的团队。

1.4 与 CRISP-DM 的对照

CRISP-DM（Cross-Industry Standard Process for Data Mining）六步：Business Understanding → Data Understanding → Data Preparation → Modeling → Evaluation → Deployment。本书六阶段与之高度对应，但 ML Systems 视角强调三点差异：

CRISP-DM本书 Workflow系统增强
Business Understanding问题定义显式 Machine 约束（内存/延迟/离线）
Deployment部署 + 监控监控为独立阶段，闭环反馈至采集/训练
（隐含）阶段接口契约每阶段可验证交付物，防 handoff 失败

Boehm (1981) 经典结论：需求阶段修复缺陷成本约为编码阶段的 10×，测试阶段约 15×，运维阶段约 100×。对 ML 系统，「需求错误」常表现为：优化了错误指标（准确率 vs 灵敏度）、忽略了部署约束（512 MB）、或训练数据编码历史偏见（Amazon）。Workflow 的价值是把高成本错误左移到 Stage 1–2。

十四、ML vs 传统软件生命周期

维度传统软件ML 系统

延伸：Software 2.0 破坏 OS 局部性假设

Unix 以来 OS 优化时空局部性：读字节 X 则很快读 X+1。ML 训练每 epoch 随机 shuffle TB 级数据 → L1 ~1 ns，DRAM ~50–100 ns，NVMe ~10–100 µs，差距 10⁴–10⁵×。DataLoader 必须自建 prefetch/pin memory，不能指望 page cache 启发式——这是铁律 $L_{lat}$ 项在 Software 2.0 中的系统来源之一。

MLflow 可复现链（DR 训练 run 示例）

Stage 3 交付的不只是「96% 准确率」，而是可复现 run。一次 DR 训练应留下：

mlflow.set_tag("data.dvc_rev", "fundus_v3.a3f2c1d")
mlflow.log_param("arch", "mobilenetv2_1.0")
mlflow.log_param("img_size", 224)
mlflow.log_metric("val_sensitivity", 0.923)
mlflow.log_artifact("preprocess.yaml")
mlflow.pytorch.log_model(model, "model")

preprocess.yaml 内写死 mean=[0.485, 0.456, 0.406]；INT8 量化后模型约 3.5 MB。

Registry 晋升条件写死：农村子群灵敏度 ≥ 0.90 且模型 ≤ 512 MB 才 Staging → Production。复现时：git checkout a3f2c1d && dvc pull && mlflow run . -P seed=42 应得到 ±0.002 内的同一指标。

十七、阶段一：问题定义

5.1 从业务到 ML 规格

DR 筛查：业务目标 = 减少漏诊；ML 规格 = 灵敏度 ≥90%、推理 <2 s、模型 ≤512 MB、可离线运行。约束必须在 Day 1 写入，否则模型团队会优化错误目标（测试集准确率而非临床可用性）。

5.2 War Story：Amazon 招聘 AI 偏见

2014–2017 Amazon 用历史简历训练排序模型。训练数据反映过去 10 年男性主导录用 → 模型学会惩罚含「women's」等词的简历。团队发现后关闭项目。

Workflow 教训：问题定义阶段须问「标签是否编码历史偏见？」「成功指标是否伤害公平性？」——这属于 Responsible Engineering，但必须在 Stage 1 嵌入，不能留到部署后。

5.3 约束传播预览

$$N_{\text{stage}} = 6 \quad \Rightarrow \quad \text{潜在约束交互} = 2^{N_{\text{stage}}-1} = 2^5 = 32$$

六阶段两两组合可产生 32 种约束交互（如「512 MB 限制 ↔ 数据采集分辨率 ↔ 评估子群划分」）。Workflow 的价值是让这些交互显式化，而非在生产环境意外碰撞。

十八、阶段二：数据采集

6.1 Lab-to-Field 分布鸿沟

DR 训练集常来自城市医院高分辨率眼底相机；部署场景是农村诊所低照度、非散瞳、消费级相机。这不是小噪声——是协变量偏移（Covariate Shift），足以让 96% 实验室准确率在现场崩溃。

6.2 带宽 Napkin Math

$$T_{\text{upload}} = \frac{N_{\text{img}} \times S_{\text{img}}}{B_{\text{net}}} \quad \text{例：} \frac{10{,}000 \times 5\,\text{MB}}{10\,\text{Mbps}} \approx 11.6\,\text{小时}$$

若标注需云端 GPU，往返延迟叠加——边缘采集 + 联邦学习（Federated Learning）成为 workflow 备选：本地训练梯度，只上传聚合更新，保护隐私并减带宽。

6.4 联邦学习：DR 场景的定量权衡

MobileNetV2 INT8 权重 ~3.5 MB；若每轮上传完整权重而非梯度，10 诊所 × 3.5 MB × 100 轮 = 3.5 GB 出口流量。FedAvg 只传梯度（与权重同量级）或 LoRA 增量（可压至 <100 KB/轮）。

具体 workflow：中心下发 $w_0$ → 各诊所本地训 1 epoch（~200 张/local）→ 上传 $w_i$ → 聚合 $w = \sum_i \frac{n_i}{N} w_i$。设 10 诊所、每轮 1 MB 更新、100 轮 ≈ 1 GB 总流量（vs 集中上传 10×200×5 MB = 10 GB 原始图）。

非 IID 风险可量化：若诊所 A 全为散瞳图、诊所 B 全为非散瞳，聚合后农村 B 子群灵敏度可从 0.92 跌至 0.78——Stage 4 须按诊所分层报告，而非只看全局 AUC。

6.5 标注成本与主动学习

眼底图像专家标注 ~$1–5/张。10 万张 = $10万–50万。Workflow 可嵌入 Active Learning：模型对不确定样本优先送标，用 20% 标注预算达到 80% 全量效果——但须监控主动采样是否引入选择偏差（总是标「难例」可能 oversample 边缘分布）。

十九、阶段三：模型开发

7.1 约束驱动架构

ResNet-50 ~100 MB+ FP32，超 512 MB 预算。MobileNetV2（~14 MB FP32，~3.5 MB INT8）+ ImageNet 迁移学习：在约束内最大化准确率。

Depthwise Separable Convolution（MobileNet 核心）

$$\text{标准卷积 FLOPs} \approx D_K^2 \cdot M \cdot N \cdot D_F^2 \qquad \text{深度可分离} \approx D_K^2 \cdot M \cdot D_F^2 + M \cdot N \cdot D_F^2$$

当 $M,N$ 通道数大时，深度可分离将计算量从 $O(M \cdot N)$ 降至 $O(M+N)$ 量级——这是「512 MB 平板能跑 DR 模型」的算法基础。

7.2 集成 vs 生产

5 模型集成 +2% 准确率但 5× 推理成本。Workflow 决策：集成用于离线评估 benchmark；生产部署单模型 + 校准。Platt Scaling / Temperature Scaling 可在不增加推理成本下改善概率校准。

二十、阶段四：评估与验证

8.1 三层验证策略

策略机制风险适用
Shadow Mode新模型并行推理，不影响用户无用户风险；无真实反馈首版上线前
Canary1–5% 流量切到新模型小范围暴露；需快速回滚性能/延迟验证
A/B Test随机分流，比较业务 KPI需足够样本量；伦理审查临床/商业决策

Canary 配置：DR 推理服务 95/5 切流

Istio VirtualService 按权重分流（DR v1=稳定版，v2=新量化模型）：

route:
- destination: {host: dr-serving, subset: v1}  weight: 95
- destination: {host: dr-serving, subset: v2}  weight: 5

自动回滚条件（Prometheus 告警规则示例）：

  • rate(inference_errors{version="v2"}[5m]) > 0.003（基线 0.1% → 0.3%）
  • histogram_quantile(0.99, latency{version="v2"}) > 2000（超 Stage 1 的 2 s SLA）

触发后 Flagger/Istio 将 weight 改回 100/0；观察窗口至少 7 天（覆盖农村诊所周一/周六客流差异）。

8.2 分层评估与子群公平

全局 95% 可能掩盖：农村子群 78%、老年子群 82%。Workflow 要求评估报告按部署环境子群分层，与 Stage 1 问题定义中的公平性约束对齐。

8.4 延伸：Temperature Scaling 公式

评估阶段发现模型 overconfident 时，可在验证集上学习温度 $T$：

$$P(y|x;\,T) = \frac{\exp(z_k / T)}{\sum_j \exp(z_j / T)} \quad T \gt 1 \Rightarrow \text{ softer 概率，改善 ECE}$$

$T$ 仅一个标量参数，不改变 argmax 分类（排序不变），但改善概率校准——适合 DR「阳性概率 > 阈值则转诊」的临床决策 workflow，且零额外推理成本（$T$ 可 baked into 最后一层 softmax）。

8.5 统计功效与 A/B 样本量

A/B 检验转诊率变化时，所需样本量 $n \approx \frac{2(z_{\alpha/2}+z_\beta)^2 \sigma^2}{\delta^2}$。若期望检测 2% 转诊率差异（$\delta=0.02$），常需数万次筛查——Workflow 须在 Stage 1 预留足够观察期，避免「两周 A/B 无显著」的伪结论。

二十一、阶段五：部署

9.1 云 vs 边缘经济账

方案单次成本10 万次/月DR 场景
Cloud API~$0.001/次~$100需稳定网络；隐私顾虑
Jetson Nano 边缘硬件 ~$99 一次性电费 ~$5离线、低延迟、512 MB 级

NVIDIA Jetson Nano：4 GB 统一内存、128 CUDA 核、~472 GFLOPS FP16——足以跑 INT8 量化的 MobileNetV2 DR 模型。Workflow 在 Stage 1 就应选定部署形态，避免 Day 153 式返工。

9.2 部署清单

  • 模型 artifact 版本 + 回滚上一版
  • 预处理 pipeline 与训练完全一致（归一化均值/方差）
  • 资源 limit：内存 hard cap、batch size=1 延迟优先
  • 健康检查：warmup 推理 + 输出 shape 校验

二十二、阶段六：监控

10.1 指标层次

层级指标告警含义
基础设施CPU/GPU、内存、QPS、p99 延迟服务不可用
模型质量准确率代理、AUC 滑动窗口性能退化
数据漂移PSI、KS statistic输入分布变化
业务转诊率、假阴性反馈临床/商业影响

10.2 PSI 手算例 + KS 确认

$$\text{PSI} = \sum_{i=1}^{B} \left( p_i^{\text{obs}} - p_i^{\text{exp}} \right) \ln \frac{p_i^{\text{obs}}}{p_i^{\text{exp}}}$$

对 DR 模型输入「图像亮度」分 4 箱（按训练集四分位切分）：

箱训练占比 $p^{\text{exp}}$本周生产 $p^{\text{obs}}$贡献
暗0.250.40(0.15)×ln(1.6)=0.073
中低0.250.22−0.003
中高0.250.20−0.006
亮0.250.18−0.009
PSI 合计≈ 0.055

0.055 < 0.1 → 暂不触发重训；但若「暗」箱单独 PSI=0.073 且持续 3 天，说明农村诊所光照恶化，应查相机/布光而非等全局 PSI 超 0.25。

KS 确认：对同一特征算 $D = \max|F_{\text{ref}}(x)-F_{\text{obs}}(x)|$。$n=500$、$D=0.18$ 时 $p \lt 0.01$（scipy ks_2samp）→ 与 PSI 一致，启动重训工单。固定阈值 0.1/0.25 仅为 Lewis (1994) 经验值；$B=4$ 时小样本会 inflate PSI，生产环境应对同一特征固定分箱边界（用训练集分位数，勿每周重算）。

10.3 血缘链：从 PSI 告警到行动

告警 PSI(brightness)=0.31 须能在 30 秒内定位：

data.dvc_rev=fundus_v3.a3f2c1d
  -> mlflow.run_id=abc123 (2026-03-15)
  -> model.registry=dr-mobilenet/Production v7
  -> deploy.k8s_image=dr-serving@sha256:9f3a…
  -> preprocess.mean=[0.485, 0.456, 0.406]

若 v7 用了 v2 数据集但部署时 preprocess.yaml 仍是 v1 的 mean/std，PSI 飙升可能是预处理不一致而非真实漂移——血缘链让工程师先查 artifact 匹配，而非盲目重训。

11.1 约束传播

512 MB 约束在 Stage 1 定义，传播路径：

11.3 约束交互矩阵（示例）

$2^5=32$ 种两两交互中，DR 案例高频碰撞：

阶段 A阶段 B交互示例
问题定义模型开发512 MB → 排除 ResNet-152

11.4 Technical Debt in ML（Sculley et al.）

Workflow 六阶段 + 契约的设计，正是为了命名并管理这些债，而非假装 ML 项目与 CRUD 应用一样线性。其中 CACE（Changing Anything Changes Everything）原则：改学习率可能要求改特征工程、数据采样、甚至评估指标——六阶段显式接口使这类连锁反应可追踪。

二十四、谬误与陷阱（Fallacies & Pitfalls）

谬误现实
「先做出好模型再考虑部署」Day 153：部署约束应反向约束模型选型
「测试集准确率高就够了」Lab-to-field 偏移 + 子群不公平可摧毁临床价值
「监控 = 看准确率」无 ground truth 时须用 PSI/代理指标 + 人工审计
「Workflow 是瀑布，做完一阶段不再回头」监控反馈常触发 Stage 2/3 重做——这是特性
「集成模型直接上生产」5× 成本；应分离 research ensemble 与 production single model

二十五、章节总结

核心要点

  1. 物理约束定义可行性：光速、功耗墙、内存墙划分 Cloud→TinyML，非设计偏好
  2. 铁律与瓶颈原则：先诊断瓶颈项，优化非瓶颈零收益；训练≠推理，阶段切换即瓶颈切换
  3. 四范式 + 工作负载原型：Compute Beast / Bandwidth Hog / Sparse Scatter / Tiny Constraint 决定部署区间
  4. 范式到 Workflow：部署约束须写入六阶段接口契约，Day 1 反向约束架构选型
  5. 六阶段 + 双流水线：问题定义→采集→开发→评估→部署→监控；每阶段可验证交付物，杜绝 handoff 失败
  6. DR 贯穿案例：512 MB / Lab-to-field / Shadow-Canary 95/5 / PSI 手算 + KS 确认 + 血缘链
  7. 混合是常态：Train-Serve Split + 分层 + 渐进部署；复杂度税可否决 ML
四范式是物理划定的区域；Workflow 是把区域约束写成各 stage 契约的系统 glue——两者合起来回答「系统该跑在哪里」与「如何不跑崩」。
