1. 概述

具身 AI 模型已从早期的 VLA（Vision-Language-Action）扩展到 WAM（World-Action Model），但实际部署却长期碎片化：每个模型家族都自带一套 Python 研究代码、特定后端假设与大量机器人侧 glue code，异构边缘设备（Jetson、RK 系、x86 边缘盒子、工作站级机器人）上几乎要为每个新模型重建软件栈。

作者通过对代表性 VLA 与 WAM 的架构分析，提炼出一条共享执行路径，并将其组织为五层架构：input adapters → sequence builders → backbone execution → head plugins → deployment adapters。Embodied.cpp 在此基础上提供三大能力——模块化多速率执行、延迟优先的融合推理、可扩展的算子与 I/O 支持，使一套后端抽象即可贯穿异构设备、机器人与仿真器。

核心结论：HY-VLA 与 pi0.5 的 C++ 部署分别取得 100.0% 与 91.0% 任务成功率；LingBot-VA 单块 Transformer 经 Q4_K 量化后显存从 312.2 MiB → 88.1 MiB，且 MAE < 3.3×10⁻²、cosine > 9.997×10⁻¹。

2. 研究背景与动机

2.1 具身部署改变了「运行时契约」

传统 LLM/VLM 服务假设：同步请求-响应路径、统一 token 接口、面向吞吐的大批量优化。而具身推理活在闭环控制过程内部，与机器人/仿真器侧存在依赖。即便有强 checkpoint，仍需被缝合进 Python 研究代码、后端专属推理路径、手写传感器封装与平台专属控制逻辑。论文据此提炼出具身推理运行时必须满足的三大要求：

  • 多速率执行（Multi-rate execution）：感知编码器、Transformer backbone、预测分支、动作头可能需在同一控制回路内以不同频率运行（层级式 VLA、快慢分离 VLA 与近期 WAM 中日益常见）。
  • 延迟优先的闭环控制（Latency-first closed-loop control）：优化目标不是吞吐而是稳定闭环控制——低延迟、低抖持、异构边缘硬件上的高效 batch-1 执行。
  • 可扩展的具身接口（Extensible embodied interfaces）：超越固定 token I/O，吸收自定义算子、具身多模态输入，以及从动作块到预测未来等异构输出。

2.2 具身模型架构谱系

论文将在线具身模型分为 VLA 与 WAM 两大族，并按内部推理结构进一步细分。下表整理自原文 Table 1。

三条对运行时设计的启示：(1) 结构组织已成为一等公民——许多新系统应被理解为交互的规划器/backbone/世界模型/动作模块；(2) 中间状态成为显式运行时对象——子目标、缓冲上下文、预测未来、潜在未来不再是隐藏细节；(3) 时序结构日益由模型定义，运行时必须支持有状态多组件编排，而非假设统一同步请求-响应路径。

2.3 现有运行时的缺口

通用运行时（llama.cpp、ONNX Runtime、SGLang、vLLM-Omni）覆盖了共享执行底座，但面向请求-响应、统一接口；仿真平台（ManiSkill、LIBERO、Isaac Sim）是训练/评测工具而非推理运行时；最接近的 vla.cpp 将 7 种 VLA 架构统一进一个 C++ 运行时，但仅 VLA 中心。下表（原文 Table 2）从「模型族覆盖」与「部署能力」两个角度量化缺口。

五层职责：输入适配器吸收在线传感器流与离线数据集样本（相机、力/触觉、IMU、基准数据集）经同一类型化具身接口进入；序列构建器负责多模态序列拼装、缓冲复用与上下文管理；backbone 执行是可托管 VLA、WAM 及未来变体的共享执行区；头部插件把动作头、流匹配/扩散头、世界预测头、动作专家变为可插拔模块；部署适配器把运行时输出桥接到仿真器与真机软件栈，使部署边界保持稳定。

3.2 模块化多速率执行

针对「不同模块刷新频率不同」的现实——感知栈可低频刷新、预测分支仅在需要未来估计时运行、动作头需以更高控制频率执行——Embodied.cpp 暴露显式执行单元、可插拔模块、共享状态/特征池与可配置刷新策略，使各组件以不同速率运行而无需强行统一为单条同步路径。下图为一个典型异步/层级式 VLA 的多速率调度示意。

3.3 延迟优先的融合执行

面向 batch-1、低延迟、低抖持的稳定控制，Embodied.cpp 优先保证控制性能，同时支持 graph replay、buffer reuse、算子融合、后端专属分发、精细 host-device 数据搬运，以在异构设备上实现高效小批量推理。其延迟模型可形式化为：

$$ T_{\text{step}} \;=\; T_{\text{parse}} \;+\; T_{\text{stage}} \;+\; T_{\text{compute}} \;+\; T_{\text{post}} $$

其中 $T_{\text{compute}}$ 为后端纯计算耗时（Table 4 仅测该项），其余为请求解析、张量暂存、输出后处理等服务侧开销。延迟优先策略要求在 $T_{\text{compute}}$ 与其余项上同时做融合与复用优化，而非仅压单点。摊销步延迟则反映动作块带来的控制频率收益：

$$ T_{\text{step, amortized}} \;=\; \frac{T_{\text{inf}}}{C} \;+\; T_{\text{overhead}} $$

其中 $C$ 为 action chunk 长度。pi0.5 采用 $C=50$ 的长动作块使摊销步延迟显著低于 HY-VLA（$C=20$），与 Table 3 数值一致。

3.4 异构后端与算子/量化策略

Embodied.cpp 通过单一后端抽象同时联合使用 CPU、GPU、NPU 等异构设备（区别于仅在 backend 间切换）。下层「具身 AI 算子仓库」收集可复用算子与模型专属 kernel，使新具身范式无需重建周边运行时即可落地。量化方面，WAM 侧采用 GGUF Q4_K（4-bit 块量化，K-Quants）替代 PyTorch BF16 权重，以大幅压缩常驻权重显存。量化误差用 MAE 与 cosine similarity 衡量：

$$ \text{MAE} \;=\; \frac{1}{N}\sum_{i=1}^{N} \left| \hat{y}_i - y_i \right|, \qquad \cos(\hat{y}, y) \;=\; \frac{\hat{y}^{\top} y}{\lVert \hat{y}\rVert \, \lVert y\rVert} $$

其中 $y$ 为 BF16 原始块输出，$\hat{y}$ 为 Q4_K 量化块输出，$N$ 为采样数（实验取 100 个随机输入）。

3.5 五层执行调度伪代码

论文未给出形式化 Algorithm 伪代码，下述 algo-box 依据论文五层架构与多速率调度描述整理而成，用于说明运行时主循环逻辑（非原文逐字）。

Algorithm 1: Embodied.cpp 多速率闭环执行（据五层架构整理）

Input: 传感器流 S = {相机, 力/触觉, IMU, ...}; 各模块刷新策略 policy[m]; 动作块长度 C

Output: 持续输出动作块至机器人/仿真器

// Layer 1-2: 输入适配 + 序列构建（低频刷新）

while control_loop_active do

if due(perception, policy) then

feat ← InputAdapter(S) // Layer 1

seq ← SequenceBuilder(feat, buffer) // Layer 2, 复用缓冲

// Layer 3: backbone 执行（batch-1, 融合后端分发）

repr ← Backbone(seq, backend=hetero_dispatch)

if future_estimation_needed then // 按需触发预测分支

repr ← PredictBranch(repr)

end

end

// Layer 4: 头部插件（高频控制率）

for t = 1 to C do

act[t] ← HeadPlugin(repr, t) // 动作头/流匹配扩散头

end

// Layer 5: 部署适配器

DeploymentAdapter.emit(act) → 机器人/仿真器

end

5. 消融与关键发现

论文本版未提供系统化的逐模块消融实验，但其对比性结果本身已构成若干关键发现：

  • Backbone 规模主导延迟与显存：HY-VLA（Hunyuan-VL，三视角 + 视频历史）vs pi0.5（PaliGemma）对比表明，在统一 C++ 运行时下，延迟与显存仍取决于 backbone 大小、视觉输入复杂度与动作块策略，而非运行时本身——说明运行时做到了「不引入额外开销」。
  • 动作块长度 $C$ 显著影响摊销步延迟：$C=50$ 的 pi0.5 摊销步延迟（56.85 ms）远低于 $C=20$ 的 HY-VLA（735.9 ms），与 $T_{\text{step, amortized}} = T_{\text{inf}}/C + T_{\text{overhead}}$ 一致。
  • Q4_K 量化显存收益巨大且精度漂移极小：显存降至 28.2%，cosine > 0.9997，证明 C++ 量化路径可在几乎无损精度下承载 WAM 侧 Transformer 组件。
  • 延迟测量口径：Table 4 仅含 $T_{\text{compute}}$，排除服务侧开销，这是评估运行时内核质量而非端到端服务的合理选择。

6. 总结与启发

论文核心论点：具身部署正收敛到一条共享执行路径，尽管模型族持续分化。Embodied.cpp 把公共路径当作基础设施、把分歧部分当作插件，五层架构使交互模式、I/O 语义、目标与部署边界保持显式，同时跨范式复用同一 backbone 执行路径。随新具身变体涌现，「稳定内核 + 可插拔任务组件」的分离价值将持续放大。

对本领域的启发：

  • 系统设计具身运行时应以「闭环控制契约」为第一性原理，而非简单扩展 LLM 服务；多速率、batch-1 低延迟、可扩展接口三者缺一不可。
  • 工程实践五层分层 + 后端抽象 + 算子仓库的组合，使新模型/新硬件的接入成本从「重建软件栈」降为「写插件」。
  • 量化部署GGUF Q4_K 在 WAM Transformer 块上展现了「显存大降、精度几乎不损」的工程价值，为边缘部署 WAM 提供可行路径。
  • 局限当前 WAM 仅为单块微基准，完整 LingBot-VA 闭环尚未稳定；缺乏端到端延迟对比与系统化消融，结论的普适性仍待更大规模验证。

7. 局限性

  • WAM 评测仅限 LingBot-VA 单个 Transformer 块，非完整模型闭环，且作者明确说明完整模型在受限边缘设备上尚未稳定。
  • 实验仅覆盖 2 个 VLA 模型与 1 个 WAM 块基准，模型多样性有限；未与 vla.cpp 等同类系统做直接端到端性能对比。
  • Table 4 延迟仅含后端计算，未报告端到端服务延迟（含 $T_{\text{parse}}/T_{\text{stage}}/T_{\text{post}}$），实际部署延迟可能更高。
  • 异构硬件「联合使用」（Hetero. HW ✓）的具体调度策略与实测数据在论文中未展开。
