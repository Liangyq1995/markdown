1. 为什么需要 LLM Gateway

企业直连 LLM Provider API 面临五大系统性问题，Gateway 是解决这些问题的统一基础设施层。

🔒 安全隔离
Provider 密钥不下发给业务方，API Key 泄漏仅影响虚拟密钥；Prompt 注入、PII 泄漏在网关层统一拦截
💰 成本管控
无限流保护导致账单爆炸；无法按团队/项目分摊 token 消费；重复请求浪费调用费用
🔁 可靠性
单 Provider 故障时无自动切换；无重试/熔断机制；Provider 限流时无排队降级
📊 可观测性
token 消耗、延迟、错误率缺乏统一追踪；无法定位慢请求；多模型成本无对比
🔀 多模型
不同 Provider API 格式各异（OpenAI/Anthropic/Gemini）；A/B 测试、金丝雀切换缺乏基础设施
核心定位：LLM Gateway 是企业 AI 基础设施的"南北向流量管控层"——类比传统 API Gateway（Kong/Nginx），但针对 LLM 的 token 计量、语义相似度、长尾流式响应等特性做了深度定制。

4. 智能路由与负载均衡

4.1 路由策略分类

策略适用场景时间复杂度核心参数
加权轮询 WRR静态多 Provider 分流O(1)权重向量 $\mathbf{w}$
最小活跃连接长连接 / 流式场景O(1)活跃请求数
延迟感知路由对延迟敏感的实时应用O(N)EMA 衰减系数 $\alpha$
Two-Choice 路由大规模 Provider 集群O(1)随机候选数 d=2
UCB 自适应Provider 性能未知/动态变化O(N)探索系数 $c$
成本优先路由批量任务、非实时场景O(N)价格矩阵 $\mathbf{P}$

4.2 延迟感知路由：EMA + 综合评分

对每个 Provider $p$，用指数移动平均维护其延迟估计：

$$\hat{L}_p(t) = \alpha \cdot L_p^{new} + (1 - \alpha) \cdot \hat{L}_p(t-1), \quad \alpha \in [0.1,\; 0.3]$$

综合路由评分（越小越优先）：

$$\text{score}(p) = w_1 \cdot \frac{\hat{L}_p}{L_{max}} + w_2 \cdot \frac{c_p}{c_{max}} + w_3 \cdot \hat{e}_p + w_4 \cdot \mathbf{1}[\text{CB}_p = \text{Open}] \cdot \infty$$

其中 $c_p$ 为每 token 成本，$\hat{e}_p$ 为错误率 EMA，最后一项在熔断器打开时将该 Provider 排除。典型权重：$w_1=0.5,\; w_2=0.3,\; w_3=0.2$。

4.3 Two-Choice 路由的负载均衡数学分析

经典随机路由（每次随机选一个 Provider）的最大负载期望为：

$$\mathbb{E}[\text{MaxLoad}_{random}] = O\!\left(\frac{\log N}{\log \log N}\right)$$

Two-Choice（随机选 2 个，取负载更低者）将最大负载压缩到：

$$\mathbb{E}[\text{MaxLoad}_{2\text{-choice}}] = O(\log \log N)$$

这是 The Power of Two Choices 定理（Mitzenmacher 1996），以极小代价（多一次随机采样）获得指数级的负载均衡改善。

4.4 UCB 自适应路由（多臂赌博机）

将每个 Provider 视为一个赌博机臂，目标是最大化累积奖励（最小延迟/最高质量）。UCB1 算法：

$$\text{UCB}(p, t) = \hat{\mu}_p + c \cdot \sqrt{\frac{\ln t}{n_p}}$$

其中 $\hat{\mu}_p$ 为 Provider $p$ 的历史平均奖励（如 $1/\hat{L}_p$），$n_p$ 为已选择次数，$t$ 为总时间步，$c$ 为探索系数（通常取 $\sqrt{2}$）。每次选择 UCB 值最大的 Provider。

UCB 的关键特性：累积遗憾 $O(\sqrt{T \ln T})$，随时间自动降低探索比例，在 exploitation 与 exploration 间自适应权衡。

Algorithm 1: 综合路由决策

Input: 请求 req, Provider集合 P, 全局时间步 t

Output: 选中的 provider


// Step 1: 过滤不可用 Provider

candidates = [p for p in P if circuit_breaker(p).state != OPEN]

if len(candidates) == 0: return fallback_response()


// Step 2: 检查模型能力约束（上下文长度、多模态）

candidates = [p for p in candidates if p.ctx_len >= count_tokens(req)]


// Step 3: UCB 评分

for p in candidates:

if p.n_calls == 0: // 冷启动：优先探索未被选过的

return p

p.ucb = p.mean_reward + sqrt(2) * sqrt(ln(t) / p.n_calls)


// Step 4: 成本约束过滤（预算不足时只选低价 Provider）

if req.budget_remaining < req.est_tokens * max_cost(candidates):

candidates = filter_by_cost(candidates, req.budget_remaining)


// Step 5: 返回 UCB 最高的 Provider

return argmax(p.ucb for p in candidates)

5. 语义缓存（Semantic Cache）

5.1 工作原理

语义缓存的核心洞察：用户提问"Python 列表排序怎么写"和"Python list 如何 sort"语义相同，但传统精确匹配缓存无法命中。语义缓存通过向量相似度实现"模糊匹配"。

flowchart LR
    Q["用户请求\nquery text"] --> EM["Embedding Model\ntext-embedding-3-small\n1536-dim vector"]
    EM --> KEY["缓存键构造\n(model_id, sys_hash, query_vec)"]
    KEY --> ANN["ANN 搜索\nHNSW / IVF-PQ\nTop-K 近邻"]
    ANN -->|"sim >= τ"| HIT["Cache HIT\n返回缓存响应\n跳过 LLM 调用"]
    ANN -->|"sim < τ"| MISS["Cache MISS\n路由至 LLM Provider"]
    MISS --> LLM["LLM 生成响应"]
    LLM --> STORE["异步写入缓存\n(query_vec, response, ttl)"]
    STORE --> VDB["Vector DB\nQdrant / Redis VSS"]

5.2 相似度计算与阈值设计

标准余弦相似度：

$$\text{sim}(\mathbf{q}, \mathbf{c}) = \frac{\mathbf{q} \cdot \mathbf{c}}{\|\mathbf{q}\| \cdot \|\mathbf{c}\|} = \frac{\sum_{i=1}^{d} q_i c_i}{\sqrt{\sum_i q_i^2} \cdot \sqrt{\sum_i c_i^2}}$$

归一化向量（embedding 通常已 L2 归一化）后简化为内积：$\text{sim}(\mathbf{q}, \mathbf{c}) = \mathbf{q} \cdot \mathbf{c}$

缓存命中率定义：

$$\text{HitRate}(\tau) = \frac{|\{q \in Q : \exists\, c \in \mathcal{C},\; \text{sim}(q, c) \geq \tau\}|}{|Q|}$$

阈值 $\tau$ 的 tradeoff（典型值）：

$\tau$ 值命中率语义相似度推荐场景
0.98低（~5%）极高（几乎完全相同）精确查找类问题（SQL、代码片段）
0.95中（~20%）高（同义表达）通用推荐默认值
0.90高（~40%）中（主题相关）FAQ / 知识库问答
0.85很高（~60%）低（同领域）摘要生成（接受近似）

5.3 HNSW 索引：分层图结构

HNSW（Hierarchical Navigable Small World）是目前最主流的 ANN 算法，查询复杂度 $O(\log N)$。

核心参数：

  • M（每层最大边数）：控制图密度，越大准确率越高，内存消耗线性增加。推荐 $M \in [16, 64]$
  • ef_construction：建索引时的候选集大小，越大索引质量越好，建索引越慢。推荐 128~512
  • ef_search：查询时候选集大小，越大召回率越高，延迟越大。推荐 64~256

分层结构：向量随机分配到层 $l \sim \lfloor -\ln(\text{Uniform}(0,1)) \cdot m_L \rfloor$，$m_L = 1/\ln(M)$。高层稀疏（远程跳转），低层密集（精细搜索），实现"高速公路 + 小路"的导航效率。

5.4 缓存键设计（精确 + 语义结合）

完整缓存键需要同时考虑语义内容和上下文参数：

def build_cache_key(request: ChatRequest) -> CacheKey:
    # 精确匹配维度（不同则必须区分）
    exact_dims = {
        "model": request.model,
        "system_prompt_hash": sha256(request.system_prompt),
        "temperature": round(request.temperature, 2),
        "max_tokens": request.max_tokens,
    }
    # 语义匹配维度（query embedding）
    query_text = extract_last_user_message(request.messages)
    query_vec = embed(query_text)  # [1536-dim float32]

    return CacheKey(exact=exact_dims, semantic=query_vec)

def lookup(key: CacheKey, vdb: VectorDB, threshold=0.95):
    # 先精确过滤（model + system_prompt_hash 必须相同）
    filter_expr = build_exact_filter(key.exact)
    # 再语义搜索
    results = vdb.search(
        vector=key.semantic,
        filter=filter_expr,
        top_k=5,
        ef=128
    )
    if results and results[0].score >= threshold:
        return results[0].payload["response"]
    return None  # Cache MISS

5.5 缓存失效策略

  • TTL：基于时间的硬过期，默认 1~24 小时（知识时效性敏感场景缩短）
  • LRU 淘汰：向量 DB 容量满时驱逐最久未使用条目
  • 版本失效：模型版本升级后，旧缓存条目自动失效（通过 model_version 字段过滤）
  • 语义漂移检测：定期对缓存命中结果做质量抽样，若人工/自动评估分下降则降低 $\tau$ 或清空缓存

6. 限流与配额管理

6.1 Token Bucket（令牌桶）

令牌桶是 LLM 场景最适合的限流算法，因为它可以天然支持以 token 为粒度的限流（而非 QPS）。

桶状态更新公式：

$$B(t) = \min\!\left(B_{max},\;\; B(t_{prev}) + r \cdot (t - t_{prev})\right)$$

其中 $B_{max}$ 为桶容量（burst 上限），$r$ 为令牌填充速率（tokens/秒）。每次请求消耗：

$$\Delta B = N_{input} + N_{output}^{est}$$

由于 output token 数在请求前未知，可用历史平均值估算，或采用事后扣减（先放行，收到响应后扣除实际 output token）。

6.2 滑动窗口计数器（Redis 原子实现）

使用 Redis Sorted Set 实现精确滑动窗口，时间戳作为 score，token 数作为 member value。

-- Lua 脚本：原子操作保证无竞争
-- KEYS[1]: rate_limit:{tenant_id}:{model}
-- ARGV[1]: current_timestamp_ms
-- ARGV[2]: window_size_ms (e.g., 60000 for 1 min)
-- ARGV[3]: token_cost (input + estimated output)
-- ARGV[4]: max_tokens_per_window

local key = KEYS[1]
local now = tonumber(ARGV[1])
local window = tonumber(ARGV[2])
local cost = tonumber(ARGV[3])
local limit = tonumber(ARGV[4])
local window_start = now - window

-- 清理过期条目
redis.call('ZREMRANGEBYSCORE', key, 0, window_start)

-- 统计当前窗口内 token 消耗
-- 用 ZRANGEBYSCORE 获取所有成员的 score 之和
local entries = redis.call('ZRANGEBYSCORE', key, window_start, now, 'WITHSCORES')
local total_tokens = 0
for i = 2, #entries, 2 do
    total_tokens = total_tokens + tonumber(entries[i])
end

-- 检查是否超限
if total_tokens + cost > limit then
    -- 返回剩余等待时间（最老条目过期时间）
    local oldest = redis.call('ZRANGE', key, 0, 0, 'WITHSCORES')
    local retry_after = 0
    if #oldest > 0 then
        retry_after = math.ceil((tonumber(oldest[2]) + window - now) / 1000)
    end
    return {0, retry_after}  -- 被限流
end

-- 记录本次消耗（用唯一 member + score=token_cost）
local member = now .. ':' .. math.random(1000000)
redis.call('ZADD', key, cost, member)
redis.call('PEXPIRE', key, window)
return {1, limit - total_tokens - cost}  -- 放行 + 剩余配额

6.4 自适应限流：基于 Provider 响应动态调节

当 Provider 返回 429 时，Gateway 应动态降低向该 Provider 的发送速率：

$$r_{new} = r_{old} \cdot (1 - \beta \cdot \mathbf{1}[\text{provider\_429}]) \cdot (1 + \gamma \cdot \mathbf{1}[\text{success\_streak}])$$

AIMD（Additive Increase Multiplicative Decrease）策略：收到 429 时乘性减小（$\times 0.5$），成功时线性恢复（$+5\%$），与 TCP 拥塞控制同构。

Virtual Key 哈希存储（永不存储明文）：

import hashlib, os, secrets

def create_virtual_key(tenant_id: str, permissions: dict) -> tuple[str, str]:
    """返回 (明文key, 存储记录)，明文仅返回一次"""
    key_raw = "vk-" + secrets.token_urlsafe(32)  # 展示给用户
    salt = os.urandom(32)
    key_hash = hashlib.pbkdf2_hmac(
        'sha256',
        key_raw.encode(),
        salt,
        iterations=100_000  # NIST 推荐最低值
    )
    record = {
        "key_hash": key_hash.hex(),
        "salt": salt.hex(),
        "tenant_id": tenant_id,
        "permissions": permissions,  # {"models": ["gpt-4o"], "max_tpd": 100000}
        "created_at": now_utc(),
        "last_used": None,
    }
    return key_raw, record  # 明文只返回这一次，不持久化

def verify_key(key_raw: str, record: dict) -> bool:
    salt = bytes.fromhex(record["salt"])
    expected = bytes.fromhex(record["key_hash"])
    computed = hashlib.pbkdf2_hmac('sha256', key_raw.encode(), salt, 100_000)
    return hmac.compare_digest(computed, expected)  # 恒定时间比较，防时序攻击

7.4 零停机密钥轮换

生产环境密钥轮换需双密钥过渡，避免业务中断：

  1. 生成新 Key（vk-new-xxx），与旧 Key 同时有效（双密钥窗口期，建议 72h）
  2. 业务方在窗口期内替换为新 Key
  3. 窗口期结束，Gateway 自动吊销旧 Key
  4. 审计日志记录完整轮换轨迹

8. 流式响应代理（SSE 深度）

8.1 SSE 协议详解

Server-Sent Events（SSE）是 LLM 流式输出的主流协议，基于 HTTP/1.1 chunked transfer：

HTTP/1.1 200 OK
Content-Type: text/event-stream
Cache-Control: no-cache
Connection: keep-alive
X-Accel-Buffering: no

id: 1
event: message
data: {"id":"chatcmpl-xxx","object":"chat.completion.chunk","choices":[{"delta":{"content":"Hello"},"index":0}]}

id: 2
data: {"choices":[{"delta":{"content":", world"},"index":0}]}

data: [DONE]

关键字段：

  • id:——事件 ID，客户端断线重连时通过 Last-Event-ID Header 续传
  • retry:——建议重连间隔（毫秒），Gateway 可注入此字段控制客户端重连频率
  • event:——事件类型，OpenAI 标准只用 message（默认），可扩展 error、ping
  • data: [DONE]——终止标记，Gateway 收到后关闭上游连接并发送给客户端

8.2 背压（Backpressure）控制

当客户端消费速度慢于 Provider 输出速度时，Gateway 需要缓冲机制防止 OOM：

Algorithm 2: 流式代理背压控制

Input: upstream（Provider SSE 连接）, downstream（Client 连接）

Config: buf_limit = 256 chunks, heartbeat_interval = 15s


buffer = AsyncQueue(maxsize=buf_limit)

token_count = 0


// 生产者协程：读取 Provider 数据

async def producer():

async for chunk in upstream.iter_bytes():

await buffer.put(chunk) // 满时自动阻塞（背压传导）

token_count += estimate_tokens(chunk)

await buffer.put(None) // 发送 EOF 信号


// 消费者协程：转发给 Client

async def consumer():

last_ping = now()

while True:

try:

chunk = await asyncio.wait_for(buffer.get(), timeout=5.0)

except TimeoutError:

// 发送心跳防止客户端超时断开

await downstream.write(b"data: {}\n\n")

continue

if chunk is None: break

await downstream.write(chunk) // 零拷贝转发


await asyncio.gather(producer(), consumer())

return token_count // 用于事后计费

8.3 流式 Token 实时计数

流式场景下需要实时估算 token 消耗（用于限流和计费）。由于 BPE 分词是批量操作，chunk 级别的 token 计数采用启发式估算：

$$\hat{N}_{tokens}(chunk) = \left\lceil \frac{\text{len}(chunk_{text})}{4} \right\rceil$$

平均 1 个 token ≈ 4 个英文字符（3.5~4.5 的经验区间）。流结束后用 tiktoken 精确计数并调整账单差额。

9. 熔断器（Circuit Breaker）

9.1 三态状态机

stateDiagram-v2
    [*] --> Closed: 初始状态
    Closed --> Open: 失败率 >= θ (如 50%)\n或连续失败 >= N 次
    Open --> HalfOpen: 等待 T_recovery 秒\n(指数退避后)
    HalfOpen --> Closed: 试探请求成功
    HalfOpen --> Open: 试探请求失败
    Closed --> Closed: 正常请求
    Open --> Open: 拒绝请求(快速失败)\n返回 503 / 降级响应

9.2 失败率计算（滑动时间窗口）

在最近 $W$ 秒的时间窗口内统计失败率：

$$r_f(t) = \frac{\sum_{i \in [t-W, t]} \mathbf{1}[\text{req}_i = \text{fail}]}{\sum_{i \in [t-W, t]} 1} \geq \theta$$

触发 Open 状态的复合条件（任意满足其一）：

  • 窗口内失败率 $r_f \geq \theta_{rate}$（通常 50%）
  • 窗口内绝对失败次数 $\geq N_{min}$（防止低流量时误触，通常 10 次）
  • P99 延迟超过 $L_{max}$（慢请求熔断，如 30s）

9.3 指数退避重试

Open 状态的恢复等待时间（含 jitter 防惊群效应）：

$$t_{wait}(k) = \min\!\left(t_{max},\;\; t_{base} \cdot 2^k\right) + U(0,\; \sigma^2)$$

其中 $k$ 为重试次数，$t_{base}=1s$，$t_{max}=60s$，$U(0, \sigma^2)$ 为均匀随机抖动（$\sigma = t_{wait}/4$）。

9.4 多级 Fallback 链

flowchart LR
    REQ["请求"] --> P1{"Provider A\ngpt-4o"}
    P1 -->|"CB Open"| P2{"Provider B\nclaude-3-5-sonnet"}
    P2 -->|"CB Open"| P3{"Provider C\ngemini-1.5-pro"}
    P3 -->|"CB Open"| P4{"自托管模型\nLlama-3-70B"}
    P4 -->|"全部不可用"| DG["降级响应\n503 + Retry-After\n或缓存旧响应"]
    P1 & P2 & P3 & P4 -->|"成功"| RESP["正常响应"]

    style DG fill:#3a1e1e,stroke:#f38ba8
Algorithm 3: 熔断器核心状态转换

class CircuitBreaker:

state: CLOSED | OPEN | HALF_OPEN

failure_window: SlidingWindow(size=60s)

open_since: timestamp

retry_attempt: 0


def call(provider_fn):

if state == OPEN:

elapsed = now() - open_since

wait = min(60, 1 * 2**retry_attempt) + rand()

if elapsed < wait: raise CircuitOpenError

state = HALF_OPEN


try:

result = provider_fn()

on_success() // HALF_OPEN → CLOSED

return result

except Exception as e:

on_failure(e)

raise


def on_failure(e):

failure_window.record(1)

if state == HALF_OPEN:

state = OPEN; open_since = now(); retry_attempt += 1

elif failure_window.rate() >= 0.5 and failure_window.count() >= 10:

state = OPEN; open_since = now(); retry_attempt = 0


def on_success():

failure_window.reset()

if state == HALF_OPEN: state = CLOSED; retry_attempt = 0

10.4 尾部采样策略（Tail-Based Sampling）

对于高 QPS 场景，100% trace 采样成本过高，尾部采样在请求完成后按规则决定是否保留：

  • 高延迟请求（P95 以上）：100% 保留
  • 错误请求（5xx）：100% 保留
  • 高成本请求（> $0.1）：100% 保留
  • 正常请求：1~5% 随机采样

10.5 成本分摊公式

单次请求成本（美元）：

$$\text{cost}_{req} = \frac{N_{input} \cdot P_{input} + N_{output} \cdot P_{output}}{10^6}$$

其中 $P_{input}$、$P_{output}$ 为每百万 token 价格（如 GPT-4o：$2.50 / \$10.00$）。

月度团队账单：

$$\text{bill}_{team}(T) = \sum_{req \in T} \text{cost}_{req} \cdot (1 + \text{markup\_rate})$$

11.2 Prompt Injection 检测

规则层（低延迟，< 1ms）——正则匹配高风险 pattern：

INJECTION_PATTERNS = [
    # 角色扮演绕过
    r"ignore\s+(all\s+)?(previous|prior|above)\s+instructions?",
    r"pretend\s+(you\s+are|to\s+be)\s+(?:DAN|evil|jailbreak)",
    r"you\s+are\s+now\s+(?:freed?|unrestricted|without\s+limits?)",
    # 系统提示词覆盖
    r"new\s+(?:system\s+)?prompt[:\s]",
    r"override\s+(?:system|safety|guidelines)",
    # 编码绕过（Base64/Hex/ROT13）
    r"(?:base64|hex|rot13|unicode\s+escape)\s+decode",
    # 多语言注入（检测后强制翻译）
    r"[؀-ۿ]{20,}",  # 阿拉伯语大段文本
]

def detect_injection(text: str) -> tuple[bool, str]:
    for pattern in INJECTION_PATTERNS:
        if re.search(pattern, text, re.IGNORECASE):
            return True, f"Injection pattern: {pattern[:50]}"
    return False, ""

分类器层（中等延迟，10~50ms）——轻量 BERT 分类器（如 deberta-v3-small）输出注入概率分数，阈值 0.85。

11.4 越狱对抗鲁棒性

常见越狱手法及防御：

12. 成本控制与计费

12.1 tiktoken BPE 计数原理

OpenAI 使用字节对编码（BPE）进行分词，不同模型词表不同：

import tiktoken

def count_tokens(messages: list[dict], model: str) -> int:
    """精确计算 chat completion 的 token 数（含格式开销）"""
    try:
        enc = tiktoken.encoding_for_model(model)
    except KeyError:
        enc = tiktoken.get_encoding("cl100k_base")  # 默认

    # OpenAI chat format 的格式开销
    tokens_per_message = 3  # <|start|>{role}\n{content}<|end|>
    tokens_per_name = 1     # 如果有 name 字段

    n_tokens = 3  # 每次 completion 的基础开销 <|start|>assistant<|message|>
    for msg in messages:
        n_tokens += tokens_per_message
        for key, value in msg.items():
            n_tokens += len(enc.encode(str(value)))
            if key == "name":
                n_tokens += tokens_per_name
    return n_tokens

注意：Anthropic Claude 使用自己的 tokenizer，Gemini 使用 SentencePiece，同一段文本在不同模型下 token 数可能差异 10~30%，成本计算必须使用各自 tokenizer。

12.2 预算强制执行

限额类型触发条件响应行为告警
软限额（Soft Limit）已用额度 >= 80% 预算继续放行，发送警告邮件立即
硬限额（Hard Limit）已用额度 >= 100% 预算429 拒绝，响应含 budget_reset_time立即

16. 核心洞见

🔑 洞见 1：语义缓存是 ROI 最高的单一优化
对于知识问答、代码生成等场景，30~40% 的请求语义重复。语义缓存命中不仅节省 LLM 调用费用，还将延迟从秒级降至毫秒级。阈值 0.95 是大多数场景的最佳平衡点。
🔑 洞见 2：Token 级限流比 QPS 限流更公平
一个发送 1000 token prompt 的用户和一个发送 10 token 的用户，QPS 相同但资源消耗相差 100 倍。只有 Token 级限流才能真正公平地分配 LLM 资源。
🔑 洞见 3：UCB 路由在 Provider 性能频繁变化时显著优于静态权重
Provider 的延迟和可用性会随时间变化（高峰期 GPT-4o 变慢、某 Provider 发版时不稳定），UCB 自适应路由能在数分钟内自动发现最优 Provider，无需人工干预调整权重。
⚠️ 陷阱：Gateway 本身成为单点
Gateway 引入了新的 SPOF。生产部署必须：① 多实例部署（最少 3 个）②Redis 用 Sentinel/Cluster 模式③ 依赖的 Vector DB 做主备 ④ Gateway 挂掉时考虑降级为直连 Provider 的 bypass 模式
⚠️ 陷阱：异步日志丢失与计费不准
将 token 计费写入放在 background task 中虽然提升性能，但 Gateway 崩溃时会丢失未持久化的计费数据。建议先写 Redis 原子计数（毫秒级），再异步同步到 DB；或使用 WAL（Write-Ahead Log）保证计费数据不丢失。
