一、开篇：为何需要 ML 基准测试

剪枝模型在 A 加速器上 2× 更快，在 B 上无改善；增大 batch 提升利用率却违反延迟 SLO。每项优化都带承诺——基准测试是将理论主张转化为可验证工程知识的纪律，量化 peak 与 sustained 性能之间、实验室与生产之间的鸿沟。

定义：ML 基准测试

在代表性 ML 工作负载上端到端测量系统性能，将厂商峰值规格与 realistic 条件下可持续的吞吐/延迟解耦。A100 峰值 312 TFLOP/s，生产 Transformer 训练 MFU 通常 30–50%（93.6–156 TFLOP/s）——$\eta_{\text{hw}}$ 鸿沟须由基准量化。

  • 系统基准：硬件是否在 realistic 负载下兑现承诺（带宽饱和、dispatch 开销）
  • 模型基准：优化是否在全输入分布上保留质量（非仅测试集）
  • 数据基准：模型是否泛化到含噪声/偏移的真实数据

三条原则

  1. 基准是代理，非真理——Offline 10K QPS vs Server 模式可能差一个数量级
  2. Goodhart 定律：指标成为目标即失效（BLEU 刷榜 vs 用户延迟）
  3. 端到端 > 组件指标：推理 5 ms→10 ms 模型阶段在 50 ms 流水线中仅 ~1.2× 端到端改善

三、基准粒度

粒度测量对象优势局限
Micro单 kernel（GEMM）隔离硬件能力miss 系统交互
Macro单层/单模型 forward模型级 profiling无数据管道开销
End-to-end完整 pipeline最接近生产难归因瓶颈

工程决策决定粒度：采购 GPU 看 macro+scaling；SLO 验证必须 end-to-end（含预处理、队列、后处理）。MobileNetV2 灯塔示例：INT8 3.5 MB + EdgeTPU 2 ms 推理，仍需验证低光 edge case 精度与真实手机图像分布——系统/模型/数据三维缺一不可。

四、训练 vs 推理基准

同一加速器在训练与推理中相反方式失败：训练 waste 天数于梯度同步；推理 miss SLO 于 tail latency 尖峰。故 MLPerf Training 与 Inference 分离。

维度TrainingInference
计算方向Forward + BackwardForward only
内存参数+梯度+优化器+激活（3–4× 推理）权重+激活+KV cache
优化目标Time-to-accuracy、scalingLatency 分位数、QPS
绑定约束小 scale 算力；大 scale 通信 BW延迟、tail、冷启动
能耗模式一次性摊销（GPT-3 ~1287 MWh）每 query 累积（$E = P \times T$）

五、训练基准

$$T_{\text{train}} = \operatorname{arg\,min}_{t}\big\{\text{Accuracy}(t) \geq \text{target accuracy}\big\}$$
$$\text{Throughput} = \frac{N_{\text{samples}}}{T_{\text{train}}}$$

吞吐 alone 无意义——MLPerf ResNet-50 须达 75.9% top-1 才有效。未达目标的"快"不算数。

5.1 扩展效率

$$\text{Eff}_{\text{scaling}} = \frac{T(1)}{N_{\text{GPU}} \times T(N_{\text{GPU}})} \times 100\%$$

例：单卡 24 h，8 卡 4 h → $\text{Eff} = 24/(8 \times 4) = 75\%$。丢失 25% 来自 AllReduce（10–15%）、CPU↔GPU 拷贝（3–5%）、负载不均（2–5%）。

5.2 MFU（Model FLOPs Utilization）手算

$$\text{MFU} = \frac{\text{Achieved FLOP/s}}{\text{Peak FLOP/s}} = \frac{6 \times N \times D \times H \times L \times T / T_{\text{step}}}{R_{\text{peak}}}$$

例：GPT-2 117M，batch=32，seq=1024，A100 FP16 峰值 312 TFLOP/s，实测 step 120 ms：

  • 每 step FLOPs ≈ $6 \times 32 \times 1024 \times 768 \times 12 \approx 1.8 \times 10^{12}$
  • Achieved = $1.8 \times 10^{12} / 0.12 \approx 15$ TFLOP/s
  • MFU = $15/312 \approx 4.8\%$（小模型 GPU 利用率极低——CPU/Python 开销主导）

LLM 7B+ scale MFU 30–50% 常见；MFU 低 ≠ 浪费，小 scale 通信/launch 占比高是物理现实。

六、推理基准与 MLPerf Inference

6.1 推理指标

  • Latency：单请求延迟；生产关注 p95/p99 而非均值
  • Throughput：满足 SLO 的有效 QPS——违反 SLO 的请求不计入
  • Tail latency：多组件 fan-out 时 tail 放大（Tail at Scale）

6.2 MLPerf 执行场景

场景负载模式优化目标
SingleStream逐条顺序最低延迟
MultiStream多流并行多传感器/多摄像头
ServerPoisson 到达、SLO 约束延迟约束下最大 QPS
Offline批量全可用最大吞吐

Server 场景要点

10,000 QPS 但 5% 违反 99%ile SLO → 报告有效 QPS 9,500。Server 模式模拟真实 serving：请求随机到达、batch 与队列竞争同一延迟预算。

6.3 有效 QPS 手算

$$\text{QPS}_{\text{valid}} = \text{QPS}_{\text{raw}} \times (1 - p_{\text{SLO violation}})$$

例：ResNet-50 Server 模式测得 raw 12,000 QPS，p99 目标 15 ms，实测 8% 请求 p99 > 15 ms → 有效 QPS = $12000 \times 0.92 = 11040$。若只报 12K 则 overstate 产能 7.3%。

6.4 Offline vs Server 鸿沟

场景ResNet-50 V100说明
Offline batch=128~45,000 img/s最大吞吐，无 SLO
Server p99<15 ms~8,500 img/sPoisson 到达 + 动态 batch
SingleStream~117 img/s (8.5 ms)最低延迟

Offline 数字比 Server 高 5× 常见——用 Offline 规划 Server 容量将严重 under-provision。

七、功耗测量

SPEC Power（2007）在 0–100% 共 11 档负载测 ssj_ops/W——ML serving 很少 100% 满载，部分负载效率决定真实电费。Green500 按 FLOP/s/W 排名，教训是最快集群 ≠ 最经济集群。

$$E_{\text{total}} = \text{Power} \times T$$

300 W 加速器、10 ms 推理 → $300 \times 0.01 = 3$ J（~0.0008 Wh）。MLPerf Power 标准化测量边界：加速器 alone vs 整机 vs 机架级——边界选择可差 2–3×。

测量边界包含适用
ComponentGPU/TPU 芯片硬件能效对比
NodeCPU+GPU+内存+风扇单节点部署规划
Rack/Cluster网络、存储、冷却TCO 与碳排放

算法能效 vs 硬件功耗

压缩（INT8 量化）通过减少工作量降能耗，非仅换更省电硬件。MobileNet 深度可分离卷积 + INT8 可在算法与数值两层同时攻击 $D_{\text{vol}}$ 与 $O$ 项。

八、最佳实践与陷阱

  • 统计 rigor：多次 run、报告分布而非单次 best；GPU boost/thermal throttling 可淹没小增益
  • Benchmark-production gap（2–10×）：漂移、节流、动态负载、静默退化——再精密的仪器 alone 无法消除
  • Benchmark gaming：test-set 调参、kernel 特化——MLPerf 多工作负载缓解
  • 模型评估盲区：高准确率 ≠ 校准良好；须测子群指标（DR 农村 0.88 vs 全局 0.95 → 拒绝部署）与分布外性能

移动/边缘 omitted 条件

厂商 burst 推理数字若未测 sustained 热节流，steady-state 性能可远低于峰值——智能手机 类部署最常被误导的 omitted 条件。

九、章节总结

核心要点

  1. 基准是 D·A·M 协同设计的问责机制——验证 Data/Algorithm/Machine 是否真正匹配
  2. 系统/模型/数据三维 + micro/macro/e2e 粒度，按决策问题选择
  3. 训练看 time-to-accuracy 与 scaling efficiency；推理看 SLO 约束下的 QPS 与 tail
  4. MLPerf 四场景（Single/Multi/Server/Offline）反映不同部署 physics
  5. 功耗须定义测量边界；算法压缩与硬件能效互补
  6. Goodhart + benchmark-production gap：设计 for benchmark = 对 shifting reality 过拟合
Measured 什么，就 improved 什么——MLPerf Training 版本间进步持续超越 Moore 定律，正因标准化测量创造 competitive pressure 驱动全栈优化。
