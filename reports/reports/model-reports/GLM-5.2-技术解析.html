阅读主线：长程任务 ≠ 只把窗口拉大。GLM-5.2 的叙事是「1M 要在真实编码 Agent 轨迹上可用」——用训练数据覆盖大规模实现 / 自动研究 / 性能优化 / 复杂调试，再用 IndexShare 把稀疏注意力的索引成本压下去，再用 slime + 单轨迹 PPO + Anti-hack 把后训练做稳。

一、发布要点与能力画像

GLM-5.2 被定位为面向长程任务的旗舰模型。官方强调四项新增/强化能力：

  • Solid 1M Context：稳定支撑长程工作的 100 万 token 上下文，而不只是「宣称支持」。
  • Advanced Coding + Flexible Effort：更强编码能力，并提供多档 thinking effort，在性能与时延之间权衡。
  • Improved Architecture：IndexShare 让每 4 个稀疏注意力层共享同一 indexer，1M 上下文下每 token FLOPs 约降 2.9×；改进 MTP 层，投机解码接受长度最高提升约 20%。
  • Pure Open：MIT 开源，无区域限制。
「1M context is easy to claim, but much harder to keep reliable under real engineering pressure.」——长上下文要在 messy coding-agent trajectories 上仍然保质，而不是只吃更多 token。

二、1M 上下文架构：IndexShare 与 MTP

2.1 IndexShare for DSA

  • 每 4 个 Transformer 层共享一个轻量 indexer。
  • indexer 放在 4 层组的第一层，算出的 topk indices 复用给后续 3 层。
  • 3/4 层不再重复做 indexer 点积与 topk，1M 下每 token FLOPs 约降 2.9×。
  • 从 mid-training 起用 IndexShare，序列长度从 128K 起步。
$$ \text{Indexer cost ratio} \approx \frac{1}{4}\quad(\text{every 4 layers share one indexer}) $$ 
graph TD
  L1[Layer 1: Indexer + Sparse Attn] --> L2[Layer 2: reuse topk]
  L2 --> L3[Layer 3: reuse topk]
  L3 --> L4[Layer 4: reuse topk]
  L4 --> L5[Layer 5: new Indexer]
  L5 --> L6[Layer 6: reuse topk]
工程直觉：稀疏注意力里，贵的往往不只是「挑 k 个 token」，而是每层都跑一遍 indexer。IndexShare 把「选谁」和「怎么算」解耦——选指标准每 4 层更新一次。

2.2 MTP：IndexShare + KVShare

改进 MTP 层，服务投机解码两个目标：

  1. 降低 draft 成本：MTP 上也用 IndexShare。
  2. 提高接受率：消除 GLM-5.1 MTP 中 training–inference 不一致。

IndexShare 后第二步复用第一步 topk，使 $h_5$ 只能 attend 到 $h_1\ldots h_4$，KV 全部来自目标模型 hidden，与训练对齐。另引入 Rejection sampling 与 End-to-end TV loss。

三、1M 上下文 Serving 工程

上下文扩到 1M 后，瓶颈从算力转向 KV-cache 容量、随长度增长的 kernel、CPU 侧调度。IndexShare 降 FLOPs，但不按比例减小 KV 体积。

  1. 在 LayerSplit 上做更细粒度显存管理与并行，抬高可用 KV 容量。
  2. 优化随长度增长的 kernel，并与 cache 传输流水线协同。
  3. 优化 CPU 侧 cache 管理与调度，减少 GPU 流水气泡。
系统取舍：架构侧省的是 indexer 计算；Serving 侧仍要正面打 KV。两条账分开看。

四、slime：Agentic RL 基础设施

slime 覆盖 white-box / black-box rollout、compact trajectory、sub-agent workflow。后训练用 slime 做并行 OPD，十多个 expert 合并进最终模型，全过程约 2 天。训推可对接不同并行、路由、PD disaggregation；配合 KV-cache FP8 提升大规模 RL 与推理并发。

五、长程 RL 与 Anti-hack

5.1 单轨迹 Critic PPO

长程轨迹经 compaction 后，同 prompt 下 trace 数量与长度不齐。从 group-wise 转向 critic-based PPO：对单条 rollout 学习，用 critic 估 token-level advantage；所有 compacted 子轨迹纳入训练，用 token-level loss 处理长度不平衡。

5.2 Anti-hack

编码 RL 易 reward hacking（读评测产物、抄答案、curl 源码等）。两阶段检测：规则过滤器（高召回）+ LLM judge（保精度）。在线拦截可疑 tool call 并返回 dummy，但不终止整条 rollout，避免训练不稳。

设计要点：惩罚「这一步捷径」，不是「整局作废」。

八、要点总结

维度结论
产品叙事长程 Agent 交付，而不是「更大窗口」口号
架构IndexShare 砍 indexer 成本；MTP+KVShare+TV loss 抬高投机接受长度约 20%
系统1M Serving 瓶颈在 KV/调度/kernel
后训练slime + 并行 OPD（约 2 天）；长程用单轨迹 critic PPO
安全训练Anti-hack：规则+LLM judge，在线拦截单步
开源位势长程三连开源领先；闭源仍以 Opus 系列为标尺
若只记三件事：(1) IndexShare 让 1M DSA 算得起；(2) slime/OPD/Anti-hack 让长程 Agent RL 训得稳；(3) 分数上开源第一梯队，闭源仍以 Opus 为标尺。
