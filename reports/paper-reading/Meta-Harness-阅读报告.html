1. 核心问题与动机

1.1 什么是 Harness？

flowchart LR
    subgraph SYS["LLM 系统"]
        HARNESS["Harness（套件）\n决定模型看什么信息\n• 检索策略\n• 记忆管理\n• 工具调用逻辑\n• Prompt 构建\n• 状态更新规则"]
        MODEL["LLM 模型权重\n固定不变"]
        HARNESS --> MODEL
    end
    TASK["任务"] --> HARNESS
    MODEL --> OUTPUT["输出"]
    NOTE["同一个 LLM + 不同 Harness\n可产生 6× 的性能差距！"] -.-> SYS
核心洞见：修改同一个固定 LLM 的 Harness，可以在同一基准上产生 6 倍的性能差距。这意味着 Harness 工程的重要性与模型选择本身相当——但目前这个过程几乎完全依赖人工设计。

1.2 现有文本优化方法的致命缺陷：反馈压缩

方法反馈压缩方式MTok/迭代问题
OPRO窗口（解答, 分数）对0.002丢失执行轨迹细节
TextGrad当前版本的文本反馈0.015只看当前候选，无历史

单次 Harness 评估可产生多达 10,000,000 tokens 的诊断信息——比现有方法的最大反馈预算高出约 3 个数量级。

2. Meta-Harness 方法

2.1 核心设计：文件系统作为无损反馈通道

flowchart TD
    FS["文件系统 D\n存储所有历史信息：\n候选 Harness 源码 / 执行轨迹 / 得分\n每个候选 = 一个目录"]
    PROP["编码 Agent（提议者）\nClaude Code / Claude Opus 4.6\n读取 FS 中全部历史（中位数 82 个文件/迭代）\n诊断失败原因 → 提出改进版本"]
    EVAL["评估\n在任务上运行新 Harness\n收集执行轨迹"]
    LOG["记录全部日志到文件系统\n源码 + 执行轨迹 + 分数"]
    FS --> PROP --> EVAL --> LOG --> FS

2.2 正式目标函数

$$H^{*} = \arg\max_{H}\; \mathbb{E}_{x \sim X,\; \tau \sim p_M(H,x)}\; r(\tau, x)$$

其中 $M$ 为固定 LLM，$X$ 为任务分布，$H$ 为 Harness 程序，$\tau$ 为执行轨迹，$r(\tau, x)$ 为任务奖励函数。

多目标时（如准确率 vs 上下文 token 数），报告 Pareto 前沿而非单一指标。

2.3 关键设计决策：编码 Agent vs 原始 LLM

提议者必须是编码 Agent（而非原始 LLM），原因：

  • 历史快速超出单次上下文限制，Agent 需自主决定读取哪些历史文件
  • 必须通过 grep、cat 等文件操作工具选择性检索（而非一次性吞入）
  • 需要直接编辑代码并通过交互验证修改的正确性
Algorithm: Meta-Harness 搜索循环

Input: 任务分布 X，固定 LLM M，初始 Harness H₀，预算 N

初始化：文件系统 D ← ∅

for i = 1, …, N do

// 1. 提议阶段：编码 Agent 读取文件系统

H_new ← CodingAgent.propose(D) // 选择性读取历史，诊断失败，生成改进

// 2. 评估阶段

score, traces ← Evaluate(H_new, M, X)

// 3. 记录阶段：无损存储所有信息

D ← D ∪ {(H_new, score, traces)}

end for

return argmaxH∈D score(H)

核心发现：摘要不能替代原始轨迹
提供摘要比只给分数几乎没有提升（34.9% vs 34.6%），而完整日志带来质变（50.0%）。这证明了压缩确实丢失了诊断关键信息——失败模式的根因往往藏在执行轨迹的中间步骤中，摘要无法保留这些因果线索。

4. 局限性

  • 提议者质量依赖：目前依赖 Claude Code + Opus 4.6 作为提议者，提议者能力直接影响搜索效率；更弱的提议者会显著降低发现优质 Harness 的速度
  • 计算成本高：每次搜索运行数小时，不适合频繁迭代的快速实验场景
  • 过拟合风险：在代码空间中过拟合更易检测（可见的 if 链、硬编码逻辑），但仍需人工审查以确保 Harness 的泛化性
  • 任务特异性：当前每个任务领域需要独立的搜索过程，跨任务的 Harness 知识迁移未充分探索

5. 核心洞见与读后评注

"元优化"范式：优化优化者本身
Meta-Harness 的哲学是"用 LLM 优化 LLM 的工作方式"。这不是 fine-tuning（改变权重），不是提示词优化（改变单次输入），而是改变信息流动的架构——决定模型在什么时候看到什么信息。这是一个更高层次的自动化，理论上比调整模型本身更高效（因为 Harness 可以即时更改，权重无法）。
完整日志 vs 摘要：信息论视角
摘要本质上是有损压缩——任何压缩都会以某种方式丢失信息，而哪些信息在优化中是关键的，事先无法确定。Meta-Harness 的关键决策是让提议者自主决定读取哪些历史信息（通过文件系统操作），而不是由外部系统预先决定哪些信息"值得"保留。这是自适应检索 vs 固定摘要的核心区别。
对 Agent 系统工程的实践启示
Harness 工程目前是 AI 应用开发中最耗时且最依赖专家直觉的环节。Meta-Harness 展示了一个路径：先用人工设计基础 Harness，再用自动搜索在其基础上继续优化。实验中仅 4 次评估就达到了竞争对手需要 60 次才能达到的水平——这暗示了搜索效率与诊断信息的丰富度直接相关，验证了"更多信息 → 更快找到好方案"的直觉。
