Multi-Agent 协同架构深度解析报告

综合两篇知乎博客：多角色 Agent 协同合作 · 多 Agent 代理协同的三种架构 · 2026-05

来源说明：本报告综合自两篇知乎技术博客，非学术论文。内容覆盖 ChatDev、MetaGPT、AgentVerse、GameAgents 等主流框架，以及 LangGraph 图式框架的工程实践。

1. 为什么需要 Multi-Agent？

单一 Agent 的根本局限（清华大学 AgentVerse 实验验证）：
  • 工具过载：同时处理数十个工具效果显著下降于专注单一工具集的 Agent
  • 提示词干扰：混合多个角色的系统提示导致角色边界模糊，输出质量下降
  • 失败传播：单一 Agent 一步失败可能导致整个任务崩溃；Multi-Agent 可隔离失败
  • 并行化受限：单 Agent 无法真正并行处理独立子任务

1.1 Multi-Agent 优势的形式化理解

设任务 $T = T_1 \oplus T_2 \oplus \ldots \oplus T_k$（k 个子任务），单 Agent 与 Multi-Agent 的对比：

维度单 AgentMulti-Agent
工具空间$|\mathcal{F}_\mathrm{all}|$（全部工具）$|\mathcal{F}_i| \ll |\mathcal{F}_\mathrm{all}|$（每 Agent 只有相关工具）
注意力集中度分散于所有工具和子任务每 Agent 集中于专属子任务
失败隔离全局失败子任务级失败，可局部重试
并行度顺序执行无依赖子任务可并行

3.1 通用 Multi-Agent 执行循环

flowchart LR

    INIT --> LOOP["主循环"]

    CHECK -->|是| OUT["输出最终结果"]

5. 图式框架：LangGraph 的工程实践

flowchart LR
    subgraph GRAPH["图式框架（LangGraph）"]
        N1["Agent 节点 1\n（状态）"]
        N2["Agent 节点 2\n（状态）"]
        N3["Agent 节点 3\n（状态）"]
        N1 -->|"条件边\n（转移矩阵）"| N2
        N2 -->|"确定边"| N3
        N3 -->|"条件边"| N1
    end
    subgraph CONV["对话式框架"]
        C1["Agent A"] -->|"消息"| C2["Agent B"] -->|"消息"| C3["Agent C"]
    end
    GRAPH -->|"更灵活"| BENEFIT["支持非顺序工作流\n精确控制状态转移\n可并行分支"]
为什么推荐图式框架：
  • 每个 Agent 是图节点，连接是边，通过边控制状态转移——支持非线性、循环、条件分支工作流
  • 可以精确定义转移条件（哪个 Agent 在什么条件下被激活），比对话式框架更可控
  • 天然支持并行分支（从一个节点出发的多条边可以并行执行）

6. Multi-Agent 通信的形式化描述

6.1 消息传递模型

Multi-Agent 系统可形式化为消息传递图 $G = (V, E, \mathcal{M})$：

组件定义说明
$V = \{a_1, \ldots, a_n\}$Agent 集合每个 Agent 有角色、工具集、局部记忆
$E \subseteq V \times V$通信边有向边 $(a_i, a_j)$ 表示 $a_i$ 可向 $a_j$ 发消息
$\mathcal{M}$消息空间消息类型：工具调用结果 / 自然语言 / 结构化数据

6.2 可见性矩阵

$$V_{ij} = \begin{cases} 1 & a_j \text{ 的消息对 } a_i \text{ 可见} \\ 0 & \text{否则} \end{cases}$$

三种架构的可见性矩阵模式：

  • 独立代理网络：$V = \mathbf{1}_{n\times n}$（全 1 矩阵，全局可见）
  • 中介者模式：只有中介者的行/列为 1，其余 Agent 间为 0
  • 分层团队：块对角矩阵（层内可见，层间只通过接口暴露）

7. 工程实践注意事项

问题说明解决方案
上下文爆炸多轮对话 + 多 Agent 历史快速超出 context window工作记忆压缩（MemAgent）/ 选择性共享 / 分层架构
执行时间过长分层代理层级过多导致串行延迟积累路由 Agent 用小模型加速；无依赖子任务并行
架构混合三种架构不互斥，实际中可组合如分层团队内部使用共享草稿板
调试困难Agent 间交互路径复杂，失败定位难结构化日志 + 可视化执行图（LangSmith 等）

8. 核心洞见与实践建议

架构选择决策树
  • 任务间依赖强、需要互相监督 → 独立代理网络（全局共享草稿）
  • 任务分类路由明确、各任务相对独立 → 代理中介者模式
  • 任务规模极大、需要多层级分解 → 分层代理团队
  • 需要精确控制流、非顺序工作流 → 图式框架（LangGraph）
Environment 抽象的工程价值
MetaGPT 的 Environment 类是工程实践中最可复用的抽象——把"多 Agent 系统的全局状态"封装成一个对象，Agent 只通过 read/write Environment 与外界交互，而不是直接对话。这极大降低了 Agent 间的耦合度，新增 Agent 只需实现 Environment 接口，无需修改其他 Agent。
状态机 vs 图式框架的选择
状态机（GameAgents 风格）适合有限、明确的状态转移（如游戏场景）；图式框架（LangGraph 风格）适合动态、条件复杂的工作流。实际 Agent 工程中，大多数任务更适合图式框架——因为 Agent 的行为空间很难预先穷举，图中的条件边可以优雅地处理运行时决策。
