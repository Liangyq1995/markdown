第7章 容错（Fault Tolerance）

核心主线规模使故障必然 → 系统可靠度乘性衰减 → Young-Daly checkpoint 最优间隔 → 分布式 checkpoint / 弹性恢复 → SDC 的 check-and-verify
学习目标从组件 MTBF 推算 fleet MTBF 与 checkpoint 频率；区分 fail-stop 与 Byzantine/SDC；设计可验证的恢复路径

一、规模算术：故障从例外变常态

单卡 MTBF 50,000 h（~5.7 年）看似可靠；10,000 GPU 同构 fleet 仅 GPU 项：

$$\text{MTBF}_{\text{system}} = \frac{\text{MTBF}_{\text{component}}}{N} = \frac{50{,}000}{10{,}000} = 5\ \text{h}$$

加入 PCIe、电源、网络域后，10k H100 集群实测级联 $\lambda_{\text{system}} \approx 0.271$ 次/h → MTBF ≈ 3.7 h（~6.5 次/天）。Llama 3 在 16,384 H100 上 54 天 419 次故障 → 观测 MTTF ~3.1 h，与理论 1/N 曲线吻合。

系统可靠度：$R_{\text{system}} = (R_{\text{component}})^N$

独立组件串联：任一失效则系统失效。

手算：单 GPU 可用性 99.9%（$R=0.999$），$N=1000$：

$$R_{\text{cluster}} = 0.999^{1000} \approx 0.368$$

即任意时刻全集群同时可用概率仅 36.8%——不能指望硬件「全绿」，软件必须自动吸收失效。

二、Young-Daly：checkpoint 最优间隔

$$\tau_{\text{opt}} = \sqrt{2 \cdot T_{\text{write}} \cdot \text{MTBF}_{\text{system}}}$$

$T_{\text{write}}$ 不是小进程 dump——70B Adam 全状态 checkpoint 可达数百 GB；175B 超 1 TB。总浪费 = checkpoint 开销 + 期望重做工作，U 形曲线在 $\tau_{\text{opt}}$ 取最小。

算例

$\text{MTBF}_{\text{system}}=5$ h，$T_{\text{write}}=15$ min = 0.25 h：

$$\tau_{\text{opt}} = \sqrt{2 \times 0.25 \times 5} = \sqrt{2.5} \approx 1.58\ \text{h}$$

集群加倍 → MTBF 减半 → 最优间隔仅 ×$\sqrt{2}\approx1.4$，不必线性加倍 checkpoint I/O；但需更快存储压 $T_{\text{write}}$，否则 checkpoint tax 吃掉算力。

三、故障分类与检测

类型表现ML 后果应对
瞬态丢包、节流、单 bit flip梯度污染、loss 漂移重试 + 统计监控
Fail-stop进程/GPU 无响应AllReduce 全员阻塞heartbeat + checkpoint 重启
Byzantine / SDC仍响应但数值错优化轨迹 poison冗余计算、梯度范数监控、check-and-verify
correlated机架 PDU、交换机、驱动 bug冗余同域失效跨 rack/region 副本

3.1 Fail-stop 与 heartbeat

$$T_{\text{timeout}} = H + k\sigma_d, \quad k \approx 3\text{–}5$$

同步训练中一个 rank 沉默 → 9999 GPU 空等计费。过紧 timeout 会把正在写 checkpoint 的慢 rank误判为故障；过松则浪费检测窗口内的算力。

3.2 SDC 与 check-and-verify

Check-and-Verify 机制

对每块 gradient shard / AllReduce 结果计算 CRC 或 hash，跨 rank 比对或做冗余归约；digest 不一致则阻塞 optimizer step。AllReduce 默认假设「活着即正确」——fleet 规模下必须「Trust, but verify」。

100k GPU 暴露算例：单卡 SDC 率 $10^{-6}$/h，2 s 步长 → fleet 暴露 ~56 GPU·h/步，$\Pr(\ge1\ \text{SDC}) \approx 0.0056\%$/步 → 约每 18,000 步（~10 h）一次静默错误。无校验则半天内参数被污染；Google TPU 用 gradient norm spike + 热备 drain 可疑芯片。

指数位单 bit flip 可把梯度放大 $10^{38}$ 量级——loss 曲线看似「训练正常」实则已毁。SDC 比 crash 更危险：无异常栈，只有 rollback-worthy checkpoint。

四、恢复与 ML 特有经济性

4.1 分布式 checkpoint 与弹性

  • 同步 checkpoint：全员 barrier 后写；简单但拉长步时
  • 异步 checkpoint：后台线程写上一版；需版本化防半写读
  • TorchElastic：rendezvous 重建进程组，$N_{\min}$–$N_{\max}$ 弹性伸缩

4.2 训练 vs 服务

70B LLM 故障成本量级

25k GPU × \$2/GPU·h ≈ \$1.2M/天算力。丢 24 h 进度 ≈ \$1.2M + 排期延误。Checkpoint 350–700 GB；RecSys 连续训练更怕embedding 新鲜度而非 checkpoint 大小。

4.3 故障注入

TensorFI / NVBitFI / PyTorchFI 在 tensor 层注入；staging 应用 chaos 分区、延迟、kill pod。软件注入快但可能跳过 ECC 掩蔽——生产声明需硬件校准（beam test、Fidelity 映射）。

五、章节总结

三条规则

  1. 规模上故障是连续背景，不是工单例外
  2. 用 $\tau_{\text{opt}}=\sqrt{2 T_{\text{write}} \cdot \text{MTBF}}$ 定 checkpoint；投资高带宽 checkpoint 存储
  3. 训练容忍分钟恢复；服务要冗余与快速 failover；SDC 需 check-and-verify，不能仅靠 restart
容错花出去的是协调算力与 I/O，买回的是 fleet 在统计必然故障下仍能完成 months-long run 的能力——同一套基础设施还解锁 spot 实例（第 8 章）。
