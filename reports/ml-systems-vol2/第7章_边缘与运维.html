一、开篇：同一模型，两种物理

Vol.1 灾害响应（DR）案例在同一 MobileNet 损伤检测模型上走完六阶段 workflow——其中部署端形成两极：

  • 数据中心（第 6 章）：70B LLM @ 8×H100，continuous batching，~900 tok/svalid，$/M tok 驱动容量
  • 边缘（Jetson）：batch=1，p99 180 ms，无队列，coin-cell 级功耗预算

二者都叫「serving」，优化目标几乎正交：舰队问 $/token 与 SLO headroom；边缘问 mW、KB 与离线可用。本章沿这条光谱展开——先推到网络边缘的 opposite physics，再拉回数千模型共享 GPU 池的平台运维：数据不必集中，但监控、版本与 Canary 必须集中。

二、边缘约束：mW 与 KB 先于 TFLOP/s

热节流：手机 sustained 性能可低于峰值 40–60%。静态内存：TinyML 无 malloc——Vol.1 MobileNet INT8 3.5 MB 仍超 524 KB 信封 6.7×，须 NAS 级架构（DS-CNN ~500 KB）。DR Jetson 验收仍是子群精度 + p99，非 FLOPs——与第 6 章 Offline 峰值是同一类误区。

DR 边缘验收（Vol.1 延续）

  • 农村子群灵敏度 ≥ 0.90（全局 0.95 不够）
  • p99 推理 < 2000 ms（batch=1，无排队掩盖）
  • PSI < 0.20 触发调查（见第 8 章完整链）

三、联邦学习：边缘上的训练传输层

当原始数据不可出设备（合规/带宽），训练 loop 从「集中梯度」变为「周期性权重上传」。FedAvg 是边缘与数据中心之间的传输协议——不是新算法，是把第 4 章 AllReduce 换成异步、稀疏、隐私约束的聚合。

$K$ 客户端，各 $n_k$ 样本，总 $n = \sum n_k$。本地训练后上传 $w_k$，服务器聚合：

$$w_{t+1} = \sum_{k=1}^{K} \frac{n_k}{n} w_k^{(t+1)}$$

三客户端 + 通信成本

A/B/C 各 1000 样本 → 权重各 1/3。若 C 仅 100 样本仍等权平均，C 梯度被放大 10×——须 $n_k/n$ 加权。

MobileNet ~14 MB FP32/轮 × 1000 设备 = 14 GB/轮 上行（聚合前）——须 INT8 权重、稀疏更新、client 采样（每轮 10% 参与）。通信成本 = 模型大小 × 参与设备 × 轮次，与第 4 章 collective 定价同构，只是 $\alpha$ 更大（蜂窝/WiFi）。

3.1 差分隐私：与第 8 章共享的 Pareto 旋钮

$$(\epsilon, \delta)\text{-DP}: \Pr[\mathcal{M}(D) \in S] \leq e^\epsilon \Pr[\mathcal{M}(D') \in S] + \delta$$

梯度裁剪（范数 $\leq C$）+ 高斯噪声。$\epsilon$ 越小隐私越强、收敛越慢——移动键盘典型 $\epsilon \approx 4$–8。FL 与数据中心 DP-SGD 共享数学；差异在设备掉线、straggler、异构算力（100× 差距）使同步轮次被最慢者拖住 → 异步 FL 或 tier 分组。

3.2 边缘 straggler 与安全聚合

  • 掉线：每轮仅采样 fraction 设备（FedProx 缓解异构）
  • 安全聚合：服务器只见加密权重和，防逆向单客户端
  • Selekt 等：按设备贡献/算力分层，避免 edge straggler 绑定全局步长

边缘闭环：本地推理满足 DR p99 → FL 更新模型 → DP 约束上传 → 下一轮本地验收。数据不出设备，但模型版本与 drift 信号仍须回平台——否则数千边缘节点各自 silent fail，中心无从感知。

四、从单模型到 N 模型平台

Vol.1 第 14 章：一个模型 + MLflow + Prometheus。规模化后（Google/Netflix 量级）：数千模型共享同一 GPU 舰队——瓶颈从 kernel 变为调度、artifact 版本爆炸、监控基数（cardinality）。边缘 FL 产生的是「很多弱连接模型」；数据中心产生的是「很多强竞争 replica」——平台层用同一套 registry + Canary 统一治理。

五、Multi-model serving 与密度经济学

10 LLM × 6×H100 争用

10 个模型各需 1×H100 满负载；舰队仅 6 卡。Naive 一模型一 Deployment → 4 模型永久 pending。

Multi-model serving（Triton/vLLM multi-LoRA）：单卡加载基座 + 多 LoRA adapter（~100 MB/个）→ 6 卡服务 10 模型。新 SLO：adapter swap 延迟（冷加载 200 ms–2 s）须写入 per-model p99，不能与 steady-state ITL 混报。

$$\text{Effective GPU Util} = \frac{\sum_i \text{GPU-seconds}_{\text{useful},i}}{\text{Fleet GPU-seconds}_{\text{provisioned}}}$$

训练 fleet Goodput 30–55%（第 5 章三因子分解）。推理 fleet 若 SLO 强制 headroom，账面 40% 可能是健康态——与训练「越高越好」不同。浪费来源：调度碎片 10–25%、checkpoint I/O 5–15%、多租户空泡 10–20%。

六、舰队 CI/CD、Canary 与 PSI 基数

Vol.1 Istio weight: 95/5 仍适用，但须 fleet-wide metric 按 model_id 聚合——全局 p99 掩盖单模型回归。触发：5 min 内 error_rate > 基线 + 0.3% → 自动 rollback artifact digest。

6.1 监控基数：500 模型不能全量 PSI

500 模型 × 20 特征 × 10 分位 = 10⁵ 时间序列——TSDB OOM。策略：

  • Top traffic 模型：全量 PSI + KS（Vol.1 四箱 $D_{\text{crit}}=0.061$ @ n=500）
  • 长尾模型：weekly batch + 采样 1% 请求
  • 边缘回传：聚合 drift 统计，非原始特征（隐私 + 带宽）

6.2 平台工程与组织

  • Internal ML Platform：统一训练提交、registry、feature store SLA
  • Conway 定律：Central platform 提供 GPU 池 + CI 模板；product team 拥有 model metrics
  • Incident：SEV 分级 + blameless postmortem；LLM 舰队保留 prompt/response 采样审计链（第 8 章）

七、章节总结

部署光谱上的闭环

  1. 边缘：mW/KB/离线；验收 = p99 + 子群精度，非 TFLOP/s
  2. FL：FedAvg $n_k/n$ + 通信 = 模型×设备×轮次；DP 与第 8 章同框架
  3. 平台：N 模型 = 调度 + 版本 + 监控基数；LoRA 密度换 swap SLO
  4. Canary/PSI：Vol.1 单模型流程扩展到 per-model_id；长尾分层采样
  5. 统一 registry：边缘与数据中心模型汇入同一 digest + rollback 链
边缘把 serving physics 推到极限；舰队 MLOps 把「上线后仍可靠」推到 N 模型规模——同一 DR 模型，Jetson 验 p99，平台验 drift。
