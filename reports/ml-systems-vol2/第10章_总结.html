一、从模型到 Fleet：设计对象的转变

前沿模型成为生产系统，当且仅当数千 accelerator、fabric link、存储层、scheduler、serving replica、安全控制与治理检查作为一台机器运转。任一层次可 bind 全系统：

  • 慢 checkpoint → 浪费训练窗口
  • 拥塞 fabric → 抹平 scaling gain
  • underprovision serving → 质量变成用户可见 latency
  • 未度量的责任约束 → 技术就绪后仍无法部署

基础 ML 工程优化 artifact（权重）；分布式 ML 工程优化使 artifact 在规模上存在的 infrastructure——数据中心、分布式协议、治理框架，将静态 checkpoint 变为全球 live service。

自底向上：Infrastructure 设定物理速率与上限 → Distributed ML 将上限转为 coordination 成本 → Deployment 将模型变为带 latency/availability/cost 义务的服务 → Governance 决定服务能否保持 secure、robust、sustainable、accountable。

专业习惯（C³）：识别 binding 的是 compute、communication 还是 coordination，跨层追踪直到优化对象是 fleet 而非单模型。

三、Fleet Law 与 C³ 映射

$$T_{\mathrm{step}}(N) = \frac{T_{\mathrm{compute}}}{N} + T_{\mathrm{comm}}(N) + T_{\mathrm{sync}}(N) - T_{\mathrm{overlap}}$$
Fleet Law 项C³典型绑定场景
$T_{\mathrm{compute}}/N$Compute单卡算力、MFU、roofline
$T_{\mathrm{comm}}(N)$CommunicationRing AllReduce、MoE all-to-all
$T_{\mathrm{sync}}(N)$CoordinationStraggler、barrier、scheduler 决策

Ring AllReduce 带宽项：每 rank 约 $2(N-1)M/N$ 字节（$M$ 为梯度大小）。Horovod 经典结论：$N$ 增大时系数 → $2\times$ message volume/rank，仍 bandwidth-optimal。

量化锚点

  • Tail latency：fan-out 100 服务器，p99 至少一台慢 → 63.4% 概率拖尾（Dean & Barroso 2013）
  • Llama 3：16,384 GPU、54 天、419 次意外中断 → 约每 3.1 h 一次 → checkpoint/elastic 是一等设计维
  • Scaling：8 GPU 94% efficiency → 8,000 GPU 38%——小集群 profiler 无法预测 straggler/sync 主导行为
  • Decode：H100 decode 仅 ~12% 峰值 FP16 tensor-core 吞吐，97% utilization 仍 memory-bound → 量化/KV 优化而非加 FLOP

六原则冲突而非独立：通信优化可能增 failure exposure；碳感知调度增 serving slack；公平监控增 latency——overhead 只能位移，不能消失。工程是在六约束内找可接受 trade-off。

Napkin Math：100× 效率来自哪？

目标 100×：硬件 4× × 算法（稀疏/蒸馏）2.5× = 10× → 剩余 10× 须来自 orchestration（路由、cache reuse、comm/compute overlap、输出验证）。

增益相乘非相加——假设线性叠加会系统性低估系统层贡献。

Composition 时代：多 model + retrieval + tool + verification 协调——binding 约束会迁移，但 habit 不变：measure orchestration overhead、state movement、failure propagation、latency budget、governance evidence 作为系统本身的一部分。

六、三维 Competencies

能力 = 约束下的工程判断，非技术 checklist。三层 governing question：

层级Governing Question掌握标志
分布式系统如何让大于单机的 workload 像一台机器协调？Ring AllReduce 流量系数；fat-tree 选型；从 MTBF×fleet size 推导预期故障 cadence；Llama 3 级「每数小时一次中断」设计 checkpoint
生产运维训练好的模型如何在 live traffic 下持续交付价值？Serving tax、continuous batching；性能 + semantic drift 双监控；canary/shadow；p99 green 但 CTR 降 12% ≠ 成功运维
治理谁承担决策成本与风险？DP 训练迭代预算；子群 bias audit 管道；碳感知调度；fairness/carbon reshape 数据管道与 scheduler——非训练后插件

治理/可持续如何 reshape 架构（各一例）

  • + Differential Privacy：训练需额外迭代 + 噪声 → batch/learning rate 与收敛预算重算
  • + Bias auditing：敏感属性 escrow 服务、子群 metric 写入 serving path 旁路
  • + Carbon-aware scheduling：scheduler 目标函数加入 time-varying CI，非仅 cost/latency

68% MFU @ 4,096 GPU 但无 drift 监控、无 canary、跳过 fairness audit → 不是完整生产系统：缺口在 Deployment + Governance 层，非训练层。

七、Fallacies 与专业纪律

  • Fallacy：更快 model = 更好 system——kernel 快但 checkpoint/网络/contention/governance 风险恶化则 fleet 更差
  • Pitfall：优化一层、把代价藏到未测量层——大 batch ↑ util ↓ tail；压缩 ↓ comm ↑ accuracy risk；碳调度 ↓ 排放 ↑ serving slack
  • Pitfall：治理/可持续当作外部 review——retrofit audit trail、demographic monitoring、deletion workflow 比设计期嵌入贵一个数量级
Fermi 对比：~25,000 H100 cluster ~17.5 MW、~$2.47\times 10^{19}$ peak FLOP/s vs 人脑 ~$10^{14}$ synaptic ops/s @ ~20 W——raw 吞吐超越但操作语义不等价，megawatt 级功耗使 efficiency 仍是 frontier。

八、三 Agenda 与章节总结

Vol.2 工程议程

  1. Systems that scale——通信、容错、基础设施天花板
  2. Systems that endure——serving、MLOps、静默失败检测
  3. Systems that serve——安全、公平、碳、auditability 写入 operating path

Key Takeaways

  1. Fleet 是对象：六原则归约为一个习惯——跨 infrastructure、communication、coordination、serving、governance 追踪 binding 约束
  2. Scale 改变概率模型：100 服务器 p99 tail 63.4%；419/54 天 failures——非「大一点的单节点」
  3. Orchestration = capability：100× 目标 silicon+算法 alone 不够，剩余 10× 在 fleet logic
  4. Obligations in the path：安全、隐私、公平、碳、auditability 是生产约束，非外部审查

Iron Law 管单节点物理；Fleet Law + 六原则管 networked collective。Vol.2 Closing：engineer intelligence 的单位是fleet——能在约束下 scale、endure，并将社会与环境义务 engineer 进 operating path 的工程师，才是 ML systems at scale 的完整定义。
