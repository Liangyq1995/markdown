核心问题 如何将代码从 LLM 的"生成目标"重新定位为智能体系统的"运行基底（harness）"，并围绕这一视角系统梳理接口层、机制层与多智能体扩展层的方法体系

关键词 Agent Harness · Coding Agent · Harness Engineering · Agentic AI

1. 核心问题与动机

大型语言模型（LLM）在代码理解与生成方面已取得显著突破——从竞争性编程到仓库级软件工程均有出色表现。 然而，主流研究长期将代码视为"输出物"：给模型一个问题，模型产出一段程序。 这种视角在单轮代码补全场景中足够，但在越来越普遍的长链任务型智能体系统中，它忽视了代码的另一面： 代码不仅是输出，更是推理的执行基底、行动的编程接口和环境状态的可检查表示。

核心论点

"Code is no longer only a target output. It increasingly serves as an operational substrate for agent reasoning, acting, environment modeling, and execution-based verification."

— 论文摘要原文

1.1 现有综述的视角缺口

现有代码生成综述通常按任务类型（函数级、仓库级、竞争编程）或技术手段（微调、提示工程、强化学习）组织， 但它们均将代码定位为终态产物，缺乏对"代码在智能体闭环中发挥何种结构性作用"的系统回答。 本文提出代码作为智能体载体（Code as Agent Harness）的统一视角， 旨在填补这一概念空白：研究焦点从"如何产生正确程序"转向"代码如何支持可靠的闭环智能体行为"。

1.2 三要素区分

论文在 harness 视角下区分了长链智能体系统的三类要素，避免概念混淆：

模型内部能力

推理、感知、规划、模拟与评估——这些是模型权重中内含的能力，不是代码本身。

系统提供的 Harness 基础设施

工具、API、沙箱、内存系统、验证器、权限边界、遥测、工作流——由人类工程师预先设计并连接模型输出与外部行动。

智能体发起的代码制品

智能体在任务执行循环中自主创建、执行、修订、持久化和共享的交互性代码对象，如回归测试、临时工具、DSL 程序、可复用技能等。

本文聚焦第三类——智能体发起的代码制品，以及模型能力如何通过与 harness 基础设施的交互来构建和演化这些制品。 代码的可执行性（executability）、可检查性（inspectability）和状态保持性（statefulness）使其天然成为 harness 接口的最优媒介： 可执行性意味着 harness 可以验证模型意图；可检查性意味着失败可被诊断并反馈；状态保持性意味着智能体的交互历史在步骤间不会丢失。

2. 背景与相关工作

2.1 领域全景

代码智能体的研究演进可以大致分为三个阶段： （1）代码生成时代（2021–2022）：Codex、AlphaCode 确立了 LLM 在代码生成上的基础能力，代码被视为纯输出目标； （2）工具增强推理时代（2022–2023）：PAL、PoT、ReAct 将代码/工具调用引入推理链，让代码承担计算委托角色； （3）智能体系统时代（2023–至今）：SWE-agent、OpenHands、Claude Code 等系统将代码与仓库、沙箱、测试、反馈闭环结合，代码开始扮演运行载体角色。 本文正是对第三阶段进行系统性综述。

4. 关键技术详解

4.1 代码作为接口层的机制

接口层回答的核心问题是：什么媒介连接模型与任务环境？ 论文论证代码是最优答案，原因在于其三个不可替代的属性：

  • 可执行性（Executability）：模型输出变成具有形式可验证结果的操作，harness 可以确认模型意图是否达成。
  • 可检查性（Inspectability）：中间计算以结构化轨迹暴露，harness 可以读取、存储、诊断并反馈失败。
  • 状态保持性（Statefulness）：演化中的程序以持久可修改形式跨步骤表示任务进度，智能体的交互历史不会在步骤间丢失。

4.1.1 代码用于推理（Code for Reasoning）

早期纯链式思维（Chain-of-Thought）强迫模型在单一文本流中同时完成问题分解与符号计算，不仅可靠性低， 还让 harness 几乎无法在中间状态进行验证。代码推理接口将两者解耦： 模型提出过程，harness 执行并观察运行时行为，将执行结果反馈进后续推理。 三种范式逐步递进：

程序委托推理流程（Program-Delegated Reasoning）

Input: 问题 Q

// Step 1: 模型生成解题程序

prog = LLM.generate_code(Q)

// Step 2: 外部解释器执行

result = interpreter.execute(prog)

// Step 3（迭代范式）: 执行结果作为奖励/反馈进入下一轮

if verify(result) == False:

prog = LLM.refine(prog, result)

return result

形式验证范式通过 Lean、Isabelle、Coq 等证明助手将推理接口从自然语言代码扩展至机器可检验的形式语言， 每个推导步骤均可由验证器审查。DeepSeek-Prover-V2、Kimina-Prover 等系统在数学定理证明上已达到竞赛级水平。 从 harness 角度看，形式语言不仅是推理工具，更是约束、认证和审计智能体行为的可执行合同。

4.1.2 代码用于行动（Code for Acting）

行动接口的核心挑战是接地（grounding）：将抽象的语言输出映射为尊重目标环境约束的可执行操作。 与推理接口不同，行动在部分可观测的动态环境中执行，失败可能通过无效状态转换、延迟反馈或静默错误出现。 代码在此扮演模型与感知模块、可供性估计、运动规划器、API、安全层之间的中介： 它序列化观测、调用规划模块、调用可执行行动，并将验证结果反馈给 harness。

三类子范式依次递进：接地技能选择（SayCan、KnowNo）从预定义技能库中选择匹配； 程序化策略生成（CaP/Code-as-Policies、RoboCodeX）直接将 Python 程序作为控制接口； 终身代码智能体（Voyager、LYRA、ViReSkill）使可执行技能库随时间持续扩展和进化。

4.1.3 代码用于环境建模（Code for Environment）

若不对环境进行显式表示，状态只能通过文本观测间接暴露给智能体，导致状态转换难以追踪、结果难以验证。 代码通过四类制品解决这一问题：程序状态（仓库、DOM 树）、执行轨迹（日志、测试结果）、 可执行模拟器（WorldCoder、CWM）以及可编程评估环境（SWE-bench、InterCode）。 其中可验证环境构建方向（SWE-smith、EnvScaler）进一步将环境接口本身视为可合成、可验证的制品。

4.2 规划与记忆机制

4.2.1 四类规划范式

4.3 工具使用与反馈驱动优化

4.3.1 四类工具使用范式

工具将智能体连接至治理的可执行接口，包括 API、仓库、终端、沙箱、验证工具和工作流编排器。 论文从工具面向的意图角度进行分类：

  • 功能导向（Function-Oriented）：标准 API/函数调用，以工具描述为接口契约（ToolCoder、ToolNet）。
  • 环境交互（Environment-Interaction）：连接终端、浏览器、IDE 等运行时环境（SWE-Agent、OpenHands）。
  • 验证驱动（Verification-Driven）：测试框架、静态分析工具、形式验证器（AutoSafeCoder、QualityFlow）。
  • 工作流编排（Workflow-Orchestration）：跨工具跨智能体的协调与路由（ChatDev、FlowGen）。

4.3.2 Plan-Execute-Verify（PEV）闭环

论文将迭代调试重新定义为更广泛的PEV 控制过程，强调可靠性来源于治理的状态转换，而非更好的修复提示： 

graph LR

该框架将静态分析、运行时错误、测试、评论、自我反思和人工审查统一为控制信号， 而非孤立的纠错手段，从而形成调节智能体在可执行程序状态上运行轨迹的"控制论 harness"。

4.3.3 智能体 Harness 工程（Agentic Harness Engineering, AHE）

AHE 将 harness 基础设施本身作为分析和优化的对象，包括工具模式（schema）、规划制品、记忆策略、 检索配置、沙箱设置、验证传感器、权限层和人工审查门控。 其核心基底是深度遥测（Deep Telemetry）： 结构化轨迹连接模型决策、harness 行动、环境状态和结果，使 harness 修订从偶发调试转变为可比较的诊断过程。 进化智能体（Evolution Agent）在此遥测基础上提出、评估并推广 harness 组件修订， 目标是在不降低之前已解决任务性能的前提下提升可靠性、降低成本、加强安全性。

4.4 多智能体协作架构

单智能体面临三重局限：上下文窗口约束（无法持有完整代码库与长历史）、专业化需求（规划、合成、测试、审查难以一人承担）、缺乏独立验证通道（难以可靠检测自身错误）。 多智能体系统通过角色分工、共享代码制品和结构化协作将这些局限一一突破。

4.4.2 工作流拓扑演化

拓扑结构从静态预定义链式（ChatDev 的 Scrum 模式）向自适应目标驱动拓扑演进： EvoMAC 通过工作流拓扑进化（基于交接、空闲角色、循环信号）， FlowReasoner 在运行时动态生成个性化工作流， BOAD 通过目标驱动的自适应层次结构协调定位、编辑、验证角色。 论文进一步提出共享代码中心 Harness 基底（Shared Code-Centric Harness Substrate）的构想： 智能体应通过声明读集、写集、假设依赖、验证义务和冲突策略来共享程序状态，实现事务级语义一致性。

5. 应用场景分析

论文梳理了六大应用领域，在每个领域中代码作为 harness 的三重身份（推理基底·行动接口·环境建模）均有具体体现。

5.1 科学发现专题：程序世界抽象

论文将科研项目建模为部分可观测程序世界 $\langle S, A, T, O, R \rangle$，其中：

  • 状态 $S$ 是包含当前假设、文献、代码制品、中间数据集和实验观测的结构化程序记忆；
  • 行动 $A$ 是类型化代码表达式：文献检索、符号/数值求解器调用、实验脚本生成、机器人控制命令；
  • 转移函数 $T$ 由 Python 解释器、Lean 核、量子化学包或机器人合成器实现；
  • 奖励 $R$ 编码新颖性、可重复性和统计显著性等研究标准。

典型案例包括：AI Scientist v2（将整篇 ML 论文表示为单一可执行轨迹）、 Coscientist（自主规划并执行钯催化偶联反应）、 Virtual Lab（在几天模拟会议中设计出 92 个 SARS-CoV-2 纳米抗体，其中 2 个获实验验证）。

7. 开放挑战与未来方向

论文在第 5.2 节详细阐述了七项开放挑战，聚焦于将 harness 视为一等系统组件后涌现的新问题， 而非单纯的基础模型能力局限。

5.2.1 Harness 级评估与 Oracle 充分性

现有评估指标混淆了基础模型能力、harness 质量、工具可靠性、反馈信息量和环境难度。 需要定义衡量执行可靠性、反馈质量、上下文持续性、安全性、协调性和可重放性的 harness 级指标。 核心瓶颈是 Oracle 充分性：评估器只能捕获窄化的可执行代理，而非完整意图规范。

5.2.2 超越可执行反馈的语义验证

代码通过测试不等于功能正确——测试集可能不完整，静态分析可能过度近似， GUI 检查器可能遗漏不可接受的中间行动。 未来 harness 需要组合多层验证制品（单元测试、集成测试、模糊测试、形式规范、人工审查）， 并让每一层声明其验证范围和置信度，构建认知感知的反馈循环。

5.2.3 无回归的自进化 Harness

固定 harness 对任务分布变化的适应性有限，但无约束自我修改带来过拟合、安全降级和稀有任务回归风险。 每项 harness 变更应像安全关键系统的代码变更一样携带变更合同： 目标失败模式、预期改善、必须保留的不变量、可证伪的评估标准和回滚语义。

5.2.4 事务性共享程序状态与语义冲突解决

多智能体系统中，现有同步机制通常同步制品而非假设。 不同智能体可能基于过时的仓库快照规划、测试更新的补丁，或记住过时的不变量。 需要语义事务机制：声明读集/写集/假设依赖，在计划、测试、检索证据、权限和记忆条目层面检测冲突， 并支持语义合并、回滚和依赖感知锁定。

5.2.5 人工监督与安全问责作为 Harness 状态

安全性不能委托给基础模型或仅编码为自然语言指令。 Harness 需要作为模型意图和真实世界后果之间的安全治理层： 按风险分类行动、强制权限层级、对不可逆或外部后果性转换要求人工批准， 并将每次批准/拒绝作为持久的 harness 状态转换记录。

5.2.6 多模态 Code-Harness 系统

GUI 智能体依赖截图、无障碍树和渲染界面状态；具身智能体依赖深度图、力/触觉信号和姿态。 未来 harness 需要多模态上下文压缩机制保留与任务相关的视觉证据， 以及将感知、行动和验证连接的接地合同（Grounding Contracts）。

5.2.7 走向 Harness 工程科学

目前 harness 设计高度依赖工程直觉和试错迭代，缺乏理论基础和系统性评估方法论。 需要建立 harness 组件的变更算子、遥测标准、跨任务演化 harness 评估、安全不变量执行框架， 以及将 harness 改善与基础模型改善区分开的因果证据。

8. 核心洞见与读后评注

洞见一：从"生成目标"到"运行基底"的范式跃迁

本文最重要的概念贡献是将代码的角色从"LLM 产出的制品"重新定位为"智能体系统赖以运行的基底"。 这不是学术措辞的变换，而是研究问题的根本转变： 前者关心"模型能生成多正确的代码"，后者关心"代码基底如何支撑可靠的闭环行为"。 这一视角转换意义深远——它将代码评估从 pass@k 等静态指标推向轨迹效率、验证强度、恢复能力等 harness 级指标， 与工业界对智能体可靠性的关切高度契合。

洞见二：三层结构的内在一致性

接口→机制→扩展的三层框架并非简单的功能分类，而是一套内在逻辑自洽的体系： 接口层确立了代码的三重功能（推理·行动·环境），机制层解决"如何使代码接口在长时间跨度上保持可靠"， 扩展层解决"如何让代码成为多智能体可共享的协调基底"。 每层的设计决策都约束了下一层的可能形态，这种嵌套一致性是该综述框架优于简单分类综述的关键。

洞见三：PEV 循环是 Harness 可靠性的核心机制

论文将"迭代调试"重新诠释为受治理状态转换驱动的 Plan-Execute-Verify 循环， 这一视角的价值在于：它明确指出可靠性来源于治理结构，而非更聪明的修复策略。 这对实践的启示是：单纯改进 LLM 的自我修复能力并不足以构建可靠智能体系统， 必须同时设计更强的 oracle（测试覆盖率、形式规范），更严格的权限边界，以及明确的 HITL 门控。 这与 Anthropic Claude Code、OpenHands 等工业系统的实践经验完全吻合。

洞见四："共享状态一致性"是多智能体的真正瓶颈

论文对多智能体系统的最深刻批评是：现有同步机制通常同步制品而非假设。 这个观察点非常精准——Git 风格的文件冲突检测无法捕捉"智能体 A 基于测试 T1 规划，智能体 B 已删除 T1"这类假设级冲突。 论文提出的事务性共享程序状态模型（声明读集/写集/假设依赖）是一个颇具远见的方向， 但实现路径仍非常模糊，尤其是"语义冲突解决"在实践中极难自动化，这是该方向最大的开放问题。

洞见五：局限性——综述广度与深度的权衡

本文以 42 位作者的规模覆盖了极广的领域，但不可避免地在每个子领域的深度上有所牺牲。 例如，"具身智能体"章节的硬件约束分析、"科学发现"中的数据质量问题、 以及"个性化推荐"中多方利益冲突的伦理维度，均点到为止。 另一个局限是评估方法本身：论文敏锐地指出现有评估指标的不足，但自身也未提出具体可操作的新指标体系， 这或许是下一篇工作的切入点。 此外，论文的 harness 视角虽然统一，但可能过度依赖"代码中心"这一假设—— 在视觉感知主导的具身场景和流式多模态场景中，代码的"统一媒介"地位仍有待验证。

洞见六：对 Claude Code 等工业系统的映射

论文在多处直接引用 Claude Code、Codex、LangChain、OpenHands 等系统， 说明理论框架与工业实践之间的距离正在快速缩短。 从 harness 工程的角度看，Claude Code 的 AGENTS.md 机制、permission tier 设计、 沙箱执行模式已经在实践中实现了论文所描述的多项 harness 机制， 包括规划作为合同形成、权限分层的 PEV 执行、以及上下文压缩与状态卸载。 这也意味着本文的框架对工程师理解和改进现有系统具有直接的指导价值，而非纯粹的学术整理。
