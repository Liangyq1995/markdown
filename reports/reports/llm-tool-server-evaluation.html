0. 使用方视角概述

0.1 两类核心使用场景

我们以离线数据生产方身份使用工具服务器：大批量调用工具生成训练数据或产生训练轨迹，不直接服务线上用户。两类场景的侧重点有所不同，但共同依赖离线工具与在线工具的行为一致性。

📦 离线数据蒸馏
批量执行包含工具调用的 prompt，生成带工具交互轨迹的标注数据，用于监督微调（SFT）或蒸馏训练。数据质量直接取决于工具输出与在线一致。

核心关注：结果确定性、与在线对齐、高吞吐、无副作用
🧠 RL 训练 Rollout
强化学习框架以大规模并行 episode 方式批量调用工具，生成训练轨迹并计算奖励。工具行为的一致性直接影响奖励信号的稳定性。

核心关注：状态隔离、确定性、高并发、Fail-Fast
维度离线数据蒸馏RL 训练 Rollout
调用模式批量串行或适度并行，离线作业大规模并行 episode（数百~数千并发）
对延迟敏感度中等（影响数据生产吞吐）高（单步超时拖垮整批 rollout）
结果确定性严格要求（数据集可复现）严格要求（奖励信号稳定）
状态隔离任务级隔离Episode 级完全隔离
副作用严禁持久化副作用严禁持久化副作用
在线对齐需求最高（数据分布决定模型行为）高（奖励函数依赖工具输出语义）

0.2 核心架构诉求：离线-在线对齐

离线工具与在线工具的行为偏差是训练数据质量的最大隐患。若离线工具返回的结果、格式、语义与线上不一致，则：

  • 蒸馏数据中的工具调用轨迹与模型实际部署环境不匹配，导致训练-推理分布偏移（Train-Serve Skew）。
  • RL 训练的奖励函数基于离线工具输出打分，而线上行为不同，导致策略在真实环境中效果下降。
核心风险

Train-Serve Skew（训练-服务偏移）：离线工具与在线工具返回不同格式的结果（如字段顺序、截断长度、空值表达方式不同），模型学到的工具使用模式无法泛化到线上，导致部署后工具调用成功率下降。

对齐需要覆盖以下几个层次：

对齐层次具体含义验证方法
结果对齐相同入参，离线与在线返回语义等价的结果（允许时效性差异，如搜索结果随时间变化）对相同 golden query 集，对比离线/在线返回差异率
格式对齐响应的 JSON 字段、嵌套结构、null 表达方式完全一致JSON Schema 双端校验
错误行为对齐相同错误条件下，离线与在线返回相同的 error_code 和 retryable 语义错误注入测试，比对两端响应
版本同步离线工具版本与在线工具版本保持同步，变更时有明确通知机制版本号 API + 变更通知订阅
超时策略对齐离线侧允许超时阈值略宽松，但超时行为（返回格式、错误码）须一致超时场景 E2E 对比测试
  • 必须
    离线工具与在线工具版本严格对应，并提供版本查询接口 工具服务需暴露 version 或等效接口，离线实例版本须与在线保持一致或有明确的版本差异声明，禁止静默升级。
  • 必须
    响应格式（JSON Schema）离线-在线完全一致 字段名称、类型、嵌套结构、null 值表达均须一致；字段顺序若影响下游解析也须固定。格式变更须同步双端，不允许单端先行。
  • 必须
    错误码与错误行为语义离线-在线一致 相同错误条件须触发相同 error_code 和 retryable 值，避免离线数据中学到的错误处理模式在线上失效。
  • 推荐
    提供 golden query 对比测试集，定期验证离线-在线结果一致性 工具服务方维护一组标准测试用例（golden set），供使用方定期跑对比测试，量化离线/在线差异率，差异率超阈值须触发告警。
  • 推荐
    工具变更时主动通知使用方并提供变更说明 工具行为、格式、策略变更须提前通知使用方（邮件/消息/订阅机制），给使用方留出数据回流验证和重新蒸馏的窗口期。
  • 可选
    提供 shadow 模式：离线请求同步打到在线，对比返回差异 高敏感场景下，离线调用同步发送到在线实例做 shadow 对比，实时检测行为偏差，无需等到模型评估阶段才发现。

0.3 核心架构诉求：资源隔离

离线数据生产（蒸馏 + RL 训练）的调用量级远高于在线推理，若共用资源，离线作业的高并发流量会直接影响在线用户体验。资源隔离是保护线上 SLA 的工程前提。

典型事故

RL 训练任务发起 512 并发 rollout，工具服务无隔离，在线推理 P99 延迟从 800ms 飙升至 8s，线上告警触发。事后溯源发现离线训练任务与在线推理共用同一服务实例和连接池。

资源隔离需覆盖以下层次：

隔离层次具体手段说明
服务实例隔离离线部署独立实例或独立集群最彻底的隔离，离线故障不影响在线
配额隔离按调用方 ID 独立分配 QPS / 并发配额共享实例时的次选方案，需精细配额管理
限流隔离离线 token 触发限流时不影响在线 token 的 rate limit 计数避免离线大流量"挤占"在线限流配额
优先级队列在线请求优先级高于离线请求资源紧张时保护在线 SLA，牺牲离线吞吐
网络隔离离线与在线使用独立的网络路径 / 负载均衡防止带宽争抢，尤其适用于高带宽工具（如图像检索）
  • 必须
    离线调用与在线调用使用独立的资源配额 通过独立实例或独立配额组实现，离线任务触发限流时不影响在线请求的配额计数；禁止共享同一限流计数器。
  • 必须
    工具服务方明确声明离线实例的容量规格 离线实例的最大 QPS、并发数、单次请求数据量上限须有文档声明；使用方需在启动大批量作业前确认容量满足需求。
  • 推荐
    提供独立的离线服务实例（而非仅配额隔离） 独立实例是最彻底的隔离手段——离线实例故障、重启、扩缩容均不影响在线实例，反之亦然。
  • 推荐
    在线请求优先级高于离线请求（优先级队列） 资源紧张时，工具服务优先处理在线请求，主动降级离线请求的处理速度；使用方需能感知并适应此降级行为。
  • 推荐
    离线作业启动前提供容量预检接口 使用方在发起大批量作业前，可调用预检接口确认当前离线实例容量是否满足预期吞吐，避免作业启动后才发现资源不足。
  • 可选
    按作业 ID 级别隔离资源配额 支持为每个数据生产作业或训练任务分配独立配额，不同离线作业之间也互不干扰，便于多团队并行使用。

1. 可靠性与性能

1.1 为什么这个维度最关键

在离线数据蒸馏场景中，工具调用失败或超时意味着一条训练样本作废，规模化后造成数据集空洞或重跑成本。对 RL 训练而言，大量 rollout 并行发起调用，任何服务抖动都会放大为训练效率的显著下降，严重时导致奖励信号缺失、episode 被迫丢弃。

核心原则

工具服务的失败模式必须是快速、明确且可恢复的——调用方宁可收到一个清晰的错误，也不能被一个永不返回的请求挂起。

1.2 具体要求

  • 必须
    P99 延迟满足业务 SLA 且有文档声明 离线蒸馏场景通常要求 P99 < 5s（可略宽松于在线）；RL 训练场景视工具复杂度单独约定，但必须明确声明上限。未声明 SLA 的服务视为不满足要求。
  • 必须
    服务可用性 ≥ 99.9% 离线数据生产作业通常不可中途中断，工具服务不可用时需有明确的错误返回，使作业能感知并择机重试，而非静默挂起导致作业假死。
  • 必须
    支持请求级超时控制，超时后服务端主动中止 客户端须能在请求粒度设置超时；工具服务端在超时触发后主动终止处理、释放资源，不产生僵尸请求。
  • 必须
    声明并保证并发容量上限，超限行为明确 文档须注明最大并发数 / QPS 上限；超限时的行为策略（排队 / 拒绝）须明确，调用方需能据此做资源规划。
  • 推荐
    提供健康检查接口（/health 或等效端点） 供调用方做 readiness 探针和自动摘流，服务就绪前应返回非 200 状态。
  • 推荐
    限流触发时返回标准化错误码（429） 触发限流时返回明确的 429 而非通用 500，便于调用方实现退避重试策略。
  • 可选
    暴露 Prometheus 兼容的性能指标 提供延迟分位数、错误率、并发数等指标，便于调用方接入监控告警体系。

1.3 典型反例

反例
  • 工具服务超时时不返回任何响应，客户端连接被挂起直到系统级 TCP 超时（数分钟），整条 agent 链路冻结。
  • 文档中无任何性能数据，使用方只能在生产压测中才能发现容量瓶颈。
  • 并发达到上限时返回 500 + 无 Retry-After，调用方无法区分服务故障与限流，触发错误告警风暴。

1.4 如何验证

  • 对工具服务发起压测，验证 P50/P95/P99 延迟是否符合声明的 SLA。
  • 模拟超时场景（阻塞 handler），确认服务端在指定时间内主动中止并返回超时错误，而非挂起。
  • 并发发送超过声明上限的请求，确认返回 429 而非 500，且响应中包含 Retry-After。
  • 调用 /health 接口，确认在服务就绪前返回非 200 状态码。

2. 错误处理

2.1 为什么错误设计会影响 LLM 行为

工具服务的错误响应会直接注入到 LLM 的上下文中。模糊的错误信息会让模型"乱猜"，产生幻觉性的重试行为或错误的自我纠正；过于详细的错误栈则可能泄露内部实现细节或造成安全风险。好的错误设计需要在两者之间找到平衡：

错误受众需要的信息不需要的信息
LLM（上下文中）发生了什么、如何修正、是否应重试内部堆栈、类名、SQL、文件路径
工程师（日志中）完整堆栈、请求参数、内部状态—

2.2 具体要求

  • 必须
    明确区分可重试与不可重试错误 通过错误码或专用字段（如 retryable: true/false）区分瞬时错误（可重试）与永久错误（不可重试），调用方据此决策。
  • 必须
    错误消息对 LLM 友好，不含内部实现细节 面向 LLM 上下文的 message 字段描述"发生了什么"及"如何修正"，避免裸露的异常堆栈或内部类名。
  • 必须
    统一错误响应结构，跨所有接口一致 所有错误响应至少包含 error_code、message、retryable 三个字段，不因接口不同而格式各异。
  • 推荐
    限流错误附带 Retry-After（毫秒级） 429 类错误在响应 body 中携带 retry_after_ms，使调用方能做智能指数退避而非盲目轮询。
  • 推荐
    每次调用分配唯一 request_id 并在错误中返回 便于调用方将 LLM 上下文中的错误与服务端日志关联，跨服务排查问题。
  • 可选
    批量操作支持部分成功表达 批量操作型工具应区分整体失败与部分成功，而非将所有场景均映射为顶层错误。

2.3 标准错误响应示例

{
  "error_code": "RATE_LIMIT_EXCEEDED",
  "message": "请求频率超出限制，请稍后重试。当前 QPS 上限：100。",
  "retryable": true,
  "retry_after_ms": 2000,
  "request_id": "req_7f3a9c2b"
}
{
  "error_code": "INVALID_PARAM",
  "message": "参数 'query' 不能为空字符串，请提供有效的搜索关键词。",
  "retryable": false,
  "request_id": "req_4d1e8a5f"
}

2.4 典型反例

反例
  • 所有错误均返回 {"error": "Internal Server Error"}，LLM 无法判断是否应该重试，倾向于反复尝试或放弃任务。
  • 参数校验失败时返回 Java 异常堆栈（NullPointerException at com.example.ToolHandler:142），LLM 将堆栈当作上下文信息处理，产生混乱推理。
  • 不同接口错误格式不一致：有的是 {"code": 400}，有的是 {"status": "fail", "reason": "..."}，调用方需为每个接口写定制化解析逻辑。

2.5 如何验证

  • 发送非法参数请求，确认返回结构化错误、retryable: false，且 message 无内部实现细节。
  • 触发限流，确认 retryable: true 且 body 中携带 retry_after_ms。
  • 用 JSON Schema 校验工具覆盖所有接口的错误响应，确认结构一致。
  • LLM 友好性测试：将错误消息原文放入 LLM 上下文，测试模型能否据此给出合理的下一步动作。

3. 安全性

3.1 为什么工具服务需要独立安全防线

工具服务器是 LLM 系统中"有执行能力"的组件，一次未授权调用可能造成数据泄露、系统破坏或资源滥用。LLM 本身容易被提示词注入（Prompt Injection）操控，因此工具服务必须在应用层之外建立独立的安全防线，不能依赖模型的"判断"来防护。

核心风险

攻击者通过精心构造的用户输入让 LLM 调用高权限工具，例如：让搜索工具读取敏感文件，让写操作工具删除数据库记录。工具服务本身是最后一道防线。

3.2 具体要求

  • 必须
    所有接口需认证，不允许匿名访问 支持 API Key、OAuth 2.0 或 mTLS 中至少一种认证机制，功能性接口必须有身份验证，匿名请求直接返回 401。
  • 必须
    基于调用方身份的细粒度授权（按工具粒度） 不同调用方（agent、用户、RL 训练任务）应有独立的权限配置，支持按工具粒度控制访问权限，越权返回 403。
  • 必须
    服务端输入验证，不信任任何客户端参数 对所有入参进行服务端校验（类型、范围、长度、字符集），防止路径穿越、SQL 注入、命令注入等攻击，LLM 传入的参数同样不可信。
  • 必须
    高风险操作有明确的范围限定（防越权横移） 写操作、删除操作等高风险工具调用须有操作范围约束（如仅限特定 namespace / 资源 ID），防止攻击者通过 LLM 实现横向移动。
  • 推荐
    最小权限原则，默认开放最小权限集 高权限工具需额外申请与审批，默认不开放。按需申请的机制防止权限蔓延。
  • 推荐
    传输层 TLS 加密（内网不例外） 所有通信通道使用 TLS 1.2+，内网调用也不作例外，防止中间人截获调用内容（含 LLM 上下文中的敏感信息）。
  • 推荐
    按调用方身份独立计量与限流，异常模式告警 异常调用模式（突发高频、异常参数组合）触发告警或自动熔断，防止 LLM 被操控后的批量滥用。
  • 可选
    高权限操作写入不可篡改的审计日志 记录调用方身份、时间、参数摘要（敏感字段脱敏），支持事后追溯和合规审计。

3.3 典型反例

反例
  • 内网无认证：工具服务在内网部署默认无认证，"反正内网安全"——LLM 被提示注入后可直接调用任意工具，无需任何凭证。
  • 路径穿越：文件读取工具未做路径限制，LLM 被诱导传入 ../../etc/passwd 实现路径穿越读取系统文件。
  • 权限粒度过粗：所有调用方共享同一 API Key，无法区分合法 agent 与被攻破的 RL 训练任务，一旦泄漏影响全系统。

3.4 如何验证

  • 移除认证头后发送请求，确认返回 401 而非有效响应。
  • 使用低权限 token 调用高权限工具，确认返回 403。
  • 发送模糊输入（超长字符串、特殊字符、路径穿越尝试 ../../etc/passwd），确认服务端校验拦截并返回 400。
  • 检查请求日志中是否记录调用方身份（而不仅是 IP），验证审计可追溯性。

4. 可观测性与可调试性

4.1 为什么 LLM 系统特别需要工具级可观测性

LLM 系统的调用链路天然复杂——一次用户请求可能经过 agent 编排、多轮工具调用、上下文管理等多个环节。当最终结果异常时，工程师需要能快速回溯到"是哪次工具调用、传了什么参数、返回了什么结果、耗时多少"。没有工具级可观测性，排查问题只能靠猜，MTTR（平均修复时间）会数倍增加。

4.2 具体要求

  • 必须
    每次调用有唯一 request_id，响应中返回 工具服务生成并在响应中返回 request_id；同时支持调用方透传上游 trace ID，实现端到端追踪。
  • 必须
    结构化日志记录每次调用的完整信息 日志字段至少包含：调用方身份、工具名称、入参摘要（敏感字段脱敏）、耗时、响应状态码、request_id。
  • 必须
    工程师日志与 LLM 错误响应分离维护 面向工程师的服务端错误日志包含完整堆栈和上下文；面向 LLM 的错误响应只含精简的友好信息，两套内容独立维护，互不干扰。
  • 推荐
    支持分布式追踪（W3C TraceContext） 接受并传播 traceparent 头，将工具调用 span 接入 Jaeger / Zipkin 等追踪系统，支持跨服务调用链路还原。
  • 推荐
    关键指标有告警配置（不依赖调用方发现） 错误率、P99 延迟等指标超过阈值时主动告警，工具服务方主动感知问题，而非等调用方反馈后才介入。
  • 可选
    支持按 request_id / 时间范围查询历史调用记录 允许调用方查询历史调用记录，支持复现历史问题场景。
  • 可选
    支持 Dry-Run 模式 提供 dry_run=true 参数，验证参数合法性、模拟执行路径而不产生真实副作用，便于调用方调试。

4.3 典型反例

反例
  • 日志只记录 HTTP 状态码，没有工具名称和参数，无法重现问题场景，只能请求工具服务方配合手动检索。
  • 多个工具服务 request_id 格式各异（有的是 UUID，有的是时间戳），无法在统一日志平台聚合查询。
  • 没有分布式追踪支持，agent 调用 5 个工具后出现错误，只能逐个服务翻日志手动对时间戳，排查耗时数小时。

4.4 如何验证

  • 发起一次调用，用响应中的 request_id 在日志系统中搜索，确认能找到包含工具名称、参数摘要、耗时的完整记录。
  • 在请求头中传入 traceparent，确认工具服务在其 span 中正确传播该值，追踪平台中可见完整调用链。
  • 故意触发服务端错误，确认工程师日志中有完整上下文，而 LLM 响应中只有精简的友好错误消息。

5. RL 训练场景专项要求

5.1 与推理场景的本质差异

RL 训练（尤其是 GRPO / PPO 类算法）需要在每个迭代中运行成百上千个并行 episode，每个 episode 都会触发工具调用序列。与推理场景不同，训练场景对工具服务有三个独特的额外要求：

维度推理场景RL 训练场景
调用并发中低并发，用户级极高并发，批量 rollout（数百~数千并行）
状态隔离可接受共享部分全局状态必须 episode 级完全隔离，防止轨迹污染
确定性允许一定随机性相同输入须产生一致输出，保证实验可复现
副作用按需产生训练期间默认禁止持久化副作用
重置能力不需要需要支持 episode 级状态重置（env.reset）
关键风险

工具服务的非确定性会污染训练信号：如果相同输入在不同 rollout 中产生不同输出（如工具内部使用时间戳、全局计数器），奖励函数在相同状态下会给出不同分数，导致训练曲线出现无法解释的抖动，且极难复现和定位根因。

5.2 具体要求

  • 必须
    声明训练场景并发容量，并提供水平扩展方案 文档明确说明训练场景下的最大并发数 / QPS 上限；训练框架在 rollout 开始前需确认服务容量可承载 batch_size × rollout_steps 的峰值并发。
  • 必须
    Episode 级状态完全隔离 通过 session_id 或等效机制区分不同 episode 的调用上下文；不同 episode 的中间状态必须完全隔离，一个 episode 的行为不得影响另一个的奖励计算。
  • 必须
    明确文档说明每个工具的副作用行为 工具服务须在文档中明确声明每个工具是否产生持久化副作用（写 DB、外部 API 调用、发送消息等）；训练阶段默认应使用无副作用模式或沙箱环境。
  • 必须
    Fail-Fast：单步超时不阻塞整批 Rollout 单个工具调用超时后，框架必须在设定时间内收到明确的超时错误，而非等待服务端长时间挂起。一个慢请求不应拖垮整个 rollout batch。
  • 推荐
    支持确定性模式（Deterministic Mode） 提供关闭随机性的选项（如固定随机种子、禁用采样），使相同输入产生完全一致的输出，保证训练轨迹可复现、不同实验结果可对比。
  • 推荐
    支持 Episode Reset 接口 提供 reset(session_id) 或等效接口，清除指定 episode 的中间状态，对应强化学习框架中 env.reset() 的语义。
  • 推荐
    训练流量与推理流量完全服务隔离 为训练任务提供独立的服务实例或命名空间，防止训练产生的高并发压力影响线上推理服务的 SLA。
  • 可选
    支持批量请求（Batch API） 允许在单次请求中打包多个工具调用，减少连接开销，提升训练吞吐效率（对高 QPS 训练场景收益显著）。
  • 可选
    训练场景专用监控视图，按 job ID 聚合 区分推理流量和训练流量的指标，按 training job ID 聚合调用统计，便于分析训练进度与工具服务状态的相关性。

5.3 RL 奖励信号完整性：基础设施故障 vs 语义错误

这是 RL 场景最容易被忽略、也最致命的问题。工具调用失败有两种本质不同的原因，对奖励的处理方式完全相反：

错误类型典型示例对 RL 的正确处理
INFRA_ERROR 基础设施故障超时、503、OOM、rate limit 打满不计入 reward，应重试或标记为"待重跑"样本
TOOL_ERROR 工具语义错误搜索无结果、查询语法错误、权限不足（业务权限）应计入 reward，policy 需要学会处理这类情况
核心风险

若把基础设施故障（如超时）当作"工具返回空结果"处理，reward = 0 会错误地惩罚 policy，让模型学会"回避工具调用"而不是"正确使用工具"。这种偏差极难从训练曲线上察觉，但会严重影响策略的最终能力。

  • 必须
    错误码强类型区分：INFRA_ERROR vs TOOL_ERROR 工具服务的错误响应必须通过 error_class 字段明确区分基础设施故障（INFRA_ERROR）和工具语义错误（TOOL_ERROR），不能仅依赖 HTTP 状态码区分（5xx/4xx 均可能出现在两类场景中）。
  • 必须
    INFRA_ERROR 已在服务端尽力重试后才透出 工具服务端对 INFRA_ERROR 内部重试 N 次后才返回给调用方；调用方收到 INFRA_ERROR 意味着服务已经尽力，训练框架可据此直接标记该样本为"待重跑"而不再重试。
  • 推荐
    INFRA_ERROR 率有 SLO 约束，超标主动告警 工具服务对离线作业承诺 INFRA_ERROR 率上限（如 < 0.1%）；超出阈值时主动告警，而非等训练团队发现 reward 异常后才溯源。 
{
  "error_code": "SEARCH_TIMEOUT",
  "error_class": "INFRA_ERROR",
  "message": "搜索服务内部超时，已重试 3 次。请将本样本标记为待重跑。",
  "retryable": false,
  "request_id": "req_9b2c4d1a"
}

{
  "error_code": "NO_RESULTS_FOUND",
  "error_class": "TOOL_ERROR",
  "message": "搜索词 'xyzabc123' 未找到相关结果，这是正常的工具返回。",
  "retryable": false,
  "request_id": "req_7e3f8c0b"
}

5.4 跨训练迭代的工具行为稳定性

RL 训练通常持续数天、跨越数十次迭代。若工具的底层数据（搜索索引、知识库、推荐系统）在训练期间发生静默更新，则：

  • 同一 policy 在第 1 轮 rollout 用工具找到了正确答案，在第 10 轮同样的 query 工具返回了不同结果 → reward 信号发生漂移，policy 质量曲线失真
  • 训练曲线看似在"进步"，实际上可能是工具底层数据变化带来的伪提升，导致错误的 early stopping 判断
  • 必须
    工具底层数据变更须有版本号，且变更前主动通知 每次底层数据更新（索引重建、知识库刷新）须带版本号，并在变更前通知使用方；禁止在进行中的训练 run 期间静默更新底层数据。
  • 推荐
    支持数据版本锁定（Snapshot 模式） 一次训练 run 可绑定固定的数据快照版本（X-Tool-Data-Version: snapshot-2026-07），保证整个训练期间工具底层数据不变，奖励 landscape 稳定。
  • 推荐
    提供跨版本 diff 能力，量化工具行为漂移 对同一批 golden query，可对比两个数据版本的工具返回差异率；差异率超阈值时触发告警，提醒训练团队评估是否需要重跑受影响的迭代。

5.5 典型反例

反例
  • 状态隔离缺失：工具服务无 session 隔离机制，所有 episode 共用同一个"当前搜索历史"状态，前一个 episode 的行为影响后一个的奖励计算，导致训练数据分布偏移。
  • 真实副作用：搜索工具实际写入用户行为日志，召回工具实际触发推荐系统更新，训练跑一轮后线上数据被大量污染。
  • 训练/推理共用：训练任务高峰期与线上推理流量共用同一服务实例，导致推理 P99 延迟飙升，触发线上告警。
  • 非确定性：工具内部结果依赖当前时间戳排序，相同查询在两次 rollout 中返回不同顺序，奖励函数计算结果不一致，训练曲线剧烈抖动。

5.6 如何验证

  • 确定性验证：开启确定性模式后，用相同参数连续调用同一工具 N 次，对比所有响应是否完全一致（字段顺序、数值均相同）。
  • 状态隔离验证：在 session A 中写入状态，在 session B 中读取，确认 B 完全无法感知 A 的状态。
  • 副作用验证：在沙箱环境完整跑一轮训练，事后检查所有外部系统（数据库、日志、消息队列）确认无真实副作用产生。
  • 并发压测：模拟训练场景下的并发量（如 512 并发 rollout），验证服务 P99 延迟和错误率不超标，且无跨 session 数据污染。
  • Fail-Fast 验证：注入一个永不返回的调用，确认超时错误在设定时间内返回，其他并行调用不受影响。

6. 离线数据质量保证

6.1 幂等性与断点续传

离线数据生产作业动辄跑数十小时、跨越数百台 worker。机器 OOM、网络抖动、调度抢占都会导致作业中断重启。若工具调用不具幂等性，重跑时同一请求可能得到不同结果（搜索索引已更新、限流后换了不同副本），导致训练数据集内部不一致。

核心区别

在线推理中，用户重试本来就期待最新结果，不幂等是可接受的。离线作业重跑时，已调用但未落盘的 sample 必须能原样重现——否则数据集的不同子集是由不同"世界观"的工具产生的，分布不一致。

  • 必须
    支持幂等 Key，TTL 覆盖作业最大重试窗口 客户端可携带幂等 Key（建议格式：job_id + sample_idx + call_idx），服务端在 TTL 内返回缓存响应而不重新执行。TTL 须覆盖作业最大重试窗口（通常 ≥ 72h），而非按在线业务设计的几秒钟。
  • 必须
    有副作用的工具支持幂等 token 去重 对会产生写操作的工具（代码执行、数据库写入），须通过幂等 token 确保重复请求不产生重复副作用，而不是每次重跑都再执行一次写操作。
  • 推荐
    提供作业级调用日志，支持从 checkpoint 续跑 工具服务或调用方 SDK 维护按 job_id 组织的调用日志，作业恢复时可跳过已成功调用的 sample，不重复消耗配额也不重新发起请求。

6.2 结果完整性与截断策略

工具服务通常因 token 限制或延迟约束对结果截断。在线场景中用户有感知能力，可识别截断并追问；但训练管道没有这个能力——模型会把截断后的输出当作完整输出学习，错误地认为任务已完成，或在 RL 中因关键信息缺失导致任务不可解、reward 为 0（但这不是 policy 的问题）。

  • 必须
    每次响应显式携带截断元数据（is_truncated + total_size） 响应必须包含 is_truncated: true/false 和 total_chars（或 total_tokens）字段，绝不允许静默截断。调用方据此决定是否分页拉取或跳过该样本。
  • 必须
    离线调用可配置更高的返回长度上限 离线请求可通过参数指定比在线更高的返回长度上限（如 64K vs 4K），保证蒸馏数据的信息完整性不因在线约束而被动损失。
  • 推荐
    支持分页拉取，覆盖超长结果 对代码执行输出、长文档检索等场景提供游标分页（cursor + has_more），让调用方按需拉取完整结果，而不是被迫接受截断版本。
  • 推荐
    截断策略可配置（error / paginate / truncate+flag） 结果超长时的处理策略允许调用方配置：error（报错让调用方决策）、paginate（自动分页）、truncate_with_flag（截断并标记），而不是统一静默截断。

6.3 作业级管理能力

工具服务器通常以请求粒度管理资源，但离线场景的自然管理单元是作业（job）。缺乏作业级管理会导致：某个失控作业独占全部配额、作业取消后 worker 仍持续发请求、无法提前预估成本导致预算失控。

  • 必须
    作业注册与生命周期管理（注册/暂停/取消） 支持通过 job_id 注册作业并管理其生命周期；作业取消后，服务端拒绝该 job 的后续所有请求，防止 zombie worker 持续消耗配额。
  • 必须
    作业级独立配额上限（QPS + 总调用量） 每个 job_id 有独立的 QPS 限制和总调用量上限，超出时返回明确的限流错误；不同作业之间互不影响，一个失控作业不应饿死其他作业。
  • 推荐
    提供成本预估接口（启动前可预检） POST /job/estimate：给定样本数、工具类型、预期并发，返回预估调用次数、配额消耗量和完成时间，便于提前做资源规划和预算审批。
  • 推荐
    服务端背压信号（X-Backpressure-Delay） 服务端在接近容量瓶颈时在响应头中携带 X-Backpressure-Delay: 500ms，指导客户端主动降速，而不是等到触发 429 才被动退避，平滑控制并发。
  • 推荐
    支持作业优先级调度 不同类型的离线作业（数据蒸馏 / RL 训练 / 探索实验）可设置优先级，资源紧张时高优作业优先服务，低优作业自动排队等待。
  • 可选
    作业进度可观测（已完成 / 错误分布 / 预计剩余时间） 按 job_id 查询当前进度：已完成调用数、缓存命中率、INFRA_ERROR 率、预计剩余时间，便于及时发现异常（如某个 worker 卡住）。

6.4 训练数据合规性

这是最容易被工程团队忽视、但后果最严重的维度。在线推理中，工具结果不落盘，实时消费后即丢弃；离线场景的工具结果会持久化为训练数据，受到更严格的数据监管——版权、ToS、隐私保护均适用，违规可能导致模型无法商用或引发法律风险。

常见法律风险
  • ToS 违规：大多数第三方搜索 API（Bing、Google、Serper）的服务条款明确禁止将返回结果用于训练 ML 模型，违反可能导致账号封禁和法律索赔。
  • 版权风险：工具返回的网页内容、代码片段可能受 CC BY-NC 或 GPL 等限制，禁止用于商业训练。
  • PII 泄露：工具结果中的姓名、手机、邮箱等 PII 一旦进入训练数据，形成长期隐私风险，且事后难以彻底清除。
  • 必须
    每个工具明确标注"是否允许离线训练用途" 工具服务方须在文档中为每个工具标注其数据来源的合规状态：training_allowed / inference_only。不在白名单内的工具不得用于生成训练数据。
  • 必须
    结果落盘前完成 PII 检测与脱敏 工具结果在调用方落盘前须经过 PII 检测（姓名、电话、邮箱、身份证号等）和脱敏；脱敏可在服务端完成（更彻底）或由调用方 SDK 完成（更灵活），但不得跳过。
  • 推荐
    响应携带内容 license 标签 工具响应中携带 content_license 字段（如 public_domain、cc_by、cc_by_nc、proprietary），供下游数据管道按 license 类型过滤，避免混入不可用数据。
  • 推荐
    每条调用记录保留来源溯源信息 调用日志记录：来源域名、采集时间、工具版本、数据版本，支持事后合规审计和"数据删除传播"（right to be forgotten）场景下的定点清除。

6.5 Schema 版本治理

离线训练管道（数据清洗、特征提取、reward 计算）通常对工具返回的字段结构有强依赖。工具服务的 schema 变更（字段改名、类型变化、字段删除）会静默破坏下游解析，且因为是离线批量作业，往往数据集已全部生产完才在训练时发现问题，造成大量返工。

  • 必须
    API 路径携带版本号，旧版本至少维护 6 个月 接口路径须包含版本（如 /v2/tool/search），每个版本的 schema 不可变；旧版本在新版本发布后至少维护 6 个月，给使用方足够的迁移窗口。
  • 必须
    Breaking Change 提前 2 周通知，附迁移指南 任何 schema breaking change（字段删除/改名/类型变化）须提前至少 2 周通知所有使用方，并提供迁移指南和自动化验证脚本；禁止静默升级。
  • 推荐
    每次响应携带 schema_version，调用方可据此做版本适配 响应中携带 schema_version 字段，调用方可在解析前做版本检查，发现版本不符时提前报错而不是静默解析出脏数据。
  • 推荐
    CI 中加入 Contract Test，防止 schema 退化 在工具服务的 CI 流水线中对所有对外 schema 跑 contract test，任何 breaking change 在发布前被自动拦截，而非在使用方的离线作业中才被发现。

6.6 典型反例

反例
  • 幂等性缺失：蒸馏作业跑到一半因机器故障重启，重跑时搜索索引已更新，前后两批数据是不同时间点的工具输出，数据集内部出现分布不一致，模型在该子集上的表现出现系统性偏差。
  • 静默截断：代码执行工具静默截断超长输出但不携带任何标记，训练数据中"执行成功"但结果不完整的样本大量存在，模型学到"执行后直接给出答案"的错误模式。
  • 合规忽视：使用某搜索 API 生成大规模蒸馏数据，上线前法务审查发现该 API 的 ToS 禁止用于训练，数百万条训练样本需全部丢弃重新生产。
  • Schema 静默变更：工具服务把 result.score 从 float 改为 string，奖励函数在计算时静默转型出错，RL 训练跑了 3 天才从指标异常中发现，整个 run 作废。

6.7 如何验证

  • 幂等性验证：用同一幂等 Key 发送两次请求，对比两次响应的每个字段是否完全一致；间隔 24h 后再发送，确认 TTL 覆盖到位。
  • 完整性验证：构造超长结果的请求，确认响应携带 is_truncated: true 而非静默截断；调用分页接口确认可拼接出完整结果。
  • 作业管理验证：注册一个 job，取消后继续发送该 job_id 的请求，确认服务端返回拒绝而非继续处理。
  • 合规验证：对接入的每个工具工具查阅 ToS，确认"离线训练用途"明确允许；对 100 条样本结果跑 PII 检测，确认脱敏覆盖率。
  • Schema 稳定性验证：保存一组 response fixture，每次工具服务升级后对比 schema 是否有 breaking change；集成 contract test 自动化此流程。
