概述：为什么仓库探索是编码 Agent 的核心能力

在软件工程自动化的研究版图中，SWE-bench 等基准以「能否生成通过测试的补丁」为唯一度量，推动了 Claude Code、SWE-agent、AutoCodeRover 等系统的快速迭代。然而，这种端到端的二元评估掩盖了 Agent 在流程各阶段的真实能力差异。当一个 Agent 无法修复 issue 时，根本原因究竟是「探索了错误的代码区域」还是「找到了正确区域但生成了错误补丁」？现有基准无法区分这两种失败模式。

仓库探索（Repository Exploration）是编码 Agent 流水线的第一步，也是最关键的一步。一个真实的代码仓库平均包含 759 个文件、18 万行代码，而修复一个 issue 往往只需要精确定位到 4.3 个文件、4.7 个区域、约 1578 行上下文。在如此高的信噪比挑战下，Agent 必须依靠对自然语言 issue 的理解、代码语义的把握以及多步交互式导航，才能找到真正相关的代码证据。

为什么行级探索比文件级更重要？现有的 bug 定位研究（如 LocAgent、OrcaLoca）通常只评估到文件或函数粒度。但实验表明，即使 Agent 找到了正确的文件（HitFile 高达 0.64–0.68），其行级召回率（Recℓ）往往只有 0.14–0.19。这意味着 Agent 虽然进入了正确的「邻域」，却仍然遗漏了修复所需的关键代码行。行级覆盖不足直接导致下游补丁生成失败——实验中，当核心上下文覆盖率从 75% 降至 50% 时，修复率出现断崖式下降。

SWE-Explore 的核心洞察在于：探索质量是可以独立测量的。通过将仓库探索形式化为「在固定行预算内返回相关代码区域排序列表」这一标准化任务，任何检索方法、搜索 Agent 或长上下文选择器都可以在同一评估框架下进行公平比较。这种解耦设计使研究者能够精确诊断 Agent 的探索瓶颈，为改进方向提供明确指引。

核心论断：仓库探索不是端到端修复的附属品，而是一个独立的、可测量的、对下游修复行为具有高度预测力的核心能力维度。

核心局限性分析

  • 二元评估盲区：SWE-bench 的 pass/fail 指标无法区分「探索失败」与「合成失败」两种截然不同的根因。一个找到了正确代码但生成了语法错误补丁的 Agent，与一个连正确文件都没找到的 Agent，在排行榜上得到相同的分数。
  • 粒度不足：Loc-Bench、ContextBench 等中间评估基准停留在文件或函数粒度，无法揭示 Agent 是否真正读取了修复所需的关键代码行。
  • 缺乏统一对比框架：稀疏检索、密集检索、Reranker 和 Agentic 探索器从未在同一个任务定义下进行公平比较。
  • 真值来源不可靠：人工标注成本高昂且难以保持一致性，特别是在跨十种语言的大规模评估中。
  • 下游验证缺失：现有探索/定位基准没有直接验证其指标是否真正预测下游修复成功率。

基准设计：SWE-Explore 构建方法

任务形式化

SWE-Explore 将仓库探索定义为独立的功能性任务。给定一个 issue $q$ 和仓库快照 $R$，探索器返回相关代码区域的排序列表：

$$f : (q, R) \mapsto P = (r_1, r_2, \ldots, r_K)$$

其中每个区域 $r_i = (p_i, s_i, e_i)$ 由文件路径 $p_i$ 和行范围 $[s_i, e_i]$ 组成。探索器不需要生成补丁，不访问真值，也不强制要求与仓库交互。这种设计使得稀疏检索器、交互式 Agent 和长上下文选择器都能在同一输出契约下进行比较。

数据来源与规模统计

SWE-Explore 从三个公开数据集构建：SWE-bench Verified、SWE-bench-Pro 和 SWE-bench Multilingual。经过「至少两条成功轨迹」的过滤后，保留 848 个实例，覆盖 10 种编程语言和 203 个开源仓库。

真值构建：轨迹驱动行级标注

直接人工标注在如此规模下既昂贵又难以保持一致性。SWE-Explore 提出了一种轨迹驱动的自动标注方法，从成功修复 issue 的 Agent 轨迹中提取行级真值。

Algorithm 1: 轨迹驱动行级真值构建

Input: T = 成功轨迹集合（|T| ≥ 2），来自 GPT-5.4, Gemini-3-Pro, Sonnet-4.6, GLM-5.1, Kimi-K2.6

// Step 1: 从每条轨迹提取可观测读取动作

for τ in T:

R(τ) ← extract_reads(τ) // editor views + cat/head/tail/sed-n + grep -n hits

// 归一化为 (path, start_line, end_line) 三元组，丢弃无法映射的动作

// Step 2: 跨轨迹取交集，得到保守核心候选

R_core_raw = ∩τ∈T R(τ) // 文件级、行级交集

R_opt_raw = (∪τ∈T R(τ)) \ R_core_raw // 可选区域：交集外的成功读取

// Step 3: LLM 辅助精化，提升关键可选区域

for candidate in R_opt_raw:

if llm_is_load_bearing(candidate, issue, trajectories):

R_core_raw ← R_core_raw ∪ {candidate}

// Step 4: 人工审核，删除不支持的区域

R_core ← human_audit(R_core_raw) // 最终行级核心真值

Output: R_core（主要评分目标），R_opt（诊断用可选上下文）

三种真值变体对比：

变体构建方式特点用途
纯交集（R_int）所有轨迹的逐行交集最保守，高精度低召回消融分析
精化核心（R_core）交集 + LLM 提升 + 人工审核平衡精度与召回主要评分目标
完全并集（R_union）所有轨迹的并集高召回，含探索性冗余消融分析

三维评估体系

设 $L(r)$ 为区域 $r$ 覆盖的 $(path, line)$ 集合，$L(P) = \bigcup_i L(r_i)$ 为预测列表覆盖的全部行，$Y = L(R_{core})$ 为行级核心真值，行预算为 $B$，$P_{\leq B}$ 为累计行数不超过 $B$ 的最长预测前缀。

维度一：覆盖率（Coverage）

行级精度与召回：

$$\text{Prec} = \frac{|L(P) \cap Y|}{|L(P)|}$$

$$\text{Rec}_\ell = \frac{|L(P) \cap Y|}{|Y|}$$

$$\text{F1} = \frac{2 \cdot \text{Prec} \cdot \text{Rec}_\ell}{\text{Prec} + \text{Rec}_\ell}$$

粗粒度命中率（实践中重要的事件）：

文件级命中率：$\text{HitFile} = \frac{|\{p : \exists i, p_i = p\} \cap \text{Files}(Y)|}{|\text{Files}(Y)|}$

区域级命中率：$\text{HitRegion} = \frac{|\{r \in R_{core} : \exists i, L(r_i) \cap L(r) \neq \emptyset\}|}{|R_{core}|}$

维度二：排序（Ranking）

将 nDCG 适配到行预算设置。每个预测区域 $r_i$ 的增益 $g_i$ 等于其覆盖的新核心行数，按预测顺序处理，在预算 $B$ 内累计折扣增益：

$$\text{DCG}@B = \sum_{i \in P_{\leq B}} \frac{g_i}{\log_2(i+2)}$$

$$\text{nDCG}@B = \frac{\text{DCG}@B}{\text{IDCG}@B}$$

其中 IDCG 通过贪心算法在相同行预算下构建理想排序（每步选取剩余增益最大的真值区域）。主实验使用 $B \in \{100, 300, 500\}$。

首次有用命中（FUH）：设 $i^{*}$ 为预测列表中第一个与 $Y$ 有行级交集的排名，则：

$$\text{FUH} = \begin{cases} 1 - i^{*}/|P|, & \text{若存在这样的 } i^{*} \\ 0, & \text{否则} \end{cases}$$

FUH 越高，表示有用证据在排序列表中出现越早。

维度三：上下文效率（Context Efficiency）

$$\text{CtxEff} = \frac{|L(P) \cap (L(R_{core}) \cup L(R_{opt}))|}{|L(P)|}$$

量化预测上下文中有多大比例是有效证据（核心或可选），而非无关代码。互补指标噪声率（NoiseReg）定义为既不与 $R_{core}$ 也不与 $R_{opt}$ 重叠的预测区域比例，作为区域级诊断。

文件级 vs 行级：关键差距分析

关键发现

发现 1：Agentic 探索器显著优于经典检索

稀疏检索（BM25、TF-IDF）和轻量密集检索（Potion）在大多数指标上接近随机基线，而每个 Agentic 探索器都显著高于它们。这证明仓库探索无法通过一次性词项或嵌入检索来有效完成——与仓库的多步交互已经是达到现代编码 Agent 指标范围的必要条件。

发现 2：低 F1 主要是召回问题

尽管文件命中率和排序分数较高，大多数非 Oracle 探索器的 F1 仍然很低，限制因素通常是行级召回率而非精度。通用编码 Agent 的 HitFile 和 nDCG@500 很高，但 Recℓ 仅在 0.14–0.19 之间。这表明足够广泛的仓库探索仍是当前代码 Agent 的核心瓶颈。

发现 3：通用编码 Agent 表现出人意料地相似

Claude Code、Codex、OpenHands、Mini-SWE-Agent 和 AweAgent 在覆盖率、排序和效率指标上高度匹配，尽管它们在实现和框架复杂度上差异显著。这一相似性表明：研究探索子问题不需要复杂的修复框架；更简单的探索器接口就能暴露相同的行为模式。

发现 4：LLM 选择改变操作点，但不消除瓶颈

用相同的 Mini-SWE-Agent 框架运行不同 LLM：GPT 系列最强，Kimi-K2.6 和 Sonnet-4.5 居中，GLM-4.7 和 Gemini-3-Pro 靠后。但更重要的规律是：无论哪种 LLM，文件命中率都远高于行级召回率。仅替换基础模型无法消除探索瓶颈。

发现 5：专门定位器仅在拓宽搜索时有效

学术 Agent 并不一致优于通用编码 Agent。AutoCodeRover 精度高但保守，OrcaLoca 噪声极低但遗漏大量区域，LocAgent 与通用 Agent 表现相近。CoSIL 是主要例外：其迭代代码图搜索实现了最高的非 Oracle Recℓ（0.788）和 F1（0.602），表明迭代式图搜索是高召回探索的重要组成部分。

发现 6：缺失核心证据比冗余上下文更具破坏性

在受控上下文降级实验中，当核心证据覆盖率从 75% 降至 50% 时，修复率出现阈值式断崖下降。这种阈值模式表明：修复器不是从每个额外区域平滑积累价值，而是需要多个核心证据同时存在才能完成正确修复。相比之下，冗余上下文（噪声注入）在阈值以上的危害相对较小。

Agentic vs 检索的差距量化

局限性

  • 实例选择偏差：SWE-Explore 仅包含被至少一个 Agent 成功解决的实例（需要 ≥2 条成功轨迹），因此不代表所有未解决仓库级 issue 的完整分布。对于当前 Agent 无法解决的困难问题，本基准无法提供直接评估。
  • 轨迹驱动真值的近似性：从成功轨迹提取的行级真值是有用上下文的经验近似，而非证明。某些有效的解决路径可能依赖与观测轨迹不同的证据——其他代码区域同样可以支持有效的补丁生成。
  • 语言分布不均：Python 占 64.5%，主要因为 SWE-bench Verified 以 Python 为中心。非 Python 语言（如 C++ 仅 7 个实例）的评估结果统计显著性较低。
  • 受限上下文验证的局限性：下游修复协议使用固定的补丁框架（Mini-SWE-Agent + GPT-5.4），仅作为探索指标的外部效度检验，不是对补丁生成能力的绝对度量。更高的修复率可能反映更强的补丁框架而非更好的探索。
  • K=5 的固定预算：主实验固定每个探索器返回 5 个区域，与平均 4.7 个核心区域对齐。这个选择对于核心区域数量差异大的实例可能不够灵活。
  • 时效性问题：真值来自 GPT-5.4、Gemini-3-Pro 等强模型的成功轨迹。随着模型能力提升，成功轨迹可能采用不同的探索策略，真值可能需要更新。

总结与启发

SWE-Explore 的出现标志着编码 Agent 评估范式的一次重要转变：从「能否修复问题」的二元判断，走向「如何探索仓库」的细粒度诊断。这一转变的意义不仅在于提供了一个新的基准，更在于它揭示了当前 Agent 能力的结构性瓶颈——行级召回率是区分优秀探索器的关键轴。

对研究方向的深度启发：

第一，探索与修复的解耦研究。当前大多数系统将探索和修复耦合在一个端到端流水线中，这使得改进探索能力的努力难以被独立衡量。SWE-Explore 提供的解耦框架使研究者可以专注于探索子问题，而不必同时优化补丁生成质量。这类似于信息检索领域将检索（retrieval）和重排序（reranking）分开研究的传统。

第二，行级覆盖的重要性被长期低估。实验清晰地表明，文件命中率（HitFile ≈ 0.64–0.68）与行级召回率（Recℓ ≈ 0.14–0.19）之间存在巨大鸿沟。这意味着现有 Agent 虽然能找到正确的文件，却经常遗漏关键代码行。未来的改进方向应聚焦于如何在找到正确文件后，进一步精确定位到关键代码段。

第三，CoSIL 的迭代图搜索提供了重要的方向性信号。CoSIL 以整文件粒度换取高召回率（Recℓ=0.788），虽然精度较低，但其修复率接近 Oracle（59.3% vs 59.7%）。这说明在当前技术水平下，高召回率的宽泛探索比高精度的保守探索更有利于下游修复。未来研究应探索如何在保持高召回率的同时提升精度——即「先广后精」的两阶段探索策略。

第四，上下文效率是一个被忽视的维度。CtxEff 与修复率的 Pearson 相关系数高达 0.950，高于所有其他指标。这意味着「选择了多少有用内容」比「覆盖了多少真值」更能预测修复成功。对于有行预算限制的实际系统，提升上下文效率（减少噪声、增加信噪比）可能比单纯提升召回率更有价值。

第五，多语言探索能力亟待关注。当前基准中 Python 占 64.5%，但 Go、JavaScript、Rust 等语言的仓库结构、命名约定和代码组织方式与 Python 存在显著差异。Agent 在非 Python 语言上的探索能力是否同样强健，是一个值得深入研究的问题。

最终洞察：SWE-Explore 不仅是一个基准，更是一种研究方法论的范式——它告诉我们，评估 Agent 能力不应只看最终结果，而应解构流水线中每个关键步骤的质量。随着 Agent 系统复杂度的增加，这种细粒度的能力评估框架将变得越来越重要。
