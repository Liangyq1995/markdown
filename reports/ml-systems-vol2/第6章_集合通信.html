第6章 集合通信（Collective Communication）

《Machine Learning Systems at Scale》Vijay Janapa Reddi · MIT Press · Vol.2 · 生成日期：2026-07-04

核心主线并行策略决定通信原语 → α-β/LogP 成本模型 → Ring/Tree/分层 AllReduce → 拓扑感知路由 → 压缩与计算-通信重叠
学习目标用定量模型估算集体通信耗时，为 DP/TP/PP/MoE 选择正确原语与算法，并识别 NCCL 实测与理论模型的差距

一、从并行到通信：梯度同步

10,000 GPU 同步 SGD 时，计算随 GPU 数线性扩展，但协调是全局的——梯度、激活、参数必须跨物理链路移动。C³ 视角下，集合通信是 fleet 的「指令集」：AllReduce、AllGather、ReduceScatter、AllToAll 决定铁律中的通信项是否成为瓶颈。

定义：梯度同步（Gradient Synchronization）

同步数据并行中，每个 worker 贡献本地梯度，经全局归约（通常求和）后，所有副本收到相同结果并执行一致更新。若不同步，各 GPU 模型副本发散，不再近似全局 SGD。

1.1 70B 梯度体量与 Ring AllReduce 速算

BF16 下每参数 2 字节，70B 模型每 GPU 每步梯度：

$$M = 7 \times 10^{10} \times 2\ \text{B} = 140\ \text{GB}$$

Ring AllReduce 带宽项（每节点发送量近似恒定）：

$$T_{\text{bandwidth}} = 2 \cdot \frac{N-1}{N} \cdot \frac{M}{\beta}, \quad T_{\text{latency}} = 2(N-1)\alpha$$

代入：64 GPU、InfiniBand NDR $\beta=50$ GB/s、$\alpha=1.5\,\mu\text{s}$：

  • $T_{\text{bandwidth}} \approx 1.97 \times 140/50 \approx 5.51$ s
  • $T_{\text{latency}} = 126 \times 1.5\,\mu\text{s} \approx 0.2$ ms → 纯带宽主导

用户速算 $2 \times 140/50 \approx 5.6$ s 即此场景的一阶近似。单步 AllReduce 占 5+ 秒时，必须与 backward 重叠或采用分层/压缩，否则 GPU 空等。

1.2 规模放大：通信占比 25% → 80%

规模互联通信+同步占步时有效计算

64 GPU（8 节点）IB NDR 50 GB/s~55%~45%

8→4096 GPU 的跃迁不是「加机器就线性加速」：同一 70B Ring AllReduce 在跨 pod 时暴露 IB 带宽悬崖，同步屏障叠加后通信+同步可吞掉 80% 步时。

二、α-β 模型与临界消息大小

$$T(n) = \alpha + \frac{n}{\beta}, \quad n^* = \alpha \cdot \beta$$

手算：InfiniBand NDR 临界大小

$\alpha=2\,\mu\text{s}$，$\beta=50$ GB/s → $n^* = 2\times10^{-6} \times 5\times10^{10} = 100$ KB。

  • 4 KB MoE 路由包（$n \ll n^*$）：96% 时间是启动税 → 融合 100 个包为 400 KB：$100\alpha=200\,\mu\text{s}$ → $\alpha+n/\beta\approx10\,\mu\text{s}$，约 20× 改善
  • 140 GB 梯度（$n \gg n^*$）：带宽主导 → 压缩 payload、分层 AllReduce 有效；仅降 $\alpha$ 几乎无效
互联$\alpha$$\beta$（单向）$n^*$
NVLink 4.01–2 μs450 GB/s~0.7 MB

PCIe Gen52–5 μs64 GB/s~224 KB

2.1 分层 AllReduce：128 GPU / 16 节点

平坦 Ring 跨 IB 传完整 140 GB → ~5,557 ms。分层：节点内 NVLink ReduceScatter + 跨节点传 $M/16$ shard + 节点内 AllGather → ~1,201 ms，约 4.6×。工程含义：先吃满快链路，再让慢链路只搬归约后的分片。

2.2 LogP 与重叠

AllReduce 网络延迟 $L_{\text{lat}}=100\,\mu\text{s}$ 可与 500 μs backward 重叠；但发起/接收开销 $2o=100\,\mu\text{s}$ 不可隐藏。优化 GPUDirect、降 $o$ 往往比盲目加 $\beta$ 更有效。

三、集体原语与算法选择

原语并行策略瓶颈Ring 代价（大消息）
AllReduce数据并行带宽$2(N-1)M/(N\beta)$，延迟 $\mathcal{O}(N)$
AllGather / ReduceScatterFSDP/ZeRO-3带宽+频率每层一次，峰值内存升 $N$ 倍
AllToAllMoE / DLRM延迟+争用逻辑 $\mathcal{O}(N^2)$ 连接，易撞 bisection 墙
P2P Send/Recv流水线延迟微批 handoff

MoE AllToAll 手算（8 GPU，4096 token）

BF16 hidden 2048 → 4.096 KB/token。每 GPU 512 token，均匀路由 64 专家（8/GPU）：向其余 7 GPU 各发 64 token → $64 \times 4.096 = 262$ KB/链路，共发 1.84 MB。

$\alpha=3\,\mu\text{s}$，$T \approx 3+5=8\,\mu\text{s}$/链路；7 链路并行 ≈ 8 μs。但每层两次 AllToAll，且热门 expert 造成热点——MoE 瓶颈常在 $\alpha$ 与负载均衡，而非 raw $\beta$。

3.1 Ring vs Tree

大梯度：Ring 带宽最优。小消息（TP 片、MoE gate）：Tree 延迟 $\mathcal{O}(\log N)$ 更优。NCCL 实测：1 KB 消息有效 $\alpha$ 比裸线高 7–8×（注册+协议）；1 GB 消息仅慢 7–15%——小消息必须用实测 $\alpha$ 选型。

3.2 压缩、稀疏与重叠

  • 梯度压缩：140 GB→1.4 GB 仍远大于 $n^*$，仍带宽界；需 error feedback 防收敛劣化
  • Bucket 融合：合并小 AllReduce，降 $\alpha$ 摊销
  • 层间重叠：early layer 梯度 AllReduce 与 late layer backward 并行；Horovod/DDP bucket_size 即此

四、章节总结

工程决策清单

  1. 先算 $M=2P$ 字节与 $T \approx 2M/\beta$，判断通信是否占步时主导
  2. 用 $n^*$ 区分 latency-bound（融合、拓扑）vs bandwidth-bound（压缩、分层、多 rail）
  3. 3D 并行：TP 锁 NVLink 域，PP 同 rack，DP 跨 rack 且可重叠
  4. MoE/DLRM 优先 AllToAll 争用与 $\alpha$，不是盲目加带宽
  5. 在目标集群 benchmark 小/大消息 AllReduce，校准有效 $\alpha,\beta$
集合通信的守恒律：每加一块 GPU，本地算力 +1，但全局协调的路径长度、启动次数或 bisection 流量不一定 +1。算法与拓扑是训练「可扩展性」的一等公民。
