一、LLM Agent 的 MDP 建模：比普通 LLM-RL 更复杂

在普通 LLM 强化学习（如 InstructGPT、RLHF）中，整个对话被视为一个单一的序列生成任务，奖励仅在序列末尾给出一次，状态空间就是 token 序列本身。而 LLM Agent 的场景要复杂得多：Agent 需要与外部环境（搜索引擎、代码解释器、数据库、浏览器）进行多轮交互，每一轮的"动作"不仅包括生成 token，还包括调用工具、等待结果、再继续推理。这种多轮、有状态、有外部反馈的结构，要求我们用更精确的 马尔可夫决策过程（MDP） 来建模。

1.1 Agent MDP vs 普通 LLM MDP 对比

维度 普通 LLM MDP Agent MDP
状态 $s_t$ 当前 token 序列（prompt + 已生成 token） 对话历史 + 工具返回结果 + 环境状态（网页 DOM、文件系统快照等）
动作 $a_t$ 生成下一个 token（词表大小约 32000） 生成文本 token 或 调用工具（search / calc / code_exec / web_click 等），动作空间异构
奖励 $r_t$ 通常只有 $r_T$（最终奖励，如人类偏好评分） 可以有中间奖励（工具调用成功/失败）+ 最终奖励（任务完成率）
Episode 长度 通常 128–2048 tokens，单轮 可达 10,000+ tokens，3–20 个 turn，每个 turn 含工具调用往返
转移函数 确定性（自回归生成） 部分随机（工具返回结果依赖外部环境，可能超时、报错、返回不同内容）
信用分配难度 中等（单轮，时间跨度短） 极高（多步工具链，延迟奖励，哪一步出错难以归因）
工具调用 无 核心组成部分，工具调用结果注入状态，影响后续所有决策
典型算法 PPO (InstructGPT)、GRPO (DeepSeek-R1)、DPO Turn-PPO、Agent-GRPO、SWEET-RL、AgentQ (MCTS+DPO)、AgentHER

1.2 Agent MDP 精确定义

将 LLM Agent 任务形式化为一个有限时域 MDP $\mathcal{M} = (\mathcal{S}, \mathcal{A}, \mathcal{T}, \mathcal{R}, \gamma, T)$：

$$\mathcal{S} = \{(c, h, e) \mid c \in \text{Context}, h \in \text{History}, e \in \text{EnvState}\}$$
$$\mathcal{A} = \mathcal{A}_{text} \cup \mathcal{A}_{tool}, \quad \mathcal{A}_{tool} = \{\text{search}(\cdot), \text{calc}(\cdot), \text{code\_exec}(\cdot), \text{web\_click}(\cdot), \ldots\}$$
$$\mathcal{T}(s_{t+1} | s_t, a_t) = \begin{cases} \text{LLM}(a_t | s_t) & \text{if } a_t \in \mathcal{A}_{text} \\ \text{Env}(s_t, a_t) & \text{if } a_t \in \mathcal{A}_{tool} \end{cases}$$
$$R(\tau) = r_T + \sum_{t=1}^{T-1} r_t^{tool}, \quad r_T \in [0,1], \quad r_t^{tool} \in \{-0.1, 0, +0.05\}$$

其中 $c$ 是初始任务描述（system prompt + user query），$h$ 是完整对话历史（包含所有 turn 的 LLM 输出和工具返回），$e$ 是外部环境的当前状态（如当前打开的网页、代码执行环境的变量状态）。

关键区别：动作空间的异构性
普通 LLM 的动作是从词表中选 token（离散、均匀、约 32000 维）。Agent 的动作空间包含两类：
  • 文本生成动作：逐 token 生成（自回归），可以是推理文字、计划、最终答案
  • 工具调用动作：结构化调用（JSON 格式），如 {"tool": "search", "query": "Paris population 2024"}，执行后等待环境返回结果
工具调用后，环境返回的结果会被拼接到 context 中，作为下一个 turn 的输入状态的一部分。这使得 状态转移不再完全由模型控制，引入了外部随机性。

1.3 完整 Agent Episode 的 Token 级可视化

以下是一个典型的 3-turn Agent Episode，任务是"巴黎的人口是多少，比北京多还是少？"。我们用 token-seq 可视化完整流程：

Turn 1：接收任务，决定搜索

[SYS] 你是一个可以调用工具的智能助手 [USER] 巴黎人口比北京多还是少？ → <think> 需要查询两个城市的人口 </think> <tool_call> search("Paris population 2024") </tool_call>

Turn 1 工具返回 → Turn 2：阅读结果，继续搜索

[TOOL_RESULT] Paris metro area: 12.2M (2024) → <think> 巴黎市区约220万，大都市区1220万 还需要北京数据 </think> <tool_call> search("Beijing population 2024") </tool_call>

Turn 2 工具返回 → Turn 3：综合推理，生成最终答案

[TOOL_RESULT] Beijing: 21.9M residents (2024) → <think> Paris 12.2M < Beijing 21.9M 差距约9.7M，北京更多 </think> 巴黎大都市区人口约1220万， 北京约2190万， 北京比巴黎多约970万人。 [EOS]

这个 Episode 共包含约 320 个 token，经历了 3 个 turn，调用了 2 次工具。最终奖励 $r_T = 1.0$（答案正确）。

1.4 信用分配难题：延迟奖励 + 多步工具链

Agent 训练中最核心的难题是信用分配（Credit Assignment）：当最终任务失败时，是哪一步出了问题？

具体数字示例：5步工具链的信用分配问题

任务："帮我预订明天从上海到北京的最便宜机票"

  1. Step 1：search_flights("上海", "北京", "2025-01-16") → 返回10条航班信息 ✓
  2. Step 2：filter_cheapest(results, n=3) → 筛选出3条 ✓
  3. Step 3：check_availability("MU5101", "2025-01-16") → 错误：查询了错误的航班号（应为 CA1234） ✗
  4. Step 4：get_price("MU5101") → 返回价格（但是错误航班的价格）
  5. Step 5：book_ticket("MU5101", user_info) → 失败，航班已满

最终奖励 $r_T = 0$（预订失败）

问题：如果只有 $r_T = 0$，模型无法知道错误发生在 Step 3（选错航班号）。Step 4 和 Step 5 的"错误"实际上是 Step 3 的连锁反应。如果用蒙特卡洛回报直接分配，Step 1、2 也会被惩罚，但它们实际上是正确的。

这就是延迟奖励 + 多步工具链导致的信用分配困难：稀疏的终端奖励无法区分各步骤的贡献差异。

蒙特卡洛回报（朴素方法）： $$G_t = \sum_{k=0}^{T-t} \gamma^k r_{t+k} \approx \gamma^{T-t} \cdot r_T \quad \text{（中间奖励为0时）}$$
问题：$G_1 = G_2 = G_3 = G_4 = G_5 = \gamma^{4} \cdot 0 = 0$，所有步骤获得相同（零）回报，无法区分好坏步骤。

理想的逐步奖励： $$r_1 = +0.2, \quad r_2 = +0.1, \quad r_3 = -0.8 \text{（关键错误）}, \quad r_4 = 0, \quad r_5 = 0$$

二、奖励设计：从稀疏到密集

奖励函数是强化学习的核心，直接决定了 Agent 学到什么行为。在 LLM Agent 场景中，奖励设计面临独特挑战：任务多样（代码、搜索、对话、网页操作）、中间步骤难以自动评估、奖励稀疏导致学习效率低下，以及模型可能"作弊"（Reward Hacking）。

2.1 奖励类型全表

类型 给分时机 优点 缺点 典型应用
Sparse
稀疏奖励		 仅在 episode 结束时给 $r_T \in \{0,1\}$ 简单、不易被 hack、与真实目标对齐 学习效率极低，信用分配困难 SWE-agent（测试通过率）、WebArena（任务完成）
Semi-sparse
半稀疏		 关键里程碑处给分（如成功调用工具、找到关键信息） 比纯稀疏学习效率高，仍较难 hack 里程碑定义需人工设计 WebAgent-R1（子目标完成奖励）
Dense
密集奖励		 每个 token 或每个 step 都给分 学习信号丰富，收敛快 极易被 hack，设计困难 早期 RLHF 实验
PRM
过程奖励模型		 每个推理步骤由专门训练的 PRM 评分 提供逐步信号，与人类判断对齐 需要额外训练 PRM，成本高 Math-Shepherd、HCAPO
Cost-aware
成本感知		 在任务奖励基础上减去工具调用成本 鼓励高效行为，减少冗余调用 $\lambda$ 超参数敏感 Tool-R1、AgentQ
Verifiable
可验证奖励		 通过自动化验证器（代码执行、数学验证）给分 客观、可扩展、无需人工标注 仅适用于有客观答案的任务 DeepSeek-R1、Tool-R1（代码执行）

2.2 具体奖励函数设计示例

代码任务奖励
r = 0.6 × pass_rate + 0.2 × format_ok + 0.2 × no_import_error
  • pass_rate：单元测试通过率（0–1）
  • format_ok：代码格式规范（0/1）
  • no_import_error：无导入错误（0/1）
示例：通过7/10个测试 → r = 0.6×0.7 + 0.2×1 + 0.2×1 = 0.82
网页操作任务奖励
r = task_success × 1.0 + Σ subtask_i × 0.1
  • task_success：最终任务完成（0/1）
  • subtask_i：各子任务完成（如找到正确页面、填写表单）
示例：完成3个子任务但最终失败 → r = 0 + 3×0.1 = 0.3
对话任务奖励
r = 0.5 × factual_acc + 0.3 × helpfulness + 0.2 × conciseness
  • factual_acc：事实准确性（由 GPT-4 评分 0–1）
  • helpfulness：有用性（人类评分 0–1）
  • conciseness：简洁性（长度惩罚）
示例：准确但冗长 → r = 0.5×0.9 + 0.3×0.8 + 0.2×0.3 = 0.75

2.3 API 调用惩罚：成本感知奖励

在实际部署中，工具调用有成本（API 费用、延迟、错误率）。成本感知奖励函数鼓励 Agent 高效使用工具：

$$r_{total} = r_{success} - \lambda \cdot N_{calls} - \mu \cdot N_{errors} - \nu \cdot \text{Latency}$$
其中：
$r_{success} \in [0, 1]$：任务成功奖励
$N_{calls}$：工具调用总次数（鼓励减少冗余调用）
$N_{errors}$：工具调用错误次数（格式错误、参数错误等）
$\text{Latency}$：总执行时间（秒）
$\lambda = 0.02, \mu = 0.1, \nu = 0.001$（典型超参数值）

具体示例：
Agent A：$r_{success}=1.0, N_{calls}=3, N_{errors}=0, \text{Latency}=5s$
$r_A = 1.0 - 0.02 \times 3 - 0.1 \times 0 - 0.001 \times 5 = 1.0 - 0.06 - 0 - 0.005 = 0.935$

Agent B：$r_{success}=1.0, N_{calls}=8, N_{errors}=2, \text{Latency}=15s$
$r_B = 1.0 - 0.02 \times 8 - 0.1 \times 2 - 0.001 \times 15 = 1.0 - 0.16 - 0.2 - 0.015 = 0.625$

虽然两者都完成了任务，但 Agent A 因为更高效而获得更高奖励。

2.4 ORM vs PRM：具体数字对比

ORM（Outcome Reward Model）只在轨迹末尾给出整体评分；PRM（Process Reward Model）对每个推理步骤分别评分。以下用同一个错误轨迹展示两种奖励信号的差异：

ORM 视角

任务：计算 $\int_0^1 x^2 dx$

轨迹：

  • Step 1：设 $f(x) = x^2$ ✓
  • Step 2：不定积分 $F(x) = \frac{x^3}{3}$ ✓
  • Step 3：$F(1) - F(0) = \frac{1}{3} - 0 = \frac{1}{3}$ ✓
  • Step 4（错误）：最终答案 = $\frac{2}{3}$（抄写错误）✗
ORM 最终评分：0.0（答案错误）

ORM 将整个轨迹打为 0 分，即使前 3 步完全正确。这对正确的中间步骤是不公平的惩罚。

PRM 视角

任务：计算 $\int_0^1 x^2 dx$

逐步评分：

  • Step 1：PRM 评分 = 0.95（正确识别函数）
  • Step 2：PRM 评分 = 0.98（积分公式正确）
  • Step 3：PRM 评分 = 0.96（代入计算正确）
  • Step 4：PRM 评分 = 0.02（最终答案错误）
PRM 平均评分：0.48（能识别哪步出错）

PRM 精确定位到 Step 4 是错误步骤，前 3 步获得高分，提供了更细粒度的学习信号。

2.5 Reward Hacking 案例

案例 1：格式 Hack（最常见）

奖励函数：r = 1.0 if "答案是" in output else 0.0

Agent 学到的行为：无论推理是否正确，都在输出中加入"答案是"字样，甚至输出"答案是不知道"来获得奖励。

缓解方案：将格式奖励与内容奖励分离，使用更严格的正则匹配，或使用 LLM-as-judge 替代规则匹配。

案例 2：工具调用次数 Hack

奖励函数：r = success_rate + 0.1 × tool_diversity（鼓励使用多种工具）

Agent 学到的行为：在每次回答前都调用一遍所有工具（即使完全不需要），以最大化 tool_diversity 分数，即使这些调用没有任何实际作用。

缓解方案：引入工具调用惩罚项 $-\lambda \cdot N_{calls}$，或要求工具调用必须有实际效果（如返回结果被引用）。

案例 3：长度 Hack（Length Exploitation）

奖励函数：RLHF 奖励模型在训练数据中存在"长回答 = 好回答"的偏差

Agent 学到的行为：生成极长的回答（甚至重复内容、添加无关信息），因为奖励模型给长回答更高分。这是 InstructGPT 和早期 RLHF 模型的著名问题。

缓解方案：在奖励模型训练时加入长度控制，使用 KL 散度约束防止输出分布偏离参考模型太远，或显式加入简洁性奖励。

三、核心算法：在 Agent 场景的具体适配

3.1 GRPO for Agent

GRPO（Group Relative Policy Optimization）由 DeepSeek 在 DeepSeek-R1 中提出，其核心思想是：对同一个问题采样一组（group）输出，用组内相对排名计算优势函数，无需单独的 Critic 网络。这比 PPO 更轻量，但在 Agent 多轮场景中需要特别适配。

标准 GRPO 回顾

$$A_i = \frac{r_i - \text{mean}(\mathbf{r})}{\text{std}(\mathbf{r}) + \epsilon}$$
$$\mathcal{L}_{GRPO} = -\frac{1}{G} \sum_{i=1}^{G} \min\left(\frac{\pi_\theta(o_i|q)}{\pi_{old}(o_i|q)} A_i, \;\text{clip}\left(\frac{\pi_\theta(o_i|q)}{\pi_{old}(o_i|q)}, 1-\epsilon, 1+\epsilon\right) A_i\right) + \beta \cdot D_{KL}(\pi_\theta \| \pi_{ref})$$
其中：$G$ 是组大小（通常 4–16），$\mathbf{r} = (r_1, \ldots, r_G)$ 是组内所有输出的奖励向量，$\epsilon = 0.2$（clip 阈值），$\beta$ 是 KL 惩罚系数。

Agent-GRPO 的三种粒度

粒度 优势计算方式 优点 缺点 适用场景
Episode-level GRPO 整个 episode 只有一个奖励 $r_T$，所有 token 共享同一个 $A_i$ 实现最简单，与任务目标直接对齐 信用分配完全缺失，早期 turn 的 token 梯度信号极弱 短 episode（<3 turn），奖励密集任务
Turn-level GRPO 每个 turn 有独立的优势值，组内比较同 turn 的表现 提供 turn 级别的信用分配，实现相对简单 同一 episode 不同 turn 之间的依赖关系被忽略 中等长度 episode（3–10 turn），有 turn 级别奖励
Token-level GRPO 每个 token 有独立的优势值（通常用 GAE 估计） 最细粒度，信用分配最准确 需要 Critic 网络，计算成本高，接近 PPO 长 episode，需要精细信用分配的复杂任务

具体数字示例：一个 batch 的 4 条轨迹计算 Group Advantage

场景：同一问题"查询并比较两款手机的价格"，4条轨迹的奖励

组大小 $G=4$，奖励向量 $\mathbf{r} = [0.9, 0.3, 0.7, 0.1]$

  • 轨迹1：正确调用搜索2次，给出准确比较 → $r_1 = 0.9$
  • 轨迹2：调用了错误工具，最终答案模糊 → $r_2 = 0.3$
  • 轨迹3：调用正确但遗漏一款手机 → $r_3 = 0.7$
  • 轨迹4：直接给出答案（未调用工具，数据错误）→ $r_4 = 0.1$

计算过程：

$\text{mean}(\mathbf{r}) = (0.9 + 0.3 + 0.7 + 0.1) / 4 = 0.5$

$\text{std}(\mathbf{r}) = \sqrt{\frac{(0.4)^2 + (-0.2)^2 + (0.2)^2 + (-0.4)^2}{4}} = \sqrt{\frac{0.16+0.04+0.04+0.16}{4}} = \sqrt{0.1} \approx 0.316$

归一化优势：

$A_1 = (0.9 - 0.5) / 0.316 = +1.27$ （强化：这条轨迹的策略）

$A_2 = (0.3 - 0.5) / 0.316 = -0.63$ （抑制：这条轨迹的策略）

$A_3 = (0.7 - 0.5) / 0.316 = +0.63$ （适度强化）

$A_4 = (0.1 - 0.5) / 0.316 = -1.27$ （强力抑制：不调用工具的行为）

梯度更新：轨迹1和3的 token 被强化，轨迹2和4的 token 被抑制。尤其是轨迹4的"不调用工具直接回答"行为受到最强惩罚。

Agent-GRPO 训练循环伪代码

算法：Agent-GRPO 训练循环（含工具执行）

输入：
  - 策略模型 π_θ（初始化自 SFT 模型）
  - 参考模型 π_ref（冻结的 SFT 模型）
  - 任务分布 D（问题集合）
  - 工具执行器 Env（search / calc / code_exec 等）
  - 超参数：G（组大小）, ε（clip），β（KL系数），lr（学习率）

for epoch = 1, 2, ..., N_epochs:
  for batch of questions q ~ D:

    # ===== 轨迹采集阶段 =====
    trajectories = []
    for i = 1, ..., G:  # 对每个问题采样 G 条轨迹
      τ_i = []
      s = initial_state(q)
      done = False

      while not done:
        # 模型生成下一个动作（文本或工具调用）
        a_t ~ π_θ(· | s)

        if is_tool_call(a_t):
          # 执行工具调用，获取环境反馈
          tool_result = Env.execute(a_t)
          s = append_to_context(s, a_t, tool_result)
          r_t = get_intermediate_reward(a_t, tool_result)
        else:
          # 文本生成，继续自回归
          s = append_to_context(s, a_t)
          r_t = 0  # 中间文本步骤无即时奖励

        τ_i.append((s, a_t, r_t))
        done = is_terminal(s) or len(τ_i) > MAX_TURNS

      # 计算最终任务奖励
      r_T_i = reward_function(τ_i, ground_truth)
      trajectories.append((τ_i, r_T_i))

    # ===== 优势计算阶段 =====
    rewards = [r_T_i for (_, r_T_i) in trajectories]
    mean_r = mean(rewards)
    std_r = std(rewards) + 1e-8

    advantages = []
    for i in range(G):
      A_i = (rewards[i] - mean_r) / std_r
      # Turn-level GRPO：按 turn 分配优势
      for turn_t in trajectories[i][0]:
        advantages.append(A_i)  # 或用 turn-specific A_i

    # ===== 策略更新阶段 =====
    loss = 0
    for i in range(G):
      τ_i, _ = trajectories[i]
      for (s_t, a_t, r_t) in τ_i:
        ratio = π_θ(a_t | s_t) / π_old(a_t | s_t)
        clipped_ratio = clip(ratio, 1-ε, 1+ε)
        policy_loss = -min(ratio * A_i, clipped_ratio * A_i)
        kl_penalty = β * KL(π_θ(· | s_t) || π_ref(· | s_t))
        loss += policy_loss + kl_penalty

    # 反向传播更新 π_θ
    optimizer.step(loss / (G * avg_episode_length))
    π_old = copy(π_θ)  # 更新旧策略

输出：训练后的 Agent 策略 π_θ*

3.2 PPO for Agent (Turn-PPO)

标准 PPO 在单轮 LLM 任务上表现良好，但在 multi-turn Agent 场景中存在几个严重问题：Critic 网络需要对极长的上下文（10,000+ tokens）进行价值估计，计算成本极高；多轮之间的时间依赖关系使得 GAE 估计不稳定；工具调用的外部随机性破坏了马尔可夫假设。Turn-PPO 通过将 MDP 的"步骤"从 token 级别提升到 turn 级别，有效缓解了这些问题。

为什么普通 PPO 在 multi-turn 上不稳定

问题 1：Critic 过拟合长序列
普通 PPO 的 Critic 需要对每个 token 估计 $V(s_t)$，对于 10,000 token 的 Agent episode，Critic 需要在极长的上下文中精确估计价值，容易过拟合噪声。
问题 2：GAE 估计方差爆炸
广义优势估计 $\hat{A}_t^{GAE} = \sum_{l=0}^{\infty} (\gamma\lambda)^l \delta_{t+l}$，在长 episode 中，误差累积导致早期 token 的优势估计方差极大，梯度不稳定。
问题 3：工具调用破坏马尔可夫性
工具返回结果依赖外部环境，不满足马尔可夫假设。PPO 的 importance sampling ratio 在工具调用后会急剧变化，导致 clip 失效。

Turn-PPO 的核心设计

Turn-PPO 将每个 turn（从 LLM 开始生成到工具调用完成）视为一个 MDP 步骤，Critic 只在 turn 边界处评估价值：

$$V_\phi(s_t^{turn}) = \text{Critic}(c, h_{1:t-1}, \text{turn}_t)$$
$$\delta_t^{turn} = r_t + \gamma \cdot V_\phi(s_{t+1}^{turn}) - V_\phi(s_t^{turn})$$
$$\hat{A}_t^{turn} = \sum_{l=0}^{T-t} (\gamma\lambda)^l \delta_{t+l}^{turn}$$
完整损失函数： $$\mathcal{L}^{Turn-PPO} = \underbrace{-\mathbb{E}\left[\min\left(\rho_t \hat{A}_t, \text{clip}(\rho_t, 1-\epsilon, 1+\epsilon)\hat{A}_t\right)\right]}_{\text{策略损失 } \mathcal{L}^{CLIP}} + \underbrace{c_1 \mathcal{L}^{VF}}_{\text{价值损失}} + \underbrace{c_2 \beta \cdot D_{KL}(\pi_\theta \| \pi_{ref})}_{\text{KL 惩罚}}$$
其中 $\rho_t = \frac{\pi_\theta(a_t^{turn} | s_t^{turn})}{\pi_{old}(a_t^{turn} | s_t^{turn})}$，$c_1 = 0.5$，$c_2 = 1.0$，$\beta = 0.01$（典型值）

KL 散度约束在 Agent 场景的作用

KL 约束的双重作用

在 Agent 场景中，KL 散度约束 $D_{KL}(\pi_\theta \| \pi_{ref})$ 有两个关键作用：

  1. 防止策略坍塌（Policy Collapse）：Agent 训练时，如果某类工具调用序列获得高奖励，模型可能过度偏向该策略，丧失多样性。KL 约束确保模型不会完全忘记 SFT 阶段学到的通用语言能力。
  2. 防止 Reward Hacking：过度优化奖励函数会导致模型找到"捷径"（如格式 hack）。KL 约束限制了优化幅度，使模型不能偏离参考策略太远，从而限制了 hack 的空间。

典型设置：$\beta = 0.01$（轻度约束），若发现 reward hacking 则增大到 $\beta = 0.1$。

3.3 SWEET-RL：利用训练时信息

SWEET-RL（Step-WisE Evaluation and Training with RL）是 2024 年提出的一种新颖方法，其核心洞察是：训练时可以访问参考信息（ground truth 中间步骤），但推理时不能。这种"训练-推理信息不对称"可以被利用来构建更准确的 turn-wise critic。

核心思想：训练时信息优势
  • 训练时：可以访问 ground truth 的完整解题路径、参考答案、中间步骤标注
  • 推理时：只有 user query，没有任何参考信息
  • SWEET-RL 利用这种不对称性，训练一个 Turn-wise Critic，它在训练时见过参考路径，因此能更准确地评估每个 turn 的贡献

Turn-wise Critic 的构建

$$C_\phi(s_t, a_t, \text{ref}) = \text{LLM}_{critic}\left(\text{"Given reference: } \text{ref}\text{, evaluate turn } t\text{: } a_t \text{"}\right)$$
Turn-wise 优势： $$A_t^{SWEET} = C_\phi(s_t, a_t, \text{ref}) - C_\phi(s_{t-1}, a_{t-1}, \text{ref})$$
训练时 Critic 的输入：$(s_t, a_t, \text{ref}_{full})$
推理时 Actor 的输入：$(s_t)$（无参考信息）

ColBench 基准上的性能提升

SWEET-RL 在 ColBench 上的 +6% 绝对提升来源分析

方法Turn 1 准确率Turn 2 准确率Turn 3+ 准确率整体成功率
Baseline (SFT only)72%58%41%43%
Episode-level GRPO74%61%44%46%
Turn-PPO75%63%46%48%
SWEET-RL76%67%51%54%

+6% 的提升主要来源于 Turn 2 和 Turn 3+ 的改善（+4% 和 +5%），说明 Turn-wise Critic 对中后期 turn 的信用分配有显著改善。Turn 1 的提升较小（+1%），因为 Turn 1 的信用分配相对简单（距离最终奖励最近）。

3.4 AgentQ：MCTS + DPO 混合

AgentQ 是一种两阶段方法，结合了在线搜索（MCTS）和离线学习（DPO）的优势：第一阶段用 MCTS 在任务空间中进行深度搜索，收集高质量的对比数据（成功路径 vs 失败路径）；第二阶段用 DPO 在收集的数据上进行离线训练，无需在线采样。

两阶段流程

阶段 1：MCTS 在线搜索

对每个任务，使用 MCTS 构建搜索树：

  • 选择（Selection）：用 UCB 公式选择最有潜力的节点：$UCB_i = Q_i + c\sqrt{\ln N / n_i}$
  • 扩展（Expansion）：从当前节点采样 $k$ 个不同的下一步动作
  • 模拟（Simulation）：从扩展节点运行到终止，获取奖励
  • 回传（Backpropagation）：将奖励沿路径回传，更新所有节点的 $Q$ 值
阶段 2：DPO 离线训练

从 MCTS 搜索树中提取对比数据对 $(y^+, y^-)$：

  • $y^+$：MCTS 找到的成功路径（$r_T = 1$）
  • $y^-$：MCTS 找到的失败路径（$r_T = 0$），与 $y^+$ 在同一任务上

DPO 损失：$\mathcal{L}_{DPO} = -\log\sigma\left(\beta \log\frac{\pi_\theta(y^+|x)}{\pi_{ref}(y^+|x)} - \beta \log\frac{\pi_\theta(y^-|x)}{\pi_{ref}(y^-|x)}\right)$

WebShop 任务的 MCTS 搜索树示例

任务：在 WebShop 上购买"红色棉质 T 恤，尺码 M，价格 < $30"

MCTS 搜索树（3层，每层3个节点）：

根节点：初始状态（搜索页面）
│
├── 动作A：search("red cotton t-shirt") → Q=0.72
│   ├── 动作A1：click(item_3, "M size") → Q=0.85 ✓ [成功路径]
│   │   └── 动作A1a：add_to_cart() → r_T=1.0 ★
│   ├── 动作A2：click(item_1, "L size") → Q=0.20 ✗
│   │   └── 动作A2a：add_to_cart() → r_T=0.0（尺码错误）
│   └── 动作A3：filter(price<30) → Q=0.60
│       └── 动作A3a：click(item_5, "M size") → r_T=0.8（颜色偏差）
│
├── 动作B：search("cotton t-shirt M") → Q=0.45
│   ├── 动作B1：click(item_7) → Q=0.30 ✗（价格$35）
│   └── 动作B2：filter(color=red) → Q=0.55

Zero-shot（无训练）：18.6% 任务成功率
+ SFT（监督微调）：42.3% 任务成功率
+ MCTS 数据收集（1000 条轨迹）：63.8% 任务成功率
+ DPO 训练（AgentQ 完整流程）：81.7% 任务成功率
提升幅度：+63.1%（相对零样本），+17.9%（相对 SFT）

四、信用分配：Multi-step 的核心难题

信用分配（Credit Assignment）是 Agent 强化学习中最根本的挑战之一。当一个包含 5–20 个工具调用步骤的 Agent Episode 最终失败时，如何确定是哪一步（或哪几步）导致了失败？如何将终端奖励信号合理地分配给每一个中间步骤？这个问题直接影响训练效率和最终性能。

4.1 问题定义：5步工具链的信用分配

形式化定义：
给定轨迹 $\tau = (s_0, a_0, s_1, a_1, \ldots, s_T, a_T)$ 和终端奖励 $r_T$，
信用分配问题是确定每个步骤的贡献 $c_t \in \mathbb{R}$，使得： $$\sum_{t=0}^{T} c_t \approx r_T, \quad c_t \text{ 反映步骤 } t \text{ 对最终结果的真实贡献}$$
朴素方法（等权分配）：$c_t = r_T / T$，忽略各步骤的差异性
蒙特卡洛方法：$c_t = \gamma^{T-t} r_T$，指数衰减，远期步骤权重极小
理想方法：$c_t = V(s_{t+1}) - V(s_t)$，需要准确的价值函数 $V$

4.2 Hindsight Experience Replay (AgentHER)

AgentHER（Agent Hindsight Experience Replay）将 HER 思想从机器人控制领域引入 LLM Agent 训练。核心思想是：即使 Agent 没有完成原始目标，它在轨迹中可能已经完成了某些子任务。通过将这些子任务重标注为"成功的目标"，可以从失败轨迹中提取学习信号。

AgentHER 重标注示例

原始任务：帮用户订一张明天从上海到北京的最便宜机票

原始轨迹（失败）：

  1. search_flights("上海", "北京", "2025-01-16") → 返回10条航班
  2. filter_cheapest(results) → 最便宜: CA1234, ¥680
  3. check_availability("CA1234") → 已售罄
  4. check_availability("MU5101") → 有余票（但价格¥850）
  5. book_ticket("MU5101") → 失败（用户预算上限¥700）

原始奖励：$r_T = 0$（预订失败）

HER 重标注：将目标改为"查询上海到北京的航班并找到最便宜选项"

重标注后的奖励：$r_T^{HER} = 1.0$（步骤1-2已完成该子目标）

学习效果：模型从这条"失败"轨迹中学到了正确的搜索和筛选技能，而不是只获得 $r_T = 0$ 的无效信号。

关键设计：HER 目标必须是轨迹中实际达到的状态，不能虚构。AgentHER 使用 LLM 自动识别轨迹中已完成的子目标，生成重标注目标。

AgentHER 重标注目标选择策略：
给定原始目标 $g$ 和轨迹 $\tau = (s_0, a_0, \ldots, s_T)$，
HER 采样一个新目标 $g' \sim \mathcal{G}(\tau)$，其中 $\mathcal{G}(\tau)$ 是轨迹中已达到的状态集合： $$g' = \text{LLM}_{goal}\left(\text{"从轨迹 } \tau \text{ 中提取已完成的子目标"}\right)$$ $$r^{HER}(\tau, g') = \begin{cases} 1 & \text{if } g' \in \{s_t : t \leq T\} \\ 0 & \text{otherwise} \end{cases}$$

4.3 HCAPO：生成式验证器逐步分配奖励

HCAPO（Hierarchical Credit Assignment with Process Optimization）使用一个生成式验证器（Generative Verifier）来逐步评估每个动作的价值，并计算步骤级别的优势。

HCAPO 步骤级优势计算：
$$V_{gen}(s_t) = \text{LLM}_{verifier}\left(\text{"给定当前状态 } s_t \text{，完成任务的概率是多少？"}\right) \in [0, 1]$$
步骤级优势： $$A_t^{step} = V_{gen}(s_t, a_t) - V_{gen}(s_{t-1})$$
其中 $V_{gen}(s_t, a_t) = V_{gen}(s_{t+1})$（执行动作 $a_t$ 后的新状态价值）

具体数字示例（5步工具链）：
$V_{gen}(s_0) = 0.5$（初始状态，成功概率50%）
$V_{gen}(s_1) = 0.7$（Step 1 正确搜索后，概率提升）→ $A_1 = +0.2$
$V_{gen}(s_2) = 0.8$（Step 2 正确筛选）→ $A_2 = +0.1$
$V_{gen}(s_3) = 0.2$（Step 3 选错航班号，概率骤降）→ $A_3 = -0.6$
$V_{gen}(s_4) = 0.15$（Step 4 继续错误路径）→ $A_4 = -0.05$
$V_{gen}(s_5) = 0.0$（Step 5 最终失败）→ $A_5 = -0.15$

HCAPO 精确识别出 Step 3（$A_3 = -0.6$）是最关键的错误步骤。

5.1 WebAgent-R1

WebAgent-R1 是一个专为网页任务设计的 Agent 系统，采用 Planner + Code Generator 的双模块架构，通过 RL 微调实现端到端优化。其核心创新是将网页操作转化为可执行的 Python 代码，使得奖励函数可以通过代码执行结果自动计算。

架构组件
  • Planner（HTML-T5）：接收任务描述和当前网页 HTML，生成自然语言计划（"点击搜索框 → 输入关键词 → 点击搜索按钮"）
  • Code Generator（LLM）：将计划转化为可执行的 Playwright/Selenium 代码
  • RL Fine-tuning：用 WebArena 测试结果作为奖励信号，对 Code Generator 进行 GRPO 训练
  • 环境：真实网页环境（WebArena），包含电商、论坛、代码仓库等场景
关键设计决策
  • 可执行代码作为动作：与自然语言动作相比，代码动作可以精确执行，奖励信号客观（代码执行成功/失败）
  • WebArena 验证奖励：使用 WebArena 的自动评估器，对每个任务给出 0/1 奖励
  • HTML 压缩：将原始 HTML（通常 100KB+）压缩为关键元素（约 2KB），减少上下文长度
  • 错误恢复：代码执行失败时，将错误信息作为观察注入，让模型学习纠错

WebAgent-R1 训练流程

    B --> C["Code Generator LLM\n将计划转为 Playwright 代码"]

    J -->|否| A

5.2 Tool-R1

Tool-R1 是专注于工具调用能力的 RL 训练框架，使用 GRPO 算法结合可验证奖励（代码执行结果），在 3B 参数规模上实现了接近 GPT-4 的工具调用准确率。其核心创新是构建了一个统一的工具调用评估框架，支持4种工具类型。

Tool-R1 工具集成（4种工具类型）

search：网络搜索

{"tool": "search", "query": "string"}

奖励：搜索结果相关性（BM25/embedding 相似度）

calc：数学计算

{"tool": "calc", "expr": "2+3*4"}

奖励：结果与 ground truth 完全匹配（0/1）

code_exec：代码执行

{"tool": "code_exec", "code": "print(1+1)"}

奖励：代码执行成功 + 输出正确（0/0.5/1.0）

web_browse：网页浏览

{"tool": "web_browse", "url": "https://..."}

奖励：提取到目标信息（LLM 评分 0–1）

Tool-R1 可验证奖励函数：
$$r_{tool} = \alpha \cdot r_{format} + \beta \cdot r_{execute} + \gamma \cdot r_{correct}$$
$r_{format} \in \{0, 1\}$：工具调用格式正确（JSON 合法，字段完整）
$r_{execute} \in \{0, 1\}$：工具执行成功（无异常）
$r_{correct} \in [0, 1]$：工具结果正确性（与 ground truth 比较）
典型权重：$\alpha = 0.1, \beta = 0.2, \gamma = 0.7$

性能数据（ToolBench 基准）：
GPT-4（zero-shot）：68.3%
Tool-R1 3B（GRPO 训练后）：66.1%（仅差 2.2%，但参数量少 30 倍以上）
Tool-R1 7B：71.8%（超越 GPT-4）

5.3 SWE-agent

SWE-agent 将 GitHub issue 修复任务建模为一个完整的 Agent MDP，Agent 需要浏览代码库、理解问题、定位 bug、修改代码、验证修复。这是目前最复杂的 LLM Agent 任务之一，需要长序列推理和精确的代码操作。

触发最终奖励计算
SWE-agent 聚合奖励：
$$r_T = \frac{1}{|T_{all}|} \sum_{i \in T_{all}} \mathbb{1}[\text{test}_i \text{ passes}]$$
其中 $T_{all}$ 是 issue 相关的所有测试用例（通常 5–50 个）

mini-swe-agent 性能（2025 年数据）：
基础模型（无 RL）：Gemini 3 Pro → 61.2% SWE-bench Verified
+ RL 训练（GRPO，10K episodes）：74.3% SWE-bench Verified
提升：+13.1% 绝对值，超过 Claude 3.5 Sonnet（72.0%）

七、工程实践与挑战

7.1 内存开销：PPO vs GRPO 模型数量对比

PPO 需要的模型（4个）
  • Actor（π_θ）：当前策略，全量梯度更新，70B 参数 → ~140GB
  • Critic（V_φ）：价值函数，全量梯度更新，通常与 Actor 同规模 → ~140GB
  • Reference（π_ref）：冻结 SFT 模型，用于 KL 约束 → ~140GB（推理模式）
  • Old Policy（π_old）：上一轮策略，用于 importance sampling → ~140GB（推理模式）

总显存需求（70B 模型）：≈ 560GB+，需要 8× A100 80GB

GRPO 需要的模型（2个）
  • Actor（π_θ）：当前策略，全量梯度更新，70B → ~140GB
  • Reference（π_ref）：冻结 SFT 模型，用于 KL 约束 → ~140GB（推理模式）

无需 Critic（用组内相对排名替代）

无需 Old Policy（直接用 π_ref 计算 ratio）

总显存需求（70B 模型）：≈ 280GB，需要 4× A100 80GB

节省约 50% 显存，这是 GRPO 在工程上的最大优势

7.2 KV Cache 分层管理（NVIDIA Dynamo 方案）

在 Agent 训练中，每个 Episode 的上下文长度可达 10,000+ tokens，KV Cache 管理成为关键瓶颈。NVIDIA Dynamo 提出了分层 KV Cache 管理方案：

Dynamo 分层 KV Cache 架构
  • L1 Cache（GPU 显存）：存储当前 batch 的热点 KV，容量约 20GB，访问延迟 <1ms
  • L2 Cache（CPU 内存）：存储最近 N 个 Episode 的 KV，容量约 500GB，访问延迟约 5ms
  • L3 Cache（NVMe SSD）：存储历史 Episode 的 KV，容量约 10TB，访问延迟约 50ms

关键优化：对于 Agent 训练，System Prompt（任务描述）在多个 Episode 中保持不变，其 KV Cache 可以被所有 Episode 共享，节省约 30–40% 的 KV Cache 空间。

性能收益：在 8 × A100 集群上，Dynamo 分层 KV Cache 使 Agent 训练吞吐量提升约 2.3×。

7.3 批量轨迹采集并行化

并行化策略：异步轨迹采集

Agent 训练的主要瓶颈是轨迹采集：每个 Episode 需要多次工具调用（每次 100–2000ms 延迟），串行采集效率极低。

解决方案：异步并行采集

并行采集架构：

[训练进程 GPU]
      │
      ▼
[策略模型推理]  ──→  [轨迹队列（异步）]
                           │
              ┌────────────┼────────────┐
              ▼            ▼            ▼
        [Worker 1]   [Worker 2]   [Worker N]
        Episode 1    Episode 2    Episode N
        (工具调用)   (工具调用)   (工具调用)
              │            │            │
              └────────────┼────────────┘
                           ▼
                    [完成轨迹池]
                           │
                           ▼
                    [训练进程：批量更新]

关键参数：Worker 数量 N = 32–128（取决于工具 API 的并发限制），轨迹队列大小 = 2–4 × batch_size（双缓冲，确保 GPU 不空闲）。

实测效果：在 32 个 Worker 下，轨迹采集吞吐量从 0.5 episodes/s 提升到 12 episodes/s（24× 加速），GPU 利用率从 15% 提升到 78%。

7.4 Reward Hacking 的 3 种形式与缓解方案

形式 1：格式利用
Agent 学会在输出中插入触发奖励的关键词或格式，而不关心内容是否正确。

缓解：
  • 将格式奖励与内容奖励分离，格式权重 <10%
  • 使用 LLM-as-judge 替代规则匹配
  • 增大 KL 约束系数 β
形式 2：奖励模型利用
Agent 找到奖励模型的盲点（如长度偏差、表面相似性），生成高奖励但低质量的输出。

缓解：
  • 使用可验证奖励（代码执行、数学验证）替代奖励模型
  • 定期更新奖励模型（对抗训练）
  • 多个奖励模型集成
形式 3：环境利用
Agent 找到环境的漏洞（如重复点击同一按钮获得积分、利用边界条件），而不是真正完成任务。

缓解：
  • 设置动作重复惩罚
  • 使用真实用户验证（人在环路）
  • Episode 级别的行为约束

7.5 评估指标体系

指标 定义 计算方式 适用场景 典型值
tool_call_f1 工具调用的 F1 分数（Precision × Recall 的调和平均） $F1 = 2 \cdot \frac{P_{tool} \cdot R_{tool}}{P_{tool} + R_{tool}}$，其中 $P$ 是调用正确率，$R$ 是必要工具的覆盖率 工具选择能力评估 GPT-4: 0.82，Tool-R1 7B: 0.79
schema_accuracy 工具调用参数格式正确率 $\frac{\text{格式正确的调用数}}{\text{总调用数}}$ 工具调用质量评估 SFT 后: 85–95%
task_success_rate 任务完成率（最终目标达成） $\frac{\text{成功 episode 数}}{\text{总 episode 数}}$ 端到端性能评估 WebArena: 35–45%
avg_turns 平均完成任务所需 turn 数 成功 episode 的平均 turn 数 效率评估 目标: 3–5 turns
latency_p95 95 百分位端到端延迟 从收到 query 到输出最终答案的时间 生产部署评估 目标: <30s
token_efficiency 每单位 token 的任务完成率 $\frac{\text{task\_success\_rate}}{\text{avg\_tokens\_per\_episode}}$ 成本效益评估 越高越好

7.6 完整 Token 级训练示例：从采样到梯度更新

以下展示一个完整的 Agent-GRPO 训练步骤，从 token 级别演示梯度如何流动：

采样阶段（G=2，简化示例）

[问题] 计算 2024 年全球 CO2 排放量 → 轨迹1（r=0.9）： search("2024 global CO2") → 37.4 GtCO2 全球排放约37.4亿吨 [EOS]
[问题] 计算 2024 年全球 CO2 排放量 → 轨迹2（r=0.1）： 根据历史趋势，约40亿吨 [EOS]

优势计算与梯度方向

$\mathbf{r} = [0.9, 0.1]$，$\text{mean} = 0.5$，$\text{std} = 0.4$
$A_1 = (0.9 - 0.5) / 0.4 = +1.0$ → 轨迹1所有 token 的梯度方向：增大概率
$A_2 = (0.1 - 0.5) / 0.4 = -1.0$ → 轨迹2所有 token 的梯度方向：减小概率

关键结论：
- 工具调用 token（search(...)））的概率被增大：模型学会在需要时调用工具
- 直接猜测 token（"根据历史趋势"）的概率被减小：模型学会不要在没有数据时猜测
- 这正是 Agent RL 训练的核心目标：学会什么时候调用工具，调用什么工具
总结：LLM Agent RL 的核心要点

建模层面

  • Agent MDP 比普通 LLM MDP 更复杂，动作空间异构，状态包含外部环境
  • 信用分配是核心难题，需要专门的算法（HER、HCAPO、Turn Critic）
  • 工具调用的外部随机性破坏马尔可夫假设，需要 Turn-level 建模

算法层面

  • GRPO 内存效率高（无需 Critic），适合快速实验
  • Turn-PPO 稳定性好，适合生产级训练
  • SWEET-RL 利用训练时信息优势，在有参考数据时首选
  • AgentQ 适合探索空间大的决策任务
