1. 核心问题与动机

在软件工程 Agent（SWE-Agent）的训练和推理中，验证代码补丁的正确性通常依赖于在 Docker 容器内运行单元测试。这带来巨大的工程负担：

  • 每个代码仓库需要定制 Docker 镜像，配置依赖环境
  • 环境配置耗时，不同仓库依赖冲突频繁
  • 在大规模 RL 训练中，运行数万次测试的计算和时间成本极高

Dockerless 的核心假设：正确性判断不一定需要执行代码。通过 Agent 对代码仓库的主动探索和静态分析，可以在不运行任何测试的情况下评估补丁质量。

6. 消融实验与关键发现

  • Agentic 探索 vs. 固定静态分析：允许 Agent 自适应搜索比固定规则分析 AUC 高约8点
  • SFT 过滤效果：用 Dockerless 过滤后的轨迹训练，比随机采样轨迹提升明显
  • RL 奖励信号质量：Dockerless 奖励信号与真实测试信号的相关系数约 0.82
  • 多语言的特别收益：SWE-bench Multilingual +8.7% 是最大提升，说明 Dockerless 在多语言仓库上的环境配置优势更明显

7. 局限性

  • 对于依赖运行时状态（如数据库状态、网络请求）的 bug，静态分析无法完全验证
  • Agentic 探索本身需要多次 LLM 调用，推理成本不可忽视
  • 在极度复杂的仓库（如 Linux 内核）上，证据收集的覆盖率仍有限

8. 核心洞见与读后评注

关键洞见：代码正确性验证的核心是"收集证据"，而不一定是"执行代码"。Dockerless 将验证问题转化为一个信息检索和推理任务，彻底绕开了环境配置的工程瓶颈，同时构建了完整的无环境后训练闭环。

这篇论文最重要的工程贡献是打通了一个完整的"无 Docker 代码 Agent 后训练 Pipeline"。对于工业界的代码 Agent 开发团队，环境配置往往是 RL 训练规模化的最大瓶颈。Dockerless 的出现意味着可以在任意代码仓库上进行 Agent 训练，无需为每个仓库单独准备环境。

从方法论角度，将"执行验证"转化为"Agentic 证据推理"是一个重要的范式转变。它揭示了 LLM 在代码理解上的一个独特优势：语义层面的理解有时比机械执行更高效地捕捉程序意图。
