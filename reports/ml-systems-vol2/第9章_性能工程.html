一、内存墙与 Roofline

H100：FP16 峰值 ~989 TFLOP/s，HBM 带宽 3.35 TB/s → ridge point（FP16）：

$$I_{\text{ridge,FP16}} = \frac{989 \times 10^{12}}{3.35 \times 10^{12}} \approx 295\ \text{FLOP/byte}$$

FP8 算力 ~1979 TFLOP/s → $I_{\text{ridge,FP8}} \approx 591$ FLOP/byte。算术强度低于 ridge → memory-bound；高于 → compute-bound。

batch-1 decode 为何 MFU 个位数仍「正常」

自回归 decode 算术强度 ~1 FLOP/byte，远低于 295——GPU 在等 HBM 搬权重，不是 Tensor Core 不够快。比 GPU 应看带宽 + 容量，不是峰值 TFLOP/s alone。

二、Prefill / Decode 双体制

2.1 Prefill（提示处理）

一次 forward 并行处理 $S$ 个 token，GEMM 形状含 batch=$S$。$S=1024$ 时 $I \approx 2S/2 = 1024$ FLOP/byte（FP16 权重）→ Tensor Core 吞吐限制。FlashAttention 对 prefill 收益最大（消 $S^2$ 中间矩阵）。

2.2 Decode（逐 token 生成）

$$I_{\text{decode}}(B) = \frac{2PB}{P s_{\text{param}} + B d_{\text{model}} s_{\text{elem}}}$$

$B=1$ 时 deeply memory-bound；增大 $B$ 线性提高 $I$，但 KV cache 占满 HBM——70B FP16 140 GB 权重占 8×H100 后，每卡约 62.5 GB 给 KV。

配置目标典型手段
实时聊天TTFT <200 ms，ITL <50 ms低精度权重、spec decode
批处理摘要吞吐 / 成本大 batch、INT4/FP8

三、融合、FP8 与编译

3.1 算子融合

Conv-BN-ReLU 未融合：3 次 launch、6 次 HBM 往返。Transformer 层 bias-GELU-dropout 融合可省 67 MB/层 × 80 层 ≈ 5.4 GB/forward 流量。

FlashAttention（IO-aware）

$S=8192$，64 head，$d=128$，FP16：朴素 attention HBM 驻留 ~34.9 GB/层；FlashAttention 持久状态 ~537 MB/层 → ~65× 材料化状态削减（online softmax 在 SRAM 分块）。

decode 阶段收益较小（瓶颈是 KV 读而非 $S^2$ 矩阵），prefill 长上下文收益最大。

3.2 FP8 精度红利

FP8 Tensor Core 算力 2× FP16，字节数减半 → decode 有效带宽 2×；prefill 同时吃算力+带宽。Horowitz 量级：HBM 读 ~640 pJ vs SRAM ~0.5 pJ——融合把访问从 HBM 拉到 SRAM，1000 GPU 可省 ~320 kW 内存子系统功率。

3.3 推荐优化顺序（memory-bound serving）

  1. 瓶颈修复：memory-bound batch-1 → INT4/FP8 权重 + KV 压缩 先于 compile
  2. FlashAttention 族 + PagedAttention
  3. torch.compile / CUDA Graph 消 launch gap
  4. Speculative decoding（最后，需 draft 模型）

四、案例：70B LLM Serving Playbook

目标：8×H100 NVLink；TTFT <500 ms，ITL <50 ms，集群吞吐 ≥1000 tok/s。基线（FP16 eager）：TTFT 1200 ms，ITL 85 ms，280 tok/s，max batch=4。

Round 1 — 精度工程

  • AWQ INT4 权重：17.5 GB/GPU → 4.4 GB/GPU；权重读流量 ~4× 降
  • INT8 KV cache：每请求 cache 2× 小 → 可用 KV 从 ~62.5 GB 升到 ~75.6 GB/GPU
  • 结果：batch=1 ITL 48 ms ✓；batch=32 吞吐 720 tok/s（仍不足）

Round 2 — 融合

  • torch.compile max-autotune：element-wise 14%→4%
  • FlashAttention-2 + CUDA Graph：launch overhead 12%→~0；attention decode −30%
  • 结果：TTFT 380 ms ✓，ITL 32 ms，batch=32 吞吐 1050 tok/s ✓

Round 3 — 自适应 Speculative Decoding

1.5B INT4 draft（0.75 GB）一次提案 5 token（4 ms）；70B 验证 ~32 ms。$p_{\text{acc}}=0.78$，$k=5$：

$$\text{ITL}_{\text{eff}} = \frac{4+32}{(1-0.78^{6})/(1-0.78)} \approx \frac{36}{3.5} \approx 10.3\ \text{ms/token}$$

相对 Round2 的 32 ms 约 3.1×。但 batch≥16 时 verification 不再「免费」→ 仅低负载开 spec，高负载回退自回归。

4.1 速增不可相乘

INT4 先缓解 HBM 压力后，FlashAttention 单独测 1.9×，叠加仅再 1.4×——二者都攻击内存项，第一轮后瓶颈迁移。Round1 后大 batch 偏 compute-bound；再堆带宽优化收益递减。

五、章节总结

Playbook 要点

  1. 先测后优：症状 → 应用层 → 分布式 → kernel；错诊 = 零收益
  2. prefill 优化 FLOPs/FlashAttention；decode 优化 bytes（量化、KV、带宽）
  3. FP8/INT4 是带宽杠杆；融合是 HBM 往返杠杆；compile 是 launch 杠杆
  4. 每轮优化后 reprofile——waterbed 效应，下一刀看新瓶颈
  5. 生产栈典型组合：INT4 + INT8 KV + FlashAttention-2 + compile + 条件 spec decode
性能工程不是追 peak TFLOP/s，而是让 tensor 路径匹配硅片物理：更少字节、更少 launch、更久留在 SRAM——在 C³ 的 Compute 维把 placement 与通信之外「本地执行」的浪费挤干。
