一、Llama 3 锚点：可靠性算术

Meta 在 16,384 张 H100 上训练 Llama 3，wall-clock 54 天，期间记录 419 次硬件/软件故障。平均故障间隔 MTTF ≈ $(54 \times 24) / 419 \approx \mathbf{3.1\ \text{h}}$——约每 3 小时一次中断，不是偶发工单，而是训练背景噪声。第 4 章把 350 GB 梯度 AllReduce 定价为通信问题；本章追问：当任一 rank 在 3 h 内必然失效，months-long run 如何不被拖垮？

单卡 MTBF 约 50,000 h（~5.7 年）看似可靠；fleet 按串联模型缩放：

$$\text{MTBF}_{\text{system}} = \frac{\text{MTBF}_{\text{component}}}{N} = \frac{50{,}000}{16{,}384} \approx 3.05\ \text{h}$$

与 Llama 3 观测 3.1 h 几乎重合——说明 GPU 本体已主导失效率；若再计入 PCIe retimer、电源域、leaf 交换机，$\lambda_{\text{system}}$ 还会略升。10k H100 集群实测级联故障率 $\lambda \approx 0.271$ 次/h → MTBF ≈ 3.7 h（~6.5 次/天），与 Llama 3 同量级。

系统可靠度：$R_{\text{system}} = (R_{\text{component}})^N$

独立组件串联：任一失效则同步训练步无法完成。

Llama 3 手算：单 GPU 可用性 99.9%（$R=0.999$），$N=16{,}384$：

$$R_{\text{cluster}} = 0.999^{16384} \approx 1.6 \times 10^{-7}$$

任意时刻全 fleet 同时可用概率趋近于零——不能指望硬件「全绿」，软件必须用 checkpoint + 弹性恢复持续吸收失效。54 天内 419 次故障意味着平均每次恢复若浪费 30 min 有效算力，累计损失 ≈ 209 GPU·h × 16k 卡规模下的协调成本——容错不是运维选项，是完成 pretrain 的前置条件。

可靠性算术给出第一个工程结论：checkpoint 间隔、检测 timeout、恢复路径必须在 ~3 h MTTF 量级上设计，而非按「几周一故障」的实验室经验。

还可从故障率反推「有效训练时间占比」。设 MTTF = 3.1 h，平均恢复 $T_{\text{recover}} = 0.25$ h（15 min），则长期稳态：

$$\eta_{\text{avail}} = \frac{\text{MTTF}}{\text{MTTF} + T_{\text{recover}}} = \frac{3.1}{3.35} \approx 92.5\%$$

仅 fail-stop 恢复就吃掉 ~7.5% $\eta_{\text{runtime}}$——尚未计入 checkpoint pause、SDC rollback、gang 排队。Llama 3 54 天若 $\eta_{\text{avail}} = 92.5\%$，等价于多烧 ~4 天算力在 restart 上；把 $T_{\text{recover}}$ 从 15 min 压到 5 min → $\eta_{\text{avail}} \approx 97.4\%$，节省 ~2.6 天 wall-clock。下一节用 Young-Daly 把 MTTF 直接映射为 checkpoint 频率，并接上第 3 章存储 tier 的 GB 账单。

二、Young-Daly 与检查点存储

checkpoint 在「丢多少进度」与「写 checkpoint 吃多少算力」之间取 U 形最优。Young-Daly 公式（Daly 2006 对 Young 1974 的扩展）给出闭式解：

$$\tau_{\text{opt}} = \sqrt{2 \cdot T_{\text{write}} \cdot \text{MTBF}_{\text{system}}}$$

$\tau$ = checkpoint 间隔；$T_{\text{write}}$ = 单次 checkpoint wall-clock 写时间（含 barrier + I/O）；MTBF = 系统平均故障间隔。总浪费 = checkpoint 开销 + 期望重做工作，在 $\tau_{\text{opt}}$ 取最小。

Llama 3 量级算例

取 $\text{MTBF}_{\text{system}} = 3.1$ h。70B LLM 全状态 checkpoint（权重 + Adam $m,v$）约 350–700 GB；175B 超 1 TB（见第 3 章：350 GB 权重 + 1,400 GB 优化器 ≈ 1,750 GB）。

若 16k GPU 分片写、本地 NVMe 同步（第 3 章推荐路径）使 $T_{\text{write}} = 12$ min = 0.2 h：

$$\tau_{\text{opt}} = \sqrt{2 \times 0.2 \times 3.1} = \sqrt{1.24} \approx 1.11\ \text{h}$$

若错误地写远端 PFS、$T_{\text{write}} = 45$ min = 0.75 h（争用训练读 tier）：

$$\tau_{\text{opt}} = \sqrt{2 \times 0.75 \times 3.1} \approx 2.16\ \text{h}$$

写慢不仅拉长 pause，还推远最优间隔——每次故障平均多丢 ~1 h 进度。Llama 3 若按 ~1 h checkpoint，与 $T_{\text{write}} \approx 10$–15 min 的假设自洽。

2.1 链第 3 章：checkpoint GB 与存储 tier

第 3 章将 checkpoint 定位为「保险丝」——与训练读「燃料线」争用不同带宽剖面。最优路径：同步写本地 NVMe（Tier 2）→ 异步复制 PFS/S3（Tier 3/4）。175B 检查点 1,750 GB / 10 min → 平均写带宽：

$$\text{BW}_{\text{ckpt,avg}} = \frac{1750\ \text{GB}}{600\ \text{s}} \approx 2.9\ \text{GB/s per job}$$

256 节点各写 ~6.8 GB 分片，30 s 内完成 → 每节点 ~227 MB/s，单盘 NVMe 可承受；但 128 节点同时打 PFS → 1.8 TB 突发，必须与训练读分 tier。Llama 3 规模（16k 卡）下，$T_{\text{write}}$ 直接决定 Young-Daly 的 $\tau_{\text{opt}}$——投资 NVMe + GDS 不是存储章孤立话题，是容错章的 ROI 杠杆。

集群加倍 → MTBF 减半 → $\tau_{\text{opt}}$ 仅 ×$\sqrt{2} \approx 1.4$，不必线性加倍 checkpoint 频率；但必须压 $T_{\text{write}}$，否则 checkpoint tax 吃掉 MFU。企业 NVMe 1 DWPD × 7.68 TB ≈ 7.68 TB/天可写；每 1 h 写 700 GB 分片 ≈ 16.8 TB/天——需多盘条带或降 checkpoint 粒度（仅 sharded optimizer state）。

Young-Daly 总浪费率可展开为（Daly 2006）：

$$W(\tau) = \frac{T_{\text{write}}}{\tau} + \frac{\tau}{2 \cdot \text{MTBF}}$$

第一项 = checkpoint 频率 × 单次写开销；第二项 = 期望故障间隔内平均重做工作量（三角形分布近似）。对 $\tau$ 求导令 $dW/d\tau = 0$ 即得 $\tau_{\text{opt}} = \sqrt{2 T_{\text{write}} \cdot \text{MTBF}}$。代入 Llama 3 参数（$T_{\text{write}}=0.2$ h，MTBF = 3.1 h）：

$$W_{\min} = 2\sqrt{\frac{T_{\text{write}}}{2 \cdot \text{MTBF}}} = 2\sqrt{\frac{0.2}{6.2}} \approx 11.4\%$$

即最优策略下仍有 ~11% 时间花在 checkpoint + 重做——这是 months-long run 的物理下限，只能通过更快 NVMe/GDS（降 $T_{\text{write}}$）或更大 MTBF（更小 $N$ 或更可靠硬件）压缩，不能靠「少 checkpoint」逃避。

Young-Daly 假设 fail-stop 且恢复时间远小于 MTBF。SDC（静默数据损坏）破坏该假设——下一节展开。

三、故障谱系与检测

Llama 3 的 419 次故障并非同质：部分 rank 硬挂（fail-stop），部分仍响应但梯度 poison（SDC），部分与 rack PDU / 交换机 correlated。检测策略必须分型，否则要么误杀慢 rank，要么放行 poison 步。

3.1 Fail-stop 与 heartbeat

同步训练中一个 rank 沉默 → 其余 16,383 GPU 空等计费。timeout 需统计标定：

$$T_{\text{timeout}} = H + k\sigma_d, \quad k \approx 3\text{–}5$$

$H$ = 正常 heartbeat 间隔，$\sigma_d$ = 延迟抖动标准差。过紧会把正在写 checkpoint 的慢 rank误判为故障，触发不必要全局 restart；过松则在检测窗口内烧掉整 fleet 算力。Llama 3 级 run 常在 checkpoint 期间临时放宽 timeout，写完再收紧。

3.2 SDC 与 check-and-verify

Check-and-Verify 机制

对每块 gradient shard / AllReduce 结果计算 CRC 或 hash，跨 rank 比对或做冗余归约；digest 不一致则阻塞 optimizer step。AllReduce 默认假设「活着即正确」——16k GPU fleet 下必须「Trust, but verify」。

暴露算例：单卡 SDC 率 $10^{-6}$/h，2 s 步长、16,384 GPU → 每步 fleet 暴露 ~9.1 GPU·h，$\Pr(\ge1\ \text{SDC/步}) \approx 1 - e^{-9.1 \times 10^{-6} \times 2/3600} \approx 0.005\%$ → 约每 20,000 步（~11 h）一次静默错误。无校验则半天内参数被污染；Google TPU fleet 用 gradient norm spike + 热备 drain 可疑芯片。

浮点指数位单 bit flip 可把梯度放大 $10^{38}$ 量级——loss 曲线看似「训练正常」实则已毁。SDC 比 crash 更危险：无异常栈，只有 rollback 到已验证的 checkpoint。Llama 3 若每 1 h checkpoint、11 h 遇 SDC，最多浪费 1 h 进度；若无 verify、SDC 持续 24 h 才被发现，等价于整整一天算力产出有毒。

四、恢复路径与 ML 经济性

检测之后是恢复。分布式 LLM 训练的状态不是单进程 checkpoint 能概括的——optimizer sharding、PP stage、TP group 都需一致重建。

4.1 分布式 checkpoint 与弹性 rendezvous

  • 同步 checkpoint：全员 barrier 后写；语义简单，但拉长步时、与 heartbeat timeout 冲突
  • 异步 checkpoint：后台线程写上一版；训练继续，需版本化防半写读
  • TorchElastic：rendezvous 重建进程组，$N_{\min}$–$N_{\max}$ 弹性伸缩——为第 4 章 3D 并行提供「丢 rank 后重组」的入口

Llama 3 恢复典型路径（与 Slurm/K8s 编排联动）：

  1. 检测（30 s–2 min）：NCCL watchdog / heartbeat 超时，定位 fail rank 与 correlated 域（同 rack？）
  2. Drain（1–3 min）：Slurm scontrol update NodeName=… State=DRAIN 或 K8s taint，防止坏卡被重新调度
  3. Checkpoint 加载（5–10 min）：从本地 NVMe 读最近 verified 分片，并行 hydrate optimizer state
  4. Rendezvous（2–5 min）：TorchElastic/c10d 重建进程组，3D 并行坐标（TP/PP/DP）须与放置一致
  5. Resume：从断点 step 继续，首步 AllReduce 做 check-and-verify

合计 wall-clock 10–20 min 在 54 天 run 中可接受；但若 MTTF 仅 3.1 h，恢复占 15 min 意味着 ~8% 时间花在 restart——仍须优化 $T_{\text{write}}$ 与 gang 快速重分配（第五节）。419 次 × 15 min ≈ 104 GPU·h 级协调开销（单 rank 视角），fleet 级乘 16k 的空等成本远高于此。

故障成本量级

16,384 GPU × \$2/GPU·h ≈ \$786k/天 算力。丢 24 h 进度 ≈ \$786k + 排期延误 + 机会成本（竞品先发）。一次 15 min 空等 ≈ \$16k。Checkpoint 700 GB × 每 1 h ≈ 16.8 TB/天写放大——存储 ROI 与算力 ROI 同表核算。

4.3 故障注入与 staging 验证

TensorFI / NVBitFI / PyTorchFI 在 tensor 层注入；staging 用 chaos 分区、延迟、kill pod 验证恢复路径。软件注入快但可能跳过 ECC 掩蔽——生产 SLA 声明需硬件校准（beam test、Fidelity 映射）。Llama 3 级 run 在正式开跑前应用缩小版 gang（256–1024 GPU）做 end-to-end 故障演练，量测实际 $T_{\text{recover}}$ 而非假设值。

至此，容错闭环完成：MTTF 算术 → $\tau_{\text{opt}}$ → 分型检测 → checkpoint 恢复。但 Meta 工程师还会发现另一种空转——硬件全绿，16k GPU 却在队列里等 gang 凑齐，或在 AllReduce 里等拓扑不佳的 straggler。故障之外，调度同样决定 months-long run 能否在 54 天内跑完；checkpoint 间隔与 gang 放置是同一 C³ coordination 预算的两面。

五、故障之外：调度引起的 GPU 空转

10,000 GPU × \$2/GPU·h = \$480k/天。fleet 利用率从 50% 提到 80% 等价于白买 3,000 GPU·当量，年省 \$52M 量级——与容错投资同量级杠杆。ML 调度区别于普通云 batch job：同步 AllReduce 要求 gang scheduling（全有或全无）——1024 GPU 任务拿到 900 块仍 100% 浪费（~\$1,800/h 空烧），因缺 rank 无法完成一步迭代。

War Story：OpenAI K8s gang 死锁（2021）

7,500 节点 K8s 上两个实验各要整集群；调度器各放一半 pod → 两个 job 都无法 AllReduce → 集群「很忙」但零 useful step。Llama 3 若犯同样错误：16k 卡看似满载，实际可能两个 pretrain 互相占坑却都跑不动——419 次硬件故障之外，还会叠加人为调度死锁。教训：分布式 ML 必须把 gang 语义编进调度器（Slurm job array + pack、K8s PodGroup / Volcano / Kueue），「部分 pod 已调度」≠ 部分进度。

gang 语义与第 4 章 3D 并行绑定：TP group 必须同节点 NVLink，PP stage 需相邻 rack，DP replica 需 rail-aligned AllReduce——拓扑约束是 gang 调度的子集。此外，multi-tenant fleet 面临 fragmentation：剩余 GPU 总量够开 16k gang，但被小 job 切成无法拼齐的碎片。

例：20k GPU fleet，Job A 占 12k，Job B 占 5k，剩余 3k——不够任何 8k+ pretrain，3k 卡空转或只能跑小 trial。Consolidation 策略：低优先级 job 抢占 + checkpoint 让路（Slurm PreemptMode），或 Tiresias 按 attained service 重排队列。Llama 3 级 flagship job 通常独占 partition（--exclusive）规避 fragmentation——代价是 fleet 利用率数字难看，但 Goodput（有效 pretrain 步）最大化。

六、编排范式：Slurm vs Kubernetes

大 pretrain 与推理服务对编排器的诉求分裂：前者要 gang、fair-share、长 job 抢占策略；后者要 Deployment、HPA、快速 pod 替换。Llama 3 类 job 常见落点：Slurm partition 跑 pretrain，K8s 管 CI/CD / RBAC / 推理——混合而非宗教战争。

6.1 Slurm ML 扩展

  • --gres=gpu:h100:8 + --exclusive：整节点 gang，避免 NVLink 邻居被抢
  • --array=0-99：超参 sweep 一次提交，scheduler backfill 小 trial 填 gang 空隙
  • 异构 job（hetjob）：8 GPU 节点训练 + CPU 节点 tokenization 并行
  • PreemptMode + GraceTime：SIGTERM → 60–300 s 写 checkpoint（第二节 NVMe 路径）→ SIGKILL
  • TRES 加权：H100 GPU·h 与 V100 不同价，fair-share 按经济成本而非核数
  • prolog/epilog：启动前查 NVLink 拓扑、ECC 计数；失败节点自动 drain

6.2 Kubernetes 与混合架构

K8s 控制环天然适合推理：Deployment 保副本数、node 失效自动换 pod。分布式训练需 PyTorchJob/MPIJob + PodGroup 保证 gang——否则重现 OpenAI 死锁。混合模式：K8s Operator 把 TrainingJob CRD 翻译成 sbatch，用户面统一 YAML，执行面仍用 Slurm gang。

# TorchElastic：声明弹性范围，供调度器 resize
torchrun --nnodes=128:256 --nproc_per_node=8 \
  --rdzv_backend=c10d --max_restarts=3 train.py

128:256 节点 = 1,024–2,048 GPU。负载低时扩 gang 减 wall-clock；高优先级 job 到达时缩 gang + checkpoint 让路——与 Young-Daly 的 $\tau_{\text{opt}}$ 联动：resize 太频则 $T_{\text{write}}$ 爆炸。

七、拓扑感知放置

gang 凑齐只是第一步；放错拓扑同样烧算力。64 GPU 随机散列 vs 同 leaf 打包：1 GB AllReduce 延迟 120 ms → 25 ms（4.8×）。Llama 3 的 3D 并行（TP×PP×DP）把放置规则写死：

$$\text{Cost}_{\text{locality}} = \sum_{i

$d=0$ 同节点 NVLink（$w=0$）；$d=1$ 同 rack leaf（$w=1$）；$d=2$ 跨 rack IB（$w=10$）。调度器最小化 collective 通信代价，而非单纯 bin-packing 提高利用率。

3D 并行放置规则（Llama 3 量级：TP=8, PP=16, DP=128 → 16k GPU）

  1. TP=8：每组锁在同一 NVLink 节点（900 GB/s），绝不跨节点
  2. PP=16：相邻 stage 放同 rack leaf（~50 GB/s，1 hop），减 pipeline bubble 激活传输
  3. DP=128：副本跨 rack；rail-aligned——各节点 GPU $r$ 连同一 ToR，AllReduce 不跨 rail 争用

反例：TP 跨两节点 → 1 GB 激活 2.2 ms（NVLink）变 20 ms（IB），约 9× 慢，80 层 transformer 每层付税 → 端到端吞吐损失 15–30%。

静态 topology.conf 不够——「limping switch」CRC 高仍显示 up。生产级拓扑感知需三层信号：

  • 配置层：Slurm TopologyPlugin=topology/tree + topology.conf 定义 leaf/rack/block
  • 实测层：NCCL all-to-all 带宽矩阵；低于 P50 50% 的 GPU 对标记 straggler
  • 运维层：switch SNMP CRC/error counter；连续 3 次超阈 → 自动 drain rack

劣化 rack 若 >20% 降速且 run 还剩数周，触发 checkpoint 迁移（10–15 min）——又回到第二节 NVMe 写路径与第四节恢复 SLA。Llama 3 级 run 常在每日低负载窗口做 rack 迁移，避免与 peak AllReduce 争 IB。

拓扑与容错在此闭合：坏 rack 既是 correlated 故障源（第四节 PDU/交换机行），也是 straggler 源（拖慢全体 16k GPU 的同步步）。一次 5% straggler 在同步 AllReduce 中可让 $\eta_{\text{runtime}}$ 降至 ~95%——与 8% restart 开销同量级，须同等重视。

八、Goodput 与 ML 定制调度器

SM 占用 92% 不代表有效训练——Google C³ 用 Goodput 分解三类损失，Llama 3 级 run 应监控同一指标：

Goodput 三因子

$$\text{Goodput} = \eta_{\text{program}} \times \eta_{\text{runtime}} \times \eta_{\text{scheduling}}$$
  • $\eta_{\text{program}}$（Compute）：MFU、有效 FLOPs——代码是否喂满 H100
  • $\eta_{\text{runtime}}$（Communication）：AllReduce stall、故障恢复、straggler、checkpoint pause
  • $\eta_{\text{scheduling}}$（Coordination）：gang 排队、抢占、fragmentation、resize

三者相乘。例：$\eta_{\text{prog}}=0.35$，$\eta_{\text{run}}=0.85$（含 8% 恢复），$\eta_{\text{sched}}=0.90$ → Goodput ≈ 26.8%——fleet 看似忙，有效训练仅四分之一。419 次故障主要打 $\eta_{\text{runtime}}$；gang 死锁打 $\eta_{\text{scheduling}}$。

九、Spot、弹性与成本

容错基础设施的第二个 ROI：使 spot / 抢占实例经济可行。云 spot 可比按需便宜 60–70%，但随时被回收——没有第二节 checkpoint 栈 + 第四节弹性 rendezvous，spot 不可用。

$$C_{\text{effective}} = C_{\text{spot}} \times \frac{T_{\text{total}}}{T_{\text{productive}}}$$

算例：512 GPU × 14 天 70B fine-tune。按需 \$344k；spot 65% 折扣，但 15% 时间花在 panic checkpoint + restart → $T_{\text{productive}}/T_{\text{total}} = 0.85$：

$$C_{\text{effective}} = 0.35 \times 344\text{k} \times \frac{1}{0.85} \approx \$142\text{k}\ \text{（省 59%）}$$

wall-clock +18% 但 bill −59%——research budget 常见取舍。AWS spot 2 min / GCP 30 s 抢占通知 → GraceTime 内必须完成 NVMe 同步写（第二节），否则丢 >1 h 进度，spot 优势被 Young-Daly 惩罚抵消。

Llama 3 本身跑在 Meta 自有 fleet，但同一算术适用于 cloud burst：16k H100 按需 ≈ \$786k/天；若 30% spot 混部且 checkpoint 栈成熟，有效成本可降双位数百分比——容错与编排是成本方程的联合变量，不是事后运维。

Spot 混部可执行配置（Slurm + checkpoint 栈）

# Slurm：spot partition 允许抢占，GraceTime 对齐云厂商通知
PartitionName=spot PreemptMode=REQUEUE GraceTime=120
# prolog：注册 SIGTERM handler，触发 async checkpoint 到 NVMe
# epilog：上传 PFS 副本（第 3 章 Tier 3 异步路径）

# torchrun：max_restarts 与 spot 回收频率匹配
torchrun --max_restarts=10 --rdzv_backend=c10d ...

AWS spot 平均中断间隔 ~2–4 h（因实例类型/区域而异）——与 Llama 3 MTTF 3.1 h 同量级，同一套 Young-Daly $\tau_{\text{opt}} \approx 1$ h 同时覆盖硬件故障与 spot 回收。GraceTime=120 s 要求 $T_{\text{write,panic}} \lt 120$ s（仅写最近 sharded state，非全量 700 GB）——需在工程上维护「轻量 panic checkpoint」与「完整 periodic checkpoint」两档。

十、章节总结

容错 × 编排：Llama 3 决策清单

  1. MTTF 算术先行：16k GPU → ~3 h MTTF；$R_{\text{cluster}} \approx 0$——软件必须持续吸收失效
  2. Young-Daly + 第 3 章存储：$\tau_{\text{opt}}=\sqrt{2 T_{\text{write}} \cdot \text{MTBF}}$；压 $T_{\text{write}}$ 靠本地 NVMe + 独立 checkpoint tier，而非盲目缩短间隔
  3. SDC 比 crash 毒：16k GPU 约每 11 h 一次静默错误风险；check-and-verify 是发布级 pretrain 必需
  4. 恢复分钟级可接受，但 MTTF 3 h 时 15 min restart ≈ 8% $\eta_{\text{runtime}}$——与 gang 快速重分配共同优化
  5. 故障之外仍空转：gang + topology 优先于 bin-packing；OpenAI 死锁是调度 bug，非硬件 bug
  6. Goodput 相乘：MFU、恢复、排队三类损失不可互相掩盖；92% SM ≠ 有效训练
  7. 同一 checkpoint 栈买三件事：抗硬件故障、抗 spot 抢占、抗弹性 resize——Slurm GraceTime 与 K8s PodGroup 是同一基础设施的不同 API

容错让 fleet 在统计必然故障下仍能完成 Llama 3 式 months-long run；编排决定故障之外 GPU 是否空转——checkpoint 间隔与 gang 调度是同一 C³ coordination 预算的两面。下一章（第 6 章 性能与规模化推理）讨论工作落到正确 GPU、故障与排队清零之后，内核与 serving 栈如何把本地执行推近 Roofline 上限。
