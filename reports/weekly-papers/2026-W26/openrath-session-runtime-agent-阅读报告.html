概述

现代 Agent 系统在构建多步骤、多角色协同任务时面临一个隐蔽但严重的问题：运行时状态高度碎片化。 对话记录、工具副作用、内存事件、沙箱放置信息、分支溯源和重放证据分散在不同的控制器日志、提供商追踪和外部系统中， 彼此之间缺乏统一的连接。一旦模型、提供商、工作空间或提示词发生变化，最终答案几乎无法被审计或复现。

OpenRath 提出了以 Session 为中心的运行时状态模型，将上述所有碎片化信息统一为一个可分支、可检视、可重放、后端感知且可组合的一等公民运行时值。 其编程模型的灵感来自 PyTorch 的架构风格——不是 PyTorch 的张量数学，而是"一个中心运行时值在可复用模块间流动"的接口设计哲学。

论文明确将其主张限定在受控运行时属性范围内，广泛的基准测试和实时提供商质量评估留待后续工作。 这是一篇以运行时架构设计为核心的系统论文，而非 benchmark-driven 的实证论文。

研究背景与动机

单 Agent 的消息循环（接收消息 → 调用模型 → 执行工具 → 追加观察）对于单一助手场景是有效的。 但当工作分布到多个角色、工具、内存存储、沙箱和恢复执行时，这个循环就成了一个弱状态边界。

碎片化运行时状态的具体表现

消息列表保留了对话表面，但通常不暴露以下关键信息：

  • 角色溯源（Role Provenance）：某条消息由哪个角色/Agent 产生
  • 废弃分支（Abandoned Branches）：探索过但被丢弃的执行路径
  • 工具放置（Tool Placement）：工具在哪个沙箱/后端执行
  • 工作空间副作用（Workspace Effects）：文件系统、代码执行的实际影响
  • 内存召回/提交事件（Memory Recall/Commit Events）：内存何时被读取或写入
  • 被压缩丢弃的证据（Evidence Discarded by Compression）：上下文压缩后消失的工具结果

多 Agent 场景的关键压力点

隐藏运行时状态问题（Hidden Runtime State Problem）

多 Agent 工作创建多条运行时路径（收集、编辑、验证、压缩），共享的转录文本对下游 Agent 引入噪声， 隐藏的控制器状态使分支溯源无法重建。OpenRath 将这一现象定义为"隐藏运行时状态问题"， 并将可分支性（branchability）视为运行时状态的属性，而非控制器侧的约定。

核心设计：Session 抽象

OpenRath 编程模型的核心规则是：所有运行时组件只能变换或标注 Session，不得自行发明私有的转录格式、放置信息、工具日志、内存格式或工作流状态。 这条规则确保了整个系统的可审计性——证据存在于程序已经传递的值中，而不是需要重建的旁路通道。

Session 记录的字段

Session 是一个携带以下信息的运行时值：

Session 包含的七类信息
  • Conversation Chunks（对话块）：有序的对话片段，包含角色、内容、工具调用和结果
  • Sandbox Placement（沙箱放置）：后端意图和工作空间绑定，在执行前即被记录
  • Lineage Metadata（谱系元数据）：父 Session、fork/detach/merge 操作记录、分支溯源
  • Token Usage（Token 使用量）：累计的提示词和补全 Token 计数
  • Pending Work（待处理工作）：尚未完成的工具调用或工作流步骤
  • Tool Evidence（工具证据）：工具结果、错误、沙箱输出，作为结构化 chunk 追加
  • Memory Boundary Records（内存边界记录）：召回和提交事件的可见运行时记录

对象词汇表（Object Vocabulary）

围绕 Session，OpenRath 定义了六个配套抽象，每个都有严格的运行时边界：

对象运行时边界不拥有的内容
Agent 可复用的 Session → Session 变换，携带本地提示词、提供商、工具和内存策略 不拥有对话图——谱系属于 Session
Tool 模型可见的可调用对象：schema 验证、session 上下文、沙箱分发、返回证据 不拥有放置权——通过活跃沙箱执行
Sandbox 文件、命令、代码、外部工具执行的放置边界 不暴露私有执行状态给 Agent
Memory 跨运行的持久状态平面，召回/提交为可见运行时事件 不成为隐藏的提示词文本
Workflow Agent、工具、分支、压缩、内存、子工作流的组合面 不创建独立的编排状态
Selector 读取 Session，路由到自描述工作流之一，空工作流表示结束 不硬编码下一 Agent 的路由逻辑

Tool 边界细节

工具执行遵循分层路径：模型看到 FlowToolCall schema；Session 循环合并内置工具和用户工具； 将 schema 发送给提供商；按名称解析返回的工具调用；验证参数；以活跃 Session 调用选中工具； 工具通过 session 的沙箱分发后端负载（用于副作用）；所有结果（参数错误、未知工具、异常、成功） 都成为 tool-result chunk 追加到 Session，而不是被丢弃进控制器流。

Selector：控制流转运行时路由

Selector 是 OpenRath 偏离静态工作流图的关键设计。它读取当前 Session 状态，路由到多个自描述工作流之一。 路由决策本身成为 Session 记录的一部分，使得"下一步执行哪个 Agent"这一决策具备可审计性。 当 Selector 返回空工作流时，表示执行结束。

关键操作：Fork / Merge / Replay

Session 的可分支性、可合并性和可重放性是 OpenRath 区别于传统 Agent 框架的核心能力。 这三个操作都是显式的运行时操作，作用于程序已经传递的值，而非从外部日志重建的状态。

Session 生命周期阶段

阶段可审计的内容
Create初始用户文本、Agent 提示词、角色、有序 chunk 状态
Place来自 Session.to(...) 的后端意图、工具执行的工作空间
Transform模型调用、工具请求、结果、错误、压缩器、工作流步骤、使用量
Branch父 Session、fork、detach、merge、分支溯源、merge 输入
Persist可重放的 chunk、谱系 JSONL 行、使用量、来源证据
Release沙箱句柄所有权、后端生命周期

分支操作语义

  • Fork：复制状态同时保留父子关系，用于并行工作的独立探索
  • Detach：从复制内容创建新的谱系根，切断与父 Session 的关联
  • Merge：合并兼容的 Session，记录两个父节点；兼容性包括沙箱兼容性——两个 Session 必须共享活跃的沙箱句柄或指向同一未绑定后端，使放置成为运行时图的一部分

持久化与重放机制

运行中的 Session 可以向 Session JSONL 存储追加行。谱系导出将 Session 投影为包含以下字段的 JSONL 行： 标识符、父标识符、谱系操作符、谱系类型、chunk 计数、累计使用量。 格式被刻意设计为可用命令行工具检视，无需专用查看器。

运行时架构

运行时架构回答一个核心问题：Session 在穿越 Agent、工具、沙箱、分支和存储工件时，如何保持可检视性？ OpenRath 使用一个小型生命周期，而非为每个阶段引入独立的运行时对象。

后端边界表

边界所有者与角色
放置意图（Placement Intent）Session 在执行前存储后端名称和开启规格
资源生命周期（Resource Lifetime）沙箱句柄跨分支共享/释放活跃执行资源
能力声明（Capability Claim）后端类声明隔离级别和支持的工具负载
具体执行（Concrete Execution）后端实例运行本地、OpenSandbox 或未来后端操作
证据返回（Evidence Return）Session 循环将结果或错误追加到 session 流

多 Agent 多 Session 设计

多 Agent 设计被刻意保持"intentionally small"：Agent 是可复用层，Workflow 是可复用组合，移动的值是 Session。 这避免了在从单 Agent 扩展到多 Agent 时引入新的共享可变对象、隐藏消息总线或仅控制器可见的追踪。

组合模式

模式组合方式可检视内容
一 Agent，多 Session 同一 Agent 参数应用于新建/fork/恢复/沙箱绑定的 Session 提示词层稳定；对话、放置、谱系、使用量在 Session 上
多 Agent，一状态 专业 Agent 各自消费并返回 Session；工作流将返回值向前传递 规划、工具使用、压缩、QA、综合后的中间状态可检视
嵌套工作流 子工作流在 forward(session) 背后隐藏内部 Agent 结构 父节点看到一个返回的 Session，而非私有编排格式
控制面 chunk、工具结果、谱系字段、使用计数器、持久化文件、回调绑定到 Session 失败、预算超限、分支溯源、中断运行成为可审查工件

实验结果与评估协议

OpenRath 采用审计优先（Audit-First）的评估哲学：将证据范围限定在运行时主张，而非排行榜主张。 评估围绕三个问题展开：运行时主张是否有可重建的证据包支撑？每个证据包是否声明了自身边界？每个可见主张是否在主张账本中有映射？

后续评估的基线与指标设计

论文为后续基准测试提供了系统性的基线分类建议：

  • 单 Agent 循环基线
  • 多 Agent 共享转录基线
  • 工作流/DAG 运行器基线
  • Notebook 或脚本基线
  • 沙箱工具 Agent 基线
  • 内存/RAG 基线

指标应追踪：运行时正确性、溯源覆盖率、可重放性、后端可移植性、效率、任务质量、控制/安全事件。

局限性与范围边界

OpenRath 在论文中对自身局限性保持高度透明，明确列出了每项能力的当前状态和需要满足什么条件才能提出更强主张。 这种"主张账本"方法本身也是论文设计哲学的体现。

边界当前状态提出更强主张的前提
基准测试 仅有确定性烟雾运行器和证据包 固定工作负载、基线适配器、指标、实时提供商运行、评审员评分工件
后端对等性 本地后端通过；OpenSandbox 显式跳过 后端能力矩阵、配置的 OpenSandbox 包、记录的挂载/导出/失败行为

多 Agent 控制 Session 暴露分支/合并/工具/谱系证据；无策略层 角色权限、工具权威、内存提交门、合并策略、人工审查要求

安全注意：间接提示注入风险

论文明确指出，使用工具的 Agent 在交互式环境中存在间接提示注入（Indirect Prompt Injection）风险。 这是工具使用型 Agent 的已知攻击向量，需要在工具权威限制和人工审查门方面进行专门评估。

总结与启发

OpenRath 的核心论点是：多 Agent 系统不仅仅是提示词图、工具注册表、追踪流或基准测试框架—— 它是一个运行时，其中对话 chunk、分支谱系、沙箱放置、工具副作用、内存交互、使用量、工件和重放证据必须保持连接。

核心洞见

Session 作为边界的设计原则

每个主要组件要么变换 Session，要么标注 Session，要么通过其放置分发工作，要么发出运行后可检视的证据。 因为证据存在于程序已经传递的值中（而非重建的旁路通道），它在审查者需要时精确可用。

未来扩展的治理标准

论文提出了新能力进入系统的治理标准：

新能力只有在满足以下条件之一时才能进入系统：变换 Session、向 Session 附加证据、或通过 Session 暴露后端副作用。 这防止了隐藏旁路通道的积累。

结语论点

"如果过去十年的深度学习使张量成为网络围绕其构建的值，那么下一代 Agent 系统需要同样的转变： 一个所有组件读取、变换和解释的单一运行时值。OpenRath 提出这个值就是 Session。"

对工程实践的启发

  • 状态统一优先于功能堆叠：在设计 Agent 框架时，首先明确"运行时值是什么"比堆叠功能更重要
  • 可审计性是一等公民：工具证据、分支溯源、内存事件应作为结构化数据附加到运行时值，而非散落在日志中
  • 主张账本是诚实的工程实践：明确区分"已证明"、"部分证明"和"待证明"的能力，是系统设计成熟度的体现
  • PyTorch 类比的迁移价值："一个中心运行时值在可复用模块间流动"的模式可能是 Agent 系统工程化的关键缺失环节
  • 安全需要显式设计：间接提示注入等风险不能靠运行时架构自动解决，需要专门的工具权威控制和人工审查门
