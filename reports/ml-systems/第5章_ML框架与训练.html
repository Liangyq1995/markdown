一、框架三大问题

第 4 章定义了算子与架构；本章问：谁把这些算子跑在硅片上，并自动求梯度。 一切 ML 框架可归结为三个问题：

问题问什么失败症状
Execution如何在 GPU/CPU 上跑算子？GPU 0% 利用率
Differentiation如何自动求 $\partial L/\partial W$？手写梯度错维度
Abstraction如何组合层而不写 CUDA？重复 boilerplate

1.1 抽象阶梯

越往上开发越快；越往下控制 $\eta_{\text{hw}}$。生产路径：默认 L2–L3，热点用 L0 custom kernel（第 11 章硬件加速）。

二、Execution 与 Kernel Launch Tax

每个 GPU kernel 启动固定开销约 5–50 μs（驱动+调度）。1000 个 tiny op → 50 ms 纯 overhead，零有用 FLOPs。对策：torch.compile / XLA / CUDA Graph 融合算子，把 1000 次 launch 并成 1–10 次。

铁律 $L_{\text{lat}}$ 在框架层的表现：小 batch 推理时 launch 占比可超 30%。框架不会替你做融合——仍须 profile。

三、Differentiation 与 Autograd

x = torch.tensor([2.0], requires_grad=True)
y = x ** 2 + 3 * x
y.backward()
print(x.grad)  # tensor([7.])  因 dy/dx = 2x+3 |_{x=2} = 7

计算图 tape：前向存中间值 → 反向按链式法则。内存代价：训练需存激活 ≈ 参数量 2–3×（与第 4 章一致）。Autograd 把 Algorithm 轴的反向传播从手写 bug 源变成框架契约。

四、单步训练解剖

框架的核心交付物是可重复的单步：zero_grad → forward → loss → backward → step。

optimizer.zero_grad()
logits = model(batch_x)           # forward
loss = F.cross_entropy(logits, y) # loss
loss.backward()                   # backward
optimizer.step()                  # W -= lr * grad

单步时间分解（典型 ResNet A100）：forward ~40%，backward ~40%，optimizer ~10%，DataLoader ~10%。DataLoader 饥饿时后者可飙至 50%+——瓶颈在 $D/BW$ 而非 $O$。

阶段铁律项典型优化
DataLoader$D_{\text{vol}}/BW$多 worker、pin memory、预取
Forward/Backward$O/(R\eta)$AMP、算子融合
Optimizer内存 + 带宽融合 Adam、ZeRO 分片

五、训练系统与 Batch 内存

训练 = 在铁律下重复数十亿次「前向→loss→反向→更新」。瓶颈在 $D/BW$（DataLoader）、$O/(R\eta)$（算力）或 $L_{\text{lat}}$（分布式同步）中的最大项。

$$M_{\text{train}} \approx M_{\text{params}} + M_{\text{grad}} + M_{\text{opt}} + M_{\text{activations}}(B)$$

Adam 优化器：$M_{\text{opt}} \approx 2\times M_{\text{params}}$（一阶+二阶矩）。ResNet-50 FP32 102 MB 权重 → 单卡至少 ~400 MB 优化器状态+梯度，不含激活。激活随 batch $B$ 线性增——OOM 时先降 $B$ 或用 gradient checkpointing（算力换内存）。

六、混合精度 (AMP)

FP16 矩阵乘 ~2× 吞吐；梯度下溢风险 → Loss Scaling：初始 $S=2^{16}$，若 grad inf 则 $S/=2$。

scaler = torch.cuda.amp.GradScaler()
with autocast():
    loss = model(x)
scaler.scale(loss).backward()
scaler.step(optimizer); scaler.update()

AMP 同时攻击 $O$（更快 GEMM）与 $M_{\text{activations}}$（FP16 激活减半）——框架层与训练系统层的交汇点。

七、分布式：DDP 与其他并行

7.1 数据并行 (DDP)

$N$ 卡各算 batch $B/N$，每步 all-reduce 梯度。通信量/卡/步：$2 \times |\text{params}|$ bytes（FP32 grad）。ResNet-50 25M 参数 → ~100 MB/step；1 Gbps 网络 → 0.8 s 仅通信，算力空转。

$$T_{\text{step}} \approx T_{\text{compute}} + T_{\text{sync}} \quad \text{Amdahl：若 sync 占 40\%，无限卡加速上限 } 1/0.6 \approx 1.67\times$$

八、Checkpoint、选型与总结

8.1 Checkpoint 与容错

每 $K$ step 存 model.pt + optimizer.pt + scaler + epoch。100B 模型 checkpoint 100 GB+ → 写 S3 带宽成为 $D/BW$ 项。故障恢复：从最近 checkpoint 重跑最多 $K$ step，而非从头。

8.3 谬误对照

谬误现实
「框架会替你做系统优化」仍须 profile DataLoader、融合、精度
「eager 够快」生产 inference 常需 compile/TRT
「加卡线性加速」Amdahl + 通信上限 ~1.67×（sync 40% 时）
「大 batch 总是更好」泛化与内存 trade-off；OOM 先降 $B$

章节总结

  • 框架三问：Execution（kernel launch tax）、Differentiation（autograd tape）、Abstraction（nn.Module）
  • 单步解剖：DataLoader 饥饿时 $D/BW$ 可成主瓶颈；forward/backward 各 ~40%
  • 训练系统：$M_{\text{train}}$ 四项账；AMP 用 loss scaling 换吞吐；DDP 通信量 $\propto$ 参数量
  • Checkpoint 把故障恢复 bound 在 $K$ step；框架选型随硬件生态（GPU/TPU/遗留 TF）
