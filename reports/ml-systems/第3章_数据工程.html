第3章 数据工程

《Introduction to Machine Learning Systems》Vijay Janapa Reddi · MIT Press · Vol.1 · 生成日期：2026-07-04

核心主线数据即源码 → 数据物理 → 四支柱 → KWS 贯穿 → 采集/管道/处理/存储/运维健康
学习目标将 79% 工程师时间花在的数据工作，从「清洗」提升为可版本化、可监控的 Dataset Compilation

一、开篇：数据是真正的源码

传统软件：程序员写逻辑。ML：程序员写优化过程，从数据中提取行为逻辑。改数据 = 改系统行为，无需改一行传统代码——且数据会随世界漂移，模型静默退化。

Definition 4.1：Data Engineering

管理数据从源到模型的生命周期：采集、转换、存储、治理。在铁律中治理 $D_{\text{vol}}$（字节移动）；在 D·A·M 中是 data-machine 协同设计——算法再快，也学不快于机器能喂入的数据。

误区：「数据工程 = 数据清洗」。正解：Dataset Compilation——像编译器把源码变成二进制，管道把原始观测变成模型消费的训练张量。

1.1 编译器类比

编译器阶段数据管道阶段作用

数据集须 git 式版本化、单元测试（质量断言）、调试。删一行训练数据 ≈ 删一行源码；重训 ≈ 重新编译。train/val/test 是信任边界——泄漏（同用户跨 split、增强副本跨 split）会让评估虚高。

二、数据的物理：Gravity、Entropy、Feeding Tax

2.1 数据引力（Data Gravity）

$$T_{\text{move}} = \frac{D_{\text{vol}}}{BW} \quad \text{例：} \frac{1\,\text{PB}}{12.5\,\text{GB/s}} \approx 80{,}000\,\text{s} \approx 22\,\text{h}$$

AWS egress 约 $0.09/GB → 1 PB 迁出 ≈ $90,000。若训练 < 22 h 且算力 < $90k，代码迁到数据（Lakehouse：Spark 直接在存储节点算）比搬数据划算。经验法则：PB 级算到数据；GB 级算到代码。

2.2 信息熵与选择增益

$$\text{Data Selection Gain} \propto \frac{\text{Information Entropy}}{\text{Data Gravity}}$$

100 万张相同图片：高引力、零熵。1 万条 diverse 边缘案例：低引力、高熵。去重减质量不减熵 → 提升比率；主动学习加高熵样本同理。

2.3 Feeding Tax（喂料税）

ResNet 类图像训练：GPU 可达 ~1843 img/s，存储管道仅 ~250 MB/s → 加速器空闲。Feeding tax 可超 77.5%——$\eta_{\text{hw}}$ 被 I/O 吃掉。饱和需 ~1.1 GB/s 传输；JPEG 解码在 CPU 上常比 GPU 前向更慢 → DataLoader 8+ worker、pin memory 是铁律 $D/BW$ 项的具体体现。

三、四支柱框架与 KWS 案例

3.1 Data Cascade

War Story：Pipeline Jungle（zip_code）

上游把 zip_code 从 int 改为 string（国际邮编）。管道静默 cast "02139" → 2139，前导零丢失。模型把 2139 当未知类别 → 整区申请人拒贷。

防御：版本化 Data Contract（schema、单位、语义、允许范围）在 ingestion 接口强制执行。

3.2 四支柱

支柱问什么KWS 实例

3.3 KWS Napkin Math：假阳性目标

目标：每月最多 1 次误唤醒。1 s 窗口 × 24 h × 30 天 = 2,592,000 窗口/月。

$$\text{FPR}_{\text{window}} = \frac{1}{2{,}592{,}000} \approx 3.9 \times 10^{-7} \quad \Rightarrow \quad \text{非关键词拒绝率需 } 99.99996\%$$

「99% 准确率」在此无意义——须用 FA/Hr（False Accepts per Hour）。模型须 <64 KB（SoC always-on island 含权重+预处理）。

5.1 质量监控：K-S 检验算例

监控 session_duration：训练 baseline $P_0$ vs 当前 serving $P_t$，$n_0=n_t=1000$。

$$D_{\text{KS}} = \max_x |F_{P_0}(x) - F_{P_t}(x)| \quad D_{\text{crit}} \approx 1.36\sqrt{\frac{n_0+n_t}{n_0 n_t}} \approx 0.061 \text{（}\alpha=0.05\text{）}$$

若观测 $D_{\text{KS}}=0.08 > 0.061$ → 拒绝「同分布」假设，触发调查/重训工单（不是只上 dashboard）。分类特征用 PSI（第 2 章手算例），非 K-S。

5.3 漂移 taxonomy

类型变化检测
Covariate shift$p(x)$ 变，$p(y|x)$ 不变PSI/KL 于输入特征
Label shift$p(y)$ 变，$p(x|y)$ 不变预测分布变化
Concept drift$p(y|x)$ 变需 ground truth
Label quality drift标注可靠性降Cohen's $\kappa$ 下滑
$$\kappa = \frac{p_o - p_e}{1 - p_e} \quad \text{例：基线 } \kappa=0.85 \to 6\text{ 月后 } 0.72 \Rightarrow \text{新标注员缺培训}$$

5.4 可靠性：Circuit Breaker

特征服务连续失败 → breaker open，serving 回退 stale cache 或默认特征，而非 cascade timeout。Dead Letter Queue 存失败记录——欺诈 DLQ 曾发现新支付类型，驱动定向采集而非仅 log。

5.5 Batch vs Stream / ETL vs ELT

Batch：容忍 staleness 换效率。Stream：Kafka 等，freshness 换运维复杂度。ELT：先 raw load 到 Lakehouse 再 transform——配合 Delta 直接在存储层算特征，减 PB 级 copy 的 $D_{\text{vol}}/BW$ 成本。

5.6 War Story：Microsoft Tay (2016)

Twitter 公开输入 = 实时训练信号。24 h 内协调攻击 → 数据投毒 → 种族歧视输出。教训：UGC 管道无 adversarial 控制 = 安全面，不是 plumbing。

5.7 DataLoader 瓶颈（Napkin Math）

A100 训 ResNet-50：单卡 forward+backward ~2 ms/image → 理论 ~500 img/s。实测常仅 ~120 img/s，因 JPEG decode 在 CPU ~6 ms/张。加 worker 至 8：decode 并行 → ~480 img/s，GPU 利用率从 ~24% 升到 ~96%。

$$T_{\text{step}} = \max(T_{\text{compute}}, T_{\text{io}}) \quad T_{\text{io}} \approx \frac{N_{\text{workers}}}{T_{\text{decode}}} \text{ 饱和前由 decode 主导}$$

Investment 顺序：先 profile 哪项绑定 → 再加 GPU。这与第 2 章「迭代税」同构：快实验循环依赖 feed 管道，非裸算力。

六、系统化数据处理

6.1 Training-Serving Skew（一致性铁律）

Materialized View 陷阱

训练：batch 用 weekly refresh 物化视图算 7 日滚动均值。Serving：实时 join 重算。逻辑「相同」→ 值不同 → 准确率静默降 10–15%，无报错。

解：共享代码库（非复制粘贴）；归一化 mean/std 与模型 artifact 一起 persist；Feature Store 双接口读同一预计算值。

6.2 KWS 音频：MFCC 参数必须一致

25 ms 窗、16 kHz、13 MFCC——训练与 always-on island 上预处理参数差 5 ms STFT 窗 → 特征 skew → 性能崩溃。SNR > 20 dB、唤醒词时长 500–800 ms 为质量门。

6.3 幂等变换

重试/重跑须产出相同输出。类别编码：训练集 vocabulary 持久化，serving 未知类映射 UNK。Outlier：mean/std 只用训练集统计量，serving 复用。

七、标注与存储

7.1 标注经济学

KWS $150K 预算：~60% 标注（$90K ÷ $0.12/条 ≈ 750K 条，含 20% review）。多标注员投票提质量但 3× 成本；$\kappa < 0.4$ 时训练数据噪声模型必继承（Landis & Koch）。

7.2 存储层次与格式

层带宽/延迟ML 用途
对象存储 S3高延迟，100–200 MB/s 磁盘归档 raw
Parquet 列存谓词下推、压缩训练 batch 读
RAM50–200 GB/sFeature cache、在线 serving

7.3 Delta Lake Time Travel（数据集版本）

训练 run 须绑定数据 snapshot。Delta 事务日志支持按版本/时间点查询：

DESCRIBE HISTORY fundus_features;
SELECT * FROM fundus_features VERSION AS OF 5238;
SELECT * FROM fundus_features TIMESTAMP AS OF '2026-03-15 08:00:00';
RESTORE TABLE fundus_features TO VERSION AS OF 5238;

与 DVC hash、MLflow tag data.dvc_rev 链式：复现 = checkout 同一 VERSION + 同一预处理 commit。

7.4 Feature Store

Uber Michelangelo 模式：batch 训练与 online serving 读同一 feature table。无 Feature Store 时 batch 7 日滚动 vs stream 实时窗口 → 典型 5–15% 线上 acc 损失。lookup 延迟目标 1–10 ms（Table 4.6）。

7.5 Parquet 列裁剪算例

1 TB CSV 全表读入训练：$D_{\text{vol}}=1$ TB。Parquet 列存 + 只读 12/200 列：有效读 ~60 GB（假设均匀列宽）→ 铁律 $D/BW$ 项降 ~16×。配合 predicate pushdown（WHERE date >= '2026-01-01'）进一步减 scan。

7.6 文件格式选型

格式训练在线

Parquet列裁剪、压缩、schema批量导出
TFRecord/Arrow框架原生、prefetch 友好—

八、运维数据健康

LiDAR 标注 15% 框偏 10–20 cm 持续 3 月——schema 全 valid，仅统计监控 label-sensor 对齐分布才发现。推荐系统 50k events/s：吞吐 <40k/10 min 告警；user_age null 从 <1% 升到 >5% 告警；p95 管道延迟 >30 s（SLA 10 s）须定位 ingestion/transform/validation 哪段。

漂移响应占 MLOps effort 约 30–40%。PSI > 0.2 或 KL 超阈 → 分级告警 → 第 8 章编排重训。区分：均值 8→12 min/6 月是 drift（重训）；突降到 3 min 是采集 bug（修源系统）。

九、谬误与陷阱

谬误现实
「更多数据总是更好」1M 相同图 < 10K diverse；看 Selection Gain
「清洗完就完事」机械正确 ≠ 语义正确（全员 age=25 默认值）
「训练 serving 逻辑一样就行」须同一代码+同一数据源+同一 timestamp 语义
「benchmark SOTA 即可上线」ImageNet 复用 ≠ 部署分布；须测 gap
「加 GPU 加速训练」DataLoader 饥饿 → 零加速；先 profile $T_{\text{step}}=\max(T_{\text{compute}},T_{\text{io}})$

十、章节总结

  • 数据 = 源码：Dataset Compilation，非事后清洗
  • 物理约束：Gravity（22 h/$90k PB 迁移）、Feeding tax（77.5%）、能量 173×–10⁴×
  • 四支柱 + KWS：FPR $3.9\times10^{-7}$/窗、64 KB、$150K 预算配置
  • 管道：K-S $D_{\text{crit}}=0.061$、GX 断言、漂移四类、Tay 投毒
  • 一致性：Feature Store / 共享代码；Delta VERSION AS OF 绑训练
