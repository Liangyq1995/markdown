Unit 0

Welcome to The Context Course

课程导论 · 核心理念 · 工具安装 · 学习路径

Unit 0 确立了整门课程的核心命题：代码 Agent 的质量上限由上下文决定，而非模型能力。无论是 Claude Code、Codex 还是 OpenCode，它们共享同一个约束——Agent 只能利用它拥有的上下文工作。

核心理念：上下文工程

为什么上下文工程是关键技能？

以"将数据集发布到 Hugging Face"为例，没有上下文时 Agent 需要猜测认证方式、数据集 schema 和必填字段，可能卡住、反复提问或填入错误值。

提供认证步骤、数据集格式、API 格式和常见坑的说明后，同一个任务完成得更快、更可靠。

代码 Agent 的质量上限由你给它的上下文决定。上下文工程是将那些上下文结构化，让 Agent 能找到并使用它的实践。

Unit 1

Skills：可移植的代码 Agent 知识

什么是 Skills · SKILL.md 格式 · 构建第一个 Skill · 跨 Agent 兼容

Agent Skills 是 Agent 上下文的基础构建块。一个 Skill 是一个自包含的知识包，让 Agent 擅长某项特定任务。Skills 可跨项目移植、安装后可复用、格式化便于 Agent 解析、并可通过脚本和 API 扩展。

没有 Skills 的困境

失败 1：认证问题

Agent 知道需要认证，但不知道你的特定环境如何配置。

失败 2：配置错误

Agent 不知道你的数据集格式或如何转换，填入看似合理但错误的值。

失败 3：缺少最佳实践

模型上传了，但缺少 model card、许可证信息、必要的元数据字段。

Skill 的本质：从 Prompt 到可移植知识

❌ 传统方案：基于 Prompt 的上下文

  • 每次对话重复粘贴同样的长提示词
  • 散落的 wiki 页面
  • 团队成员各自重建相同上下文
  • 单次对话结束即消失

✅ Skill 方案：结构化可移植知识

  • 一次定义，一处更新
  • 跨域可组合
  • Agent 按需自动加载
  • 跨项目、跨 Agent 可移植

Agent Skills 规范（agentskills.io）

Skills 遵循开放标准 Agent Skills Specification，由 Anthropic 创建，现已被 30+ 代码 Agent 采用。该规范确保：Skills 跨不同 Agent 和平台工作；Agent 可自动发现和加载相关 Skills；社区可共享和改进 Skills。

SKILL.md 格式详解

SKILL.md 是一个 Skill 的核心，分为两部分：YAML Frontmatter（元数据配置）和 Markdown 正文（给 Agent 的指令）。

目录结构

my-skill/
├── SKILL.md              # 核心 Prompt 和指令（必需）
├── scripts/              # Python/Bash 可执行脚本
├── references/           # 文档，通过 Read 工具加载进上下文
└── assets/               # 模板和二进制文件（仅路径引用）

完整 SKILL.md 示例（数据集发布 Skill）

# Dataset Publishing Skill

Helps you publish datasets to Hugging Face Hub with proper formatting,
metadata, and best practices.

## Prerequisites
- Authenticated with `hf auth login`
- Dataset in supported format (CSV, JSON, Parquet, Arrow)

## Steps

### Step 1: Authenticate
Run the authentication check script:
```bash
python {baseDir}/scripts/check_auth.py
```

### Step 2: Validate Dataset Format
```python
from datasets import load_dataset

print(dataset)
```

### Step 3: Push to Hub
```python
dataset.push_to_hub("your-username/dataset-name")
```

## Common Pitfalls
- Always include a dataset card (README.md)
- Set license in metadata
- Use `private=True` for sensitive data

Unit 2

MCP：模型上下文协议

动态工具连接 · MCP 架构 · 构建服务端 · Gradio 集成 · 部署到 HF Spaces

Unit 1 介绍的 Skills 是静态的、预写的上下文，非常适合固定知识。但 Skills 无法获取新信息或执行实时操作。MCP（Model Context Protocol） 填补了这个缺口：它给 Agent 提供动态上下文——通过统一协议调用函数、读取文件、查询数据库并与 API 交互。

Skills vs MCP：互补而非替代

Skills 提供知识（"如何做 X"），MCP 提供工具和数据（"执行 X 并返回结果"）。两者通常配合使用：Skills 告诉 Agent 该做什么，MCP 工具让 Agent 真正去做。

MCP 是什么

MCP 是让 AI 应用与外部数据和工具交互的开放标准。它位于 Agent 和一切外部资源之间：文件、数据库、API、服务。

用 FastMCP 构建 MCP 服务器

from fastmcp import FastMCP

mcp = FastMCP("my-hf-tools")

@mcp.tool()
def search_models(query: str, limit: int = 5) -> list[dict]:
    """Search Hugging Face Hub for models matching query."""
    from huggingface_hub import HfApi
    api = HfApi()
    models = api.list_models(search=query, limit=limit)
    return [{"id": m.id, "downloads": m.downloads} for m in models]

@mcp.resource("hf://datasets/{dataset_id}")
def get_dataset_info(dataset_id: str) -> str:
    """Get metadata about a HuggingFace dataset."""
    from huggingface_hub import dataset_info
    info = dataset_info(dataset_id)
    return f"Dataset: {info.id}\nSize: {info.size_in_bytes} bytes"

if __name__ == "__main__":
    mcp.run()
Unit 3

Plugins：打包工具用于分发

插件解剖 · 构建与发布 · 上下文演进路径 · 团队一致性

Plugins 是上下文工程演进的最高层。它们将 Skills、MCP Servers、脚本和配置打包成一个可分发的单元，解决团队协作中重复搭建上下文的问题。

上下文工程的演进路径

Prompts：原始指令。脆弱，难以复用，团队成员间不一致。
Skills：打包的 Prompt + 工具。更有组织，但没有依赖管理。
MCP Servers：标准化工具接口。可组合，但学习曲线陡峭。
Plugins：可复用扩展。清单（manifest）+ 捆绑组件（Claude Code/Codex）或代码模块（OpenCode）。

为什么 Plugins 重要

个人开发者

跳过繁琐设置：安装 Python lint 插件或 API 文档插件，直接继承他人精心整理的成果。

团队协作

Plugins 是一致性单元——每个人获得相同的工具和指令，消除"谁的环境跑得通"的问题。

开源社区

可发布到 Marketplace 的可共享工件，形成生态，让更多人受益。

关键术语

术语含义
Skill可复用的 Prompt + 元数据
MCP Server标准化工具提供者（文件 I/O、API 调用、数据库查询）
Integration连接外部服务（GitHub、Slack、Google Drive）
Manifest清单优先插件系统（Claude Code/Codex）使用的元数据文件
Marketplace插件发布和发现的目录

Unit 4

Subagents：编排多 Agent 工作流

为什么需要子 Agent · 并行与串行模式 · 上下文隔离优势 · 调用方式

当任务超出单个上下文窗口所能处理的范围时，就需要 Subagents。子 Agent 系统让每个阶段拥有独立的上下文窗口，防止上下文膨胀降低输出质量。

为什么需要子 Agent

上下文隔离的价值

以"代码审查"为例：父 Agent 完成设计讨论和实现决策后，测试子 Agent 只接收最终代码，而不是完整的设计历史。这让每个阶段保持专注，防止上下文膨胀。子 Agent 还能对前一个 Agent 的工作更加挑剔和批判性，确保输出尽可能健壮。

子 Agent 模式

模式 1：并行分解（Fan-out）

父 Agent（任务：分析大型代码库）
    │
    ├─→ Subagent 1：读取并总结后端文档（50 个文件）
    ├─→ Subagent 2：读取并总结前端文档（40 个文件）
    └─→ Subagent 3：读取并总结数据库文档（30 个文件）

等待全部完成 → 聚合结果 → 最终架构概览

模式 2：串行流水线

研究子 Agent → 实现子 Agent → 审查子 Agent
（收集资料）    （编写代码）    （测试验证）

清晰的关注点分离，易于追踪进度。

何时启用子 Agent：信号识别

  • 任务需要读取超过 50+ 个文件（单 Context 装不下）
  • 多个独立子任务可以并行执行
  • 不同阶段需要不同的专业知识焦点
  • 后期阶段的质量会受到前期讨论历史干扰
  • 需要对先前工作进行独立批判性审查
Unit 5

Hooks：观测和守护 Agent 生命周期

Hook 事件 · 生命周期 · 四大 Agent 平台 · Gradio 监控面板

Hooks 让你在 Agent 执行的每个关键节点观测、拦截和修改行为——无需修改 Agent 代码本身。它们是 Agent 可观测性和安全守护的基础。

什么是 Hooks

Hook 是在 Agent 生命周期特定事件触发时运行的处理器。核心心智模型在所有四个平台上保持一致：事件触发 → 处理器运行 → 处理器影响 Agent 下一步。只有语法和事件名称不同。

核心 Hook 事件

事件Claude CodeCodexOpenCodePi
工具调用前PreToolUsetool.execute.beforetool_call—
工具调用后PostToolUsetool.execute.aftertool_result—
用户提示提交UserPromptSubmit—before_agent_start—
会话结束Stop / SessionEndsession.idleagent_endsession_shutdown

Hooks 如何影响 Agent

Hooks 不仅仅是观测工具——它们可以改变下一步发生的事情：

退出码（命令行 Hooks）

  • 0：成功，继续执行
  • 2：阻止 PreToolUse / UserPromptSubmit

JSON 输出（更精细控制）

{"decision": "block", "reason": "危险命令"}
{"additionalContext": "注入额外上下文"}
{"continue": false, "stopReason": "任务完成"}

常用 Hook 场景速查

场景使用的 Hook实现方式
阻止危险命令（如 rm -rf）PreToolUse on Bash匹配 Bash(rm )，退出码 2
审计所有文件写入PostToolUse on Edit/Write记录到日志文件
为所有提示注入额外上下文UserPromptSubmit返回 additionalContext
会话结束自动清理SessionEnd清理临时文件、发送通知

内置工具与沙箱约束

工具功能安全约束
list_directory(path)列出目录内容路径限制（Path confinement）
read_file(path, max_chars)读取文件路径限制 + 大小限制
write_file(path, content)创建/修改文件路径限制，默认禁用
exec_cmd(args)执行 shell 命令仅白名单命令：ls, cat, pwd, echo, head, tail, wc, rg
final_answer(text)结束 Agent 循环调用后立即终止
